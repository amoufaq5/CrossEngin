# R18 — incident-response / observability / feature-flags / dr (contracts, -runtime, -runtime-pg)

Tree reviewed: HEAD 7bc8db9 (2026-10-14). Read-only; nothing built or run.

## Summary (10 lines max)
- ~14.7k source LOC across 11 packages. Roughly 60% is zod contracts + stores that **no deployed entry point reaches**. What is reachable: an in-process SLO burn/latency loop (`--slo-config`/`--slo-defaults`), auto-declare/auto-cancel of `meta.incidents` rows, a DR "readiness" snapshot computed from a static JSON file (`--dr-readiness-config`), and a read-only `operate-server replay` drift check. **None of it is enabled in `deploy/docker-compose.yml`.**
- There is no telemetry export of any kind: no OpenTelemetry, no Prometheus endpoint, no structured logs (232 `console.*` call sites), no trace collection (`TraceCollector` has zero callers), no synthetic prober.
- DR is bookkeeping only: no backup, restore, replication or failover action exists; nothing in any app even *writes* a failover/drill row. Readiness answers `ready: true` for empty input and that feeds a certification control.
- Feature flags: nothing evaluates a flag. The SLO "flag rollback" writes a `KillSwitch` row that nothing reads and nothing ever releases.
- Incident lifecycle: only `declared → cancelled` is reachable; no route can triage/resolve/close; sev1/sev2 cannot be closed.
- Two real defects in the one live path (SLO → page): a persistence failure after a successful declaration silently loses the page for the whole episode; declaration failures are swallowed with no log because `onDeclarationError` is never wired.
- SQL quality in the `-pg` packages is good (all values bound, identifiers static/validated, optimistic revision guards, advisory-locked id allocation with unique-index backstop). Tenant scoping on reads is inconsistent across packages (DR reads set no tenant context).
- Heavy copy-paste across `-pg` packages (11 copies of `asString`, 3 identical `Clock` modules, 3 base32 encoders, 4 near-identical revision stores).

## Findings

### R18-01 [High] [CONFIRMED] [Reliability] A persistence error after a successful declaration loses the page for the whole breach episode
- Where: `packages/observability-runtime-pg/src/persisting-engine.ts:78-117` (same shape `latency-persisting-engine.ts:64-101`); `packages/observability-runtime/src/engine.ts:315`; `apps/operate-server/src/slo.ts` `evaluateOnce` (the `for (const decision of await evaluator())` loop inside one try/catch).
- Evidence: `const decisions = await engine.evaluate(at);` — by then the engine has declared the incident and done `this.active.set(surface, {...})` (engine.ts:315). The wrapper then runs `await killSwitchStore.record(...)`, `await enforcementStore.record(action)`, `await evaluationStore.record(record)` with no try/catch. Any throw (DB blip, a zod refusal in `enforcementActionFromDecision`, a 23505 on the kill-switch id) rejects the whole `evaluate()`; the scheduler's `catch (err) { this.opts.onError?.(err); }` runs and `onPage` is never called for the `breach_opened` decision. Next tick the surface is in `active`, so the decision is `breach_ongoing` whose summary carries `pages: []` (slo.ts "An ongoing breach is one episode already paged for").
- Impact: an incident row exists in `meta.incidents`, nobody is paged, and nothing re-pages. The throw also aborts the remaining evaluators for that tick (latency engine not evaluated). One easy trigger is R18-11.
- Fix: persist per decision inside its own try/catch and always return the decisions; or deliver pages before persisting projections; or re-page when an incident has no `paged` timeline entry.
- Effort: S

### R18-02 [High] [CONFIRMED] [Reliability] SLO declaration failures are swallowed with no log, and paging depends on the database being up
- Where: `packages/observability-runtime/src/enforcement.ts:201-206, 222-227, 250-255` (`onError?.(...)`; `return null`); `apps/operate-server/src/slo-config.ts:191-204` (options built without `onDeclarationError`); grep `onDeclarationError` in `apps/` → 0 hits.
- Evidence: `declareEnforcementIncident` catches every error and calls an optional sink that the only caller never supplies. `PostgresIncidentDeclarer.declare` needs an advisory lock + SELECT + INSERT. `FallbackIncidentDeclarer` exists (`incident-response-runtime/src/fallback-declarer.ts`) but `buildSloEnforcement` uses the bare Postgres declarer (slo-config.ts:186-188).
- Impact: when Postgres is unreachable or slow — the likeliest cause of a 5xx burn — the availability breach cannot be declared, so no page is planned, and there is not even a log line (the failure never reaches the scheduler's `onError` because it is caught lower down). The loop is mute exactly when it matters.
- Fix: wire `onDeclarationError` to the logger; wrap the declarer in `FallbackIncidentDeclarer` for SLO too so the page goes out with an unpersisted id.
- Effort: S

### R18-03 [High] [CONFIRMED] [Substance vs modelling / compliance] DR is record-keeping only; nothing writes a failover or drill; readiness is self-reported and vacuously "ready"
- Where: `packages/dr-runtime/src/failover.ts:93-165` (every method is `FailoverRecordSchema.parse({...record, status})`; `actualRpoSeconds`/`actualRtoSeconds` are caller inputs); `packages/dr-runtime/src/readiness.ts:82-156`; `apps/operate-server/src/dr-readiness.ts:26-34, 98-108`; `packages/certification-runtime/src/evidence.ts:~136` (`satisfied: report.ready`).
- Evidence: (a) No code performs a backup, restore, replication check or failover — grep for `pg_dump|pg_basebackup|wal-g|pgbackrest` hits only `deploy/README.md`/`ORACLE.md` prose. (b) `planFailover|startFailover|completeFailover|recordDrillResult|planDrill|recordFailover` have **no caller outside `dr-runtime`/`dr-runtime-pg`**; the only files in `apps/` mentioning failover/drill are `dr-readiness.ts`, `cli.ts`, `replay.ts`, `node.ts` (readers). So `meta.dr_failover_executions` and `meta.dr_drill_executions` cannot hold a row in any deployment; node.ts:2850's comment "the failover/drill executions recorded through the API" describes an API that does not exist. (c) Runbooks, backups and replication lag come from the operator's JSON file (`DrReadinessInputConfigSchema`), not from any measurement. (d) `assessDrReadiness({})` → every list empty → `totalIssues: 0` → `ready: true`; `overdueDrills([])` is empty, so "never ran a drill" reads as "no drill overdue".
- Impact: a deployment with `{"input":{}}` persists `ready=true` hourly and the certification engine reports control `resilience.dr_readiness` satisfied — a falsely-true DR control in a SOC2/HIPAA report. RPO/RTO tiers (`DEFAULT_DR_TIERS`) are enforced against nothing.
- Fix: make empty evidence `not ready` (require ≥1 verified backup and ≥1 executed drill per declared tier); source backup/replication facts from the database (`pg_stat_replication`, backup tool manifests); add a writer for drill results or delete the tables; stop feeding certification from self-declared JSON.
- Effort: L

### R18-04 [High] [CONFIRMED] [Observability] No metrics, traces or structured logs leave the process; the SLO loop cannot see the outages that matter most
- Where: no `@opentelemetry/*`, `prom-client`, `pino`, `winston`, `@sentry/*` in any `package.json`; `/metrics` appears nowhere (only `apps/operate-server/src/health.ts` paths); 232 `console.(log|info|warn|error)` call sites in `apps/operate-server/src`; `TraceCollector`, `SyntheticTracker`, `redact`, `parseTraceparent`, `computeErrorBudget`, `AlertRuleSchema`, `StatusPageComponentSchema` have zero non-test references outside their own packages.
- Evidence: SLO inputs are real — `SloRequestObserver` maps each gateway `PipelineExecution` to a `RequestOutcome` (`apps/operate-server/src/slo.ts`, 5xx = error, latency = `totalDurationMs`). But they live in a per-process `RollingWindow` (`observability-runtime/src/window.ts:66-147`): lost on restart, not shared between replicas, and only fed by requests that reach the pipeline. A dead process, a crashed boot (the binary has many deliberate boot refusals), a wedged event loop, a refused connection, or zero traffic produce **no samples**, and `minSamples` (20/50, `burn-rate.ts:38,47`) then guarantees no breach. There is no external prober to cover that.
- Impact: at 3am the on-call has: container stdout as free text, `/health` + `/readyz`, and — only if someone enabled `--slo-config` with a PagerDuty/Slack route — a page naming an incident id and a "signal" string. No dashboards, no latency histograms, no per-tenant error rates, no trace for a slow request, no DB/pool metrics, no way to answer "is it down for everyone?".
- Fix: add OTel SDK (traces + metrics) or at minimum a Prometheus `/metrics` with request counters/histograms from the existing execution sink; JSON logs with request id; one external synthetic check.
- Effort: M

### R18-05 [High] [CONFIRMED] [Substance vs modelling] Feature flags are never evaluated; the SLO "flag rollback" is a stored intent that is never applied and never released
- Where: `packages/feature-flags/src/producers.ts:263-291` (the package's own total map answers `"none"` for all 17 evaluation reasons); `packages/feature-flags-pg/src/kill-switch-store.ts:147-156` (`record`), `:258` (`release`), `:217` (`listActiveForFlag`); `packages/observability-runtime-pg/src/persisting-engine.ts:90-94`.
- Evidence: grep for `chooseTargetingRule|computeStableBucket|findActiveKillSwitch|isKillSwitchActive|listActiveForFlag|PostgresFeatureFlagStore|PostgresTargetingRuleStore|\.release(` outside the two packages → no production caller. On a breach with `rollback` configured the engine writes a `triggered_active` kill-switch row naming a `flagId` for which no `meta.feature_flags` row can exist (no writer). On recovery the wrapper writes only an action row; nothing calls `release`, so every auto kill switch stays `triggered_active` forever (no `expiresAt` either: `expiresAtIso` is never passed, engine.ts:303-312).
- Impact: "kill switch", "rollout ramp", "auto-rollback on SLO breach" are not capabilities. If an evaluator is ever added, every historical auto kill switch is still active and would immediately pin those flags to their safe value.
- Fix: either build the evaluator + release-on-recovery, or remove `rollback` from `SloRegistrationConfigSchema` so operators cannot configure a no-op.
- Effort: L

### R18-06 [Medium] [CONFIRMED] [Substance vs modelling] Incident lifecycle is unreachable; every incident ends `cancelled`; sev1/sev2 cannot be closed
- Where: `packages/incident-response-runtime-pg/src/declarer.ts:38-79` (the only production consumer of `PersistentIncidentEngine`; calls `declare`, `findOpenFor`, `load`, `cancelIfUntriaged`); `packages/incident-response/src/incidents.ts:357-370, 396-410`; `packages/incident-response-runtime/src/transitions.ts:201-214`.
- Evidence: no file under `apps/` references `assignRole|changeSeverity|attachPostmortem|transition(` on an incident; no `/incidents` route. Schema: leaving `declared` needs 3 (sev1: 5) active role assignments, sev1/sev2 additionally need `publiclyVisible=true`, and `closed` needs `rootCause` + (sev1/sev2) `postmortemId` — none of which any surface can supply. So an auto-declared incident sits `declared` until its signal clears, then is auto-`cancelled`.
- Impact: MTTA/MTTR/SLA (`sla.ts`), postmortem, comms and runbook models produce no data. A sev1 integrity or SLO incident that self-clears is recorded as "cancelled" with no acknowledgement, no root cause, no postmortem obligation. An acquirer should treat incident management as a paging dedup key + a row, not a process.
- Fix: minimal authenticated incident routes (ack, assign, note, resolve, close) or integrate an external tool and drop the model.
- Effort: M

### R18-07 [Medium] [CONFIRMED] [Reliability] An ongoing breach never escalates in severity
- Where: `packages/observability-runtime/src/engine.ts:180-186`; `latency-engine.ts:174-180`.
- Evidence: when `verdict.breached && existing !== undefined` the engine emits `breach_ongoing` and ignores `verdict.worstSeverity`. Default thresholds: slow-burn → `sev3` (routes to P2, typically ticket/Slack), fast-burn → `sev2` (page).
- Impact: an outage that starts as a slow burn (sev3, non-paging) and worsens into a fast burn stays a sev3 incident; on-call is never paged. Only a full recovery + re-breach would re-grade it.
- Fix: compare `verdict.worstSeverity` with `existing.severity`; on worsening, change severity on the incident and emit a page at the new grade.
- Effort: S

### R18-08 [Medium] [CONFIRMED] [Correctness / claims] Declared SLO semantics are mostly not what is enforced
- Where: `packages/observability/src/slo.ts:24-52`; `packages/observability-runtime/src/engine.ts:159-166`; `latency-engine.ts:130,159`; `window.ts:72-73`.
- Evidence: the availability target's `window` (e.g. "30d") is never read — the engine only evaluates the 1h/5m and 6h/30m burn windows over a 24h in-memory buffer capped at 100k samples per surface. No error budget over the SLO window is ever computed (`computeErrorBudget` has no caller). The `incidents` target kind and latency `endpointClass` are parsed and ignored. Latency is judged on one fixed 5-minute window regardless of the target's `window`. With several replicas each holds its own window and evaluates independently.
- Impact: an SLO document a customer or auditor reads ("99.9% over 30 days") is not measured anywhere; nothing can report attained availability.
- Fix: persist per-minute good/total counters per surface and compute budget over the declared window; reject target kinds the engine cannot honour.
- Effort: M

### R18-09 [Medium] [CONFIRMED] [Data / claims] "Persists every evaluation" is false; action rows grow one per tick per ongoing breach with no retention
- Where: `packages/observability-runtime-pg/src/persisting-engine.ts:103-116` (`if (decision.kind === "breach_opened")`), `:96-101`.
- Evidence: an evaluation row is written only when a breach opens; healthy ticks and ongoing ticks write none, so `countBreachesSince` counts breach *openings*. Conversely a `breach_ongoing` action row is inserted every tick (default 60s) per breaching surface for the life of the breach. No store in scope has a delete/prune.
- Impact: no time series of burn rate exists for post-incident analysis; `meta.slo_enforcement_actions` grows ~1,440 rows/day per stuck breach (and an incident nobody can close can stay breached indefinitely).
- Fix: write a compact evaluation per tick (or per state change) and stop writing `breach_ongoing` rows; add retention.
- Effort: S

### R18-10 [Medium] [LIKELY] [Tenant scoping] DR store reads set no tenant context, unlike their writes and unlike the SLO stores

### R18-11 [Low] [CONFIRMED] [Validation] SLO config accepts values that only fail later, inside the tick

### R18-12 [Low] [CONFIRMED] [Performance] Rolling window work on the request path and unbounded-by-time retention
- Where: `packages/observability-runtime/src/window.ts:78-91, 93-103, 105-118`.
- Evidence: `prune()` has no caller anywhere (grep), so `retentionMs` is dead and only the 100k cap bounds a surface. At the cap every request does `list.splice(0, 1)` on a 100k array. Every request is recorded for every surface (registered or not) in **both** engines' windows. `count()` linearly scans up to 100k samples × 4 windows × registration per tick; `latencyStats` sorts the window each tick.
- Impact: with `--slo-defaults` (one SLO per entity operation, hundreds of surfaces) memory is up to surfaces × 100k × 2 sample objects; CPU cost on the hot path at saturation.
- Fix: time-bucketed counters + a latency sketch (t-digest/HDR) per surface; drop unregistered surfaces.
- Effort: M

### R18-13 [Low] [CONFIRMED] [Reliability] Close-out edge cases leave rows or alerts dangling
- Where: `packages/incident-response-runtime-pg/src/declarer.ts:72-79`; `persisting-engine.ts:147-160`; `observability-runtime/src/engine.ts:188-199`.
- Evidence: `cancelIfUntriaged` returns null for any status other than `declared`, and the declarer maps null to `"human_owned"` — so an incident another replica already cancelled is reported `human_owned` and its alert is deliberately left open by this replica. A revision conflict on the cancel throws → `"failed"`; the engine has already done `this.active.delete(surface)`, so there is no retry and the row stays `declared` until a later breach adopts it.
- Fix: distinguish `already_closed`; retry close-out once on revision conflict.
- Effort: S

### R18-16 [Low] [SUSPECTED] [Concurrency] Incident id allocation holds a session advisory lock on one pooled client while querying on others
- Where: `packages/incident-response-runtime-pg/src/incident-store.ts:136-153`; `packages/kernel-pg/src/node-pg.ts:121-133` (out of scope, read for this).
- Evidence: `withAdvisoryLock` checks out a client, takes `pg_advisory_lock`, then `fn()` issues its SELECT/INSERT through `pool.query` on a different client. Correct for mutual exclusion, but each declaration needs two pool slots and no pool `max`/`connectionTimeoutMillis` is set; N concurrent declarers ≥ pool size (pg default 10) can all hold a slot waiting on the lock while the holder waits for a slot. Not reachable with the sequential SLO scheduler alone; needs follow-up under the three escalators + request load. Would also break under a transaction-mode pooler (the Supabase guide correctly prescribes session mode).
- Effort: S (run allocation+insert on the lock-holding client)

## Verified strengths (things that are genuinely done well, with file:line)
- All SQL in the four `-pg` packages binds values; table/schema names are constants or regex-validated (`kill-switch-store.ts:25,142`; `upsert-guard.ts:45-52,150-160`). No injection path found.
- Incident id allocation: allocate + insert under one advisory lock (`incident-store.ts:136-153`) with `incidents_year_sequence_key` and the partial unique index `idx_incidents_auto_declared_open` (meta-schema.ts:4289-4292) as backstops; duplicate-episode adoption via `findOpenFor` (`:266-283`).
- Optimistic concurrency with a `revision` predicate and zero-row = conflict (`incident-store.ts:180-196`), and append-only timeline check before SQL (`records.ts:232-241`).
- DR upsert guard is a real fix, not `DO NOTHING`: scope-unchanged + not-stale + legal-transition predicates derived from the contract's transition map, and a zero-row write is diagnosed and thrown (`upsert-guard.ts:57-147, 206-266`).
- Rows are re-parsed through the zod contract on read (`rowToIncident`, `rowToKillSwitch`, `rowToFeatureFlag`), so hand-edited rows fail loudly.
- Write paths distinguish tenant vs platform scope and set exactly one of tenant context / platform-write GUC (`observability-runtime-pg/records.ts:323-334`; `kill-switch-store.ts:319-329`).
- SLO engine handles restart adoption, in-flight declaration dedup (`engine.ts:124,170,272-292`) and uses multi-window burn-rate correctly (`burn-rate.ts:87-102`).
- Bounded in-memory sinks (`tracing.ts:94-128`, `synthetics.ts:124-140`).
- The codebase is unusually candid in-source about what is not wired (`producers.ts`, `subsystem-survey.ts`).
