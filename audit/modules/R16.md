# R16 — packages/notifications, packages/notification-providers

## Summary (10 lines max)
- The provider clients are carefully written (no secrets in error text, strict fail-closed bounce parsing, TwiML escaping, push payload allow-list), but the **deployed notification stack delivers almost nothing real**: SMS, voice and push are handed an email address / user id as the recipient, and email/SMS/voice bodies are fixed stub strings because the template engine is wired to no external sender.
- 18 providers declared, 4 external clients implemented (SES, Twilio SMS, Twilio Voice, FCM) + in-app = 5/18. Credentials are one platform-wide set read from flat env vars; no per-tenant sender identity.
- Large contract surface is dead: dedup, per-recipient rate limiting, per-user quiet hours, on-call rotation, `ProviderConfigSchema`, `validateRenderInput` have zero callers outside the package.
- Security-relevant: quiet hours `drop_silently` drops `security_alert`; hard-bounce/complaint suppressions are permanent, override security alerts and have no lift route; the bounce loop depends on an unshipped relay holding the master secret.
- Reliability: the send timeout is a race without cancellation and no sender accepts an AbortSignal, so a slow provider yields duplicate SMS/calls/emails. Paging reaches only the first recipient of a multi-recipient target and fans out sequentially.
- In-house SigV4 is correct for its one fixed request but has no AWS known-answer test and is not a general signer. No SSRF reachable by a tenant was found; endpoint/webhook URLs are operator config, unvalidated.
- No Arabic/RTL/ICU support in templates; numbers are locale-grouped even inside JSON webhook payloads.

## Findings

### R16-01 [High] [CONFIRMED] [Capability] SMS, voice and push cannot deliver to anyone through the deployed drain
- Where: `apps/operate-server/src/delivery-drain.ts:125-131`; `packages/notification-providers/src/voice-twilio.ts:389-402`; `push-fcm.ts:518-525`; `sms-twilio.ts:249-250`; `packages/notifications/src/audiences.ts:147-174`
- Evidence: `addressFor` returns `channel === "in_app" || channel === "push_mobile" ? recipient.userId : recipient.email`. So `sms` and `voice_call` get the user's **email**, `push_mobile` gets a **user UUID**. The voice sender refuses (`if (!isE164(request.recipientAddress))` → `voice_recipient_not_e164`), the push sender refuses (`looksLikeFcmRegistrationToken` rejects a UUID), and the SMS sender has no guard: `To: request.recipientAddress` posts the email to Twilio. Sender comments admit it: "The serving recipient directory hands this channel the user's *email address* today". The `AddressBook`/`resolveUserAddress` contract that would hold phone numbers and device tokens has no caller and no table.
- Impact: three of four external channels are structurally undeliverable. SMS additionally burns a Twilio request per recipient and (LIKELY, Twilio 21211) records a terminal `bounced_hard`. `deploy/README.md:389-391` shows `channels: in_app, email, sms` as a healthy state.
- Fix: add a per-user phone / device-token directory (table + write routes), resolve per channel, and add the missing E.164 guard to `TwilioSmsSender.send`.
- Effort: L

### R16-02 [High] [CONFIRMED] [Capability] External channels send fixed stub text; the template engine reaches no provider
- Where: `packages/notification-providers/src/email-ses.ts:16-24, 261-266`; `sms-twilio.ts:66-67`; `voice-twilio.ts:150-152`; `apps/operate-server/src/delivery-senders-env.ts:175-186, 236-248, 372-381`; `apps/operate-server/src/digest-template.ts:186,197`
- Evidence: `SendRequest` has `templateId`, `locale`, `recipientAddress` and no content. Default composers: `subject: \`CrossEngin notification: ${request.templateId}\``, body "A notification (…) is waiting for you in CrossEngin". The env builder constructs every sender without a `compose` option. `renderTemplateContent` has exactly one non-test caller, the in-app digest summary. `validateRenderInput` has none.
- Impact: no tenant-authored email/SMS/voice content can be sent (no invoice email, no password reset, no receipt). Template authoring, four-eyes approval and per-channel escaping exist for content that only the in-app digest renders. The email subject also discloses the template id (`lab_result.critical_ready` is itself sensitive, as `push-fcm.ts:93-97` acknowledges for push).
- Fix: carry rendered content (or a render callback) through `SendRequest`; render in the drain with the approved template version; keep the stub as the fallback for classified content.
- Effort: L

### R16-03 [Medium] [CONFIRMED] [Security] Quiet hours can silently drop security alerts
- Where: `packages/notifications/src/throttling.ts:121-149`; reached via `apps/operate-server/src/delivery-throttle.ts:228-245`, `delivery-drain.ts:244`
- Evidence: `decideQuietHoursAction` bypasses only for `config.bypassCategories.includes(category)` or `priority === "critical"`; otherwise `case "drop_silently": return { action: "drop", … }`. `NON_SUPPRESSIBLE_CATEGORIES` is never consulted here, unlike in `computeDispatchEligibility` and `shouldWithholdDuplicate`. The drain turns `drop` into a terminal `dropped` attempt.
- Impact: a tenant policy of `drop_silently` (or a wide window) discards `security_alert`/`transactional` notices of non-critical priority with no retry. The same omission exists in `evaluateRateLimit` (`throttling.ts:205-225`, currently uncalled).
- Fix: treat non-suppressible categories as `send_now` (or at worst `defer`) in `decideQuietHoursAction`; add the test.
- Effort: S

### R16-04 [Medium] [CONFIRMED] [Reliability] Send timeout does not cancel the request; duplicates on retry
- Where: `apps/operate-server/src/delivery-senders.ts:180-214`; `packages/notification-providers/src/email-ses.ts:530-533`; `sms-twilio.ts:284-295`; `voice-twilio.ts:409-420`; `push-fcm.ts:571-579`
- Evidence: `sendWithTimeout` resolves a `failed` result when its timer fires but never aborts `sender.send`. None of the four `ChannelSender`s passes a `signal` to `fetchImpl` (the page senders and both token providers do). No idempotency token is sent to any provider.
- Impact: a provider that answers after 10 s still sends; the drain has already recorded `failed` and scheduled a retry, so the recipient gets a second SMS, call or email. Hung sockets accumulate against a stalled provider.
- Fix: pass an `AbortSignal` through `SendRequest`/sender options and abort on timeout; treat post-timeout ambiguity as "unknown", not retryable, for voice/SMS.
- Effort: M

### R16-05 [Medium] [CONFIRMED] [Security] Bounce trust rests on an unshipped relay; suppressions are permanent, override security alerts and cannot be lifted
- Where: `packages/notification-providers/src/bounce-webhook.ts:21-42, 1177-1202, 1259-1296`; `packages/notifications/src/preferences.ts:21-45, 298-312`; `apps/operate-server/src/bounce-webhook-env.ts:40-49`; `apps/operate-server/src/suppression-store.ts:321-394`
- Evidence: the module verifies only the platform's own HMAC and states SNS/Twilio native signatures "cannot be verified here"; "A deployment therefore terminates the provider's native scheme at the edge … and re-signs". No such relay exists in `deploy/` or `apps/`. The per-tenant key is `HMAC(NOTIFICATION_BOUNCE_SECRET, "bounce-webhook:"+tenantId)`, so a relay serving more than one tenant must hold the master secret. The payload is not cross-checked against the tenant in the URL (the SES sender stamps a `tenant_id` tag at `email-ses.ts:484-491`; nothing reads it back). `hard_bounce` and `spam_complaint` are in both `PERMANENT_SUPPRESSION_REASONS` and `UNCONDITIONAL_SUPPRESSION_REASONS`, and the store has `write`/`writeAll`/`get`/`activeSuppressions` only — no delete or expire.
- Impact: (a) out of the box the bounce loop cannot run, so dead addresses are retried forever; (b) anyone holding the relay secret can permanently stop any address in any tenant from receiving mail, including security alerts and receipts; (c) a mistaken suppression can only be undone with SQL. Forgery without the secret was not found: verification is constant-time, tolerance-bounded and precedes parsing.
- Fix: ship the relay (verify SNS RSA signature / Twilio HMAC-SHA1 natively — node:crypto has both); bind the event to the tenant via the SES tag; add an audited lift route; consider not letting `spam_complaint` block `security_alert`.
- Effort: M

### R16-06 [Medium] [CONFIRMED] [Reliability] A page reaches only the first recipient, and channels are tried one after another
- Where: `packages/notification-providers/src/page-dispatch.ts:191-194, 413-415, 477-500`
- Evidence: `case "email_digest": return target.recipients?.[0] ?? null; case "sms": return target.phoneNumbers?.[0] ?? null;`. Fan-out is `for (const target of directive.channels) { outcomes.push(await this.one(…)) }`, and `one` may sleep up to the 30 s retry budget plus a 10 s timeout per attempt.
- Impact: a policy listing three on-call phone numbers pages one. A degraded first channel delays every later channel of a `sev1` by up to ~60 s.
- Fix: iterate all addresses of a target; run channels with `Promise.all`.
- Effort: S

### R16-07 [Medium] [CONFIRMED] [Compliance] Channel opt-in is declared and never enforced; no unsubscribe mechanism exists
- Where: `packages/notifications/src/channels.ts:75,84,111`; `preferences.ts:169-179`; `email-ses.ts:465-497`
- Evidence: `requiresOptIn: true` for sms, push_mobile and voice_call has no reader anywhere in the workspace. `isPreferenceOptedIn` returns `!requiresExplicitOptIn(category)` when no row exists, i.e. opted in to everything but marketing on every channel. The SES payload carries no `List-Unsubscribe` header or link, and no code writes an `unsubscribe` or `manual_block` suppression except the Twilio STOP code path.
- Impact: SMS/voice without recorded consent (TCPA / PECR exposure once R16-01 is fixed); bulk email without one-click unsubscribe fails Gmail/Yahoo sender requirements.
- Fix: gate `requiresOptIn` channels on an explicit matrix entry; add List-Unsubscribe and a signed unsubscribe route.
- Effort: M

### R16-08 [Medium] [CONFIRMED] [Dead code] Dedup, rate limiting, per-user quiet hours and on-call rotation have no caller
- Where: `packages/notifications/src/dedup.ts` (whole file); `throttling.ts:151-225`; `quiet-hours.ts:191-298`; `audiences.ts:70-185`; `channels.ts:132-197`; `templates.ts:208-235`; `delivery.ts:343-386`
- Evidence: grep across `apps/` and `packages/` (excluding tests and these two packages) finds zero references to `computeDispatchDedupSha256`, `decideDispatchDedup`, `evaluateRateLimit`, `countRecentDeliveries`, `decideUserQuietHoursAction`, `resolveEffectiveQuietHours`, `findActiveOncallUser`, `resolveEscalationChain`, `validateRenderInput`, `summarizeDispatches`; the notifications `ProviderConfigSchema` likewise (the `sso` hit is a different schema).
- Impact: no duplicate suppression and no per-recipient rate limit in production, so a looping producer floods recipients and the SES/Twilio bill. Roughly 900 source lines plus ~1,500 test lines maintain behaviour no deployment runs.
- Fix: wire or delete; at minimum wire the per-recipient rate limit before enabling real content.
- Effort: M

### R16-09 [Low] [CONFIRMED] [Privacy] Provider error text stores raw recipient addresses beside the hashed one
- Where: `packages/notification-providers/src/sms-twilio.ts:309-312`; `voice-twilio.ts:433-436`; `email-ses.ts:546-549`; `packages/notifications/src/delivery.ts:171,184`
- Evidence: `errorMessage: truncateErrorMessage(parsed.message ?? …)` persists the provider's message verbatim. Twilio's 21211 and SES's `MessageRejected` messages quote the destination address. The attempt row otherwise stores only `recipientAddressSha256`.
- Impact: PII (and, today, users' emails sent as SMS `To`) in `meta.notification_deliveries.error_message`, defeating the hashing design.
- Fix: store the provider code only, or redact address-shaped tokens.
- Effort: S

### R16-10 [Low] [CONFIRMED] [Security hardening] Outbound URLs and endpoint overrides are unvalidated; webhook response and URL are persisted
- Where: `packages/notification-providers/src/page-slack.ts:140-195`; `page-pagerduty.ts:160`; `sms-twilio.ts:239`; `push-fcm.ts:482`; `email-ses.ts:454`; `apps/operate-server/src/page-record.ts:136-137`; `packages/observability/src/alerts.ts:45`
- Evidence: `WebhookPageSender.send(content, url)` posts to whatever `url` the alert policy holds (`z.string().url()`, any scheme, any host including 169.254.169.254 or loopback), follows redirects (no `redirect: "manual"`; `FetchLike` has no such field), returns `errorMessage: truncateErrorMessage(text)` and `reference: url`, both written to the audit record. `SES_ENDPOINT_URL`, `TWILIO_BASE_URL`, `FCM_BASE_URL`, `PAGE_*_ENDPOINT` accept `http://` although they carry Basic credentials / bearer tokens / SigV4; only the FCM token and metadata endpoints enforce a scheme (`fcm-token.ts:313-324`, `metadata-token.ts:289-307`). The webhook signature is optional (`page-slack.ts:116`).
- Impact: not tenant-reachable — the URL and overrides come from operator config/env — so this is hardening, not a live SSRF. It becomes one the day alert policies or the `webhook` notification channel become tenant-editable. Webhook URLs with embedded tokens are copied into the audit log.
- Fix: require https, block private/link-local ranges, disable redirects, stop persisting the response body and full URL.
- Effort: S

### R16-11 [Low] [CONFIRMED] [Correctness] Template rendering ignores variable types, drops declared fields and breaks numeric JSON
- Where: `packages/notifications/src/templates.ts:303-313, 355-359, 373, 379, 388-400, 249-251, 281-287, 137`
- Evidence: `formatValue` formats any number with `value.toLocaleString(locale)` regardless of the declared `VariableType`; `date` and `currency` have no formatter. In a webhook `payloadJsonTemplate`, `{"amount": {{n}}}` renders `1,234.5` (invalid JSON) and locale-specific digits. `collectOptional` substitutes `preheader`, `fromName`, `replyTo`, `deepLink`, `iconAsset`, `actionLabel`, `actionUrl` only to collect missing names — `RenderedContent` has no field for them, so they are never output. The `url` type accepts `javascript:` (`z.string().url()`) and `escapeMarkupValue` is context-insensitive, so `href="{{link}}"` is not protected by the engine (the app's authoring allow-list is the only guard). `bodySizeBytes` is declared by the author, not computed.
- Impact: wrong amounts/dates in notices once content is wired; silently discarded template fields; XSS safety depends on a different module. No code execution: the engine is a single regex replace with no expressions, conditionals or loops.
- Fix: format by declared type; emit or remove the dropped fields; refuse non-http(s) URL values; compute size.
- Effort: M

### R16-12 [Low] [CONFIRMED] [i18n] No RTL, plural or script support; SMS segment maths assumes GSM-7
- Where: `packages/notifications/src/templates.ts:131, 271-328`; `channels.ts:204-213`; `email-ses.ts:459-463`; `push-fcm.ts:138-146`
- Evidence: locale regex `^[a-z]{2}(-[A-Z]{2})?$` (no `zh-Hant`, no 3-letter languages); no ICU plural/select and no use of `@crossengin/i18n`; no `dir="rtl"` handling. `computeSmsSegments` is `Math.ceil(bodyBytes / 153)` over UTF-8 bytes, wrong for UCS-2 (Arabic: 70/67 characters per segment). `fromHeaderValue` is `` `${fromName} <${fromAddress}>` `` with no RFC 2047 encoding or quoting, so a non-ASCII or comma-bearing sender name is malformed (LIKELY rejected by SES). Push notices are matched by exact locale string with fallback to `notices[0]`.
- Impact: Arabic deployments get mis-costed SMS, unlocalised push and possibly rejected email sends.
- Fix: use the i18n package; encode display names; count UCS-2 segments.
- Effort: M

### R16-13 [Low] [LIKELY] [Correctness] Own-configuration failures classified as recipient hard bounces
- Where: `packages/notification-providers/src/email-ses.ts:277-279, 342-344`; `push-fcm.ts:267-270, 315-318, 390-393`
- Evidence: `SES_PERMANENT_RECIPIENT_TYPES = ["MessageRejected"]`; SES returns `MessageRejected` for a sandbox account, an unverified identity and content rejection, not only for a bad recipient. FCM: the comment says "A bodyless 404 is not read as `UNREGISTERED` … because a wrong project id answers 404", but `parseFcmErrorBody` falls back to `record["status"]`, and `"NOT_FOUND"` is in `FCM_PERMANENT_RECIPIENT_CODES`; Google API errors always carry `status`, so a wrong project id classifies `bounced_hard`.
- Impact: terminal, non-retried outcome for a misconfiguration; fixing the config does not deliver the queued dispatches. Contained today because the drain writes no suppression from a send outcome.
- Fix: bounce only on the `FcmError` detail `UNREGISTERED`; move `MessageRejected` to the configuration list or inspect its message.
- Effort: S

### R16-14 [Low] [CONFIRMED] [Maintenance] In-house SigV4 is single-purpose and has no known-answer test; static AWS keys only
- Where: `packages/notification-providers/src/email-ses.ts:126-240, 429-457, 519, 531`; `email-ses.test.ts:102-170`; `page-email.ts:188-209`
- Evidence: I traced the chain (`AWS4`+secret → date → region → service → `aws4_request`; canonical request; string to sign) and it matches the specification for a POST with a fixed path, empty query and four or five lowercase headers. It does not URI-encode the path, sort or encode a query, or handle duplicate headers, so it is not reusable for another AWS call. Tests assert shape only (`toMatch(/^[0-9a-f]{64}$/)`, "changes when the payload changes"); no AWS-published vector. Credentials are static `accessKeyId`/`secretAccessKey`; there is no IMDS, IRSA, ECS or STS refresh. SUSPECTED: with `baseUrl`/`endpoint` overridden, the signed `host` (`email.<region>.amazonaws.com`) differs from the host the HTTP client transmits; `page-email.ts:199-203` concedes a Host-rewriting proxy "will produce a signature AWS rejects".
- Impact: long-lived AWS keys in the environment; a silent signing regression would pass the suite; region is interpolated into the host unvalidated (operator input).
- Fix: add the AWS test-suite vector; or use `@aws-sdk/client-sesv2` / `aws4`, which also gives credential-provider chains.
- Effort: S (vector) / M (SDK)

### R16-15 [Low] [LIKELY] [Correctness] FCM token-endpoint override changes the JWT audience
- Where: `packages/notification-providers/src/fcm-token.ts:590, 676-681`
- Evidence: `endpoint = opts.endpoint ?? credentials.tokenUri ?? GOOGLE_TOKEN_URI` and `buildJwtAssertionClaims({ tokenUri: this.endpoint })` sets `aud` to the override. The option is documented "for an egress proxy", where Google still requires `aud = https://oauth2.googleapis.com/token`.
- Impact: `invalid_grant`, classed non-retryable, so every push is `dropped` with a message blaming the service account.
- Fix: keep `aud` on the credentials' token URI and use the override only as the request URL.
- Effort: S

### R16-16 [Low] [CONFIRMED] [Code quality] Test doubles exported from the production entry point; minor validation gaps
- Where: `packages/notification-providers/src/index.ts:6`; `sms-twilio.ts:213-215`; `templates.ts:506`; `quiet-hours.ts:40-66`
- Evidence: `export * from "./test-fakes.js"` ships `FakeFetch`, `TEST_WEBHOOK_SECRET` (32 bytes of `7`) and signing helpers in the public API. `hasApiKey` checks `!== undefined` only, so empty `apiKeySid`/`apiKeySecret` pass (the page SMS sender checks length). `channel === "marketing_only_channel" as never` is an unreachable branch. `zoneFormatters` caches one `Intl.DateTimeFormat` per distinct string; zone ids are case-insensitive, so user-supplied spellings grow it without bound (unreachable today, see R16-08).
- Impact: low; the well-known test secret is the notable one if anyone wires it by mistake.
- Fix: move fakes to a `./testing` subpath export; tighten the checks.
- Effort: S

## Verified strengths (things that are genuinely done well, with file:line)
- No credential appears in any error or log string I could find: FCM key defects are named without quoting the PEM (`fcm-token.ts:269-310`), OpenSSL errors are not forwarded (`fcm-token.ts:452-470`), device tokens and phone numbers are reported by length only (`push-fcm.ts:518-525`, `voice-twilio.ts:397-401`, `bounce-webhook.ts:1058-1062`).
- Bounce parsing is fail-closed and explicit: signature before parse (`bounce-webhook.ts:1181-1202`), unknown statuses refused rather than read as "not a failure" (`:699-705, 998-1004`), explicit code tables (`:659-671, 836-846`), busy/no-answer never suppress (`:777-780, 1007-1013`), all-or-nothing planning (`:1281-1289`), idempotent suppression id (`:361-371`).
- TwiML injection is closed: full XML escaping plus control-character stripping (`voice-twilio.ts:71-84`), locale allow-list for the attribute (`:92-101`), entity-safe clipping (`:132-138`). Inline TwiML avoids an unauthenticated content-serving route.
- Push payloads are checked against a catalog and an identifier allow-list on every send and refused before any network call (`push-fcm.ts:176-204, 530-544`).
- Token providers: in-flight collapse, expiry skew, lifetime cap, rejection never cached (`fcm-token.ts:654-668, 729-737`); EC-key trap caught at construction (`:246-256`); https enforced for the assertion (`:313-324`); mandatory `Metadata-Flavor` header and plaintext restricted to link-local/loopback (`metadata-token.ts:289-324`).
- Page senders all use AbortController timeouts and classify 429 as retryable (`page-pagerduty.ts:36-39, 159-204`); `Retry-After` parsing guards the `Date.parse("-5")` trap (`retry-after.ts:98-137`); retry is bounded by a total budget (`page-dispatch.ts:315-321, 483-490`).
- Header/CRLF injection: none reachable — every provider call is a JSON or form-encoded body, with `encodeURIComponent` on path segments and form values (`sms-twilio.ts:33-49`).
- Consent vs deliverability split is coherent and tested (`preferences.ts:284-332`); non-suppressible categories cannot be opted out of by any source (`:144-165`).

## Test quality notes
- ~1,150 tests across 21 files; ratio of test to source lines ≈ 1.3:1. Tests assert real behaviour (classification tables, refusal reasons, exact request bodies) rather than snapshots.
- Everything runs against `FakeFetch`; there are no recorded provider fixtures, no contract tests and no live-sandbox test for SES, Twilio, FCM, PagerDuty or Slack. Provider error shapes are the authors' reading of the docs.
