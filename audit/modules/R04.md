# R04 — packages/kernel-pg (schema reconciliation, DB connectivity, pgcrypto tooling)

## Summary (10 lines max)
- Migration model is "reconcile a TS catalog against pg_catalog": additive-only, no down path, no backup step, no SQL files. The planner is careful about *data* safety (refuses populated type changes / NOT NULL / CHECK) but is blind to *lock* safety: no `CONCURRENTLY`, no `lock_timeout`/`statement_timeout`, index rebuilds as DROP+CREATE in one transaction.
- Even the "read-only" paths (`drift`, `apply --plan`) request ACCESS EXCLUSIVE on every existing table that declares an expression (one probe at a time, no lock_timeout).
- The only real DB binding (`node-pg.ts`) has no pool `error` listener, no timeouts, no pool sizing; an idle-connection error crashes the serving process. It has no tests beyond `rowsResult`.
- `PGSSLMODE` handling is not what the code claims: with `ssl` left undefined node-pg re-reads `process.env.PGSSLMODE` itself, so unset/`allow` = never TLS, explicit `prefer` = mandatory verified TLS. `require` = no certificate validation. No CA can be supplied.
- CLI: unknown flags and any `--flag=value` form are silently dropped, so `apply --plan=true` / `apply --dry-run=1` / `apply --dryrun` execute the migration. "Production" guard is a database-name substring.
- pgcrypto stack uses `pgp_sym_encrypt` defaults (AES-128, SHA-1 S2K, no AEAD). `encrypt --apply` uses one static key for a whole schema (serving store uses per-tenant keys), drops the column's NOT NULL/indexes/constraints, holds ACCESS EXCLUSIVE for the whole table rewrite.
- `proveWideningSafe`, `rotateSchema`, the decrypting-view/trigger emitters, `listAppliedHashes` have no non-test caller anywhere. `surveyCheckAdmission` is wired (operate-server boot).
- `withTenantContext` is NOT in this package (9+ per-package copies elsewhere); kernel-pg only supplies `setPlatformWriteSql`/`scopeFilter`. Settings it does issue are transaction-local and bound.
- Identifier quoting is strict where it matters; raw interpolation is confined to trusted catalog text. Tests are 100% offline fakes; no test touches a real Postgres.

## Findings

### R04-01 [High] [CONFIRMED] [Availability] Pool has no `error` listener, no timeouts, no sizing — an idle-connection error terminates the API process
- Where: packages/kernel-pg/src/node-pg.ts:87-95; consumer apps/operate-server/src/node.ts:740
- Evidence: `const pool = new Pool({ host, port, user, password, database, application_name, ...ssl })` — nothing else. No `pool.on("error", …)` anywhere in `packages/*/src` or `apps/operate-server/src` (grep), and no `uncaughtException`/`unhandledRejection` handler in operate-server. `pg-pool@…/index.js:62` does `pool.emit('error', err, client)` for an idle client that errors; an `EventEmitter` `error` with no listener throws. No `max` (default 10), no `connectionTimeoutMillis` (a saturated pool waits forever), no `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout`, no keepalive.
- Impact: a Postgres restart, failover, admin `pg_terminate_backend`, or a NAT/pooler idle reset kills the serving process (in-process schedulers, drains, in-memory state with it). Compose `restart: unless-stopped` masks it as a restart loop. A slow query or a lock wait is unbounded; 10 slow requests exhaust the pool and every other request hangs with no timeout.
- Fix: add `pool.on("error")`, expose `max`/`connectionTimeoutMillis`/`statement_timeout`/`lock_timeout`/`idle_in_transaction_session_timeout` on `PgConfig`; `client.release(err)` on failed ROLLBACK (see R04-13).
- Effort: S

### R04-02 [High] [CONFIRMED] [Migration safety] Planned DDL takes long blocking locks on populated tables; no CONCURRENTLY, no lock/statement timeout
- Where: packages/kernel-pg/src/reconcile.ts:373-384 (`create_index`), :457-468 (`replace_index`), :414-436 (`replace_unique_constraint`), :287-293 (`add_column`), :964-977 (`add_foreign_key`), :666-676; emitters packages/kernel/src/bootstrap/emit.ts:381-400, :113; applier packages/kernel-pg/src/applier.ts:163-165
- Evidence: `emitIndex` → ``CREATE ${uniqueKw}INDEX … ON …`` (no CONCURRENTLY; `grep CONCURRENTLY packages/kernel/src/bootstrap` = 0 hits). `emitReplaceIndex` → ``DROP INDEX …; CREATE INDEX …`` as one string, run inside `connection.transaction` (BEGIN/COMMIT) so `DROP INDEX`'s ACCESS EXCLUSIVE on the table is held for the entire rebuild — reads and writes blocked. All these steps are planned with `guarded: false` irrespective of row count (the row count is only consulted for type/NOT NULL/CHECK). `add_foreign_key` validates every existing row under SHARE ROW EXCLUSIVE on both tables (no `NOT VALID` + `VALIDATE`). `ADD COLUMN … DEFAULT <volatile>` rewrites the table. Nothing sets `lock_timeout`, so a DDL queued behind one long-running query blocks all later queries on that table (lock queue).
- Impact: on a deployment with large `meta.audit_log` / `operate_entity_records` / `workflow_events`, a catalog change to an index is a full outage of that table for the build time, with no warning in the plan ("The plan names the step … but does not estimate the cost"). `CONCURRENTLY` is structurally impossible today because every statement is wrapped in a transaction.
- Fix: non-transactional path for `CREATE INDEX CONCURRENTLY` + swap; `SET LOCAL lock_timeout`; FK as `NOT VALID` + `VALIDATE CONSTRAINT`; print row estimates (`reltuples`) per step.
- Effort: M

### R04-03 [Medium] [CONFIRMED] [Migration safety] "Read-only" drift / plan requests ACCESS EXCLUSIVE on every existing table that declares an expression
- Where: packages/kernel-pg/src/expression-render.ts:90-98, :145-149, :164; callers reconcile.ts:1209, bin/crossengin-pg.ts:181 (`drift`), :132 (`apply --plan`)
- Evidence: each probe runs ``ALTER TABLE ${fq} ADD CONSTRAINT ${probe} CHECK (${req.expr}) NOT VALID`` then `ROLLBACK TO SAVEPOINT`. `ALTER TABLE … ADD CONSTRAINT CHECK` (even `NOT VALID`) needs ACCESS EXCLUSIVE on the table. The savepoint rollback releases it again, so locks are taken one probe at a time rather than accumulated — but there are several hundred probes (one per index predicate, policy USING/CHECK, table CHECK and column CHECK; the package's own comment says 777 column checks) across every RLS-bearing table, and nothing sets `lock_timeout`. The statement also requires table ownership.
- Impact: a `drift` cron or a `--plan` is not read-only: each probe must reach the head of the table's lock queue. Behind one long-running transaction on a hot table it waits indefinitely, and every query arriving after it on that table queues behind the pending ACCESS EXCLUSIVE — a stall caused by a "report" command. Run as a non-owner, every probe throws and is swallowed (R04-04).
- Fix: render against a throwaway `CREATE TEMP TABLE … (LIKE target)`; or `SET LOCAL lock_timeout` and treat a timeout as "undetermined".
- Effort: M

### R04-04 [Medium] [CONFIRMED] [Drift accuracy] Any probe error (permission, deadlock, timeout) is swallowed and reported as drift, and `apply` then plans a real DROP+CREATE
- Where: packages/kernel-pg/src/expression-render.ts:160-163; diff.ts:278-282; reconcile.ts:471-481, :457-468
- Evidence: `} catch { return UNRENDERABLE; }` — no error class inspected. `comparePredicate`: `if (declaredRendering === null) return \`declared expression cannot be applied to this table: …\`` → pushed as `changedPolicies`/`changedIndexes` → `replace_policy` / `replace_index` steps.
- Impact: `drift` as a non-owner role reports every policy and partial index as drifted (false alarm on a correct schema). As owner, a transient failure on one probe causes a needless policy replace or full index rebuild (R04-02 cost) of a correct object.
- Fix: distinguish SQLSTATE 42xxx (genuinely inapplicable) from 42501/40P01/55P03/57014 → "undetermined, not compared".
- Effort: S

### R04-05 [Medium] [CONFIRMED] [Transport security] `PGSSLMODE` semantics differ from what the code documents and reports at boot
- Where: packages/kernel-pg/src/node-pg.ts:81-94; connection.ts:223-229, :257-264, :381; node_modules/.pnpm/pg@8.20.0/node_modules/pg/lib/connection-parameters.js:25-38, :85
- Evidence: for `allow`/`prefer` the binding passes no `ssl` key ("pass nothing and let the server decide"). node-pg then runs `this.ssl = typeof config.ssl === 'undefined' ? readSSLConfigFromEnvironment() : config.ssl`, which maps `process.env.PGSSLMODE` `prefer` → `true`, anything unmatched (`allow`, unset) → `defaults.ssl` (false). node-pg has no opportunistic TLS.
  - PGSSLMODE unset (the default, reported as `prefer`): TLS is never attempted. Boot line says "the server may decline TLS" — the client never offers it.
  - PGSSLMODE=prefer set explicitly: `ssl: true` → TLS mandatory with full certificate verification; fails against a non-TLS or privately-signed server. Reported as `plaintext_possible`.
  - `require`: `{ rejectUnauthorized: false }` — encrypted, peer unauthenticated (MITM accepted). Self-disclosed.
  - `verify-full`: only node's default trust store; no `ca`, `PGSSLROOTCERT` never read (connection.ts:349-355 says so) → unusable with a private CA (RDS/Supabase root).
  - This wire carries `app.current_tenant_id` and, on the column store, the PHI key as a bind value.
- Impact: operators cannot get "TLS if available"; the default is cleartext; the boot assurance line misdescribes two of six modes; verified TLS is unreachable on providers with a private root, pushing them to `require`.
- Fix: always pass an explicit `ssl` value (`false` for disable/allow/prefer or implement prefer honestly); add `ca` support; default to refusing cleartext for non-loopback hosts.
- Effort: S

### R04-06 [Medium] [CONFIRMED] [CLI safety] Mistyped or `=`-form flags are silently ignored, so an intended dry run executes the migration
- Where: packages/kernel-pg/bin/crossengin-pg.ts:44-61, :106-112, :143-146
- Evidence: `const flags = new Set(argv.slice(2).filter((arg) => arg.startsWith("--") && !arg.includes("=")))`; no unknown-flag rejection. `runApply` only short-circuits on exact `--dry-run` / `--plan`.

- Fix: strict flag table; unknown flag/command → exit 2.
- Effort: S

### R04-07 [Medium] [CONFIRMED] [CLI safety] Production guard is a database-name substring; deploy always passes `--confirm`; destructive ops have no real confirmation
- Where: packages/kernel-pg/src/connection.ts:402-410; bin/crossengin-pg.ts:114, :131-142, :259; deploy/docker-compose.yml:78; deploy/.env.example:6
- Evidence: `lower.includes("prod") || … lower.endsWith("_live")`. The shipped DB name is `crossengin` (compose) / `postgres` (Supabase guide) → never "production". Compose runs `apply --confirm` on every `up`. `--allow-loosening` (drops FKs) needs no confirmation, only a stderr line. `encrypt --apply` (DROP COLUMN of plaintext) is gated only by the same heuristic. No backup-before-migrate anywhere in the package.
- Impact: the guard does not fire on the documented deployments; schema changes and constraint drops apply unattended at container start.
- Fix: require `--confirm-database <name>` echo for destructive/loosening runs; optional pre-apply `pg_dump --schema-only` hook; do not auto-apply on `up` in production profile.
- Effort: S

### R04-08 [Medium] [LIKELY] [Encryption] `crossengin-pg encrypt --apply` encrypts a whole schema under one static key, while the serving store reads per-tenant keys — and it is a no-op on its default schema
- Where: packages/kernel-pg/bin/crossengin-pg.ts:224-226, :257-268; src/encryption.ts:191, :338-358; src/encryption-migration.ts:46-58, :175-189
- Evidence: key = `env[COLUMN_ENCRYPTION_KEY]` set as `app.column_encryption_key` for every column in the schema; `UPDATE … SET col__enc = pgp_sym_encrypt(col::text, current_setting('app.column_encryption_key'))` with no tenant predicate. `COLUMN_ENCRYPTION_KEY` has no other consumer in `apps/` or `packages/` (grep); the server uses `COLUMN_ENCRYPTION_SECRET` + per-tenant derivation/envelope (operate-runtime-pg/column-store.ts:98-100, node.ts:744-760; not traced end to end — hence LIKELY). Default `--schema` is `meta`, whose tables carry no `crossengin.encrypt=at_rest` comments (those are written only by operate-runtime-pg/entity-ddl.ts:316 into entity schemas).
- Impact: run as documented it reports "No plaintext columns to encrypt"; run with `--schema=public` it converts every tenant's PHI to ciphertext the serving process cannot decrypt (`Wrong key or corrupt data`) and drops the plaintext column in the same transaction. Recovery depends on the operator still holding that env value. The migration is not recorded in `_meta_migrations` and takes no advisory lock.
- Fix: delete the subcommand or make it tenant-scoped through the same `ColumnEncryptionKeySource`; refuse when the target table has a `tenant_id` column.
- Effort: M

### R04-09 [Medium] [CONFIRMED] [Encryption] Encrypt-in-place silently drops the column's NOT NULL, default, indexes, UNIQUE/CHECK/FK, and holds ACCESS EXCLUSIVE for the full table rewrite
- Where: packages/kernel-pg/src/encryption-migration.ts:52-58
- Evidence: `ADD COLUMN "x__enc" BYTEA;` (nullable, no constraints) → whole-table `UPDATE` → `DROP COLUMN "x";` → `RENAME`. Nothing re-adds NOT NULL or any index/constraint; `DROP COLUMN` removes dependent indexes and constraints without CASCADE being needed. All five statements run in one transaction (:178-186), so the ACCESS EXCLUSIVE taken by statement 1 is held through the UPDATE (pgcrypto S2K per row). No row batching, no partition refusal (unlike rotation), no confirm-readability pass.
- Impact: integrity regression on PHI identifiers (e.g. a required MRN becomes nullable) plus an outage proportional to table size.
- Fix: capture and restore attnotnull/constraints; batch; add confirm pass.
- Effort: M

### R04-10 [Medium] [CONFIRMED] [Cryptography] pgcrypto is used with defaults: AES-128, SHA-1 iterated S2K per value, CFB+MDC (no AEAD), no algorithm/version tag, key readable by any SQL in the transaction
- Where: packages/kernel-pg/src/encryption.ts:366-372
- Evidence: `pgp_sym_encrypt(${valueExpr}, ${keyRef})` — no third `options` argument anywhere in the package (`cipher-algo`, `s2k-digest-algo`, `s2k-count` all default → aes128 / sha1 / random 65536–253952 iterations). Key is a session GUC: `current_setting('app.column_encryption_key')` is readable by any statement, function or trigger executing in that transaction.
- Impact: not AES-256 (a common compliance checkbox for PHI); a per-row KDF makes bulk encrypt/rotate CPU-bound under lock; ciphertext not bound to row/column/tenant (cut-and-paste between rows of the same tenant undetected); non-deterministic so no equality/uniqueness.
- Fix: pass `'cipher-algo=aes256, s2k-digest-algo=sha256'` (or raw-key `encrypt_iv`/app-side AEAD); record parameters.
- Effort: S (options) / L (AEAD redesign)

### R04-11 [Medium] [LIKELY] [Secrets] Claim that the key reaches "no server log line" is false under common logging settings
- Where: packages/kernel-pg/src/encryption.ts:186-189; encryption-migration.ts:181; encryption-writepath.ts:679
- Evidence: comment: "The value reaches Postgres as a *bound parameter* of `set_config($1, $2, true)`, so it is in no SQL text, no `pg_stat_statements` entry and no server log line." Postgres logs bind values (`DETAIL: parameters: $1 = 'app.column_encryption_key', $2 = '<key>'`) whenever the statement is logged (`log_statement = 'all'|'mod'`? — `all`; or `log_min_duration_statement`), governed by `log_parameter_max_length` (default -1 = full). Managed providers frequently enable duration logging. Not verified against a live server here (no DB access) — standard documented behaviour.
- Impact: PHI column keys (per tenant, on every PHI read/write in the serving store which uses the same idiom) can land in database logs / log shipping.
- Fix: document `log_parameter_max_length = 0` as a deployment requirement and probe it at boot; or avoid transporting keys through the SQL session.
- Effort: S

### R04-12 [Medium] [CONFIRMED] [Concurrency] Plan is computed outside the advisory lock; lock is a session lock on an idle side connection with no timeout
- Where: packages/kernel-pg/bin/crossengin-pg.ts:132 vs :161; src/applier.ts:112; src/node-pg.ts:121-133
- Evidence: `planLiveReconciliation(conn, …)` runs first; only `applier.apply()` enters `withAdvisoryLock`. Two concurrent appliers both plan the same delta, then serialise; the second runs a stale plan (`skipApplied: false`): `CREATE TABLE` / `CREATE INDEX` / `CREATE POLICY` (no IF NOT EXISTS) fail "already exists", `replace_index` (`DROP INDEX …; CREATE …`) rebuilds a second time. `pg_advisory_lock` blocks forever (no `pg_try_advisory_lock`, no timeout). The lock lives on a dedicated client that issues no query for the whole run — if it is dropped by an idle timeout, or the connection goes through a transaction-mode pooler, mutual exclusion is silently lost; `finally { client.release() }` returns a possibly broken client. Per-statement transactions use *other* pool connections, so the lock does not make the run atomic.
- Impact: racing replicas/CI produce failed-statement noise and exit 1, and can double-rebuild indexes; no deadlock-free guarantee.
- Fix: plan inside the lock; `pg_try_advisory_lock` with bounded wait; hold lock on the same connection that executes.
- Effort: S

### R04-13 [Low] [CONFIRMED] [Reliability] Applier continues past failures by default with no dependency analysis; a failed bookkeeping write aborts the run and loses the report
- Where: packages/kernel-pg/src/applier.ts:107, :179-208, :184-191
- Evidence: `this.stopOnFailure = opts.stopOnFailure ?? false`. Later steps that depend on a failed one (index on a column whose ADD failed; FK re-add after a failed retype whose FK was already dropped at reconcile.ts:325-336) still run. A `drop_foreign_key` step succeeds, the guarded `alter_column_type` then raises (row arrived), and the FK re-add (planTableConstraints) runs against the old type — may succeed or fail; if it fails the table is left committed **without the FK**. `recordStatement` in the catch is not itself guarded: if it throws (connection lost) `apply()` rejects and the per-statement outcomes are lost. Also node-pg.ts:111-118: failed `ROLLBACK` is swallowed and the client is `release()`d without the error → a poisoned connection re-enters the pool.
- Impact: partial schema states after a failure are possible and only visible in stdout of that run.
- Fix: group dependent steps into one transaction; guard the log write; `client.release(err)`.
- Effort: M

### R04-14 [Low] [CONFIRMED] [Auditability] Migration log is not an audit trail: one mutable row per statement hash, 200-char excerpt, no actor/version, never read
- Where: packages/kernel-pg/src/migration-log.ts:19-26, :72-81; statement-hash.ts:19-23; applier.ts:144-145 with bin/crossengin-pg.ts:159 (`skipApplied: false`)
- Evidence: `statement_hash CHAR(64) PRIMARY KEY` + `ON CONFLICT (statement_hash) DO UPDATE SET … executed_at = now()` overwrites prior attempts (a failure followed by success erases the failure; re-running a rebuild erases the earlier run). Stores `excerptStatement(sql)` (≤200 chars), not the SQL; no `current_user`, host, tool/catalog version, plan id. Both CLIs pass `skipApplied: false`, so the table influences nothing; `listAppliedHashes` has no caller. The table is created with plain `conn.query` outside any transaction and is excluded from drift (canonical.ts:21) so tampering with it is unreported. Plans with `unreconciled` items and `--allow-loosening` decisions are not persisted.
- Impact: "what changed in prod schema, when, by whom" cannot be answered from the database.
- Fix: append-only log with run id, actor, full SQL, catalog hash; persist plan + refusals.
- Effort: S

### R04-15 [Low] [CONFIRMED] [Drift accuracy] Reconciliation does not compare primary keys, FORCE RLS, grants/ownership, triggers, generated/identity columns, index sort order/opclass, or non-table objects
- Where: packages/kernel-pg/src/diff.ts:572-577 (`if (idx.primary) continue;`), :781-782 (only `relrowsecurity`); introspection.ts:213-222 (`relkind = 'r'` only), :253-256

### R04-17 [Low] [CONFIRMED] [Injection hardening] Unescaped interpolation of database-sourced names/values into SQL
- Where: packages/kernel-pg/src/encryption-migration.ts:31-38, :57 (`COMMENT ON COLUMN … IS '${directiveComment(input.dataClass)}'` — `dataClass` is parsed from an existing column comment, no quote escaping); reconcile.ts:155-157 `quoted()` (`"${schema}"."${table}"` with no validation) used for live names in `manualSql` (:219, :523, :532, :541, :555) and for the executed `SELECT count(*)` (:1242, catalog names only); check-admission.ts:658-663 (`admissionRemedy`, live constraint name), :594-595 (live CHECK expression evaluated), :753-754

### R04-19 [Info] [CONFIRMED] [Design] No reversibility, no backup, schema drops are permanently manual

## Verified strengths (things that are genuinely done well, with file:line)
- Data-destroying changes are refused, not attempted: type change / NOT NULL add / CHECK only on empty tables, re-checked inside the statement (`DO $$ … count(*) … RAISE`) — reconcile.ts:993-1021, :678-700; kernel emit.ts:234-254.
- Plan never drops a table, column, index, policy or disables RLS; `allowLoosening` reaches FKs only — reconcile.ts:483-503, :517-557, :895-935.
- Replacement of index/policy/constraint is one statement in one transaction (no committed window without the policy) — emit.ts:398-412; applier.ts:163-165.
- Identifier quoting is validate-and-reject, not escape — kernel ddl/identifiers.ts:1-8; migration-log.ts:32-37; expression-render.ts:183-188; scoped-write.ts:69-76.
- Session settings are transaction-local and bound: `SELECT set_config($1, $2, true)` — encryption-migration.ts:181, encryption-writepath.ts:679; `setPlatformWriteSql` uses `is_local = true` with a constant name — connection.ts:73-75. Nothing in this package issues a session-level `SET`.
- Tenant id in scope predicates is always a bind parameter — connection.ts:157-163; encryption-writepath.ts:85-89.
- Missing-key handling is thought through: one-argument `current_setting` (raises) enforced by regex before `--apply`; empty/missing env refused before connecting — encryption.ts:263-275, :312-359; bin:232-237. Key value never on argv.
- Rotation refuses when RLS would confine the session (reads `relforcerowsecurity`), refuses partitioned tables, confirms readability under the new key before commit — encryption-writepath.ts:587-642, :726-815.
- `verify-ca` is refused instead of silently degraded — connection.ts:388-390.
