# R02 — ERP packs (pack-erp-core, -healthcare, -retail, -grocery, -construction, -education, -government)

## Summary (10 lines max)
- The packs are well-formed declarative manifests (they parse, cross-validate and are internally consistent), but as an **ERP product** they are a data model plus CRUD, not a working ERP. Only AR/AP recognition, payment settlement, journal posting, FX revaluation and WHT have runtime logic (in `operate-runtime`, out of scope); inventory, procurement receipt, manufacturing, fixed assets, HR/payroll, pricing, tax rules, cost centers and books are **tables with no behaviour**.
- **25 jobs declared, 0 implemented** (`JOB_HANDLER_PROVIDERS = []`), and all 12 event-triggered jobs name events the only emitter can never produce.
- **Workflow transition permissions are bypassable**: the lifecycle `state` field is an ordinary caller-writable field on create/update, so the SoD the packs declare (e.g. `void: erp_admin`) is not enforced. Independently, the role design itself has no segregation of duties (one `ap_clerk` can create a vendor, bill it, approve it and pay it).
- Referential integrity is decorative on the shipped store (`--store pg`): `onDelete` is not enforced and reference ids are not validated; on `pg-columns` every `one_to_many … cascade` declaration is silently ignored.
- Tax: flat per-line rate or a TaxCode rate. **Nothing** for Egypt ETA, KSA ZATCA, UAE FTA or EU VAT beyond the word "ZATCA" in one unimplemented job's description. Customers have no tax id and no address.
- Compliance packs: 5 of the 6 ids the packs name (`pci`, `haccp`, `osha`, `ferpa`, `nist-800-53`) have no definition; nothing resolves any of them.
- Six vertical packs are thin demos: 2–4 entities, 13–28 fields each. English labels only; no Arabic/RTL.
- Not executed (build/test forbidden); all findings are from reading code paths.

## Findings

### R02-01 [High] [CONFIRMED] [AuthZ / SoD] Lifecycle `state` is a plain writable field — every transition grant in the packs is bypassable by anyone with entity `create`/`update`
- Where: `packages/operate-runtime/src/handlers.ts:467-552` (update arm), `:400-465` (create arm); `packages/operate-runtime/src/validation.ts:73` (`serverManaged: f.default?.kind === "sequence"` — the only server-managed case); `packages/operate-runtime/src/compile.ts:271-340` (guards); pack grants e.g. `packages/pack-erp-core/src/permissions.ts:31-36`, `:227-232`, `:191-196`.
- Evidence: the update handler builds `const patch = { ...raw, updated_at }` and calls `store.update(tenantId, spec.entity, id, patch)`; nothing strips or refuses the workflow's `stateField`. `validateEntity` only checks enum membership. The only protection is `lockedDocumentGuard`, which fires only when the *before* state is in a locked set, and exists for exactly five entities (JournalEntry, Invoice, TaxReturn, SalesOrder, PurchaseOrder). Create applies the literal default only when the caller omitted the field.
- Impact: `erp_accountant` (Invoice `update`) can `PATCH {state:"void"}` or `{state:"paid"}` on a draft invoice although `void` is `ADMIN_ONLY` (`permissions.ts:35`), and can `POST` an invoice born `paid`. **Bill, Payment, Expense, LeaveRequest, Timesheet, FixedAsset, WorkOrder, Encounter, Case, Enrollment, PerishableLot, Project have no lock guard at all**, so `ap_clerk` can edit the amount/vendor/state of an approved or paid Bill, any `PAY_WRITERS` role can set a Payment `completed`/`refunded` or change its amount afterwards, `hr_manager` can set an Expense `reimbursed`, `case_worker` can `close` a Case (`ADMIN_ONLY` transition, `pack-erp-government/src/permissions.ts:53`). A direct jump also skips the GL effects keyed on a specific edge (draft→paid never passes `sent`, so no AR recognition is posted). The whole approval model is advisory.
- Fix: treat any field named as a workflow `stateField` as server-managed — refuse it on update, force `initialState` on create; extend `lockedDocumentGuard` to Bill/Payment/Expense/GoodsReceipt/WhtCertificate.
- Effort: M

### R02-02 [High] [CONFIRMED] [SoD / Fraud controls] Role design has no segregation of duties, and nothing could enforce maker≠checker
- Where: `packages/pack-erp-core/src/permissions.ts:97` (`VENDOR_WRITERS` incl. `ap_clerk`), `:154-155`, `:185-196` (Payment), `:221-233` (Bill), `:119-132` (PO), `:165-175` (JournalEntry), `:207-219` (Expense), `:25-37` (Invoice); `permissions-ext.ts:144` (`FiscalPeriod: crud(GL_READERS, GL_WRITERS)`); `workflows-ext.ts:14-41` (every transition's only guard is a role permission).
- Evidence (single role, full cycle):
  - `ap_clerk`: create Vendor → create Bill → `approve` Bill (`approve: ["erp_admin","ap_clerk","controller"]`) → create Payment → `submit` → `complete` → `mark_paid`. Classic fictitious-vendor fraud path, one login.
  - `procurement_manager`: create Vendor → create PO → `submit` → `approve` own PO → `receive` → create GoodsReceipt.
  - `controller`: create JournalEntry + lines → `post` → `reverse`; also edits LedgerAccount, and can set `FiscalPeriod.status` back from `locked`/`closed` to `open` (plain update, no workflow) — so the period lock in `write-guards.ts:101-113` is self-service for the role that posts.
  - `erp_accountant`: create Account, create/`send` Invoice, `mark_paid`, complete inbound Payment, `reimburse` Expense.
  - `hr_manager`: create Expense → `submit` → `approve`; creates Employee and sets `annual_salary`; creates and approves LeaveRequest.
  - The `auditable` trait declares `created_by`/`updated_by` (`packages/kernel/src/ddl/built-in-traits.ts:16-17`) but no handler stamps them (zero occurrences in `packages/operate-runtime/src` non-test code), so a record does not know who made it and a "creator may not approve" guard has nothing to compare. The workflow guard vocabulary used by the packs is `permission` only.
- Impact: fails any SOX/ICFR or external-audit walkthrough of procure-to-pay, record-to-report and payroll. Not sellable to an audited company as is.
- Fix: split maker/checker roles (AP entry vs AP approval vs treasury release; GL preparer vs poster), stamp `created_by`, add a `not_creator` guard kind, give FiscalPeriod a lifecycle with a distinct close/reopen grant.
- Effort: M (roles) / L (guard + stamping)

### R02-03 [High] [CONFIRMED] [Reachability] 25 jobs declared, 0 implemented; 12 event triggers can never match
- Where: declarations `pack-erp-core/src/jobs.ts:3-45`, `jobs-ext.ts:38-135`, and each vertical `jobs.ts`; handler registry `apps/operate-server/src/node.ts:3374` (`const JOB_HANDLER_PROVIDERS: readonly JobHandlerProvider[] = [];`); emitter `packages/operate-runtime/src/entity-events.ts:68` (`[prefix, segment(input.entity), verb].join(".")`); matcher `packages/jobs/src/enqueue.ts:77` (`j.trigger.eventName === event.name`).
- Evidence: no file outside the packs references any `erp-*-…` job id. The emitter produces `<prefix?>.<entity lowercased>.<created|updated|deleted|toState>` (e.g. `erp.salesorder.fulfilled`), while the packs declare two-part names with underscores: `erp.sales_order_fulfilled`, `erp.quote_sent`, `erp.invoice_issued` (no `issued` state exists), `erp.lead_created`, `erp.work_order_completed`, `billing.payment_received`, `retail.order_placed`, `healthcare.lab_result_received`, `construction.inspection_completed`, `education.grade_posted`, `government.permit_issued`, `erp.payroll_approved`. Several name things with no entity at all: payroll (no Payroll entity), inspection, lab result, bank statement lines.
- Impact: invoices/bills never go overdue (and with it dunning and correct aging state), depreciation is never posted, sales orders never produce invoices, work-order completion never moves stock, nothing reorders, no FX rates load, no e-invoice is submitted, no payment gateway/bank reconciliation. The pack description advertises these as features (see Claims vs reality).
- Fix: either implement handlers (17 are pure entity-store logic) and align event names with the emitter, or delete the declarations and the marketing sentence.
- Effort: L

### R02-04 [High] [CONFIRMED] [Domain completeness] Most "modules" are CRUD tables with no behaviour; essential entities are missing
- Where: entity files under `pack-erp-core/src/entities-*.ts`; absence verified by grepping `packages/operate-runtime/src` and `apps/operate-server/src` (non-test) — zero references to `StockLevel`, `StockMovement`, `GoodsReceipt`, `BillOfMaterials`, `PriceList`, `TaxRule`, `AccountingBook`, `CostCenter`, `Timesheet`, `Expense`, `Shipment`, `payment_terms`, `reorder_point`, `standard_cost`, `quantity_on_hand`, `cost_center_id`, `depreciat*`; `FixedAsset` only in mask/CLI text; `WorkOrder` only in an AI prompt.
- Evidence / gaps an accountant would hit:
  - **Inventory**: no valuation method or cost layers (FIFO/weighted average), `StockMovement` (`entities-inventory.ts:113-134`) carries quantity but no unit cost/value, no lot/serial entity although `Item.tracking` offers `lot`/`serial` (`:31-35`), no transfer/count/adjustment documents, no UoM conversion (fixed 10-value enum, `:23-27`), `StockLevel` has no uniqueness on (item, warehouse) (`:110` plain index) and quantities are user-typed. No inventory↔GL link, so **COGS and inventory asset are never posted**.
  - **Procurement**: `GoodsReceipt` has no lines (`entities-procurement.ts:103-127`) — a receipt cannot say what or how many; no 3-way match; `PurchaseOrderLine.received_quantity` is hand-edited.
  - **AP**: `Bill` has no supplier invoice number (duplicate-invoice control impossible) and no payment terms; `BillLine` has no expense/GL account and no cost center (`entities-finance.ts:194-209`), so every bill posts to one expense account; no purchase-side withholding.
  - **AR**: `Account` (customer) has **no tax registration number, no address, no payment terms, no credit limit** (`entities.ts:16-43`); `InvoiceLine` has no `item_id`, no discount, no revenue account (`:156-197`); `Invoice` has no link to SalesOrder; a `paid` invoice is terminal, so it cannot be credited/refunded (`workflows.ts:12`, `:38-44`).
  - **Cash/bank**: no BankAccount, BankStatement or reconciliation entity; `Payment` applies to exactly one invoice or bill (`entities-finance.ts:106-107`) — no multi-document allocation, no unapplied cash/advances; vendors and employees have no bank details, so nothing can actually be paid.
  - **GL**: `LedgerAccount` is flat (no parent, no subtype/control flag, `entities-finance.ts:5-27`); `JournalLine` has no partner/sub-ledger dimension; no year-end closing/retained-earnings roll; no budgets.
  - **Fixed assets**: no depreciation schedule/entry entity, no accumulated-depreciation or net-book-value field, no in-service date, a single `ledger_account_id` (no accumulated-depreciation/expense accounts), no disposal proceeds (`entities-assets.ts:5-38`).
  - **HR**: no payroll (run, payslip, earnings/deductions, statutory contributions), no attendance, no leave balances/entitlements, no contracts, no end-of-service benefit. `JournalEntry.source` lists `payroll` and `depreciation` (`entities-finance.ts:45`) for processes that do not exist.
  - **Manufacturing**: BOM + WorkOrder only; no routing, work centers, material issue, labour/overhead, WIP.
- Impact: the product can book invoices, bills, payments and manual journals. It cannot run a trading, manufacturing or payroll company's books. "ERP core (51 entities)" overstates the functional footprint by roughly the 35 entities that are inert.
- Fix: scope the claim to "invoicing + AP + GL", or build inventory valuation and receipt posting first (largest correctness gap).
- Effort: L

### R02-05 [High] [CONFIRMED] [Tax / Localisation] Tax is a flat rate; no jurisdictional e-invoicing or VAT compliance of any kind
- Where: `pack-erp-core/src/entities-pricing.ts:5-26` (TaxCode: `jurisdiction` is free text `:18`, `gl_account_code` free text `:22`); `entities-accounting.ts:132-220` (TaxJurisdiction, TaxRule, TaxReturn); `jobs-ext.ts:70-76` (the only mention of ZATCA/Peppol in the non-test codebase — a job description).
- Evidence: `TaxRule` and `TaxJurisdiction` entities are read by no runtime code (grep above; `settings.ts` only mentions a jurisdiction→account map). `TaxRule.reverse_charge`, `is_compound`, `priority`, `effective_from/to`, `rate_category` are therefore inert. `TaxReturn.output_tax`/`input_tax` are hand-entered; nothing computes a return from the ledger. Tax on a line is `tax_rate_pct` or a TaxCode's `rate_pct`.
- Absent, plainly: **Egypt ETA** (no document UUID, digital signature, EGS/GS1 item coding, activity code, branch, e-receipt, QR); **KSA ZATCA** (no UBL 2.1 XML, QR TLV, invoice hash chain/ICV/PIH, CSID onboarding, simplified vs standard invoice type); **UAE** (no TRN field, no VAT201 boxes, no emirate breakdown); **EU** (no VAT-ID/VIES, no intra-community/reverse-charge posting, OSS, EC sales list, Intrastat). No tax-inclusive pricing, no exemption reasons/certificates, no per-jurisdiction rounding, no place-of-supply logic. Buyer tax id cannot even be stored (R02-04).
- Impact: legally unusable for B2B invoicing in Egypt and KSA (clearance is mandatory), and not VAT-compliant in UAE/EU without external tooling.
- Fix: per-country localisation packs with invoice schema, numbering, signing and submission; add tax ids/addresses to parties.
- Effort: L (per country)

### R02-06 [High] [CONFIRMED] [Data integrity] Relations/`onDelete` are not enforced on the shipped store; `one_to_many` cascades are ignored on the column store; masters are hard-deleted
- Where: `packages/operate-runtime/src/handlers.ts:556-598` (delete = guard → `store.remove`, no reference check); `packages/operate-runtime/src/validation.ts:250` (`reference: acceptAny`); `packages/operate-runtime-pg/src/column-plan.ts:332-340` (`if (rel.kind === "many_to_one" && rel.onDelete !== undefined)`), `entity-ddl.ts:389` (`?? "restrict"`); `deploy/docker-compose.yml:168-170` (default `erp-core` on `--store pg`).
- Evidence: on the JSONB store nothing consults `manifest.relations` at delete or write time, so all 66 core relations are documentation. `erp_admin` can delete a `LedgerAccount` that posted journal lines reference (declared `restrict`, `relations.ts:115-121`), an `Account` with invoices, a `Vendor` with bills, a completed `Payment`, a paid `Bill` (no lock guard), leaving dangling ids; a reference field accepts any string, including an id of the wrong entity. `postedEntryImmutabilityGuard` locks only `posted` (`write-guards.ts:170`), so a **reversed** JournalEntry can be deleted and its lines edited. No pack entity uses the `soft_deletable` trait.
  On `pg-columns` the FK emitter reads only `many_to_one`, so every `one_to_many … onDelete: "cascade"` the packs declare (`relations.ts:5-11` Account→Contact, `:21-27` Invoice→InvoiceLine, and all vertical relations) becomes RESTRICT — the two stores behave differently from each other and from the manifest.
  Where cascades *are* honoured (many_to_one, column store) some are wrong for records of account: `FiscalPeriod → FiscalYear cascade` (`relations-ext.ts:50`), `Shipment → SalesOrder cascade` (`:22`), `MaintenanceOrder → FixedAsset cascade` (`:41`), `LeaveRequest → Employee cascade` (`relations.ts:189-195`), `TaxRule → TaxJurisdiction cascade` (`relations-ext.ts:59`), `StockLevel → Item cascade` (`relations.ts:31-37`). Vertical intent is worse: Account→Patient→Encounter→Observation (`pack-erp-healthcare/src/relations.ts:10,18,26`), Account→Citizen→Case/Permit (`pack-erp-government/src/relations.ts:9,17,25`), Account→Student→Enrollment incl. grades (`pack-erp-education/src/relations.ts:9,17`) all declare cascade from a billing account to clinical / civic / academic records that carry statutory retention.
- Impact: financial and regulated history can be orphaned or destroyed by one admin delete; referential integrity depends on which `--store` flag was chosen.
- Fix: enforce relations in the handler for both stores, validate reference existence/type, soft-delete masters, change record-of-account cascades to restrict.
- Effort: M

### R02-08 [Medium] [CONFIRMED] [Money] Monetary typing is inconsistent and two-decimal only; currency is unvalidated free text and missing on several amounts
- Where: `entities.ts:118-139` (Invoice totals `decimal(14,2)`, `currency` text(3)); `entities-finance.ts:183-186` (Bill `decimal(16,2)`), `:70-75` (JournalLine `16,2`); `entities-accounting.ts:14` (`Currency.decimal_places`, zero readers in runtime).
- Evidence: all totals use scale 2, so KWD/BHD/OMR/JOD/TND (3 dp) cannot be stored exactly, while `Currency.decimal_places` allows 0–6 and is read by nothing. Invoice (14,2) vs Bill/JournalLine (16,2) means an invoice can overflow before the ledger does. `tax_rate_pct` is (5,2) on InvoiceLine but TaxCode `rate_pct` is (6,3). Every `currency` is `text maxLength 3`, not a reference to `Currency`, so `"XXX"` or an inactive code is accepted; ~20 fields default to `"USD"` (e.g. `entities-finance.ts:17`, `entities-accounting.ts:103`). Amounts with **no currency**: `FixedAsset.acquisition_cost`/`salvage_value`, `MaintenanceOrder.cost`, `Lead.estimated_value`, retail `Product.unit_price`/`unit_cost`, grocery `cost_per_unit`, construction `Project.budget_amount` and `WorkOrder.cost_estimate`, government `Permit.fee_amount`. The kernel has a `currency_amount` field kind (`validation.ts:233`) that no pack uses.
- Impact: wrong amounts for 3-decimal currencies; unvalidated currency codes flow into FX logic; ambiguous amounts in verticals.
- Fix: one money type (amount + currency reference), scale driven by the currency, consistent precision.
- Effort: M

## Verified strengths (things that are genuinely done well, with file:line)
- Manifests are consistent and cross-validated in tests: every pack parses, verticals are validated after lineage resolution (`pack-erp-retail/src/pack.test.ts:60-67`), three-level lineage works (grocery→retail→core).
- Money uses `decimal` with explicit precision/scale everywhere, never float types; FX rates are `decimal(20,10)` (`entities-accounting.ts:34`); JournalLine carries transaction and functional amounts plus rate (`entities-finance.ts:70-75`).
- Every monetary *document* in core (Invoice, Bill, Payment, Quote, SalesOrder, PO, Expense, TaxReturn, WhtCertificate) carries a currency; Invoice/Bill capture a booking rate.
- Per-field grants on classified fields are thought through and tested by derived rules rather than hand lists (`pack-erp-core/src/permissions.test.ts:103-205`): update⊆read, required fields creatable, general viewer excluded; set-once semantics for `national_id`/`mrn` (`permissions.ts:280-284`, `pack-erp-healthcare/src/permissions.ts:21-25`).
- Deletes are admin-only on almost every header entity; restrict is declared on the right GL edges (JournalLine→LedgerAccount, JournalEntry→FiscalPeriod, TaxReturn→FiscalPeriod).
