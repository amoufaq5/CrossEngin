# R07 — packages/crypto, crypto-pg, sso, security, forensics, forensics-pg

## Summary (10 lines max)
- Primitives are sound: node:crypto only, AES-256-GCM with random 96-bit nonce + mandatory AAD, HKDF-SHA256 with per-tenant salt and per-purpose info, Ed25519, scrypt+HMAC-pepper, timingSafeEqual everywhere it matters. No MD5/ECB/static IV/hardcoded key found in scope.
- The weak part is the **audit-trail tamper evidence**, not the cryptography. `entry_hash` is never recomputed by any verifier; the default integrity pass (`fromCheckpoint: true`) never re-checks signatures or links at/below the latest checkpoint; checkpoints are unsigned rows in the same DB written without verifying the chain first; public keys are resolved from the same DB (tenant-scoped keys accepted, status/purpose ignored); RLS on the chain tables is `ALL`-scope so the serving role can UPDATE/DELETE entries. Net: tamper-evident against a tenant via the API; **not** against anyone with SQL write (app compromise, SQLi, DBA).
- Signed bytes do not bind the tenant/scope, and one platform key signs every tenant's chain → cross-tenant chain transplant verifies.
- `sso`, `security`, and the evidence/legal-hold/custody/attestation/e-discovery half of `forensics` are **contracts only with zero importers**. No SAML/OIDC/SCIM code path, no CSP emitted from the builder, legal holds are consulted by nothing (incl. the Art. 17 deletion pipeline).
- `KeyStore`/`InMemoryKeyStore`/crypto audit ("auto-audit of key management") is dead code: no caller, the store never calls an audit sink, key rotation/revocation of the registry has no caller.
- Password hashing: scrypt N=2^15 (4x below OWASP's N=2^17 floor, acknowledged in-code), no upper bound on stored N/r/p, no pepper versioning.
- Envelope/rekey code is careful and honest about its limits; the one secret (`COLUMN_ENCRYPTION_SECRET`) derives every tenant's column key and KEK, so the envelope adds nothing against an app-host compromise.

## Findings

### R07-01 [High] [CONFIRMED] [Tamper evidence] Default integrity proof never re-verifies anything at or before the latest checkpoint; a DB writer without the signing key can rewrite audited history undetected
- Where: `apps/operate-server/src/integrity-proof.ts:61` (`fromCheckpoint: z.boolean().default(true)`), `apps/operate-server/src/chain-verify.ts:88-110`, `packages/forensics-pg/src/checkpoint.ts:25-43`, `packages/forensics/src/tamper-evident-logs.ts:96-112`, `apps/operate-server/src/audit-anchor.ts:99-110`, `apps/operate-server/src/checkpoint-scheduler.ts:162-171`.
- Evidence: `verifyChainFromCheckpoint` loads only `sequence_number >= checkpoint+1` and runs `verifyChainSuffix` + `verifyChainSignatures(suffix, …)`. Entries ≤ checkpoint get no link check and **no signature check**. The anchor half (`verdictFor`) compares `chainEntry.entryHash !== anchor.entryHash` and `chainEntry.payloadSha256 === sha256(row)` using the *stored* columns. No verifier anywhere recomputes `entry_hash` from the canonical bytes (`verifyChainIntegrity`: only `e.priorEntryHash !== priorHash`). So: UPDATE an old `meta.audit_log` row, UPDATE that chain entry's `payload_sha256` to the new row hash, leave `entry_hash` alone → suffix valid, truncation check passes, anchor "verified", verdict `verified`. The now-invalid Ed25519 signature on that entry is never looked at. The checkpoint scheduler makes this permanent: `createCheckpoint` loads the chain and takes the tail hash **without verifying** links or signatures first, so every tick moves more history into the unverified region.
- Impact: the advertised "hash-chained, signed, checkpointed audit trail" detects middle-of-chain tampering only in the window since the last checkpoint (default cadence = checkpoint interval) or when an operator runs a full verify by hand. SOC2/HIPAA audit-integrity claims rest on this.
- Fix: (1) recompute `entryHash` from canonical bytes in `verifyChainIntegrity`/`verifyChainSuffix`; (2) verify chain (links+signatures) before recording a checkpoint; (3) in the anchor check verify the signature of every chain entry an audit row points at, or default `fromCheckpoint` to false and run full verification on a slower cadence; (4) sign checkpoints.
- Effort: M

### R07-02 [High] [CONFIRMED] [Tamper evidence] Chain, checkpoints and verification keys all live in one database the serving role can rewrite; no external anchor is ever produced
- Where: `packages/kernel/src/bootstrap/meta-schema.ts:11221-11243` (chain policies), `:11287-11308` (checkpoint policies), `:10103-10124` (`crypto_keys` policies); `packages/forensics-pg/src/checkpoint-store.ts:65-85`; `apps/operate-server/src/chain-verify.ts:25-33`; `packages/crypto-pg/src/key-registry.ts:145-158`.
- Evidence: the tenant-isolation policy on `forensic_chain_entries` and `forensic_chain_checkpoints` has no `command`, i.e. `ALL` — UPDATE and DELETE are permitted to any session that sets `app.current_tenant_id` (a PUBLIC-settable GUC). There is no trigger, no REVOKE, no append-only enforcement (`grep REVOKE|CREATE TRIGGER` in `kernel/src/bootstrap` = 0 hits). Verification resolves the public key with `registry.getByFingerprint(fingerprint, tenantId)` whose predicate is `tenant_id = $n OR tenant_id IS NULL`, with no filter on `status` or `purpose` — so a tenant-scoped row in `meta.crypto_keys` (insertable under the same tenant context) is an accepted verifier for that tenant's chain, including a `revoked` one. `externalAnchorReference` is never set by any non-test code (grep: only schema/store plumbing). Checkpoints carry no signature.
- Impact: an attacker with SQL execution in a tenant's context (SQL injection, compromised app process, DBA) needs **no signing key**: generate a keypair, insert the public key as a tenant key, rewrite+re-sign the tenant's whole chain, rewrite/delete checkpoints, rewrite audit rows → `verifyChainFull` returns OK. A DB superuser can do the same to the platform chain. Truncation detection is defeated by deleting the checkpoint rows too (`verifyChainFromCheckpoint` silently falls back to full verify when none exists). Realistic strength: (a) tenant via API — tamper-evident; (b) app-level attacker — not tamper-evident (also holds the private key, R07-04); (c) DB superuser — not tamper-evident. The comment calling a checkpoint "the external witness" (`integrity-proof.ts:120`) is wrong: it is a row in the same schema.
- Fix: pin trusted verification key fingerprints out of band (config/env, not DB); resolve platform keys only (`tenant_id IS NULL`) for chains the platform signs; require `status='active'` at signing time semantics + `purpose='evidence_sealing'`; make chain/checkpoint tables INSERT-only for the serving role (separate owner, `REVOKE UPDATE, DELETE`, or a `BEFORE UPDATE OR DELETE` trigger); publish signed checkpoints to an external append-only sink (object-lock bucket, transparency log, RFC 3161 TSA).
- Effort: L

### R07-03 [Medium] [CONFIRMED] [Tamper evidence] Signed entry bytes do not bind the tenant/scope; one key signs all chains → cross-scope transplant verifies
- Where: `packages/forensics/src/sealing.ts:38-57` (`canonicalEntryBytes` = `{sequenceNumber, kind, recordedAt, actorReference, payloadSha256, payloadSizeBytes, priorEntryHash}`), `apps/operate-server/src/audit-chain.ts:270-275` (one `ed25519ChainSigner(config)` for every tenant).
- Evidence: neither `tenantId` nor a chain id is in the canonical JSON; every chain starts at seq 0 / `GENESIS_HASH`. A full copy (or any genesis-anchored prefix) of tenant B's chain inserted as tenant A's chain passes link and signature verification.
- Impact: with DB write and no key, an attacker can replace a tenant's history with another tenant's genuine, validly signed history (or a shorter prefix of its own — see truncation). The audit_log anchor check will flag rows whose anchors no longer match, but a chain whose audit rows are deleted with it reads `verified`/empty.
- Fix: include `tenantId` (or `"platform"`) and a domain-separated chain id in the canonical bytes (new domain tag `…entry.v2`); derive a per-tenant genesis hash.
- Effort: M

### R07-04 [Medium] [CONFIRMED] [Key management] Chain signing private key is a base64 seed in a JSON config file on the app host; no KMS/HSM path, no rotation or revocation path that works
- Where: `apps/operate-server/src/audit-chain.ts:25-36` (`privateKeyBase64: z.string().min(1)` in `--audit-chain-config` JSON), `:142-151`; `packages/crypto/src/key-store.ts:62-237` (`InMemoryKeyStore`, sole `KeyStore` impl); `packages/crypto-pg/src/key-registry.ts:246-252` (`revoke`/`markRotating`).
- Evidence: `ed25519ChainSigner` signs with the raw seed held in process memory for the process lifetime. `InMemoryKeyStore`, `keyStoreChainSigner`, `buildChainWithKeyStore`, `sealEvidenceWithStore` have **no non-test importers** (grep across `apps/*/src packages/*/src`). `PostgresKeyRegistry.revoke/markRotating` have no callers; verification ignores `status` anyway. No schema validation of key length in the config (deferred to `signEd25519`).
- Impact: any app-host read (config file, memory, backup of the file) yields the ability to forge entries for every tenant and the platform; a compromised key cannot be revoked in a way verification honours; rotation = edit the file and restart (old entries keep verifying only because the old public key row stays in the DB).
- Fix: signer interface backed by KMS/HSM (sign-only); record key validity window and reject signatures outside it; wire revoke.
- Effort: M

### R07-05 [Medium] [CONFIRMED] [Audit completeness] Per-request audit chain entries commit to a payload that is not stored anywhere by the chain
- Where: `apps/operate-server/src/audit-chain.ts:154-173`, `packages/forensics-pg/src/chain-log-store.ts:248-272`.
- Evidence: `auditAppendInputFrom` builds a JSON payload (`requestId, operationId, outcome, status, principalId, correlationId`), `insertWithin` stores only `payload_sha256` + `payload_size_bytes`. Unless the same request was captured by the separately-flagged, sampled `--gateway-execution-capture`, the preimage is gone.
- Impact: for request-level entries the chain proves "an event of kind audit_event by actor X at time T existed", not what it was (operation/outcome are unrecoverable). An auditor cannot answer "what did user X do" from the chain. (Entries anchored to `meta.audit_log` rows do have a preimage.)
- Fix: persist the canonical payload (or a pointer to an immutable store) alongside the hash.
- Effort: S

### R07-09 [Medium] [CONFIRMED] [Password hashing] scrypt default N=2^15 is below OWASP minimum; stored N/r/p are unbounded; no pepper versioning
- Where: `packages/crypto/src/password.ts:32` (`{ n: 32768, r: 8, p: 1 }`), `:83` (`ENCODED_RE` `([0-9]+)`), `:99-111`, `:148-157`; `packages/kernel/src/bootstrap/meta-schema.ts:212-214` (CHECK regex also unbounded).
- Evidence: (a) OWASP: scrypt N=2^17,r=8,p=1 minimum; code comment acknowledges and chooses 2^15 for throughput. The HMAC pepper compensates only while the pepper is not co-compromised (it lives in the same process env as the DB credentials). (b) `parsePasswordHash` accepts any power-of-two N and any r,p ≥ 1; `deriveScrypt` passes `maxmem: 256*N*r` so the limit scales with the attacker-chosen value. Measured locally (pure node): N=2^20 → 2.9 s CPU and ~1 GiB per verify. Anyone who can write `meta.users.credential_hash` (no RLS on that table) can make each login attempt for that user a 1 GiB allocation on a 4-thread libuv pool. (c) the power-of-two test uses 32-bit `&`: `n = 2^32+2^31` passes (`(n & (n-1)) === 0` evaluated true locally) and then scrypt rejects → promise rejection → 500 from `verifyPassword`, contradicting its "never throws / yes or no" contract (`:209-213`). (d) no pepper id in the encoded hash; rotating `CREDENTIAL_PEPPER` invalidates every password (`deploy/.env.example:56-57` says so) — a leaked pepper cannot be rotated without a global reset. (e) no Unicode normalisation (NFKC) of the password before HMAC.
- Impact: offline cracking cost 4x lower than guidance if pepper+DB both leak; login-path DoS primitive for a DB writer; pepper incident response is all-or-nothing.
- Fix: bound N ≤ 2^20 (and r ≤ 16, p ≤ 4) in parser and CHECK; use `Number.isSafeInteger` + `Math.log2` for the power-of-two test; wrap derive errors into `unreadable_hash`; add `$pv=<n>` pepper version; raise default to 2^17 or move to argon2id.
- Effort: S

### R07-10 [Medium] [CONFIRMED] [Key management] One deployment secret derives every tenant's column key and KEK; no rotation executor for either; envelope KEK is co-located
- Where: `packages/crypto/src/key-derivation.ts:275-290, 347-363`; `packages/crypto-pg/src/data-key-store.ts:140-158` (`kekGeneration` recorded, never rotated), `:199` (`this.kekFor(tenantId)`).
- Evidence: `deriveTenantColumnKey` and `deriveTenantKek` both take `COLUMN_ENCRYPTION_SECRET`; separation is the HKDF info label only. `generation` defaults to 1 and no flag/env exposes it (grep `DEFAULT_KEY_GENERATION` callers). No code re-wraps a DEK under a new KEK generation. Wrapped DEK and ciphertext are in the same DB; the KEK source is an env var on the host that holds the DB credentials.
- Impact: compromise of the app host = decrypt all tenants' PHI, envelope or not. A leaked `COLUMN_ENCRYPTION_SECRET` cannot be rotated (no executor), only worked around per tenant via `rekey` (which changes the DEK, not the KEK). "Per-tenant keys" gives blast-radius separation only against a single derived key leaking, which has no realistic path that does not also leak the master.
- Fix: KMS-held KEK (per tenant for BYOK), KEK re-wrap command (cheap: one row per tenant), expose generation with a dual-read window.
- Effort: M

### R07-11 [Medium] [LIKELY] [Rekey] `rekeyTenant` is atomic for itself but not against concurrent writers holding the old key
- Where: `packages/crypto-pg/src/data-key-rekey.ts:318-441`.
- Evidence: the transaction takes `DATA_KEY_LOCK_SQL` (advisory, only `ensure`/rekey take it) — ordinary entity writes do not. A serving process with the old DEK cached that INSERTs a row after the confirm pass but before/after commit writes ciphertext under a key whose row is then deleted (`rekeyWithin` DELETE `generation <= from`). Nothing on the row records its key. The module's own comments name this window ("bounded, not closed"); safety depends on the CLI caller's tenant-suspended gate and a cache TTL, both outside this package and overridable (`--allow-live-rekey` per CLAUDE.md; not verified here).
- Impact: permanent PHI loss for rows written in the window if the gate is bypassed or the status gate is not enabled (it is opt-in).
- Fix: `LOCK TABLE … IN SHARE ROW EXCLUSIVE` on the affected tables inside the rekey transaction, or a per-row key-generation column.
- Effort: M

### R07-12 [Low] [LIKELY] [Schema] Platform-scope chain/checkpoint uniqueness is not enforced (NULL tenant_id); platform checkpoints duplicate
- Where: `packages/kernel/src/bootstrap/meta-schema.ts:11200-11205, 11265-11270` (UNIQUE `(tenant_id, sequence_number)`), `packages/forensics-pg/src/checkpoint-store.ts:74` (`ON CONFLICT (tenant_id, sequence_number) DO NOTHING`).
- Evidence: Postgres UNIQUE treats NULLs as distinct; the DDL vocabulary has no `NULLS NOT DISTINCT` (`meta-schema.ts:7224` comment says so). For `tenant_id IS NULL` the constraint never fires, so the advisory lock is the only guard against duplicate platform sequence numbers, and a re-recorded platform checkpoint inserts a new row each time. Not run against a live PG (build lock) — standard semantics.
- Fix: partial unique indexes `… WHERE tenant_id IS NULL`.
- Effort: S

### R07-13 [Low] [CONFIRMED] [Secret validation] The "too_uniform" entropy heuristic rejects ~24% of `openssl rand -hex 32` secrets and accepts trivially guessable ones
- Where: `packages/crypto/src/key-derivation.ts:74` (`MIN_COLUMN_SECRET_DISTINCT_BYTES = 16`), `:155-162`.
- Evidence: a hex string has exactly 16 possible byte values, all of which must appear. Measured (20k trials, pure node): 64-hex-char secrets refused 23.7%; 32-hex-char 92.7%. Meanwhile `abcdefghijklmnopqrstuvwxyz012345` passes. Deploy docs suggest base64 (`deploy/ORACLE.md:200`), which passes, but an operator using hex gets an intermittent boot refusal for a 256-bit secret. Applies to column secret, cursor secret and credential pepper.
- Fix: accept a declared encoding (hex/base64 → ≥32 decoded bytes) instead of a distinct-byte count.
- Effort: S

### R07-14 [Low] [CONFIRMED] [AEAD] Random 96-bit GCM nonce with a non-rotatable per-tenant cursor key; code comment overclaims "negligible at any volume"
- Where: `packages/crypto/src/aead.ts:59-61, 79`; `key-derivation.ts:311-327`.
- Evidence: NIST SP 800-38D limits random-IV GCM to 2^32 invocations per key (collision prob 2^-32). One seal per list page; a tenant at 1k list req/s reaches 2^32 in ~50 days, and the cursor key generation cannot be advanced (no caller passes `generation`). DEK wrap volume is trivially small — fine there.
- Impact: low (cursor confidentiality/forgery only), but the stated invariant is not true without rotation.
- Fix: rotate generation on a schedule with dual-open, or use XChaCha20-Poly1305 / AES-GCM-SIV.
- Effort: S

### R07-15 [Low] [CONFIRMED] [Webhook HMAC] Replay inside the tolerance window is accepted; future timestamps accepted symmetrically
- Where: `packages/crypto/src/hmac.ts:84-102` (`Math.abs(opts.nowSeconds - parsed.timestampSeconds)`).
- Evidence: no nonce/delivery-id store; `abs()` admits a timestamp `tolerance` seconds in the future, doubling the window. Compare is constant-time (`timingSafeEqual`, `:104-110`), canonical message is `"<ts>." || body` — correct. Single `v1` signature only, so key rotation needs a hard cut.
- Fix: dedupe on (timestamp, signature) for the window; reject future timestamps beyond small skew; accept multiple `v1=` values.
- Effort: S

## Verified strengths (things that are genuinely done well, with file:line)
- AEAD: fresh `randomBytes(12)` per seal, required AAD, explicit `authTagLength: 16`, wrong-length key throws while auth failure returns null (`crypto/src/aead.ts:43-131`). Tag length pinned on decipher prevents truncated-tag acceptance.
- HKDF: tenant id as salt, purpose+generation in info, empty tenant refused, separate info labels for column/cursor/KEK, derivation re-validates the secret (`key-derivation.ts:241-363`).
- Password: async scrypt, 16-byte random salt, HMAC pepper before KDF, `timingSafeEqual`, params stored per hash, rehash-on-login wired (`apps/operate-server/src/auth-token-route.ts:297-298`), dummy work for unknown users at current params (`password.ts:235-242`), route caps password at 1024 chars.
- Ed25519: strict base64 + length checks, 64-byte signature check, fingerprint match before verify (`signing.ts:83-135`, `forensics/src/sealing.ts:140-157`); domain tags on signed bytes.
- DEK envelope: AAD binds `[tenantId, generation]` as JSON; unwrap failure throws rather than re-provisioning; per-tenant xact advisory lock; hard delete; provenance recorded (`data-key.ts:80-122`, `data-key-store.ts:189-215, 448-464`).
- Rekey: single transaction, no catch, refuses zero-row rotation and identical keys, key values only as bind params (`data-key-rekey.ts:318-441`).
- Key registry: scope predicates beside RLS, scoped upsert guard, zero-row writes diagnosed and thrown (`key-registry.ts:89-127, 220-244`).
- Chain append: per-scope `pg_advisory_xact_lock`, append in caller's transaction available (`chain-log-store.ts:199-226`).
- SQL identifiers validated by regex before interpolation in every store (`SCHEMA_RE`), all values bound.

## Claims vs reality (docs/README/CLAUDE.md/comments that the code contradicts)
- CLAUDE.md "`crypto` — … auto-audit of key management": no code path writes a crypto audit record (R07-16).
- CLAUDE.md "`sso` — federated identity contracts", "`security` — … CSP builder": accurate that they are contracts, but they are also unimported; CLAUDE.md's own register lists both as zero-importer (consistent). Any external material presenting SSO/SCIM as a feature is contradicted.
- `integrity-proof.ts:120` "A checkpoint is the external witness": it is an unsigned row in the same database (R07-02).
- `chain-verify.ts:84-86` "Trust in the anchor comes from the earlier verification that produced it": the checkpoint scheduler performs no verification before anchoring (`checkpoint-scheduler.ts:162-171`).
- `aead.ts:59-61` "collision probability negligible at any volume this platform will reach": only with key rotation, which does not exist (R07-14).
