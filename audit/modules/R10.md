# R10 — operate-server: audit trail, integrity proof, tenant deletion/erasure, deletion requests, escalation/paging

## Summary (10 lines max)
- `meta.audit_log` is NOT a business audit trail: no entity create/update/delete, no login/failed-login, no settings change is ever written to it. Only ~10 privileged platform surfaces emit rows. Entity writes leave at most a per-request chain entry (operation id + status, no entity id, no before/after, no IP), written asynchronously after the response, sampled, and only when `--audit-chain-config` is set — which the shipped compose does not set.
- The hash chain is real (Ed25519, per-scope linear) but the scheduled "integrity proof" has structural holes: deleted audit rows are undetected, only the newest ≤500 rows are ever re-checked, history before the last checkpoint is never re-verified in the default mode, checkpoints are unsigned rows in the same database, and trust roots (public keys) live in the same database. A tamper incident auto-cancels itself once the row ages out of the 500-row window.
- "Four-eyes" on tenant deletion, schema erasure and deletion-request verification is self-asserted free text: one person with one credential satisfies it.
- A GDPR request naming ONE data subject irreversibly erases the WHOLE tenant; the subject identifier is never passed to the pipeline. No Article 15/20 path, no deadline alerting, no grace period after verify.
- Authorization on all destructive routes is a flat role-name match with no tenant binding: path tenant id is never compared with the caller's tenant.
- SQL is uniformly parameterised; schema identifiers are regex-validated; tenant-scope reads carry an explicit predicate plus RLS context. No injection found.
- Code is careful and heavily commented; tests are behavioural but run entirely against fakes.

## Findings

### R10-01 [High] [CONFIRMED] [Audit coverage] Business writes, logins and settings changes are not in the audit log
- Where: `packages/operate-runtime/src/**` (no `AuditEmitter` reference in any non-test file); `apps/operate-server/src/node.ts:1688,1808,2154,2239,2379,2445,2521,2599,3604` (every `auditEntry(` call site); `apps/operate-server/src/audit-chain.ts:154-173`
- Evidence: `grep AuditEmitter|auditEmitter` over `packages/*/src` returns no file in `operate-runtime`. The only `emit` callers are the erasure, deletion, deletion-request, audit-read, preference-admin, platform-user, read-state-backfill, notification tenant-scope, page-record and the two escalators. The only thing recorded for an entity write is `auditAppendInputFrom`: `payload: JSON.stringify({ requestId, operationId, outcome, status, principalId, correlationId, completedAt })` — no entity id, no before/after, no IP/user-agent. `credential-auth-env.ts` / `credential-store.ts` contain no `auditEntry`.
- Impact: "who changed this invoice / journal entry, from what to what" is unanswerable. `before`/`diff` columns of `meta.audit_log` are never populated by any caller (`auditEntry()` hardcodes `before: null, diff: null`, `audit-log-store.ts:207-209`). No login or failed-login trail. Fails SOX/ISO 27001/SOC 2 CC7 expectations for an ERP; the audit-read route's own doc ("who touched this record") describes data that does not exist.
- Fix: emit an audit row (entity, entityId, before/after/diff, actor incl. IP + session) inside `writeTxn`'s transaction for every create/update/delete/transition; audit login success/failure and `admin.settings.update`.
- Effort: L

### R10-02 [High] [CONFIRMED] [Audit coverage] Auditing is off by default, sampled, asynchronous and non-transactional
- Where: `apps/operate-server/src/audit-chain.ts:33` (`sampleRate: z.number().min(0).max(1).default(1)`), `:34` (`tenantOverrides`), `:212-237` (observer), `:226-227` (`catch (err) { this.opts.onError?.(err); }`); `node.ts:2945-2966`; `deploy/docker-compose.yml` (no `--audit-chain-config`, `--integrity-proof-config`, `--checkpoint-config`, `--audit-read-routes`)
- Evidence: the per-request record is appended from an execution sink after the request completed, through an in-memory promise queue; a failed append is logged and dropped. `sampleRate`, `outcomes` and `operations` filters apply uniformly — there is no carve-out for financial entities or for writes. A process crash loses every queued append.
- Impact: a business write can commit with no audit record (append failure, crash, sampling, filter), and nothing detects the gap because request entries have no expected count. On the shipped compose there is no chain at all. A sampled audit log is not an audit log.
- Fix: make the write-path audit synchronous and in-transaction (see R10-01); refuse `sampleRate < 1` / `operations` filters for mutating operations; ship the compose with the chain, checkpoint and proof configs.
- Effort: M

### R10-03 [High] [CONFIRMED] [Audit integrity] A tenant admin can switch off their own tenant's request audit
- Where: `apps/operate-server/src/audit-sampling-policy-source.ts:57-70`; `audit-chain.ts:107-119` (live policy wins per field); `packages/operate-runtime/src/settings.ts:157`; `packages/operate-runtime/src/compile.ts:805-810` (`admin.settings.update`, default admin role `erp_admin`)
- Evidence: `TenantSettingsSchema.auditSampling` is written by the tenant's own `PUT /v1/admin/settings`; `TenantAuditPolicyCache.refresh()` reads it and `shouldRecordAuditWithLive` uses `live?.sampleRate ?? base.sampleRate`. `{"auditSampling":{"sampleRate":0}}` (or `operations:["x"]`) silences the tenant.
- Impact: with `--audit-sampling-refresh-ms` on, the audited party controls whether it is audited; the settings change itself is not written to `meta.audit_log` (R10-01). Gated on that flag.
- Fix: remove `auditSampling` from tenant-writable settings (platform-only), or only allow it to *raise* the rate; audit the change.
- Effort: S

### R10-04 [High] [CONFIRMED] [Audit integrity] Deleting an audit row is undetectable; only the newest ≤500 rows are ever verified
- Where: `apps/operate-server/src/audit-anchor.ts:70-99` (loops over `rows`, never over chain entries); `audit-log-store.ts:71` (`MAX_LIMIT = 500`), `:463-465` (`ORDER BY occurred_at DESC, id DESC LIMIT`), `:469-472` (unparseable row dropped); `integrity-proof.ts:56,212-219`; `packages/kernel/src/bootstrap/meta-schema.ts:483-485` (`audit_log_tenant_isolation` has no `command` ⇒ ALL, so UPDATE/DELETE are permitted by policy; no trigger/REVOKE exists anywhere in `bootstrap/`)
- Evidence: verification is row→anchor only. A deleted row leaves an orphan `audit_event` chain entry, and orphans are normal because per-request observer entries (`audit-chain.ts:160`) use the same kind with no row. `tryAuditEntryFromRow` returning null means a row edited into an unparseable shape is silently skipped rather than reported. Rows older than the newest 500 per scope are never re-read by any pass.
- Impact: anyone with SQL access under a tenant context (the single serving DB role, a SQL-injection elsewhere, a DBA) can delete audit rows, or edit any row once 500 newer rows exist, with a `verified` verdict. Any authenticated user can manufacture those 500 rows (R10-08).
- Fix: verify chain→row as well (give row-anchoring entries a distinct kind and require a row for each); page through the whole table on a lap like the tombstone sweep; treat an unparseable row as `compromised`; make the isolation policy `SELECT, INSERT` only and add a `BEFORE UPDATE OR DELETE` trigger.
- Effort: M

### R10-05 [High] [CONFIRMED] [Audit integrity] Default proof never re-verifies history before the last checkpoint; checkpoints are unsigned, unverified and in the same database
- Where: `apps/operate-server/src/chain-verify.ts:88-110` (`verifyChainFromCheckpoint`: "this does not re-fold the prefix"); `integrity-proof.ts:61` (`fromCheckpoint` default `true`); `checkpoint-scheduler.ts:159-172` (`createCheckpoint` + `record` with no prior verification), `:188` ("Signs nothing on the checkpoint path"); `packages/forensics-pg/src/checkpoint.ts:57-73`; `audit-anchor.ts:101-114` (compares `entryHash`/`payloadSha256` columns, no signature, no hash recomputation)
- Evidence: the checkpoint is `{sequenceNumber, rootHash}` of whatever the tail currently is, inserted as a plain row; `externalAnchorReference` is never supplied. In `from_checkpoint` mode only entries after it are link/signature-checked. The anchor half trusts the stored `payload_sha256`/`entry_hash` of the chain row it finds.
- Impact: an attacker with DB write can rewrite an audit row older than the last checkpoint (≤1h by default), patch that chain entry's `payload_sha256` and both `entry_hash` copies, and every scheduled pass reports `verified` — no signing key required. A checkpoint taken after a tamper permanently blesses it. Truncation detection is defeated by deleting the checkpoint row too. "Tamper-evident" holds only against an attacker who cannot write the chain tables.
- Fix: periodic full fold from genesis (not only on demand); verify before checkpointing; sign checkpoints and publish them outside the database (object-lock bucket / transparency log); recompute `entryHash` in the anchor check.
- Effort: M

### R10-06 [High] [LIKELY] [Audit integrity] Trust root for chain signatures is the database being protected; private key is a plaintext file on the app host
- Where: `apps/operate-server/src/chain-verify.ts:25-33` (`registry.getByFingerprint(fingerprint, tenantId)`); `audit-chain.ts:29` (`privateKeyBase64` in the JSON config), `:125-139`; `audit-chain-key-registration.ts:67-75`
- Evidence: a signature is accepted if its fingerprint resolves in `meta.crypto_keys`; nothing pins the expected key to `config.publicKeyBase64`. The write grant for that table is a session GUC any connection can set (documented in CLAUDE.md as PUBLIC-scoped; not re-verified here). The signing key sits unencrypted beside the DB credentials, in the same process.
- Impact: a DB-write attacker registers their own Ed25519 public key and re-signs an entire forged chain; an app-host compromise yields the real key. No KMS/HSM, no key rotation path for the chain key, no off-box witness.
- Fix: pin accepted fingerprints from config/KMS at verification; hold the key in a KMS and sign remotely; export checkpoints off-box.
- Effort: M

### R10-07 [High] [CONFIRMED] [Incident handling] A tamper incident auto-cancels and its page auto-resolves when the row ages out of the window
- Where: `apps/operate-server/src/integrity-escalation.ts:196-217`; `integrity-proof.ts:212` (newest-N window)
- Evidence: `if (report.verdict !== "compromised") { … closeOut(openId) … if (closeOutClosesAlert(closeOut)) await this.emitResolve(openId)`. The verdict is computed over the newest `auditRowLimit` rows only, so a `hash_mismatch` row stops being read after 500 newer rows and the next pass says `verified`.
- Impact: the sev1 for a provably altered audit trail is cancelled by the system with reason "no longer finds the trail altered" although nothing was repaired. Combined with R10-08 an attacker closes their own incident; with an hourly pass they can prevent it ever opening.
- Fix: never auto-close a `compromised` episode; require a human disposition; keep the tampered row ids pinned and re-check them explicitly.
- Effort: S

### R10-08 [Medium] [CONFIRMED] [DoS / integrity] Any authenticated caller can append unlimited audit rows and chain entries
- Where: `apps/operate-server/src/audit-read-routes.ts:662-684` (`recordDenial` on every 403), `:698-710` (one row per granted list/get); `node.ts:2213-2253`
- Evidence: a principal with a UUID tenant and no audit role gets 403 and `deniedEvent` emits `audit.read_denied` into its tenant's trail — an INSERT plus a signed chain append under the per-tenant advisory lock, with `rateLimitPolicyId: null` on the routes (`:795`).
- Impact: write amplification and unbounded table/chain growth by an unprivileged user; serialises the tenant's chain; `loadChain(scope)` is read whole on every proof pass (`integrity-proof.ts:218`) so cost grows without bound; and it is the lever for R10-04/R10-07.
- Fix: rate-limit and coalesce denial records; attach a rate-limit policy; stream the anchor check instead of loading the chain.
- Effort: S

### R10-09 [Critical] [CONFIRMED] [Destructive op / GDPR] A single-subject erasure request destroys the entire tenant
- Where: `apps/operate-server/src/node.ts:3534-3552` (runner: `kind: "data_subject_erasure"` → `deleteTenantAtomically(… tenantId …)`, `attestations: []`), `:1750-1768` (sync route, same call); `deletion-request-routes.ts:303` (`subjectIdentifier` required), `:422-432`; `tenant-deletion-routes.ts:48,400`; `packages/tenant-lifecycle-pg/src/deletion-pipeline.ts:192` (optional `subjectIdentifier`, never supplied by either caller)
- Evidence: the request stores `subjectIdentifier`; neither `deleteTenantAtomically` call passes it, and the pipeline's erasures are `DROP SCHEMA` + `DELETE … WHERE tenant_id = $1`. Once `verified`, the next scheduler tick runs it; there is no grace period, no cancel window beyond `reject` racing the tick, and no un-delete.
- Impact: verifying one data subject's Article 17 request irreversibly deletes every record of that customer (all employees, ledgers, invoices) and signs a tombstone labelled `data_subject_erasure`. Catastrophic data loss by following the documented flow; also a breach of statutory retention for the tenant's own books.
- Fix: until per-subject erasure exists, refuse `data_subject_erasure` and name the flow "tenant deletion"; require an explicit tenant-level confirmation and a cooling-off period before the runner may claim.
- Effort: L (real per-subject erasure) / S (refuse + rename)

### R10-10 [High] [CONFIRMED] [AuthZ] Four-eyes is self-asserted free text on all three destructive surfaces
- Where: `tenant-deletion-routes.ts:245` (`approvedBy: z.string().min(1).max(200)`), `:393-399`; `tenant-erasure-routes.ts:135,310-318`; `deletion-request-routes.ts:309` (`submittedBy` from body), `:482` (`existing.submittedBy === principal.principalId`); `deletion-scheduler.ts:19-20` (`"system:deletion-runner"` / `"system:retention-policy"`); `principals.ts:42,62`
- Evidence: `approvedBy` is only compared for inequality with the caller's `principalId`; it is not required to be a user, to hold a role, or to have approved anything. On the async route the verifier is compared with a body-supplied string (the tests use `submittedBy: "subject@example.test"`), so the submitting principal can verify their own request; the pipeline's executor/approver are then two constants. Bare API keys all share one placeholder principal id, so the executor recorded is not a person.
- Impact: one person holding one credential (with the relevant role) deletes any tenant by typing a second name. The "three layers" all check the same forged string. The recorded approver is fabricated evidence in the tombstone and audit row.
- Fix: two-step approval: a second authenticated principal with a distinct grant must POST an approval bound to the tenant id and a nonce; record the submitting *principal* server-side and compare against it; refuse `service_account` principals.
- Effort: M

### R10-11 [High] [CONFIRMED] [AuthZ / tenancy] Destructive platform routes authorise on role name alone, with no tenant binding
- Where: `tenant-deletion-routes.ts:285-292,373-378`; `tenant-erasure-routes.ts:157-160,293`; `deletion-request-routes.ts:302,401`; `audit-read-routes.ts:463-474`; `principals.ts:159` (`primaryRole: p?.grantedScopes[0]`)
- Evidence: the tenant to delete comes from the path (or body, for a deletion request); `principal.tenantId` is never consulted, the tenant is not checked to exist, and there is no "platform tenant" concept. "Platform" roles and manifest/tenant roles share one flat string namespace taken from the first JWT scope / membership role.
- Impact: any principal in ANY tenant whose role string equals a configured deletion/erasure/submit/audit-platform role can delete or read every other tenant, including the operator's own. Safety rests entirely on nobody ever granting that role name in a customer tenant and on the IdP's `scope` claim; a mis-set `--tenant-deletion-role erp_admin` makes every tenant admin a platform destroyer.
- Fix: bind platform grants to a designated platform tenant (or a separate credential class); refuse platform role names in tenant memberships/manifests; for tenant-level self-deletion require path tenant == credential tenant.
- Effort: M

### R10-12 [High] [CONFIRMED] [Destructive op] Schema erasure and synchronous delete run against an `active` tenant, and erasure records after the fact
- Where: `tenant-erasure-routes.ts:320-359` (erase, then `recordAction`; 500 `erasure_unrecorded` after the data is gone); `node.ts:1671-1678`; `tenant-deletion-routes.ts:166-170` ("this route deletes straight from `active`")
- Evidence: neither route checks `meta.tenants.status`; `erase-schema` is `idempotencyRequired: false` and does not make the tenant read-only, so writes continue into the JSONB fallback after the drop. The audit record is attempted only after `DROP SCHEMA` committed.
- Impact: one request drops a live customer's typed tables while they are transacting; a recorder failure yields destroyed data with no audit row (acknowledged in code). No backup/restore automation exists to undo it.
- Fix: require `pending_deletion` (or `archived`) before either route proceeds; write an intent record before the drop.
- Effort: S

### R10-13 [High] [CONFIRMED] [GDPR/PDPL] No access/portability path, no deadline detection, no listing of requests

### R10-15 [Medium] [CONFIRMED] [Disclosure] Free-text audit fields bypass redaction; PII is written into audit payloads
- Where: `audit-read-routes.ts:358-359` (`reason`, `eSignature` returned verbatim), `:353` (`entityId`); `deletion-request-routes.ts:446` (`detail: request.subjectIdentifier`), `:667`; `integrity-verdict-routes.ts:348-353` and `integrity-verdict-store.ts:640` (store error text, including the raw cursor, returned as `detail`)

- Impact: personal data of an erased subject survives in the audit trail; `reason` can carry anything a caller typed; internal error text reaches clients.

### R10-16 [Medium] [CONFIRMED] [Reliability] One unparseable audit row makes every page containing it a 500
- Where: `audit-read-store.ts:133-138,189`; `audit-read-routes.ts:714-717`
- Evidence: `rowToEntry` throws on a row the schema rejects; the handler returns `audit_page_unreadable` with no way to skip. The read was already recorded as granted.
- Impact: a single corrupt/legacy row (or one deliberately corrupted via R10-04) blinds auditors for that window; the verification path meanwhile silently skips the same row.
- Fix: return the page with a tombstone entry `{id, unreadable: true}`; raise an integrity finding.

### R10-17 [Medium] [CONFIRMED] [Paging] A page that fails its ~30s retry budget is never re-sent; webhook pages are unsigned by default
- Where: `deletion-evidence-escalation.ts:801-827` (`adopted` ⇒ `page: null`), `:849-850`; `integrity-escalation.ts:219-227` (`ongoing`, no page); `page-senders-env.ts:190-194` (`new WebhookPageSender(webhookSecret === null ? {} : …)`); `packages/notification-providers/src/page-slack.ts:159,181`
- Evidence: after declaration, later ticks adopt the open incident and plan no page; an `undelivered` report is only logged (`node.ts:1866`). The webhook URL from the alert policy is passed to `fetch` with no scheme/host allow-list and default redirect following; `reference: url` is then stored in the audit row despite the comment "provider-issued, carries nothing".
- Impact: a pager outage coinciding with a sev1 means nobody is told. Operator-controlled SSRF only (config file, not tenant input) — Low; webhook URLs embedding tokens are persisted in `meta.audit_log`.
- Fix: re-page while `undelivered`; require a signing secret for webhooks; restrict to https and strip query strings before recording.

### R10-18 [Medium] [LIKELY] [Audit integrity] Proof/checkpoint scope defaults exclude tenants, and exclude deleted tenants' chains
- Where: `integrity-proof.ts:34` (`tenants` default `[]`), `:53` (`allTenants` default `false`); `checkpoint-scheduler.ts:21,33-35`; `scheduler.ts:61-67` (`PostgresTenantSource` default statuses, `status = ANY($1)`)

### R10-19 [Low] [CONFIRMED] [Robustness] Scheduler ticks can overlap; reconcile route has an unguarded throw; retention is undefined

### R10-20 [Low] [CONFIRMED] [Evidence quality] Actor attribution is thin

## Verified strengths (things that are genuinely done well, with file:line)
- All SQL parameterised; only regex-validated schema identifiers interpolated (`audit-log-store.ts:66,309`, `audit-read-store.ts:43,146,248-265`, `integrity-verdict-store.ts:22,497,586-592`).
- Tenant-scope reads carry both `withTenantContext` and an explicit `tenant_id = $1` (`audit-read-store.ts:235-243`, `audit-log-store.ts:403-424`); `getById` is always scoped (`audit-read-store.ts:207-219`); a tenant naming another tenant gets 403, not a narrowed query (`audit-read-routes.ts:483-498`).
- Audit row and its chain anchor are written in one transaction, anchor first, no UPDATE path (`audit-log-store.ts:326-365`).
- Privileged audit reads are recorded before being served and refused with 503 if unrecordable (`audit-read-routes.ts:641-655`); keyset pagination with clamped limit and capped window (`audit-read-store.ts:48,164-201`; `:55` 92 days).
- Fail-closed role checks: empty grant ⇒ nobody; null principal ⇒ 401 (`tenant-deletion-routes.ts:285-292`, `audit-read-routes.ts:452-474`).
- Deletion requires `confirmTenantId`, server-generated tombstone/request ids, idempotency key on delete and submit (`tenant-deletion-routes.ts:247,387,617-622`; `deletion-request-routes.ts:418,1075`); deletion surfaces refuse to mount without chain + capabilities (`node.ts:1719-1731,3511-3523`).
- Deletion scheduler deliberately does not run at boot; passes isolated in separate try blocks (`deletion-scheduler.ts:464-510`).
- Truncation is at least considered and unanchored rows are reported `unproven`, not `verified` (`integrity-proof.ts:201-210,235-253`).
- Page credentials come from env, not argv; page payload carries no tenant data (`page-senders-env.ts:19-34`).

## Code quality notes
