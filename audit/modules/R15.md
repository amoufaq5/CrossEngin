# R15 — packages/workflow-runtime-pg, packages/workflow-worker, packages/workflow-signal-bridge

## Summary (10 lines max)
- ~8.1k source LOC, 680 offline tests. SQL hygiene is good (bound params, validated identifiers, correct `FOR UPDATE SKIP LOCKED` claims, matching indexes); no injection found.
- **Nothing in this scope does work in a deployed binary**: no route/CLI publishes a workflow definition or starts an instance (R15-17), the job handler list is empty (R15-18), and the signal bridge is imported by nothing (R15-12).
- The distributed-safety story is weaker than the comments claim: leases are not fencing tokens (R15-03), a claimed batch is renewed one item at a time (R15-02), app clocks decide expiry (R15-10) → double execution; a started activity whose worker dies is stuck forever (R15-01); a throwing handler is an uncounted zero-delay hot loop (R15-04).
- Event append and projection are not transactional and unguarded by sequence (R15-05/06), yet workers claim from the projection.
- The subsystem only functions as an RLS-bypassing role; no store sets tenant context (R15-07). Tenant fences are hand-written predicates, mostly present; `run_id` is not tenant-unique (R15-08).
- Signal bridge, if wired as written, verifies HMAC over a re-serialised body, accepts a header-supplied tenant with a wildcard secret, and has a replay window (R15-13..15).
- Tests assert SQL text against a fake; zero concurrency or real-database coverage of the properties above.

## Findings

### R15-01 [High] [CONFIRMED] [Reliability / queue safety] An activity whose worker dies after `activity_started` is stuck forever; "crashed worker's activities are recovered" is only true before the first append
- Where: packages/workflow-runtime-pg/src/activity-claim.ts:79 (`WHERE status = 'scheduled'`), :56-58 (doc claim); packages/workflow-runtime/src/engine.ts:1823-1832 (one hop out of scope, read)
- Evidence: the claim set is `status = 'scheduled'` only. `executeScheduledActivity` appends `activity_started` *before* the handler runs, the projection flips the row to `running`, and on any later call it returns `{executed:false}` because `started = true` (`if (scheduled === null || started) return { executed: false }`). `activity_timed_out` is only ever emitted as a handler *result* (engine.ts:1768); nothing in scope or in `apps/operate-server` reads `timeout_at` / `next_retry_at` (grep: zero non-test readers). So a process crash, OOM, deploy kill past `drainTimeoutMs`, or a lost DB connection between `activity_started` and `activity_completed|failed` leaves the activity `running` permanently, outside every claim predicate, and its instance waiting forever.
- Impact: workflow instances hang silently with no detector and no recovery path (the replayer only compares projection to log; the log itself says "started"). At-most-once for the handler, not at-least-once as the docs say. Live only with `--workflow-workers --workflow-defer-activities`.
- Fix: a timeout sweeper over `(status='running', timeout_at < now())` that appends `activity_timed_out` (+retry per policy), or make the claim cover `running` rows whose lease lapsed and let the engine re-enter a started-but-unsettled attempt.
- Effort: M

### R15-02 [High] [CONFIRMED] [Concurrency] Leases are per batch but renewed per item: queued items lose their lease while an earlier item runs → double execution across replicas
- Where: packages/workflow-worker/src/job-batch.ts:68,81-96; batch.ts:61,74-88; activity-batch.ts:57,70-87; packages/workflow-runtime-pg/src/job-worker.ts:153-160 (renewal wraps only the executing item); apps/operate-server/src/workflow-workers.ts:96,101 (defaults batch 20 / lease 30 s)
- Evidence: `const jobs = await claimer.claim(opts)` leases up to 20 rows for `leaseMs`; the loop is sequential (`for (const job of jobs) { … await processor.process(job) }`) and `renewWhile(execute, { timerId: job.jobId … })` heartbeats only the row currently executing. Items 2..N are never renewed. If item 1 takes > 30 s, every other row's `claim_expires_at` lapses, another replica's `claimDueJobs` (`claim_expires_at < $1`) takes them, and worker A still executes them when it reaches them: `executeJobRun` reads `WHERE run_id=$1 AND tenant_id=$2 AND status='pending'` (job-engine.ts:243-245) and never checks `claimed_by`.
- Impact: the same job handler runs concurrently on two replicas (side effects twice — the "finalize is a no-op" guard only dedups the *status write*, job-engine.ts:315). Same shape for timers/activities, where the event-log unique key limits log damage but not handler side effects. Any handler slower than leaseMs/…/batch position triggers it.
- Fix: renew the whole claimed batch (one `UPDATE … WHERE claimed_by=$w AND id = ANY($ids)`), or claim 1-at-a-time / re-verify ownership (`claimed_by = $worker AND claim_expires_at > now()`) in the engine's read before invoking the handler.
- Effort: S-M

### R15-03 [High] [CONFIRMED] [Concurrency] No fencing: a worker that lost its lease still finalizes the run, and the lease-lost callback aborts nothing
- Where: packages/workflow-runtime-pg/src/job-engine.ts:311-317, 330-336, 453-458 (all finalizers guard on `status = 'pending'` only); packages/workflow-worker/src/renew.ts:41-44 ("does **not** abort `task`"); job-worker.ts:102 `onLeaseLost?: () => void`
- Evidence: every terminal `UPDATE` is `WHERE run_id = $1 AND tenant_id = $2::uuid AND status = 'pending'` — no `claimed_by = $worker`. `renewWhile` on a failed renewal (including a *thrown* renew, `catch { ok = false }`) just stops heartbeating and calls a logging callback. So after a lease is lost, A keeps running; B claims and starts the same run; whichever finishes first writes the outcome, and the *retry* path (`attempts = attempts + 1, started_at = …, claimed_by = NULL`) from stale worker A clears worker B's live claim, letting a third worker start it again.
- Impact: unbounded duplicate executions under slow handlers / DB hiccups; the engine's doc "mutual exclusion is the worker's lease" (job-engine.ts:202) is not enforced by any statement. Handlers must be fully idempotent, and no handler contract/type states that (the `JobHandlerContext` carries no idempotency token other than `runId`).
- Fix: carry `workerId` into `executeJobRun` and add `AND claimed_by = $worker` to the read and to every finalizing UPDATE; trip the handler's `AbortSignal` on lease loss.
- Effort: S

### R15-04 [High] [CONFIRMED] [Reliability] Poison pill: a job handler that throws is never counted, never dead-lettered, and is re-claimed in a zero-delay hot loop
- Where: packages/workflow-runtime-pg/src/job-engine.ts:289-294 (`if (!signal.aborted) throw err;`); packages/workflow-worker/src/job-batch.ts:92-95 (release on throw); job-worker.ts:125 (`sleep(result.claimed > 0 ? this.activePollMs : this.idlePollMs)`, activePollMs default 0, :78)
- Evidence: an unaborted throw "keeps its old meaning — transient infra trouble, so the run stays `pending` for re-claim without consuming a business attempt". `processJobBatch` then `release(job)` (claim cleared, `started_at` unchanged) and the worker loop sleeps `activePollMs = 0` because `claimed > 0`. The same run is at the head of `ORDER BY started_at ASC` on the next poll. Nothing increments `attempts`, nothing records the error on the row (only `failed[]` in the in-memory batch result), nothing caps it.
- Impact: one handler with a deterministic bug (TypeError on a payload shape) produces an infinite claim→throw→release loop at DB round-trip speed per replica, forever, with the run permanently `pending`; ≥ `batchLimit` such runs at the head starve every other run of that worker's `serves` set. Same structure for timers (batch.ts:84-87) and activities (activity-batch.ts:80-85).
- Fix: on throw, bump a `throw_count`/attempts and apply the declared backoff (`started_at = now + delay`), dead-letter past the ceiling; never use `activePollMs` after a batch with zero successes.
- Effort: S-M

### R15-05 [High] [CONFIRMED] [Consistency] Event append + projection writes are not transactional; log and projections (the claim tables) can diverge, and an orphan instance row can exist with no events
- Where: packages/workflow-runtime-pg/src/projecting-event-log.ts:44-66, 86-125; event-log.ts:92-123; instance-store.ts:115-160
- Evidence: `append` = `instanceStore.create(...)` → `inner.append(event)` → `persistProjections(event)`, each a bare `conn.query` (no `conn.transaction` anywhere in the three files; `grep -n transaction` over the package's non-test source finds it only at definition-store.ts:743,763). `persistProjections` itself is 1 + A + S + T sequential statements. A failure after `inner.append` (e.g. `SignalIdempotencyConflict`, a provenance refusal which "aborts the append" — comment at :104-106 — *after the event has already been inserted*, a dropped connection) leaves the event committed and the timer/activity/signal/instance rows stale. Since workers claim from `workflow_timers`/`workflow_activities`, a `timer_scheduled` whose projection write failed is never fired until some later append re-projects. Conversely a failed `inner.append` of `instance_started` leaves a `workflow_instances` row with zero events.
- Impact: silently stalled timers/activities; "refuse rather than persist" is actually "persist the event, then throw". A provenance refusal is also *sticky*: one unresolvable timer/signal/activity in an instance's log (e.g. `cron_next_fire_unresolved`, `definition_unavailable` for a definition published after boot — the map is loaded once) makes every later append on that instance commit its event and then throw, so the projection never advances again. The only repair tool (`WorkflowReplayer.resyncInstance`, itself 1+3N non-transactional statements, replayer.ts:460-478) has no caller in any app.
- Fix: run create + append + projections in one `conn.transaction`.
- Effort: M

### R15-06 [Medium] [LIKELY] [Concurrency] Projection writes have no sequence guard, so a stale writer overwrites a newer projection (lost update across replicas / worker vs API)
- Where: packages/workflow-runtime-pg/src/instance-store.ts:177-202 (`WHERE instance_id = $25` only; `sequence_cursor = $17` is assigned, not compared); timer-store.ts:119-146, activity-store.ts:65-73 (unconditional `DO UPDATE SET status = EXCLUDED.status …`)
- Evidence: each appender re-reads the whole log then rewrites every projection row. Appender A (seq N+1) reads the log before B's N+2 commits, B writes its projections, then A's older fold lands last. No statement has `AND sequence_cursor <= EXCLUDED/…`. A timer B fired can be written back to `scheduled` by A; the claim query then hands it out every poll and the engine no-ops on it (log says fired) until another event lands.
- Impact: projection regressions under multi-replica or worker+cancel-route concurrency; produces the claim/no-op loop the supervisor's `onNoProgress` throttle exists to report. One hop unverified: exact interleaving needs two processes appending to one instance within the same few ms.
- Fix: `WHERE sequence_cursor <= $17` on the instance UPDATE and a per-row cursor on child upserts; or R15-05's transaction plus `SELECT … FOR UPDATE` on the instance row.
- Effort: M

### R15-07 [Medium] [CONFIRMED] [Tenant isolation / deployability] The whole package only works as the table owner (RLS-bypassing); no store sets tenant context, and as a non-owner writes fail or silently no-op
- Where: packages/workflow-runtime-pg/src/event-log.ts:94, instance-store.ts:118,176, timer-store.ts:147, activity-store.ts:54, signal-store.ts:105, job-engine.ts:242/311/330/386/453, job-enqueue.ts:98/180, job-cancellation.ts (all bare `conn.query`); job-claim.ts:152-160 states it
- Evidence: `grep -n "withTenantContext\|set_config\|current_tenant" packages/workflow-runtime-pg/src/*.ts` (non-test) finds only definition-store.ts:33 (plus a message string in job-claim.ts:257). Every table here carries a single `ALL` tenant-isolation policy (meta-schema.ts job_runs :96-97, workflow_* likewise). So: (a) the deployment must connect as owner/BYPASSRLS, which means RLS provides **zero** isolation for this subsystem — the hand-written `tenant_id = $2` predicates are the only fence; (b) as a non-owner, `claimDue*` returns 0 rows, `upsertProjection` updates 0 rows and returns `false` which `persistProjections` discards (projecting-event-log.ts:100), and INSERTs raise 42501. Only the job queue has a boot probe (`probeJobQueueVisibility`); timers/activities/events have none.
- Impact: least-privilege DB roles are impossible for the serving process if workflows are used; a single SQL mistake in this package is a cross-tenant write with no second belt.
- Fix: per-row `withTenantContext(tenant_id)` for writes (the tenant is on every row), a dedicated BYPASSRLS/`app.platform_worker` policy arm for the claim only.
- Effort: M-L

### R15-08 [Medium] [CONFIRMED] [Tenant isolation] Several statements are keyed by a business id with no tenant predicate; job `run_id` is not globally unique
- Where: packages/workflow-runtime-pg/src/job-claim.ts:271-275, 298-301 (`WHERE run_id = $1 AND claimed_by = $2`); job-enqueue.ts:34-40 + packages/jobs/src/enqueue.ts:61-63 (`return \`${event.name}::${discriminator}::${jobId}\`` — no tenant in the key); meta-schema.ts job_runs unique = `(tenant_id, run_id)`; id-mapping.ts:25 (`WHERE instance_id = $1 LIMIT 1`); event-log.ts:141; instance-store.ts:202
- Evidence: `deterministicRunId(plan.runKey)` hashes a key without the tenant, so two tenants emitting the same event name + idempotency key (the entity-event key is `<entity>:<op>:<recordId>:<updated_at>`; record ids are per-tenant but an API/user-invoked `idempotencyKey` is caller-chosen) get the **same `run_id`**, legal under `(tenant_id, run_id)`. `releaseJobClaim`/`renewJobClaim` then match both rows when one worker holds both. Workflow ids (`instance_id`, `timer_id`, `activity_id`) are globally UNIQUE in the catalog, so those are safe by constraint, not by predicate.
- Impact: low today (worker must hold both rows); but `run_id` is treated as a global handle by `ClaimedJob.jobId` consumers. Also no index leads with `run_id`, so each renew/release (every `leaseMs/3` per running job) is a scan of `job_runs` (indexes are `(tenant_id, run_id)`, `(status, started_at)` …).
- Fix: include tenant in `runKey`; add `tenant_id` to release/renew predicates (the claimed row carries it).
- Effort: S

### R15-09 [Medium] [CONFIRMED] [Correctness] Scheduled-job producer fires every cron job's most recent past tick on first sight of a tenant, however old, and drops all other missed ticks
- Where: packages/workflow-runtime-pg/src/job-enqueue.ts:171-190; packages/jobs/src/cron.ts:448 (`cronPrevOnOrBefore(job.trigger.cron, now, …)`); apps/operate-server/src/scheduler.ts:112 (`if (this.opts.runOnStart !== false) void this.tick();`)
- Evidence: `due` is "the latest tick ≤ now" with no lower bound (tenant creation, scheduler start, last enqueued). First pass for a new tenant inserts a run for e.g. a yearly `0 0 1 1 *` close job with `started_at = <last 1 Jan>` → immediately claimable. After downtime spanning k ticks, only the last is enqueued (k−1 silently skipped) — neither behaviour is documented as a policy.
- Impact: month-end/year-end style jobs run at tenant provisioning; catch-up semantics are accidental. Latent while `JOB_HANDLER_PROVIDERS = []` (apps/operate-server/src/node.ts:3374), but the rows accumulate `pending` regardless.
- Fix: bound by `max(tenant.created_at, scheduler epoch)` and declare a misfire policy.
- Effort: S

### R15-10 [Medium] [CONFIRMED] [Clock] Due-ness and lease expiry use each replica's application clock, not the database clock
- Where: packages/workflow-runtime-pg/src/timer-claim.ts:77,84-85; activity-claim.ts:73,80-81; job-claim.ts:100,124-126; job-worker.ts:88-92
- Evidence: `const claimExpiresAt = new Date(new Date(options.now).getTime() + leaseMs).toISOString()` and `claim_expires_at < $1::timestamptz` with `$1 = options.now` from `() => new Date()` in each process. A replica whose clock runs ≥ leaseMs ahead sees every other replica's live lease as expired and steals it (→ R15-02/03 duplicates); one running behind writes leases that are already expired for peers.
- Impact: correctness of mutual exclusion depends on NTP across the fleet; default lease 30 s, min configurable 1 s.
- Fix: use `now()` / `now() + $lease * interval '1 ms'` in SQL.
- Effort: S

### R15-11 [Medium] [CONFIRMED] [Performance] Every event append re-reads the full instance log and rewrites every child projection row: O(n) reads + O(rows) writes per append, O(n²) per instance
- Where: packages/workflow-runtime-pg/src/projecting-event-log.ts:87 (`await this.inner.listByInstance(event.instanceId)`), :111-124 (`upsertMany` of all activities, signals, timers), event-log.ts:125-129 (`appendBatch` is a loop of single INSERTs, each preceded by a resolver lookup)
- Evidence: as quoted; plus the engine's own `listByInstance` calls per operation. A recurring `cron_schedule` timer makes an instance's log unbounded, so the per-fire cost grows without limit. Also `createdInstances: Set<string>` (:33, :61) is written and never read, and `WorkflowInstanceIdResolver.cache` (id-mapping.ts:7) is never evicted — both grow for the life of the process.
- Impact: throughput cliff and unbounded memory on long-lived instances / long-running servers.
- Fix: incremental projection (apply only the new event), bounded LRU for the resolver, delete `createdInstances`.
- Effort: M

### R15-13 [High if wired] [CONFIRMED] [Security / correctness] Bridge verifies the HMAC over a re-serialised body, not the raw request bytes
- Where: packages/workflow-signal-bridge/src/gateway-handler.ts:84-90
- Evidence: `const parsed = input.parsedBody; if (parsed !== null) { return JSON.stringify(parsed); } return "";` is what is handed to `verifyWebhookDelivery` as `body`. Any sender whose JSON differs byte-wise from V8's `JSON.stringify` (whitespace, key order after duplicate keys, `1.0` vs `1`, `é` vs `é`, trailing newline) fails verification — i.e. essentially every third-party producer. It also means the signed bytes and the processed object are not the same artefact (duplicate-key / `__proto__`-key payloads parse to something the signer did not sign in the same form). The package's own tests sign `JSON.stringify(obj)` and so cannot see it.
- Impact: integration cannot work with real webhooks; canonicalisation-mismatch class of signature bypass is not excluded by construction.
- Fix: plumb the raw body bytes through `HandlerInput` (the bounce webhook does this "in front of the gateway") and verify those.
- Effort: S-M

### R15-14 [Medium if wired] [CONFIRMED] [Security] Replay inside the tolerance window: the idempotency key is an unsigned header, default tolerance 300 s
- Where: packages/workflow-signal-bridge/src/gateway-handler.ts:48-54 (`pickHeader(input.request.headers, idempotencyHeader)`), secret-resolver.ts:29 (`defaultToleranceSeconds ?? 300`), bridge.ts:121
- Evidence: the signature covers timestamp+body only; `Idempotency-Key` comes from a header outside the MAC and is optional. A captured delivery can be replayed for 5 minutes with a fresh/absent key and is submitted as a new signal (dedup only applies to `exactly_once_idempotent` with a key).
- Impact: duplicate workflow transitions from a replayed webhook.
- Fix: derive the dedup key from the signed material (timestamp + body hash / signature) and persist seen signatures for the tolerance window.
- Effort: S

### R15-15 [Medium if wired] [CONFIRMED] [Tenant isolation] Tenant for an inbound webhook falls back to an attacker-supplied hint; a wildcard secret entry makes one secret valid for every tenant
- Where: packages/workflow-signal-bridge/src/gateway-handler.ts:25 (`input.principal?.tenantId ?? input.request.tenantHint ?? null`), secret-resolver.ts:34-35 (`if (entry.tenantId !== null && entry.tenantId !== input.tenantId) continue;` — `null` matches any tenant)
- Evidence: with no authenticated principal the tenant is the request's tenant header. `StaticSecretResolver` (the only resolver that exists) treats `tenantId: null` as a wildcard, so a holder of that one shared secret can submit signals into any tenant by changing the header. First-match-wins ordering also lets a wildcard entry shadow a tenant-specific one.
- Impact: cross-tenant signal injection by any party holding a shared integration secret.
- Fix: no wildcard tenant; bind the secret → tenant mapping from the secret/route, never from a header.
- Effort: S

### R15-16 [Low] [CONFIRMED] [Info disclosure / hardening] Bridge responses distinguish unknown-tenant from bad-signature and echo engine exception text; field-path extractor walks inherited properties
- Where: packages/workflow-signal-bridge/src/bridge.ts:62-65, 153-156; gateway-handler.ts:61-64; correlation.ts:21, 58
- Evidence: `secret_not_found` (`no webhook secret for tenant=… source=…`) vs `signature_invalid` are separate bodies on the same 401 → tenant/source enumeration oracle; `reason: err instanceof Error ? err.message : …` returns raw engine/DB error text to an unauthenticated-by-principal caller in a 503. `(current as Record<string, unknown>)[segment]` has no `hasOwnProperty` guard: a configured path `constructor.name` yields `"Object"` for every body. HMAC compare itself is delegated to `@crossengin/sdk` `verifyWebhookDelivery` (out of scope; not verified here for timing safety).
- Fix: single opaque 401; generic 503; own-property check.
- Effort: S

### R15-20 [Low] [CONFIRMED] [Correctness] Lease renewal predicates are tied to the pre-execution status, so renewal reports "lease lost" for healthy work
- Where: packages/workflow-runtime-pg/src/activity-claim.ts:142-144 (`AND status = 'scheduled'`), timer-claim.ts:153-155
- Evidence: the engine appends `activity_started` first, the projection flips the row to `running`, and the next heartbeat (`leaseMs/3`) matches 0 rows → `renew` returns `false` → `onLeaseLost` fires and heartbeating stops (renew.ts:41-44) for every activity that outlives one interval. Same for a timer once `timer_fired` is projected while the step loop continues.
- Impact: false "lease lost" telemetry on the only signal operators have for R15-02/03; activity renewal is effectively a no-op.
- Fix: renew on `claimed_by` alone, or keep leases meaningful for `running` rows (ties into R15-01).
- Effort: S

### R15-21 [Low] [CONFIRMED] [Reliability] Terminal status and dead-letter row are two autocommit statements; a crash between them loses the dead letter permanently
- Where: packages/workflow-runtime-pg/src/job-engine.ts:453-473 (UPDATE status, then `recordDeadLetter`), :402-405 (`catch … return "failed"`)
- Evidence: the status UPDATE commits, then the INSERT runs separately; on failure only an optional callback is invoked. A re-finalize cannot repair it because the guard (`status = 'pending'`) now matches nothing (:463).
- Impact: failed runs with no dead-letter record; nothing reconciles `job_runs.status IN ('failed','dead-lettered')` against `dead_letter_jobs`.
- Fix: one transaction (or one CTE statement).
- Effort: S

### R15-22 [Low] [CONFIRMED] [Shutdown] `stop()` waits for the in-flight handler with no abort; lease release on shutdown is best-effort and silent
- Where: packages/workflow-worker/src/job-worker.ts:135-141, worker.ts:126-132, activity-worker.ts:129-135; job-batch.ts:73-79 (`catch { /* The lease will lapse */ }`)
- Evidence: `stop()` sets flags and `await loop`; the running handler receives no `AbortSignal` on shutdown (the signal is only tripped by a recorded cancellation, abort.ts). The app-level supervisor bounds the wait with `drainTimeoutMs` (default 15 s) and then abandons the item to its lease — which, combined with R15-01, strands a started activity. Release errors and probe errors are swallowed with no hook (batch.ts:69, activity-batch.ts:65, job-batch.ts:76, abort.ts:37, renew.ts:38).
- Fix: thread a shutdown signal into handlers; surface swallowed errors through `onError`.
- Effort: S

## Verified strengths (things that are genuinely done well, with file:line)
- Claim SQL is the correct single-statement `WITH due AS (SELECT … FOR UPDATE SKIP LOCKED) UPDATE … FROM due RETURNING` shape for all three queues (timer-claim.ts:80-95, activity-claim.ts:76-91, job-claim.ts:120-135); the served-job predicate is correctly placed inside the CTE before `LIMIT` (job-claim.ts:102-117) and an empty declaration claims nothing (`= ANY('{}')`).
- Claim queries have matching composite indexes: `idx_job_runs_due (status, started_at)`, `idx_workflow_timers_due (status, fire_at)`, `idx_workflow_activities_due (status, scheduled_at)` (packages/kernel/src/bootstrap/meta-schema.ts ~775, ~7541, ~7773). (Not partial, so they include terminal rows.)
- No SQL injection found: every value is a bound parameter; the only interpolated identifiers are a schema name validated by `/^[a-z_][a-z0-9_]*$/` in every entry point (e.g. job-claim.ts:95, job-cancellation.ts:13-17, definition-store.ts:390-393) and enum constants (`quoted(statuses)`, definition-store.ts:297-301).
- Enqueue idempotency is real: deterministic v5 run id + `ON CONFLICT (tenant_id, run_id) DO NOTHING` (job-enqueue.ts:34-40, 104, 186) makes multi-replica schedulers and re-delivered events safe against duplicate *rows*.
- Job cancellation is carefully raced: premise re-asserted inside the UPDATE predicate, `COALESCE` stamping, fail-closed `cancel_requested_at IS NOT NULL` guard on finalize, reaper with SKIP LOCKED (job-cancellation.ts:131-141, 148-155, 247-253, 287-303). Every statement there carries `tenant_id = $2::uuid`.
- `executeJobRun` reads/finalizes by `(run_id, tenant_id)` (job-engine.ts:243-245 etc.), so a run is never finalized across tenants even though RLS is bypassed.
- Workflow business ids are globally UNIQUE in the catalog (`workflow_instances_instance_id_key`, `workflow_timers_timer_id_key`, `workflow_activities_activity_id_key`, `workflow_events_instance_sequence_key`), which is what actually prevents duplicate events when two workers race.
- Definition store: writes in a transaction with tenant context or an explicit platform grant, strict scope predicate on UPDATE, four-eyes predicate in SQL, zod re-parse on read (definition-store.ts:662-728, 735-768, 240-265).
- `probeJobQueueVisibility` asks the catalog rather than inferring from a zero count (job-claim.ts:193-261).
- Timer upsert only releases a claim when `fire_count` advances, and the replayer path preserves claims (timer-store.ts:111-146).
