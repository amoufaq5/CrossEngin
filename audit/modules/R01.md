# R01 — packages/operate-runtime (ERP serving engine)

## Summary (10 lines max)
- The serving engine is a competent generic CRUD/RBAC layer with an *accounting veneer*: 9 write effects post two/three-line journal entries on state edges. It is not a ledger an accountant would sign off.
- Double entry is enforced in **application code only**, at exactly one moment (JournalEntry draft→posted through update/transition). It is bypassed by creating an entry already `posted`, by moving a line out of a posted entry, and by editing a `reversed` entry. There is no DB constraint.
- Lifecycle state is an ordinary writable field: `PATCH {state: …}` skips `fromStates` and the per-transition RBAC grant and still fires the GL effects. Bill, Payment, FiscalPeriod, WhtCertificate have **no immutability guard at all**.
- All money arithmetic in effects/guards/reports is IEEE-754 `number` with nine hardcoded `Math.round(x*100)/100`; per-currency minor units, `finance.rounding`, `pricesIncludeTax` are declared and read by nothing.
- Multi-currency postings hardcode `fx_rate: 1` and `functional = transaction` amount; period-close FX revaluation is never reversed and re-posts the cumulative delta each close.
- Credit note GL reversal ignores tax (debits revenue for the gross); credit notes then appear as *positive* open receivables in AR aging.
- No row lock / state re-check in transitions: concurrent or retried transitions double-post; concurrent payments lose the auto-settle.
- Inventory, COGS, stock valuation, SO→Invoice, PO→GR→Bill matching: **absent** (zero code).
- Sequences are race-safe and unique but **not gapless** (allocated outside the write transaction, before validation).
- Tests are numerous and real for the happy paths; none exercises concurrency, the PATCH-state bypass, or create-as-posted.

## Findings

### R01-01 [Critical] [CONFIRMED] [Accounting integrity / AuthZ] Lifecycle state is mass-assignable: `PATCH {state}` bypasses `fromStates`, the per-transition RBAC grant, and re-fires GL postings
- Where: `packages/operate-runtime/src/handlers.ts:467-555` (update arm), `packages/operate-runtime/src/validation.ts:280-300`, `packages/operate-runtime/src/write-guards.ts:238-240`, `packages/operate-runtime/src/compile.ts:271-336`
- Evidence: the update arm takes the caller body verbatim — `const patch = { ...raw, updated_at: nowIso(ctx) }` (handlers.ts:494) → `store.update(tenantId, spec.entity, id, patch)` (:542). `validateBody` only checks type/enum/required per declared field (`state` is an enum, so any legal state name passes); there is no "server-owned field" concept except `serverManaged: f.default?.kind === "sequence"` (validation.ts:73), which merely *skips validation*. The transition handler's `fromStates` check (handlers.ts:657-664) and `authOperation: { kind: "transition", name }` (operations.ts:76) are only on the `POST /{id}/{transition}` route. `lockedDocumentGuard` returns null whenever the *before* state is not locked (`if (typeof beforeState !== "string" || !lockedStates.has(beforeState)) return null;` write-guards.ts:240). Every effect fires on `update` as well as `transition` (`if (input.operation !== "update" && input.operation !== "transition") return;` e.g. write-effects.ts:929).
- Concrete consequences with the shipped `erp-core` grants (`packages/pack-erp-core/src/permissions.ts:25-37,185-233`):
  - Any `WRITE_ROLES` member PATCHes a draft Invoice to `state:"void"`/`"paid"` although `void` is `ADMIN_ONLY`; a draft→`paid` invoice never posts AR recognition and is then locked.
  - Bill has **no guard**: an `AP_WRITERS` member PATCHes `state:"approved"` (approve is restricted to admin/ap_clerk/controller) → GL posted; PATCH back to `draft`, change `total`, PATCH `approved` again → second `-GL` entry. Same loop on Payment (`completed`→`draft`→`completed`) posts `-SETTLE` repeatedly; `refund` (restricted) is reachable by PATCH.
  - `FiscalPeriod.status` (no workflow, no guard): PATCH `closed`→`open`→`closed` re-opens a closed period and posts another `-FXREVAL` each time.
- Impact: segregation of duties and document lifecycle are advisory; GL can be double-posted or left unposted at will by any role holding plain `update`. This is the single most damaging finding for an ERP.
- Fix: treat a workflow `stateField` (and `posted_at`, `paid_at`, `sent_at`, `booking_rate`, `withholding_total`, `created_at`, sequence fields) as server-owned: reject in the update/create mask unless the write is the transition path; add a generic "state may only change via transition" guard derived from `manifest.workflows`.
- Effort: M

### R01-02 [High] [CONFIRMED] [Double entry] Balance is enforced only in application code on one edge; a journal entry can be created already `posted` with the balance/empty check skipped; no DB constraint
- Where: `packages/operate-runtime/src/write-guards.ts:92-113`; `packages/operate-runtime/src/handlers.ts:430-454`
- Evidence: `becomingPosted = after.state === posted && before?.state !== posted` is true for `POST /v1/journal-entries {"state":"posted", …}` (nothing forbids a non-initial state on create — R01-01). The guard then does `const entryId = input.id ?? (typeof input.after["id"] === "string" ? … : null); if (entryId === null) return null;` (write-guards.ts:112-113). On create `input.id` is `null` (handlers.ts:448) and a normal body has no `id`, so the guard **returns allow before the "at least one line" and balance checks**. Result: a `posted` entry with zero lines (the state the guard's own `empty_journal_entry` error exists to prevent), created without the `post` transition grant. Where a balance sum does run it is the only enforcement anywhere: there is no CHECK/trigger/deferred constraint (`grep -n CHECK packages/operate-runtime-pg/src/entity-ddl.ts` → none; the JSONB store cannot have one), the tolerance is `0.005` absolute (write-guards.ts:73,131) on doubles, and the guard never runs again after posting — so R01-03/R01-04 unbalance a posted entry with nothing to notice.
- Impact: "posted" does not imply "has lines" or "balanced"; trial-balance integrity is not guaranteed by construction and nothing re-verifies it.
- Fix: forbid any state other than the workflow's `initialState` on create; add a DB-level deferred constraint trigger (column store) plus a periodic ledger-integrity job.
- Effort: M

### R01-03 [Critical] [CONFIRMED] [Double entry / Immutability] A line can be moved out of (or re-pointed away from) a posted entry by PATCHing its parent reference
- Where: `packages/operate-runtime/src/write-guards.ts:227-236`
- Evidence: `const ref = input.after[config.childParentField] ?? input.before?.[config.childParentField];` — on an update `after` is `{...before, ...patch}` (handlers.ts:538), so a `PATCH /v1/journal-lines/{id} {"journal_entry_id": "<some draft entry>"}` makes `ref` the *new* (draft) parent; the old, posted parent is never consulted → `return null`. The line leaves the posted entry, which is now unbalanced. Identical for `InvoiceLine`, `SalesOrderLine`, `PurchaseOrderLine` (same generic guard).
- Impact: posted journal entries and issued invoices are not immutable; a GL writer can unbalance any posted entry with one PATCH.
- Fix: check both `before` and `after` parents; refuse a parent change when either is locked.
- Effort: S

### R01-04 [High] [CONFIRMED] [Immutability] `reversed` journal entries (and their lines) are fully editable and deletable; reversal can be repeated
- Where: `packages/operate-runtime/src/write-guards.ts:165-180` (`lockedStates: [c.postedState]`), `write-effects.ts:98-171`
- Evidence: only `posted` is locked. Once reversed, entry and lines pass `lockedDocumentGuard` (`!lockedStates.has(beforeState)` → null). So the original's amounts can be rewritten or the entry deleted (ADMIN_ONLY delete; lines `GL_WRITERS`) while its `-REV` mirror stays posted → net non-zero. Also PATCH `reversed`→`posted` (re-runs balance check, passes) then `reverse` again creates a second `-REV` entry.
- Impact: audit trail of reversals is destructible; double reversal.
- Fix: lock `reversed` too; state changes only via transitions (R01-01).
- Effort: S

### R01-05 [High] [CONFIRMED] [Concurrency] Transitions read without a lock and never re-check state: concurrent/retried requests double-post the GL; concurrent payments lose the auto-settle
- Where: `packages/operate-runtime/src/handlers.ts:646-689`; store: `packages/operate-runtime-pg/src/entity-ops.ts:126-138` (`getOp` — plain SELECT), `:164-166` (`FOR UPDATE` only inside `updateOp`), `packages/operate-runtime-pg/src/column-store.ts:446-458,529-533`; isolation: `packages/kernel-pg/src/node-pg.ts:106` (`BEGIN`, i.e. READ COMMITTED)
- Evidence: `const record = await store.get(...)` → `fromStates.includes(current)` → `store.update(…, {state: toState})`. The UPDATE has no `AND state = <from>` predicate and the earlier read takes no row lock. Two concurrent `POST /invoices/{id}/send` both observe `draft`, both write `sent`, both run `recognitionGlPostingEffect` → two `<INV>-AR` entries. On `--store pg` (JSONB, the shipped compose default) nothing stops it; on `pg-columns` the unique index on `entry_number` turns the second into a 500. Same for `payments/{id}/complete` (two `-SETTLE` entries = cash debited twice). Routes are registered `idempotencyRequired: false` (operations.ts:110).
  `paymentApplicationEffect` (write-effects.ts:1251-1270) sums *committed* completed payments; two payments completing concurrently each miss the other → neither marks the invoice paid, and nothing ever re-evaluates.
- Impact: duplicated revenue/cash postings under ordinary double-click/retry; invoices stuck open.
- Fix: `SELECT … FOR UPDATE` on the transition read (or `UPDATE … WHERE state = ANY(from) RETURNING`); lock the document row in the application effect; require idempotency keys on transitions.
- Effort: M

### R01-06 [High] [CONFIRMED] [Money] All monetary arithmetic is binary floating point with hardcoded 2-decimal rounding; currency minor units and the tenant rounding setting are ignored
- Where: `packages/operate-runtime/src/write-effects.ts:63-66` (`num` → `Number(v)`), `:846,864,875,879,893,894,1034,1456,1486`; `write-guards.ts:77-80,125-131`; `aging.ts:97,105,106`; `wht-reconciliation.ts:33-35`; settings declared and unread: `settings.ts:54-58` (`multiCurrencyEnabled`, `pricesIncludeTax`, `rounding`)
- Evidence: `const tax = Math.round(net * (rate / 100) * 100) / 100;` (write-effects.ts:864). Verified with node: `13.40 × 7.5%` → `1` (exact 1.005, half-up = 1.01). Every one of the 9 rounding sites assumes exactly 2 minor units; `grep -rn "rounding\|pricesIncludeTax\|decimal_places"` over `packages/operate-runtime/src` and `apps/operate-server/src` finds only the zod declaration. The wire layer (`decimal.ts`) is exact BigInt — but effects parse the wire string back into a double (`Number(v)`), compute, and hand a double to the store, which re-quantises (`decimal-store.ts:78`). `NUMERIC(16,2)` allows 16 significant digits; a double holds 15 (`decimal.ts:32` says so itself).
- Impact: 1-cent tax errors on ordinary rates; wrong amounts for JPY (0 dp) and KWD/BHD/JOD (3 dp); tax-inclusive pricing unsupported despite a setting that claims it.
- Fix: do effect arithmetic on `ExactDecimal`/BigInt minor units with per-currency scale and the configured rounding mode.
- Effort: L

### R01-07 [High] [CONFIRMED] [Multi-currency] Auto-posted journal lines hardcode `fx_rate: 1` and set functional = transaction amount for foreign-currency documents
- Where: `packages/operate-runtime/src/write-effects.ts:453,573,682,1030,1169,1741`; `glLine` `:706-716`
- Evidence: `const base = { journal_entry_id: …, currency, fx_rate: 1, … }` and `functional_debit: debit, functional_credit: credit`. `bookingRateStampEffect` (:1572-1601) stamps `booking_rate` on the document *after* the recognition effect ran (order in compile.ts:383-429) and the rate is never applied to the lines. A EUR 100 invoice in a USD book posts functional 100.00.
- Impact: the functional-currency ledger is wrong for every foreign-currency document; the later revaluation "corrects" against a base that was never booked.
- Fix: resolve the rate first, post `functional = round(amount × rate)`, carry the rate on the lines.
- Effort: M

### R01-08 [High] [CONFIRMED] [Multi-currency] Unrealized FX revaluation is cumulative and never reversed; re-closing a period re-posts it
- Where: `packages/operate-runtime/src/write-effects.ts:1389-1525`
- Evidence: each `→closed` edge posts `delta = round(open × rate − Σ(open × bookingRate))` (:1485-1486) against the **original booking rate**, with no reversing entry at the next period open and no memory of prior revaluations. A document open across two closes has its unrealized gain posted twice (period 1 delta + period 2 full delta from booking). Nothing prevents `closed→open→closed` (R01-01), which posts a duplicate `<period>-FXREVAL`. Lines are tagged `currency: <foreign>` and `fx_rate: rate` while `debit/credit` hold a *functional-currency* delta (:1494-1504). Payments are subtracted regardless of payment date vs period end (:1420-1442); documents are those open *now*, not at `end_date`. Row caps of 5000 are silently truncating (`limit: c.maxRows`, nextCursor ignored).
- Impact: overstated unrealized FX; not IAS 21 compliant.
- Fix: post revaluation with an auto-reversal on the first day of the next period (or track last-revalued rate per document); compute open balances as of `end_date`.
- Effort: M

### R01-09 [High] [CONFIRMED] [Accounting] Credit-note GL reversal ignores tax and partial payments; the bill side has no reversal at all
- Where: `packages/operate-runtime/src/write-effects.ts:412-474`; absence: `compile.ts:433-471`
- Evidence: recognition credits revenue (subtotal) **and** tax payable (tax) (:1036-1064). The void reversal posts exactly two lines — `debit revenue = amount`, `credit AR = amount` where `amount = total` (:426-428, 455-472). Revenue is over-reversed by the tax amount and the output-tax liability is never reversed. Withholding is also ignored (AR was debited `total − wht`, credited back `total`). If the invoice had partial payments AR is over-credited. For bills: `Bill.void` from `approved` exists in the workflow (`pack-erp-core/src/workflows.ts:153-158`) and no effect is registered for it → AP and expense stay on the books. `Payment.refund` (`completed→refunded`) likewise has no effect; the invoice stays `paid`.
- Impact: misstated revenue, VAT payable, AP after any void/refund.
- Fix: reverse by mirroring the original recognition entry's lines (as `journalReversalEffect` does) instead of recomputing; add Bill-void and Payment-refund reversals.
- Effort: M

### R01-10 [High] [CONFIRMED] [Reports] Credit notes are counted as positive open receivables in AR aging and FX revaluation; withholding makes invoices un-settleable
- Where: `packages/operate-runtime/src/write-effects.ts:282-285` (credit note created as an `Invoice` in `state: sent`, positive `total`), `aging-handler.ts:97-110`, `compile.ts:860-866`, `write-effects.ts:1443-1463`; `write-effects.ts:1248-1263`
- Evidence: the aging section is `{ entity: "Invoice", openStates: ["sent","overdue"] }` with no `document_type` filter; `computeAging` does `open = total − applied` (aging.ts:97). The voided original drops out (state `void`) and its credit note enters as `+total`. `paymentApplicationEffect` compares `applied + 0.005 < total` against the gross total: an invoice with withholding (customer pays `total − wht`, AR control debited `total − wht` at :1034) is never auto-settled and shows the WHT as an open receivable forever. `Invoice.mark_paid` is a plain user transition with no cash posting (no effect keyed on Invoice→paid in `defaultWriteEffects`), so AR is never cleared in the GL for invoices settled that way.
- Impact: AR subledger ≠ AR control account; aging overstated.
- Fix: sign credit notes negative / exclude and net them; settle against `total − withholding_total`; post or forbid `mark_paid`.
- Effort: M

### R01-11 [High] [CONFIRMED] [Period control] Period lock is checked only on a manual JE posting that carries `fiscal_period_id`; system postings and dates are unchecked
- Where: `packages/operate-runtime/src/write-guards.ts:97-109`; `write-effects.ts:442-451,1020-1029,1159-1168` (no `fiscal_period_id`, `entry_date: today`), `:126-129` (reversal carries the original's possibly-closed period)
- Evidence: `if (typeof periodId === "string" && periodId.length > 0) { … }` — an entry with no period skips the lock; nothing checks that `entry_date` lies inside the period's `start_date..end_date`, nor resolves a period from the date. Auto-postings are written "directly through the store, so they bypass the handler's guards" (comment :95) and never set a period (except FXREVAL, which posts *into the period being closed*). A reversal of an entry in a closed period creates a new posted entry stamped with that closed `fiscal_period_id` dated today. Recognition entries are dated the server's UTC "today", not the document's `issue_date`/`bill_date`.
- Impact: closed periods keep changing; cut-off is not enforceable.
- Fix: derive the period from `entry_date`, enforce the lock for every posting (including effects), date postings from the document.
- Effort: M

### R01-12 [High] [CONFIRMED] [Missing capability] No inventory, COGS, stock valuation, or document-chain automation exists
- Where: whole package — `grep -rnE "StockLevel|StockMovement|GoodsReceipt|Shipment|cogs|fifo" packages/operate-runtime/src` (non-test) returns nothing; `SalesOrder`/`PurchaseOrder` appear only in `compile.ts:308-334` as locked-document guards.
- Evidence / data-flow trace:
  - (a) **SalesOrder → Invoice → Payment → Ledger**: SO `confirm/fulfill/invoice/close` are bare state flips (`pack-erp-core/src/workflows-ext.ts:93-97`) — no Invoice is created; `Invoice` has **no `sales_order_id` field** (`pack-erp-core/src/entities.ts:79-123`). Invoice is keyed manually with client-typed `subtotal/tax_total/total` (never recomputed from lines; only used if they reconcile, write-effects.ts:941,1000). *Automated*: Invoice `send` → AR/revenue/tax entry; Payment `complete` → cash/AR entry + auto `paid` when Σ payments ≥ total. *Manual*: creating the invoice, the payment, linking `invoice_id`. *Missing*: SO→Invoice, shipment→stock, revenue/COGS matching, over-payment handling (excess is silently absorbed; payment amount > open is not rejected), payment allocation across multiple invoices.
  - (b) **PurchaseOrder → GoodsReceipt → Bill → Payment**: PO `receive` is a state flip; `GoodsReceipt` has no effect or guard; Bill has an optional `purchase_order_id` (`entities-finance.ts:173`) read by nothing — no 2-/3-way match, no GRNI accrual. *Automated*: Bill `approve` → expense/AP(+input tax) entry (all lines to ONE expense account regardless of bill-line account/item); outbound Payment `complete` → AP/cash + auto `paid`. Everything else manual/missing.
  - (c) **Inventory → COGS**: nothing. No stock decrement, no negative-stock guard, no FIFO/weighted-average, no COGS posting, no inventory asset account in `FinanceSettingsSchema` (settings.ts:52-88). `StockLevel` is a hand-edited CRUD table.
- Impact: the product cannot be represented as an inventory/manufacturing ERP; "retail"/"grocery" packs have no stock accounting.
- Effort: L (each is a subsystem)

### R01-13 [Medium] [CONFIRMED] [Double entry] Balance check sums transaction-currency amounts across mixed-currency lines; functional amounts, sign, and one-sidedness are never validated
- Where: `packages/operate-runtime/src/write-guards.ts:125-137`; `validation.ts:19-29,104-135`
- Evidence: `debit += num(line.debit); credit += num(line.credit)` regardless of each line's `currency`; `functional_debit/functional_credit` are not summed. `min: 0` declared on the fields (`entities-finance.ts:70-75`) is not part of `FieldRule` and not emitted as a CHECK → negative debits/credits and lines with both sides populated are accepted. `num()` maps an unparseable amount to `0` silently. Entries with >1000 lines are summed over the first 1000 only (`limit: c.maxLines`, nextCursor ignored).
- Impact: a multi-currency entry can be "balanced" while its functional-currency totals are not.
- Fix: balance on functional amounts (and per-currency), enforce non-negative/one-sided lines, page through all lines.
- Effort: S

### R01-14 [Medium] [CONFIRMED] [Accounting] Postings silently fall back to placeholder account strings and to a no-tax split
- Where: `packages/operate-runtime/src/write-effects.ts:439-440,1016-1018` (`?? c.arAccountRef` = `"accounts_receivable"`), `:941-944`, `:489`
- Evidence: when `finance.*AccountCode` is unset or does not resolve, `ledger_account_id` is the literal string `"accounts_receivable"`/`"revenue"`/`"cash"`… — not an id. On the JSONB store that is a dangling reference posted as `state: posted`; on `pg-columns` a FK failure → 500 on the user's `send`. `resolveAccountId` falls back to `page.records[0]` when the returned row's code does not equal the requested one (:489). If `subtotal + tax_total ≠ total` the whole gross is posted to revenue with **no tax line** and no error (:941-944). Withholding groups without a `gl_account_code`/jurisdiction default land in the *tax payable* account (:1056-1058) while certificate clearing credits a different `wht_receivable` account (:1728-1729).
- Impact: postings to non-existent accounts; VAT silently dropped; WHT receivable never nets to zero.
- Fix: refuse the transition (422) when required accounts are unconfigured or totals do not reconcile.
- Effort: S

### R01-15 [Medium] [CONFIRMED] [Mass assignment] Create/update accept undeclared and server-owned fields (`id`, `created_at`, `posted_at`, `paid_at`, totals, `booking_rate`, `withholding_total`, sequence numbers)
- Where: `packages/operate-runtime/src/handlers.ts:430-438,471-494`; `validation.ts:286-298`; `sequences.ts:141`; `packages/operate-runtime-pg/src/records.ts:41-44`
- Evidence: `body = { created_at: createdAt, ...body, updated_at: createdAt }` — a caller-supplied `created_at` overrides the server stamp. `validateBody` iterates the plan's rules only, so unknown keys are neither rejected nor stripped (stored verbatim in the JSONB document). A caller-supplied `id` matching `RECORD_ID_RE` is honoured. `if (!isBlank(out[plan.field])) continue;` — a caller-supplied `invoice_number`/`entry_number` suppresses the allocator, so numbering can be forged/back-dated (uniqueness is unenforced on the JSONB store). `booking_rate` pre-set by the client is respected (write-effects.ts:1582). `withholding_total` is client-writable and drives the WHT report.
- Impact: forged document numbers and audit timestamps; arbitrary junk keys in documents.
- Fix: strip unknown keys; declare and enforce server-owned fields.
- Effort: S

### R01-16 [Medium] [CONFIRMED] [Numbering] Document numbers are unique and race-safe but not gapless; numbering overrides can produce duplicates
- Where: `packages/operate-runtime/src/handlers.ts:436` (allocation before `validateEntity` at :441 and outside `writeTxn` at :443); `packages/operate-runtime-pg/src/sequence-store.ts:35-51` (own `withTenantContext` transaction); `settings.ts:191-205`
- Evidence: the counter is bumped and committed in its own transaction, then the create may 422 (validation), be guard-blocked, hit the record cap… or roll back. Each burns a number. The allocator's doc calls itself "gap-free-per-allocation". An admin changing `resetPeriod`/`format`/`start` (`PUT /v1/admin/settings`) switches the `periodKey` bucket and restarts at `start` with the same rendered format → duplicate numbers (only rejected on `pg-columns` where the unique index exists). Period key uses UTC, not the tenant's fiscal year/timezone.
- Impact: fails gapless-numbering requirements for tax invoices (e.g. EU/GCC/LatAm).
- Fix: allocate inside the write transaction at issue time (not at draft creation); number on `send`.
- Effort: M

### R01-17 [Medium] [CONFIRMED] [Concurrency] Optimistic locking is opt-in and not atomic
- Where: `packages/operate-runtime/src/handlers.ts:472-473,522-531`
- Evidence: `expectedUpdatedAt` is optional ("Absent → unconditional"); when present it is compared against a non-locking `store.get` and the subsequent UPDATE carries no `updated_at = $expected` predicate → two writers with the same token can both pass. Transitions and deletes have no token at all. With no guards/effects/token configured `before` is not loaded at all.
- Impact: lost updates on financial documents.
- Fix: put the token (or a version column) in the UPDATE predicate; require it for document entities.
- Effort: S

### R01-18 [Medium] [CONFIRMED] [Reports] AR/AP aging and WHT reconciliation silently truncate at 5,000 rows, mix currencies, and `asOf` is not a historical snapshot
- Where: `packages/operate-runtime/src/aging-handler.ts:61,71-102`; `aging.ts:89,105-106,126`; `wht-reconciliation-handler.ts:62,74-103`
- Evidence: `limit: maxRows` (5000) with `nextCursor` discarded for payments, documents, certificates — beyond that the report is wrong with no indicator. The comment promises "a historical aging snapshot" for `?asOf=`, but documents are those open *now* and payments are all completed payments regardless of date; only `daysOverdue` uses `asOf`. `totalOpen`/`totalsByBucket` add amounts across currencies (`currency: null` when mixed is the only hint). Both reports hold all rows in memory per request.
- Impact: materially wrong reports at modest scale.

- Effort: M

### R01-19 [Medium] [CONFIRMED] [Performance / DoS] Plan record-cap check loads up to `cap + 1` full records on every create
- Where: `packages/operate-runtime/src/entitlement.ts:154-159`; `usage-handler.ts:53-61`; `plan-catalog.ts:87-94`
- Evidence: `listPage(tenantId, entity, { limit: cap + 1, … })` then `page.records.length >= cap`. The built-in "pro" plan has `maxRecordsPerEntity: 100000` → each POST reads up to 100,001 rows (JSONB documents) to count them; `/v1/meta/usage` does it for every entity (51+). - Fix: add a `count` to `EntityStore` (`SELECT count(*) … LIMIT`).
- Effort: S

### R01-20 [Medium] [CONFIRMED] [Tax] Tax engine is a flat per-line `net × rate%`; no inclusive pricing, compound tax, reverse charge, exemptions, rate effective-dating, or per-jurisdiction rounding
- Where: `packages/operate-runtime/src/write-effects.ts:826-897,950-1006`
- Evidence: `computeLineTaxBreakdown` takes one rate per line from `TaxCode.rate_pct` (current value, not the rate valid at document date) or the line's flat `tax_rate_pct`; rounds each line to cents then sums (line-level rounding only). Groups are keyed by *label*, so two codes sharing a label but different accounts/jurisdictions are merged under the first-seen account (:866-873). The computed split is used only if `netTotal + taxTotal` equals the client-typed `total` within 0.005 (:1000); otherwise falls back to header figures or to no tax (R01-14). `TaxRule`/`TaxJurisdiction` entities are not read. Configurability is limited to account mapping.
- Impact: unsuitable for real VAT/GST/sales-tax compliance beyond a single-rate demo.

### R01-21 [Medium] [CONFIRMED] [Accounting] Effect-created records bypass validation, guards, RBAC, write-mask and sequences; numbers are derived by string suffix

## Verified strengths (things that are genuinely done well, with file:line)
- RBAC is evaluated on every entity handler before any store access, including per-transition grants and fail-closed ABAC deferral (`handlers.ts:252-275`, `:283-286`); report/admin handlers are role-gated fail-closed (`aging-handler.ts:66-70`, `admin-handlers.ts:18-24`, `job-invoke-handler.ts:53-61`).
- Tenant id always comes from the authenticated principal, never from body/path (`handlers.ts:239`, `job-invoke-handler.ts:74`); `TxEntityStore.assertTenant` rejects cross-tenant use inside a transaction (`operate-runtime-pg/src/entity-store.ts:50-54`).
- Guard → write → effects run in ONE transaction on a transactional store; an effect throw rolls the primary write back (`handlers.ts:978-988`, tested `handlers.test.ts:275`). System postings are therefore atomic with their trigger.
- Effects are edge-triggered (`before.state !== X && after.state === X`), so a no-op re-save does not re-post (`write-effects.ts:650-652,930,1137`).
- The decimal *wire* layer is exact (BigInt, half-away-from-zero = Postgres `NUMERIC`), refuses over-scale client literals with a 422, and normalises all three stores (`decimal.ts:70-153`, `validation.ts:104-135`, `decimal-store.ts:104-154`). Datetime canonicalisation is equally careful (`datetime.ts:121-175`).
- Sequence allocation is a single atomic upsert under RLS — unique and race-safe (`operate-runtime-pg/src/sequence-store.ts:36-44`).
- Licence tokens: Ed25519 over the encoded payload, zod-validated claims, tenant binding, expiry, re-verified per call (`license.ts:106-137,157-174`).
- Client errors do not leak internals: write failures return a fixed string (`handlers.ts:989-1010`); a dropped filter is a 400, not a silently wider result (`handlers.ts:299`, `list-query.ts:316-327`).
- Cursor sealing binds tenant/entity/sort as AEAD AAD and refuses rather than restarts (`cursor-seal.ts:79-117`).
- Field-level write mask runs on caller keys before validation so a 403 precedes a shape-revealing 422 (`handlers.ts:419-427,489-493`).
