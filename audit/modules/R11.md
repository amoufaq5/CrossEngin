# R11 — operate-server: notifications (routes/stores/drain/digests/templates/bounce webhook), marketplace admin/authoring, metering + Stripe sync, certification / DR / SLO, access-review lifecycle, workflow workers + cancellation

## Summary (10 lines max)
- AuthN/AuthZ on the per-user routes (inbox, read state, preferences, workflow cancel) is careful and correct: subject from the credential, tenant-scoped SQL, object-level checks; no SQL injection or mass assignment found. The bounce webhook's HMAC design is sound.
- The delivery drain is not production-safe: a retried delivery is re-sent on every tick for ever (R11-01), claimed work is stranded on any error/crash and retries are unclaimed (R11-03), undeliverable retries never retire (R11-07).
- Outbound content is a fixed nudge; SMS/voice/push are mis-addressed and cannot deliver (R11-04). Template authoring is dead on real Postgres: 4 of 5 transitions fail with a bind-count error (R11-02), and its HTML allow-list is bypassable (R11-05, latent).
- Metering under-bills by design flaw: same-day flushes overwrite each other (R11-09); usage is lost on restart and the dedup set leaks memory (R11-10).
- Compliance outputs can be vacuously green: DR readiness is READY with no data (R11-11), access-review evidence seals at 100% for an empty campaign and cannot complete otherwise (R11-12), the chain control is unscoped and link-only (R11-13).
- Marketplace authoring has no ownership/publisher identity/four-eyes (R11-14); installs are inert rows, so there is no code-execution or supply-chain exposure today.
- Three defects (R11-02, R11-06 and the SQL shape behind R11-01) were confirmed by running the literal statements on a throwaway PostgreSQL 16; the offline fakes cannot see any of them.
- Counts: 16 findings — 7 High, 6 Medium, 3 Low (R11-16 bundles nine minor items).

## Findings

### R11-01 [High] [CONFIRMED] [Correctness / duplicate sends] A delivery that is retried once is re-sent on every drain tick forever
- Where: `apps/operate-server/src/delivery-store.ts:326-349` (`dueRetries`), `apps/operate-server/src/delivery-drain.ts:462-529` (`drainRetry`), `:560-568`
- Evidence: `dueRetries` selects every delivery row with `v.next_retry_at IS NOT NULL AND v.next_retry_at <= $2 AND v.outcome IN (retryable) AND d.status = 'sending'`. There is no "latest attempt per recipient" filter. `drainRetry` sends attempt `due.attemptNumber + 1` and calls only `recordAttempt` (an `INSERT … ON CONFLICT (delivery_id) DO NOTHING`, `delivery-store.ts:270-274`). Nothing clears `next_retry_at` on the attempt-N row, and neither `advance` nor `reconcile` is called from the retry path (`reconcile`/`supersedeDeferred` are called only from `digest-assembler.ts:98-106`). So after attempt 1 = `failed`/`deferred`/`bounced_soft`/`rate_limited`, the attempt-1 row stays due for ever, the parent dispatch stays `sending` for ever, and each tick `drainRetry` re-issues `sendOnce(…, attemptNumber = 2)`; the deterministic id `dlv_sha256(dispatch:recipient:2)` makes the record a silent no-op while the provider call happens again.
- Impact: any transient provider failure (or any quiet-hours `defer`) turns into an unbounded stream of duplicate emails/SMS/calls to that recipient at the `--notification-drain-ms` cadence; `maxAttempts` is never reached (attempt number never exceeds 2); the dispatch never reaches a terminal status; due-retry rows accumulate and fill the 25-row batch. Reputation/cost/complaint exposure with a real sender configured. The in-memory test fake (`delivery-drain.test.ts:96`) returns a hand-fed list, so no test exercises the SQL.
- Fix: select only the latest attempt per (dispatch, recipient) (`NOT EXISTS (… attempt_number > v.attempt_number)`), clear `next_retry_at` on the superseded row in the same transaction as the new attempt, and reconcile the parent after a retry. Add a claim (`FOR UPDATE SKIP LOCKED`) — see R11-03.
- Effort: M

### R11-02 [High] [CONFIRMED] [Correctness / dead feature] Template lifecycle transitions other than `approve` fail against real Postgres (wrong bind count)
- Where: `apps/operate-server/src/notification-template-store.ts:339-354`, `:142-158`
- Evidence: `const params = [tenantId, ntplId, request.to, template.status, request.actorId]` — five values are always bound, but `$5` is referenced only when `to === "approved"` (`approved_by = $5`, `created_by <> $5`). For `in_review` / `draft` / `retired` the SQL references `$1..$4` with 5 binds; for `deprecated` it references `$1..$4,$6` with `$5` unreferenced. Reproduced on a throwaway PostgreSQL 16.15 with the statements exactly as built (extended protocol, which is what `pg` uses for `client.query(sql, params)`): `ERROR: bind message supplies 5 parameters, but prepared statement "" requires 4` and `ERROR: could not determine data type of parameter $5`. The approve statement runs.
- Impact: `POST /v1/notification-templates/{id}/submit` (draft → in_review) always throws → nothing can ever reach `in_review`, so nothing can ever be approved over HTTP; reject, deprecate and retire fail the same way. The whole `--notification-template-routes` authoring surface is create/list/get only. The offline fake (`notification-template-store.test.ts:107-150`) matches on SQL substrings and never counts parameters, which is why 549 lines of tests are green.
- Fix: build params per target (bind the actor only when referenced), or reference `$5` unconditionally (e.g. `AND $5::text IS NOT NULL`). Add a live-Postgres test for every transition.
- Effort: S

### R11-03 [High] [CONFIRMED] [Reliability] Delivery drain has no crash recovery and no per-dispatch error isolation; a claimed dispatch can be stranded in `rendering` for ever, and retries are not claimed at all
- Where: `apps/operate-server/src/delivery-store.ts:242-262` (claim: `queued` → `rendering`, committed before any work), `delivery-drain.ts:546-558` (loop with no try/catch per dispatch), `:432-445` (attempts recorded only after all sends), `delivery-store.ts:326-349` (`dueRetries` has no `FOR UPDATE`/claim)
- Evidence: `claimQueued` commits `status = 'rendering'` for up to 25 rows, then `drainTenant` processes them serially. If `drainDispatch` throws for one (e.g. `activeSuppressions` throws by design on one unparseable row — `recipient-resolver.ts:428`; a `recordAttempt` DB error; a schema-invalid dispatch) the exception leaves `drainTenant`, is caught per tenant in `drainTenants` (`:589-595`), and every remaining already-claimed row stays `rendering`. Nothing re-queues `rendering` rows: `grep "rendering"` over non-test sources finds only the claim constant. A process crash mid-batch has the same result, and if it happens after `sendOnce` but before `recordAttempt` the send happened with no record. Separately `dueRetries` takes no lock, so two replicas (the documented multi-server case, `node.ts:3835-3836`) both send the same retry; the deterministic delivery id hides the duplicate in the ledger.
- Impact: silent permanent loss of notifications (incl. `security_alert`/transactional) after any mid-batch error or restart; duplicate sends with >1 replica. One poison suppression row blocks a tenant's channel and strands a batch on every tick.
- Fix: lease-based claim (`claimed_by`, `claim_expires_at`) with a reaper; try/catch per dispatch that releases the claim; record each attempt immediately after its send; claim due retries with `FOR UPDATE SKIP LOCKED` inside the transaction that records the next attempt.
- Effort: M

### R11-04 [High] [CONFIRMED] [Claims vs reality] Outbound messages carry no template content; SMS, voice and push are addressed to the wrong identifier and cannot deliver
- Where: `apps/operate-server/src/delivery-senders.ts:7-15` (`SendRequest` has no body/variables), `delivery-drain.ts:125-132` (`addressFor`), `recipient-resolver.ts:53-56` (only `u.email` is selected), `packages/notification-providers/src/email-ses.ts:262-264`, `sms-twilio.ts:67`, `push-fcm.ts:501,518`
- Evidence: `addressFor` returns `recipient.userId` for `in_app`/`push_mobile` and `recipient.email` for everything else — so an SMS and a voice call are "sent" to an e-mail address and an FCM push to a user UUID (`push-fcm.ts:518` refuses anything not shaped like a registration token). There is no phone column read and no device-token registry anywhere. For e-mail, the sender composes a fixed nudge: `subject: \`CrossEngin notification: ${request.templateId}\``, body `A notification (${request.templateId}) is waiting for you in CrossEngin.` The dispatch row stores only `variables_sha256` (`notification-store.ts:23`), so the variables no longer exist at send time. `PostgresTemplateStore.find` has exactly one caller (`node.ts:2626`, the in-app digest override).
- Impact: "4 of 18 providers implemented" overstates it: only e-mail can physically deliver, and it delivers a generic "something is waiting" message, never the tenant's template. The template model (variables, locales, html/plaintext bodies, approval workflow) is not on the send path. Product/commercial gap rather than a vulnerability.
- Fix: persist (encrypted) variables or a rendered payload with the dispatch; resolve per-channel addresses (phone, device tokens) and refuse a channel with no address source at boot.
- Effort: L

### R11-05 [Medium] [CONFIRMED] [Security / stored XSS, latent] The authored-template HTML allow-list is a regex tokenizer that a browser parses differently; `<svg onload>` / `<img onerror>` / `<form>` pass
- Where: `apps/operate-server/src/notification-template-routes.ts:254-256` (`TAG_RE`, `ATTR_RE`), `:335-359` (`markupRefusals`), `:307-324`
- Evidence: `TAG_RE` treats a quote anywhere inside a tag as opening a quoted run, while HTML only opens a quoted value after `=`. Payload `<p ">alt='<svg onload=alert(1)>'">`: the scanner sees one allowed `<p>` whose "attributes" are `alt='…'` (allowed, non-URL); a browser closes `<p ">` at the first `>` and then parses `<svg onload=alert(1)>` as a real element. Re-running the module's own regexes and allow-lists verbatim (node, no repo imports) returns **zero refusals** for that payload, for `<p ">alt='<img src=x onerror=alert(document.cookie)>'">` and for a `<form action=https://evil.example/>` credential-phish block; `<script>` is still refused.
- Impact: an author + a (different) approver in one tenant can store active markup in `email.htmlBody` / `in_app.htmlBody`. Today it is **latent**: R11-02 means nothing can be approved, the only consumer of an approved template is the in-app digest (`node.ts:2626` → `GET /v1/meta/notifications` `digest.body`), and `apps/operate-web/app/inbox` does not inject it as HTML (no `dangerouslySetInnerHTML` there). It becomes a real stored XSS / phishing vector the moment transitions are fixed and any client renders `digest.body` or the e-mail sender starts using `htmlBody`. The doc comment claims the content "reaches a browser as markup" and is therefore refused — the refusal does not hold.
- Fix: parse with a real HTML parser and re-serialize from the allow-listed tree (or sanitize at render), never regex-accept author text; treat `"`/`'`/`<` outside a quoted value as a refusal.
- Effort: M
- Note (strength): variable substitution itself is safe — `packages/notifications/src/templates.ts:280-286,314-326` is a plain `{{name}}` replace with HTML-escaping in markup fields and JSON-escaping in payload templates; no expression evaluation, no property traversal.

### R11-06 [Medium] [CONFIRMED] [Correctness] A second transient (soft) bounce for an address makes the bounce webhook answer 500 for ever and the suppression can never be re-imposed
- Where: `apps/operate-server/src/suppression-store.ts:256-265` (insert), `:269-275` (holder query filters `expires_at IS NULL`), `:303-308` (throw); `packages/notification-providers/src/bounce-webhook.ts:361-371` (id = sha256(tenant|channel|address|reason), no expiry), `:1225-1232`
- Evidence: with `--bounce-transient-hours` set, an SES transient bounce plans `soft_bounce_exceeded` with an `expiresAt`. The id is deterministic. On any later transient bounce for the same address (a provider retry, a replay inside the HMAC window, or a genuinely new bounce after the first expired) `ON CONFLICT (suppression_id) DO NOTHING` writes 0 rows; `holderSql` only looks at permanent rows and finds none; the store throws `suppression insert wrote no row and no row holds the address`; the route returns `500 suppression_write_failed` (`bounce-webhook-routes.ts:575`). Reproduced on PostgreSQL 16.15: second insert `INSERT 0 0`, holder count 0, stored row still carries the January expiry.
- Impact: SES/SNS retries the 500 indefinitely; a mailbox that soft-bounces repeatedly is suppressed exactly once in its lifetime. Gated on the opt-in transient window.
- Fix: include the expiry window (or applied_at bucket) in the id for non-permanent reasons, or treat "same id exists" as `already_present` regardless of `expires_at` and extend the expiry by an explicit, bounded rule.
- Effort: S

### R11-07 [Medium] [CONFIRMED] [Correctness] A due retry whose recipient is no longer deliverable is never retired and is re-evaluated every tick
- Where: `apps/operate-server/src/delivery-drain.ts:470-480`
- Evidence: `drainRetry` rebuilds recipients with `emptyPreferenceMatrix` (line 473 — stored preferences are not consulted on a retry) and returns `null` without recording anything when the target is not in `plan.deliverable` (`if (target === undefined) return null;`). The originating row keeps `next_retry_at`, so `dueRetries` returns it again on every tick. This is reached when the user was deactivated/removed, when the address became suppressed after attempt 1, and — because the matrix is empty — for every category that requires explicit opt-in (the retry is then *always* "not opted in").
- Impact: permanent `sending` dispatches, batch slots consumed by undeliverable retries (ordering is `next_retry_at ASC`, so the oldest stuck rows starve newer ones once 25 accumulate), and conversely a user who opted *out* of a default-on category after attempt 1 is still sent the retry.
- Fix: load real preferences on retry; when the target is ineligible record a terminal `suppressed`/`dropped` attempt and clear the pending retry.
- Effort: S

### R11-08 [Medium] [CONFIRMED] [AuthZ / consent] The on-behalf preference route lets an admin opt another user *in*, and never checks the target is a member of the tenant
- Where: `apps/operate-server/src/preference-routes.ts:421-444` (`adminSubjectFrom`), `:483-630`; `preference-store.ts:211-235`
- Evidence: `PUT /v1/notifications/preferences/users/{userId}/{category}/{channel}` with `{optedIn:true, expect:"opted_out"}` is accepted for a holder of `--preference-admin-role`; `expectationPredicate("opted_out")` then overwrites the user's own `user_set` opt-out with `admin_set` opt-in. When no row exists, the `expect` is not consulted at all (plain insert), so an explicit-opt-in category (marketing) can be switched on for a user who never consented. `adminSubjectFrom` validates only that `userId` is a UUID — there is no membership lookup, so a row can be written under the admin's tenant for any `meta.users` id (the FK is to the global users table), and the 200-vs-503 difference is a cross-tenant user-existence oracle.
- Impact: consent can be manufactured by an administrator (GDPR Art. 7 / ePrivacy / CAN-SPAM exposure for marketing categories). The write is audited before it happens (`:562-582`), which mitigates but does not prevent. Cross-tenant impact is limited to existence disclosure.
- Fix: on the on-behalf surface allow only opt-*out* (or require the category to be non-consent-based); require an active membership row for the target in the caller's tenant.
- Effort: S

### R11-09 [High] [CONFIRMED] [Billing / under-billing] Metered usage is overwritten, not accumulated: every flush in the same UTC day replaces the previous one
- Where: `apps/operate-server/src/metering.ts:149-175` (`flushUsage` writes the *delta since the last flush* and then `clearSubscription`), `:228-239`; `packages/billing/src/usage.ts:52-59` (`idempotencyKey = tenant=…:meter=…:day=YYYY-MM-DD`); `packages/billing-runtime-pg/src/usage-store.ts:40-44` (`ON CONFLICT (idempotency_key) DO UPDATE SET quantity = EXCLUDED.quantity, …`)
- Evidence: the scheduler flushes every `flushIntervalMs` and each flush emits one record per bucket holding only the requests counted since the previous flush (buckets are cleared at line 172). `usageRecordFrom` keys the record by tenant + meter + **day of period start**, and the store *replaces* `quantity` on conflict. So with any interval shorter than a day, flush N+1 overwrites flush N; the stored quantity for a day is whatever the last interval of that day saw. If `StripeUsageSyncScheduler` ran in between, the first interval's figure is what Stripe got (`listUnsynced` skips an already-synced row and the Stripe `Idempotency-Key` is the same day key), and the rest of the day is never reported. Two replicas overwrite each other the same way. `subscriptionId` is not part of the key either.
- Impact: systematic under-billing of metered usage (by roughly the ratio day / flush interval); usage figures in `meta.billing_usage_records` are not trustworthy. `metering.test.ts` (11 tests) flushes once per test against a fake store and never exercises two flushes in one day.
- Fix: either accumulate (`quantity = table.quantity + EXCLUDED.quantity` with a per-flush idempotency key that includes period start *timestamp* and replica id), or keep cumulative-per-day counters durably and write the cumulative figure; include the subscription in the key; make Stripe reporting delta-based.
- Effort: M

### R11-10 [Medium] [CONFIRMED] [Billing / reliability] Metering loses usage on every restart and on a partial flush can double-count; the request-id dedup set grows without bound
- Where: `apps/operate-server/src/metering.ts:118-123`, `:155-173`, `:228-246`; `apps/operate-server/src/node.ts:4344` (shutdown calls `flushScheduler.stop()` only); `packages/billing-runtime/src/meter.ts:26-32,70-74`
- Evidence: (a) usage lives in process memory between flushes and shutdown stops the timer without a final `flushOnce()` — everything since the last tick is dropped on each deploy/crash. (b) `flushUsage` awaits `usageStore.record` per bucket and only then clears the subscription; requests observed during those awaits are added to the bucket and then deleted by `clearSubscription` (lost), and if a later `record` throws, `lastFlushAt` is not advanced and already-written buckets are re-emitted next tick with fresh random ids (`opts.ids.next()`). (c) `UsageMeter.seen` holds every `execution.requestId` ever metered; `clearSubscription` does not clear it and `reset()` is never called — one string per billable request for the life of the process.
- Impact: revenue leakage on restart; unbounded heap growth proportional to request volume (an eventual OOM on a busy API); non-deterministic counts under load.
- Fix: snapshot-and-swap the buckets atomically before any await; flush on shutdown; bound or window the dedup set; persist counters.
- Effort: M

### R11-11 [High] [CONFIRMED] [Compliance / falsely-true control] DR readiness is `READY` — and the certification control satisfied — with no drills, no backups, no runbooks and no replication data
- Where: `apps/operate-server/src/dr-readiness.ts:26-34` (all inputs `default([])`), `:93-108`; `packages/dr-runtime/src/readiness.ts:126-146` (`ready: counts.totalIssues === 0`); `apps/operate-server/src/certification.ts:125-136`; `packages/certification-runtime/src/evidence.ts:134-140`
- Evidence: runbooks, backups and replication-lag records are read from the operator's JSON config (`config.input`), not measured; failovers and drills are read from two tables that nothing in `apps/` writes (`grep drillStore|failoverStore|DrillExecutor|FailoverExecutor apps/` → only the two `listRecent` reads in this file). `assessDrReadiness` counts *issues among the records it is given*; with `{"input":{}}` every list is empty, `totalIssues` is 0 and the report is `ready: true`. `drReadinessSource` then emits `satisfied: true`, summary "DR readiness: READY (0 issues)", stamped `observedAt = now` regardless of the snapshot's age (`latest(scope)` has no freshness bound).
- Impact: a SOC 2 / HIPAA certification report can assert the `resilience.dr_readiness` control from zero evidence. This is the "falsely-true control" direction the repo's own documentation calls the compliance failure itself (it fixed the same shape for encryption coverage in `evidence.ts:97-99` and left this one).
- Fix: treat absent drills/backups/replication as `scope_absent` (unsatisfied); require a drill inside the tier's cadence; source backup/replication facts from the database/provider rather than from a typed file; bound snapshot age.
- Effort: M

### R11-12 [High] [CONFIRMED] [Compliance / falsely-true control] An access-review campaign with zero items completes immediately and seals evidence at 100% completion; with real items it can never complete
- Where: `apps/operate-server/src/access-reviews-lifecycle.ts:24-25,122-124` (static grant source, `grants`/`principals` default `[]`), `:165-200`; `packages/access-reviews-runtime/src/scheduling.ts:86-91` (`isCampaignCompletable` ⇔ no unresolved items); `packages/access-reviews/src/evidence.ts:69-72` (`total === 0 → completionRate: 1`); `apps/operate-server/src/certification.ts:188-201`, `packages/certification-runtime/src/evidence.ts:186-201`
- Evidence: without `--access-reviews-live-grants` the grant source is the config's `grants` array, default empty → `generateItems` yields nothing → next tick `isCampaignCompletable(current, [])` is true → `closeCampaign` seals a pack whose `completionRate` is 1 → `evidenceFromAccessReviewEvidence` reports "access review sealed at 100% completion", `satisfied: true`. Conversely, when items exist: the only writer of a decision anywhere in the deployed binary is `planAutoRevocations` (`grep recordDecision|decisionStore.record` → `access-reviews-runtime-pg/src/persisting-runtime.ts:311` only); there is no HTTP route for a reviewer to attest, and `planAutoRevocations` records decision rows without updating item status (`persisting-runtime.ts:300-314`), so items stay unresolved [LIKELY for the item-status half]. Auto-revocation also changes no real access — no membership or key is touched.
- Impact: the `access.periodic_review` control is satisfiable only vacuously. A certification built on it is unsupported; a human-driven review cannot be performed through the product at all.
- Fix: refuse to seal (or mark `scope_absent`) a zero-item campaign; add reviewer decision routes; make auto-revocation act on the grant and update the item.
- Effort: L

### R11-13 [Medium] [CONFIRMED] [Compliance / correctness] The certification's forensic-chain control reads the chain with no scope predicate and verifies links only
- Where: `apps/operate-server/src/certification.ts:333-343` (`SELECT … FROM forensic_chain_entries ORDER BY sequence_number ASC` — no `WHERE`), `packages/forensics/src/tamper-evident-logs.ts:96-112`
- Evidence: the reader relies on RLS alone. On an owner connection (owner bypasses RLS; the repo documents this as an ordinary deployment) it loads every tenant's and the platform's entries interleaved, so `verifyChainIntegrity` — which requires `sequenceNumber === i` from 0 — reports `sequence gap` on healthy multi-scope data; as a non-owner with `tenantId: null` it runs outside any context and sees zero rows → `[]` → `not_assessed`. And the check itself compares only `priorEntryHash` to the previous `entryHash`: it never recomputes an entry hash from its fields and never verifies a signature, so any self-consistent rewrite passes. The whole table is loaded into memory on every run (no LIMIT; the table only grows).
- Impact: the `audit.tamper_evident_log` control is either falsely failing, never assessed, or passing on a check that does not detect tampering with entry contents — depending on connection role. The stronger verifier the server uses elsewhere (`--integrity-proof-config`) is not what certification consults.
- Fix: scope the read (`scopeFilter`), reuse the integrity-proof verifier (hash recomputation + signature + checkpoint), page the read.
- Effort: S–M

### R11-14 [Medium] [CONFIRMED] [AuthZ] Marketplace authoring has no pack ownership, no publisher identity and no separation of duties
- Where: `apps/operate-server/src/marketplace-authoring.ts:60-70` (guard = "has a tenant" + role), `:98-107` (`getByPackVersion(packId, version)` — no tenant/owner), `:157-193`; `packages/marketplace-runtime/src/submission.ts:71-93`; `node.ts:1349-1350` (roles hard-coded `pack_author` / `marketplace_reviewer`)
- Evidence: pack versions are platform-global rows and no route binds a `packId` to a submitter, tenant or key. Any principal holding `pack_author` in any tenant can submit a new version of somebody else's `packId` and `withdraw` any version (`:178-185`). `submit` verifies the signature against the `publicKeyBase64` supplied in the same request body and then stores neither the key nor the submitter — the signature proves only that the caller holds *a* key. `bundleSha256`/`manifestSha256` are caller-asserted and never compared with the submitted manifest (there is no bundle upload). `recordReview`/`publish` do not check reviewer ≠ author (the author is unrecorded), and a non-`stable` channel publishes with no review (`submission.ts:118-124`). Thrown store errors are returned verbatim as `detail` (`:91-92,136-137`).
- Impact: pack squatting/takeover and unreviewed publication in the registry. Mitigated today because the registry feeds nothing: installs come from an operator-supplied JSON file (`node.ts:1327`), and an installation is a row that no serving path reads (`listForTenant` is the only reader) — an installed pack contributes no manifest content and executes no code. So supply-chain risk is currently nil *because the marketplace is inert*, not because it is controlled.
- Fix: publisher registry (packId → owning tenant + registered key), store submitter, enforce four-eyes on review/publish, verify digests server-side.
- Effort: M

### R11-16 [Low] [CONFIRMED] [Robustness] Smaller issues on the notification read/write paths
- `notification-store.ts:153-167,297-304`: offset cursor is an unbounded integer from the client (`o:<digits>`) fed to `OFFSET`; a value above bigint raises → 500, and deep offsets are O(n). `read-state-store.ts:206-211` (`indexFor`) selects **all** of a viewer's read-state rows with no LIMIT on every unread poll.
- `notification-routes.ts:313-325`: up to 200 rows × 2 resolver calls per list request (N+1 against `operate_tenant_manifests` and the digest tables).
- `read-state-store.ts:110-131`: under a concurrent duplicate mark, `ON CONFLICT DO NOTHING` returns no row and the same-statement `SELECT` cannot see the other transaction's row → the store throws "check the tenant context" → 503 for a benign race [LIKELY].
- `notification-store.ts:129-131`, `delivery-plan.ts:52`: recipient addresses are pseudonymised with unsalted `sha256(address)`; e-mail addresses and UUIDs are trivially re-identifiable by dictionary, so `recipient_address_sha256` should be classified as PII, not as a safe surrogate.
- `fax-observation-store.ts:163,169-177`: the retry guard compares only `last_call_sid`, so an interleaved redelivery (call A, call B, A again) or a replay of an older signed callback inside the HMAC window advances the run; with `--bounce-fax-suppress-after 2` that is a permanent voice suppression from two real calls.
- `bounce-webhook-routes.ts:428-449` + `node.ts:4060-4138`: the route sits in front of the gateway, so no rate-limit stage applies; each anonymous POST costs a body read up to `--max-request-body` (10 MiB default) and one HMAC. `onError` logs the raw `err` object (`node.ts:4130`), and a non-unique-violation Postgres error (e.g. a CHECK failure) carries `detail: Failing row contains (… address …)` — the PII the module otherwise keeps out of logs.
- `notification-template-routes.ts:703-711`: any store error on list (not only a bad cursor) is reported as `400 template_page_unreadable`.
- `slo-defaults.ts:25-32`: the built-in alert policy routes P1 to PagerDuty `serviceKey: "operate-default-oncall"` (a placeholder, and the routing key *is* the credential) and P2/P3 to `#slo-alerts`; with `--slo-defaults` and no override, pages go nowhere. `slo.ts:276-292`: one throwing evaluator aborts the remaining evaluators for that tick.
- `node.ts:2576`: the inbox route `GET /v1/meta/notifications` is gated on `--ai-design` roles (`allowedRoles: new Set(options.aiDesignRoles)`) and only mounts when the manifest store exists — an ordinary user role cannot read its own inbox unless it is also an AI-design role.

## Verified strengths (things that are genuinely done well, with file:line)
- Bounce webhook: nothing is written before verification (`bounce-webhook-routes.ts:428-461`); constant-time compare on equal-length hex (`packages/crypto/src/hmac.ts:98-111`); per-tenant key = `HMAC(platform_secret, "bounce-webhook:"+tenant)` so a captured signature cannot be replayed against another tenant (`bounce-webhook-env.ts:56-63`); secrets under 32 chars refuse to mount the route (`:43-53`); missing header / unknown tenant / bad signature / stale timestamp are one opaque 401 (`:60-64,368-380`); the response never echoes an address (`:598-618`).
- Suppression writes are insert-only and idempotent, with the tenant re-checked against the write context before SQL (`suppression-store.ts:256-265,341-352`); both suppression readers fail closed on an unparseable row (`suppression-store.ts:138-162`, `recipient-resolver.ts:416-432`).
- Read-state and preference routes take the subject from the credential and *refuse* a body naming one (`read-state-routes.ts:256-262,371-377`; `preference-routes.ts:254-260,498-504`); privileged sources (`system_backfill`, `admin_set`, `regulatory_requirement`) are not assertable without the grant; an unrecordable privileged write is a 503 (`read-state-routes.ts:480-505`, `preference-routes.ts:562-582`). Opt-out of a non-suppressible category is refused under every source (`preference-routes.ts:517-522`).
- Mark-read verifies the notice is in the caller's own inbox before writing (`read-state-routes.ts:387-409`) and both read-state writes are monotonic in SQL (`read-state-store.ts:110-122,167-175`).
- Template four-eyes is enforced inside the `UPDATE` predicate, not only in application code (`notification-template-store.ts:334-349`); template variable substitution is a plain placeholder replace with context-appropriate escaping and no evaluation (`packages/notifications/src/templates.ts:280-326`); URL fields must begin with a literal `https://` origin with no placeholder in scheme/host (`notification-template-routes.ts:274-304`).
- `claimQueued` uses `FOR UPDATE SKIP LOCKED` and flips status in the same transaction (`delivery-store.ts:242-262`); every store in scope carries an explicit `tenant_id` predicate beside `withTenantContext`.
- Workflow cancellation: tenant ownership checked on the loaded snapshot, mandatory explicit `disposition`, bounded `reason`, honest 500 "may be partially applied" (`workflow-cancellation-routes.ts:298-377`). The worker supervisor refuses to start a worker that would hot-loop or double-run and renews leases while a handler runs (`workflow-workers.ts:415-422,470-471,713-722`).
- Certification is fail-closed for *missing* evidence: a throwing or absent source leaves a control `not_assessed` and the framework not certifiable (`certification.ts:446-458`; `packages/certification-runtime/src/assessment.ts:41-47,102`); zero encrypted columns is `scope_absent`, not satisfied (`evidence.ts:97-99`).
- Design-review enrolment failure cannot bypass review: activation requires `reviewStatus === "approved"` (`ai-design-routes.ts:329-330`), so `review-enrolment.ts:40-44` swallowing an error is safe.

## Claims vs reality (docs/README/CLAUDE.md/comments that the code contradicts)
- CLAUDE.md: "Four of 18 notification providers are implemented … Both ends of the loop are wired for all four." Code: SMS and voice are addressed to the user's **e-mail**, push to the **user UUID**; only e-mail can deliver, and it sends a fixed "a notification is waiting" nudge (R11-04).
- CLAUDE.md `operate-server` entry: template authoring "with three fail-closed grants — author, approver (four-eyes at three layers…)" and ADR-0313 "verified live". Code: `submit`, `reject`, `deprecate`, `retire` bind a parameter the statement does not reference and fail on PostgreSQL (R11-02); only `approve` is executable and nothing can reach `in_review`.
- `notification-template-routes.ts` header / CLAUDE.md: unsafe authored content is "refused rather than stored". The allow-list is bypassable (R11-05).
- `delivery-store.ts:204-216` doc comment: the claim "is what stops the same notification from being sent twice". True for the first attempt only; the retry path re-sends indefinitely (R11-01) and is unclaimed (R11-03).
- CLAUDE.md `notifications` entry: "per-user quiet hours, where the timezone is the user's". Code: quiet hours are one tenant-level policy with the tenant's timezone (`node.ts:3864-3865`, `delivery-throttle.ts:211-236`); no per-user setting is read.
- CLAUDE.md `certification-runtime`: "evidence adapters that pull real signals from other packages (… DR readiness, forensic chain integrity, access-review completion)". Code: DR readiness is an operator-typed JSON plus two never-written tables and is READY when empty (R11-11); access-review evidence is satisfiable only by an empty campaign (R11-12); the chain check is link-only and unscoped (R11-13).
- CLAUDE.md says the owner-dependent reads were "swept" (ADR-0333). `PostgresForensicChainReader.loadChain` (`certification.ts:334-337`) still has no scope predicate.
- CLAUDE.md `billing-runtime-pg`: "persists usage …, wraps the engine so each period close is written". The server's own metering path overwrites same-day records (R11-09).
- `metering.ts` comment on `usageRecordFrom` idempotency ("re-emitting the same period's record is idempotent downstream") — the key is per *day*, the flush is per *interval*.
- `node.ts:3878` says per-tenant gateways leave "SLO, audit chain, metering, billing" on the default server; `node.ts:3958-3962` says the opposite. One of the two comments is stale (not resolved here — outside scope).
