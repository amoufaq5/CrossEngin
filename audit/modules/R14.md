# R14 — packages/workflow-engine, packages/workflow-runtime, packages/jobs (background execution)

## Summary (10 lines max)
- The three packages are well-typed, heavily commented, pure libraries (~8k LOC, 25 test files, ~770 `it`s). As *libraries* they are above-average in rigour (total maps, named refusals, log-driven idempotency).
- As a *product capability* they deliver nothing today: no deployed entry point ever calls `WorkflowEngine.startInstance` or `submitSignal`; there is no manual-action API at all; `JOB_HANDLER_PROVIDERS` is `[]`, so **zero** job handlers exist in the workspace. An ERP customer gets no approval workflow, no scheduled month-end close, no dunning from these packages (entity lifecycle transitions are a different mechanism in `operate-runtime`, out of scope).
- Even if wired, the executor has real correctness defects: saga compensation runs for activities that never ran / failed / were retried (R14-01); a failed compensation is recorded as compensated and never retried (R14-02); the "wait for signal OR timeout" pattern is impossible because a scheduled timer makes the instance undeliverable for signals (R14-03); no data from signals or activity outputs ever reaches variables, so guards can only branch on start-time input (R14-04).
- Cron: the day-skip optimisation is **not** equivalence-preserving across a DST spring-forward day — reproduced: a weekly `15 0 * * 1` in `America/New_York` skips a whole week; monthly `0 0 1 * *` in `Europe/Berlin` skips April 2030 (R14-05).
- Declared-but-unimplemented surface is large: `expression`/`abac_check` guards throw, `role_required` is always false, `onExitActions`, `slaSeconds`, `timeoutSeconds`, activity timeouts, parallel fork/join, suspend/resume, `emit_event`, `audit_log`, job `concurrency`/`rateLimit`/`idempotent`, `business_hours` timers.
- Concurrency control is "read max(seq) then insert"; a lost race after a handler ran leaves a side effect with no completion event and an activity nothing will re-run (R14-08).
- Performance: every engine step re-reads and re-folds the full instance log (several times per appended event); no snapshots, no continue-as-new, no history cap (R14-10).

## Findings

### R14-01 [High] [CONFIRMED] [Correctness/Saga] Compensation runs for activities that never executed, failed, were cancelled before start, and once per retry attempt
- Where: `packages/workflow-runtime/src/saga.ts:23-70` (`listCompensatableActivities`), consumed by `engine.ts:902-934`, `engine.ts:1872-1958`, `instance-cancellation.ts:93-99`.
- Evidence: the map is filled on `activity_scheduled` (`scheduledByActivityId.set(event.activityId, {... completedAt: event.occurredAt ...})`, saga.ts:37-53); `activity_completed` only overwrites `completedAt` (saga.ts:54-58); the output loop excludes only `compensated` ids and non-side-effect kinds (saga.ts:64-68). Nothing requires an `activity_completed`, and `activity_failed` / `activity_cancelled` / `activity_timed_out` are not consulted. `engine.ts:1747` passes `compensationActivityKey` to every retry attempt, each with a fresh `activityId` (`engine.ts:1531`). The contracts package's own planner does it right and is unused by the runtime: `workflow-engine/src/compensation.ts:50-56` filters `a.status === "succeeded"`.
- Impact: (a) an http_call "charge card" that failed twice and succeeded on attempt 3 is "refunded" three times; (b) a charge that failed outright is refunded; (c) on `cancelInstance(disposition: "compensate")`, activities cancelled at `before_handler` are still compensated although `INSTANCE_CANCELLATION_GUARANTEES.never_started` says "nothing ran, so there is nothing to undo" (`instances.ts:341-342`) and the survey field is documented as "Completed side-effect activities" (`instances.ts:461-466`). Compensations are typically money-moving (reverse posting, refund, cancel shipment).
- Test gap: `saga.test.ts` has no case with `activity_failed`/`activity_cancelled`; the engine saga fixture gives the failing activity no `compensationActivityKey` (`engine.test.ts:1497-1499`), so the defect is structurally invisible to the suite.
- Fix: track per-activity terminal outcome; compensate only `succeeded` (optionally `timed_out`/unknown under an explicit policy); collapse retry attempts to the attempt that succeeded. Reuse `computeCompensationPlan`.
- Effort: S

### R14-02 [High] [CONFIRMED] [Correctness/Saga] A failed (or unregistered) compensation is recorded as compensated; the instance ends `compensated` and it is never retried
- Where: `packages/workflow-runtime/src/engine.ts:1966-2036` (`compensateStep`), `saga.ts:59-66`, `projection.ts:384-395`, `projection.ts:555-559`.
- Evidence: handler `null` ⇒ `outcome = { status: "succeeded" }` (engine.ts:1981-1982); a thrown/failed handler only changes payload fields (`compensationStatus: outcome.status`, engine.ts:2028) — the event appended is always `activity_compensated` (engine.ts:2014). `listCompensatableActivities` drops any id with an `activity_compensated` (saga.ts:59-60), the activity projection sets `status = "compensated"` (projection.ts:559) and `compensation_completed` unconditionally sets instance status `compensated` (projection.ts:391-393). `runCompensation` returns the id in `compensatedActivityIds` regardless (engine.ts:1933).
- Impact: a rollback whose undo step failed is indistinguishable (by status, by the planner, by the return value) from a clean rollback; "idempotent re-invocation" skips exactly the steps that still need doing. With the default registry shipped to the server (`createDefaultRegistry`, activity-handlers.ts:109-114) *every* compensation key is unregistered ⇒ every saga "succeeds" having undone nothing.
- Fix: emit `compensation_step_completed` with a status (the event kind exists and is never written), only mark `activity_compensated` on success, finish in `failed` (INSTANCE_TRANSITIONS already has `compensating → failed`), treat an unregistered compensation handler as a refusal.
- Effort: M

### R14-03 [High] [CONFIRMED] [Correctness] "Wait for signal OR timeout" is impossible: any scheduled timer makes the instance deaf to signals, silently
- Where: `packages/workflow-runtime/src/projection.ts:347-353` and `:215-230`; `engine.ts:529`.
- Evidence: `timer_scheduled` ⇒ `setStatus(state, "waiting_for_timer")`; `refineStatusFromDefinition` returns early for `waiting_for_timer` so `waiting_for_signal` is never derived; `submitSignal` skips the instance: `if (state.status !== "running" && state.status !== "waiting_for_signal") continue;`. The skipped signal is not recorded, not rejected, not reported — the caller gets `matchedInstanceIds: []`. The repo's own test comment concedes it: `engine.test.ts:1853-1856` "an instance holding a scheduled timer projects as waiting_for_timer and submitSignal declines to deliver into that status".
- Mirror image: `fireDueTimersForInstance` only fires in `waiting_for_timer`/`running` (engine.ts:680), so in deferred mode a state that arms a timeout timer and schedules an activity (`waiting_for_activity`) never fires the timeout; the due row stays `scheduled`, which is the claim-forever hot loop the code comments at engine.ts:736-740 warn about.
- Impact: the canonical approval/escalation shape (approve signal with a 3-day reminder/expiry) cannot be expressed. Any instance that arms an SLA timer on entry cannot be signalled.
- Fix: stop encoding "what it waits for" as a single status; deliver signals/timers based on applicable transitions from `currentState`, record unmatched signals as `rejected` (the status and `SIGNAL_REJECTION_REASONS` already exist in `signals.ts:35-44`, unused).
- Effort: M

### R14-04 [High] [CONFIRMED] [Capability] No runtime data ever reaches workflow variables — guards can only branch on start input and literals
- Where: `engine.ts:1446-1474` (`applySetVariable` writes `action.parameters["value"]`, a literal from the definition); `engine.ts:1672-1693` (activity output is hashed, `outputSha256`, never stored or merged); `projection.ts:366-367` (`signal_received` is a no-op for variables; the payload stays in the event); `transitions.ts:9-13` (`GuardContext` = variables, currentState, principalRoles only).
- Impact: an approval signal carrying `{approved:false}`, a credit-check activity returning a score, a child workflow result — none can influence a transition. The only branching available is signal *name* / activity success-vs-failure. This is not a workflow engine an ERP process (approval thresholds, 3-way match, dunning levels) can be authored against.
- Fix: variable mapping on signal/activity/child completion (declared output→variable bindings), or expression support.
- Effort: L

### R14-05 [High for timers / Medium for jobs] [CONFIRMED by reproduction] [Correctness/Cron] Day-skip misses fires adjacent to a DST spring-forward day
- Where: `packages/jobs/src/cron.ts:298-307` (`minutesRemainingInLocalDay`, `stepsElapsedInLocalDay`), used at `:333` and `:354`. Comment at `:290-293` claims "on a DST transition day the skip simply lands early or late inside the next day, which costs extra steps and never a missed match" — false.
- Evidence: the skip is computed from local wall-clock fields assuming a 1,440-minute day. On a 23-hour day a forward skip from local 00:00 lands at 01:00 of the *next* day, jumping over 00:00–00:59; a backward skip from after the gap lands at 22:59 of the previous day, jumping over 23:00–23:59. Reproduced with a line-for-line re-implementation (`/tmp/claude-0/-home-user-CrossEngin/f416b640-191a-59fd-89b0-b5d1696255e2/scratchpad/cron_repro.mjs`, no repo imports):
  - `cronNextAfter("15 0 * * 1", 2026-03-02T05:15Z, "America/New_York")` → skip: `2026-03-16T04:15Z`; naive: `2026-03-09T04:15Z` (a whole week lost).
  - `cronNextAfter("0 0 1 * *", 2030-02-28T23:00Z, "Europe/Berlin")` → skip: `2030-04-30T22:00Z` (1 May); naive: `2030-03-31T22:00Z` (1 April) — the monthly run is skipped.
  - `cronPrevOnOrBefore("30 23 * * 6", 2026-03-08T14:00Z, "America/New_York")` → skip: previous week's Saturday; naive: last night.
- Impact: workflow `cron_schedule` timers (`timer-schedule.ts:291`, re-armed via `cronNextAfter`) silently skip an occurrence once a year for any date-sparse schedule firing in the first local hour after midnight following the transition day (weekly-Monday-00:xx in US/EU zones every year; monthly-1st-00:00 whenever the 1st follows the transition Sunday). Job scheduler (`scheduledJobsDue` → `cronPrevOnOrBefore`) is affected only when the scheduler was not running during the 23:xx window, so impact is lower. The shipped packs all declare UTC, so no shipped declaration is hit; tenant-authored manifests are.
- Test gap: the "equivalent to naive search" suite (`cron.test.ts:231-288`) uses sparse expressions only on days 1/15/29/31 and no weekly-sparse expression; none lands in the affected hour, so it passes while the property it claims is false.
- Fix: after a skip, re-read the fields and clamp to the actual local-day boundary (step back/forward minute-wise until the date changes), or compute the boundary via the zone offset.
- Effort: S

### R14-06 [High] [CONFIRMED] [Reachability] The orchestration engine is unreachable for any useful purpose in the deployed binary
- Where: callers of `.startInstance(` in non-test code: only `engine.ts:1216` (child spawn). Callers of `.submitSignal(`: `engine.ts:1400` and `packages/workflow-signal-bridge/src/bridge.ts:116`; no `package.json` in `apps/` or `packages/` depends on `workflow-signal-bridge`. `apps/operate-server/src/node.ts:2305-2322` builds the engine and mounts **only** `buildWorkflowCancellationRoutes`. No route publishes a definition, starts an instance, sends a signal or takes a manual action. The engine is built with `createDefaultRegistry()` (`workflow-runtime-pg/src/persistent-engine.ts:64`) = a no-op `audit_emit` and an echo `transformation` handler; every other activity kind resolves to `unsupportedHandler` (`engine.ts:1610-1615`).
- Impact: instances cannot come into existence, so cancellation always answers `unknown_instance` and the three `--workflow-workers` poll empty queues. All workflow correctness properties are untested in production by construction.
- Fix: product decision; minimum is start/signal/manual-action routes plus a real activity registry.
- Effort: L

### R14-08 [Medium] [LIKELY] [Concurrency] Sequence allocation is read-then-append with no retry; a lost race after a handler ran strands the activity
- Where: every append in `engine.ts` (`latestSequence` then `appendEvent`, e.g. `:553-555`, `:968-972`, `:1621-1625`, `:1671-1677`). In-memory log throws on a mismatch (`event-log.ts:17-23`); the pg log relies on a unique `(instance, sequence)` key (out of scope, seen referenced in `persistent-engine.ts:33-34`).
- Evidence: `runActivityHandler` appends `activity_started`, awaits the handler (side effect happens), then reads `latestSequence` and appends the outcome. If a timer fire / signal / second worker appended in between the read and the insert, the outcome append throws; nothing catches or retries. `executeScheduledActivity` then treats the activity as already started (`engine.ts:1823-1832`) and returns `executed:false` forever.
- Impact: side effect performed, no completion recorded, no transition, instance stuck in `waiting_for_activity`; in-process there is also no per-instance mutex, so `tickTimers` and `submitSignal` on one instance interleave across awaits.
- Fix: per-instance serialisation (advisory lock/`SELECT … FOR UPDATE` on the instance row) or optimistic retry of the append with re-evaluation.
- Effort: M

### R14-09 [Medium] [CONFIRMED] [Declared-not-implemented] Large parts of the definition contract are accepted at publication and ignored or refused at run time
- Guards: `expression` and `abac_check` **throw** in the only evaluator the server uses (`transitions.ts:54-58`; no `guardEvaluator` is passed in `persistent-engine.ts:62-74`). The throw escapes `runStepLoop`/`submitSignal` mid-append sequence, leaving a partial log (e.g. `signal_received` without `signal_consumed`). `role_required` is always false because the engine never passes `principalRoles` (`engine.ts:583-589, 725-731, 1047-1053, 1700-1706`).
- `manual_action` trigger / `manual_approval` state / `requiredRole` / `requiresFourEyes` (`definitions.ts:126-131`): no engine method applies a manual action; `manual_action_taken` is never emitted (only projected, `projection.ts:396`). An instance entering such a state waits forever.
- `onExitActions` (`definitions.ts:222`): never executed (`applyTransition`, `engine.ts:1062-1105`, runs pre, post and the new state's on-entry only).
- `emit_event`, `audit_log` actions: explicit no-ops (`engine.ts:1123-1127`).
- `slaSeconds`, definition `timeoutSeconds` / instance `timeoutAt`: computed and stored (`engine.ts:423-425`) but `isInstanceTimedOut` has no caller anywhere; activity timeouts likewise (`isActivityTimedOut` no caller; the engine imposes no timeout on `await handler(...)`, `engine.ts:1646`). A hung handler blocks its worker/request indefinitely.
- `parallel_fork` / `parallel_join` / `decision` state kinds: no semantics (single `currentState`).
- `instance_suspended`/`instance_resumed`, `compensation_step_completed`: projected, never produced.
- `activity_timed_out`: no retry and no transition is evaluated (`engine.ts:1763-1783`); there is no `activity_timed_out` trigger kind.
- `child_workflow_completed` is only raised when the child finishes synchronously inside `spawn` (`engine.ts:1250-1257`); a child that parks and finishes later never notifies its parent.
- `variables[].required/type/defaultValueJson` (`definitions.ts:238-245`): `startInstance` neither validates nor applies defaults (`engine.ts:452`).
- `business_hours` timer kind: refused at publication (`definitions.ts:583-589`) — honest, but a declared enum member no deployment can use.
- `compensationStrategy: "parallel"` runs sequentially in insertion order (`engine.ts:1923`).
- Impact: a reviewer approving a definition is approving behaviour the runtime will not perform; several of these fail as hangs rather than refusals.
- Fix: refuse at publication everything the runtime cannot serve (the pattern already used for `business_hours`), or implement.
- Effort: M (refuse) / L (implement)

### R14-10 [Medium] [CONFIRMED] [Performance/Unbounded growth] Full-log re-read and re-fold per step; no snapshot, compaction or continue-as-new
- Where: `engine.ts:990-1000` (`getInstanceState` = `listByInstance` + `projectInstance`), called in every loop iteration and before/after every action (`:1017`, `:723`, `:742`, `:1528`, `:1616`, `:1694`…), plus `latestSequence` before each append and `outstandingTimers` (another full read, `:759-761`, called inside a loop at `:821`). The pg wrapper additionally re-reads the log and upserts every activity/signal/timer row on each append (`workflow-runtime-pg/src/projecting-event-log.ts:86-124`, read for context).
- Evidence of growth: a cron timer re-arms on the same instance forever (`engine.ts:741-753`); `WorkflowTimerSchema` allows `fireCount` up to 1,000,000 and events up to sequence 1e9 (`timers.ts:51`, `history.ts:97`). Each fire appends ≥2 events and costs O(history). A per-minute cron instance reaches ~1M events/year with quadratic total cost.
- Also unbounded in-process: `instanceTenant` / `instanceCorrelation` maps never evict (`engine.ts:381-382`, `:427-430`); `InMemorySignalDeduplicator.seen` never evicts (`:307`).
- Fix: cached projection keyed by sequence, incremental fold, history cap with continue-as-new.
- Effort: M

### R14-11 [Medium] [CONFIRMED] [Correctness] Signal routing and timer ticking depend on an in-process registry that is empty after restart
- Where: `engine.ts:519-522` (`for (const [instanceId, tenantId] of [...this.instanceTenant])`), `:655`; populated only by `startInstance` (`:427`) and `registerInstance` (`:2278`), which has no caller in the workspace.
- Impact: after a process restart or on a second replica, `submitSignal` matches nothing and `tickTimers` fires nothing, with no error — while the doc on `SignalDeduplicator` (`:277-286`) reasons carefully about restarts and replicas. The "exactly_once_idempotent" guarantee is moot when delivery itself is process-local. Also O(all instances) per submit.
- Fix: resolve targets by `(tenant, correlation_key)` from the store.
- Effort: M

### R14-12 [Medium] [CONFIRMED] [Correctness] `fireDueTimersForInstance` iterates a stale snapshot
- Where: `engine.ts:685-754`.
- Evidence: `scheduled` is read once; inside the loop each fired timer may run a transition that cancels another timer (`cancel_timer`), completes the instance, or requests cancellation, but the next iteration neither re-reads outstanding timers nor re-checks status/fence. A timer cancelled by the first fire still gets a `timer_fired` (after its `timer_cancelled`), and a `timer_fired` + transition evaluation can follow `instance_completed`.
- Impact: contradicts "an already-`timer_cancelled` timer is not in the scheduled set" (`:668-669`) when two timers are due in one pass (i.e. whenever a worker is late); log contains fired-after-cancelled.
- Fix: re-derive outstanding timers and status each iteration.
- Effort: S

### R14-13 [Medium] [CONFIRMED] [Robustness] Automatic-transition loop guard throws without recording failure; no publication-time cycle check
- Where: `engine.ts:50` (`MAX_STEP_ITERATIONS = 1000`), `:1012-1060`. `WorkflowDefinitionSchema` (`definitions.ts:387-621`) does not detect automatic cycles or self-transitions; `findUnreachableStates` (`:624`) has no production caller.
- Evidence: a 2-state automatic ping-pong appends 1,000 `state_transitioned` (+ on-entry action events, each re-folding the log) and then `throw new Error("step loop … exceeded")`. No `instance_failed` is appended, so the instance stays `running` with ≥1,000 events; any later trigger repeats the 1,000 iterations. A self-transition (`fromState === toState`) is accepted by the definition schema but its event violates `WorkflowEventSchema` ("state_transitioned event must change state", `history.ts:123-128`).
- No test exercises the iteration cap (`grep exceeded engine.test.ts` → only child depth).
- Fix: fail the instance on cap; reject automatic cycles without a guard and self-transitions at publication.
- Effort: S

### R14-14 [Low] [CONFIRMED] [Robustness] Activity retry: thrown errors never retry; inline retries recurse and ignore backoff; `maxAttempts` unbounded
- Where: `engine.ts:1658-1664` (`HANDLER_EXCEPTION`, `retryable: false`); `:1741-1747` (retry → `scheduleActivity` → `runActivityHandler` recursion; `availableAt` only matters in deferred mode); `:1493-1496` (`maxAttempts` any number ≥1 from an untyped `parameters` bag, while `WorkflowActivitySchema` caps it at 50, `activities.ts:115-116`).

- Fix: validate `schedule_activity` parameters with a schema; honour backoff inline or refuse it.
- Effort: S

### R14-15 [Low] [CONFIRMED] [Performance] 6-field cron in a non-UTC zone costs up to 86,400 `Intl.formatToParts` calls per evaluation

## Verified strengths (things that are genuinely done well, with file:line)
- Cancellation is carefully designed and fenced at four driver points with the fence as an *event* (`engine.ts:677`, `:1021`, `:528`, `:1529/1620`); late handler reports cannot resurrect a cancelled instance (`projection.ts:148-151`, `:537-544`). 22+ dedicated tests.
- Signal dedup asks the instance's own log before appending (`engine.ts:540-550`, `priorReceiptSignalId` `:112-124`), and refuses an `exactly_once_idempotent` signal with no key before writing (`:635-649`).
- Timer scheduling is a total map over kinds with named refusals instead of substituted instants (`timer-schedule.ts:61-75`, `:166-232`); recurring timers re-arm only while the instance can act (`engine.ts:741-753`).
- Cron: impossible dates are separated from "not found" analytically (`cron.ts:384-391`); unresolvable time zones are refused at parse (`types.ts:107-128`); `Intl` formatter cached with a bounded map (`cron.ts:116-142`). Regex is linear (no catastrophic backtracking).
- Job cancellation contract states a bounded, honest promise (`cancellation.ts:45-55`) and the plan function orders terminal → already-requested → lease correctly (`:113-125`).
- Child-spawn and signal-dispatch recursion are bounded with named errors (`engine.ts:57-60`, `:1206-1214`, `:1383-1390`).
- `InMemoryEventLog.append` enforces dense monotonic sequences (`event-log.ts:16-23`).
- No TODO/FIXME, no `any`, no swallowed errors except the documented `scheduledTriggerDefects` catch (`cron.ts:420-424`).

## Claims vs reality (docs/README/CLAUDE.md/comments that the code contradicts)
- `cron.ts:283-296`: "Skipping is therefore equivalence-preserving by construction … never a missed match" — false across DST spring-forward (R14-05).
- `engine.ts:1860-1866` / CLAUDE.md "saga compensation planning … over the completed side-effect activities": planner includes non-completed, failed, cancelled and every retry attempt (R14-01). "idempotent — an activity that already carries an `activity_compensated` is dropped" is true but is exactly what makes a failed compensation permanent (R14-02).
