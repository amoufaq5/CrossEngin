# R12 — AI surface (ai-providers*, ai-router, ai-architect*, ml-training, architect-cli, operate-server ai-design/design-review/manifest-diff)
## Summary (10 lines max)
- The "AI" is two call sites: a one-shot prose→manifest generator behind `--ai-design` (operate-server) and a developer CLI chat with 4–6 tools. No runtime AI on business data, no RAG/embeddings/vector store, no agents on records, no evals, no training.
- Model output is properly zod- and kernel-validated before persistence (genuine strength); the server model has no tools, so prompt injection there is limited to shaping the proposal.
- CLI tools are not path-confined: `read_file` exfiltrates any json/yaml/txt/md on disk to the vendor (R12-01); write approval shows only entity counts (R12-02/03); the "hard refusal" guard is bypassable (R12-04).
- Review integrity: diff/schema/risk views omit role `inherits`, ABAC, phi→pii downgrades, traits and 11 of 16 manifest sections; diff fails open (R12-10). Default is single-user self-activation with no author recorded (R12-11).
- Cost controls are largely claimed, not wired: per-request ceiling/stream meter/inflation store are unreachable (R12-05); monthly budget is racy and $0 for proxied/local models (R12-06/07); no HTTP timeouts or cancellation (R12-08).
- Two of four CLI provider modes cannot complete a turn (R12-09). Model lists/prices hard-coded and stale; Opus priced 3× high (R12-15).
- A credential-shaped Anthropic string is committed in deploy/.env.example:117 (R12-20, unverified).
- AI code ≈12.7k LOC (≈5.7% of non-test TS); ≈4.7k on a live LLM path. Verdict: thin, well-validated wrapper; the defensible asset is the deterministic manifest compiler, not the AI.
## Findings

### R12-01 [High] [CONFIRMED] [Security / prompt-injection → file read] CLI `read_file` tool is not confined to any directory; reads any .json/.yaml/.yml/.txt/.md on the machine and ships it to the LLM vendor
- Where: apps/architect-cli/src/tools.ts:148-164, 210-237
- Evidence: `const absolute = resolve(rootDir, path);` followed only by `isExtensionAllowed(absolute)`; there is no `startsWith(root)` / realpath / symlink check. The tool's own schema advertises it: `description: "Relative or absolute path to the file."` (tools.ts:158). `fileRootDir` is never passed by the only caller (commands.ts:451-455), so root = `process.cwd()`, and `resolve(cwd, "/etc/x.json")` or `"../../x.yaml"` escapes it.
- Impact: any untrusted text that reaches the conversation (a manifest/README the model was asked to read, a tool result, a pasted customer brief) can instruct the model to call `read_file` on e.g. `~/.config/gcloud/application_default_credentials.json`, `~/.docker/config.json`, `~/.aws/sso/cache/*.json`, `~/.npmrc`-adjacent json, k8s `*.yaml` kubeconfigs, service-account key files. Contents (≤1 MiB each, 5 tool iterations/turn) enter the prompt and are sent to Anthropic/OpenAI, are echoed to stdout, and with `--persist` are stored verbatim in `meta.architect_messages` / `architect_tool_invocations`. Gated only by the operator having passed `--allow-file-read`; there is NO per-read approval.
- Fix: resolve + `realpath`, require the result to be inside `fileRootDir` (reject absolute/`..`), deny dotfiles and symlinks, add a per-read confirmation or an allow-list glob.
- Effort: S

### R12-02 [High] [CONFIRMED] [Security / human-in-the-loop is not informed] CLI write approval shows only entity counts; permissions / classification / roles / workflows changes are invisible to the approver
- Where: apps/architect-cli/src/chat.ts:422-443; apps/architect-cli/src/tools.ts:33-42, 301-315
- Evidence: the approval prompt is literally `[propose_manifest_edit] ${action} ${req.path}\n  hash: …\n  entities: +N -N ~N\nApply? [y/N]`. `WriteApprovalRequest` carries only `{path,isNew,newHash,diffSummary:{entitiesAdded,entitiesRemoved,entitiesModified}}`. The tool description sent to the model claims "The user is shown the diff against any existing file" (tools.ts:172) — false.
- Impact: an injected or hallucinated edit that changes ONLY `permissions`, `roles`, field `classification` on a non-phi class (e.g. pii→public), `workflows` transitions/guards, `jobs`, `integrations` shows as `entities: +0 -0 ~0` (or ~1) and a hash. A human cannot evaluate it. The only automatic backstop is `classifyManifestEditRefusal` (R12-04), which covers two narrow cases.
- Fix: render the full structured diff (reuse operate-server `manifest-diff.ts`, extended per R12-10) or a unified JSON diff before the y/N.
- Effort: S-M

### R12-03 [Medium] [CONFIRMED] [Security / file write] `propose_manifest_edit` path is unconfined (absolute / `..`), can overwrite any `*.json` on disk; `--auto-approve-writes` removes the human entirely
- Where: apps/architect-cli/src/tools.ts:244-250, 284, 324-326; commands.ts:436-438
- Evidence: `const absolute = resolve(rootDir, pathRaw);` … `await writeFile(absolute, JSON.stringify(proposed, null, 2) + "\n", "utf8");`. Only check is `.endsWith(".json")`. `loadExistingManifest` returns `null` when the existing file is not a manifest (tools.ts:364-365), so the overwrite of e.g. `package.json`/`tsconfig.json`/`~/.docker/config.json` is presented as `CREATE` (isNew=true) and the refusal check is skipped (`current === null → return null`, refusal.ts:13).
- Impact: content is constrained to a schema-valid manifest, so this is destructive overwrite (DoS / config clobber, e.g. replacing a deployed `--manifest-file`), not arbitrary code write. With `--auto-approve-writes` (required for one-shot mode) a prompt-injected model writes with no human. Note `isNew` mislabel: overwriting a non-manifest JSON is displayed as CREATE.
- Fix: confine to root; refuse to overwrite a file that exists but is not a manifest; show old-file presence truthfully.
- Effort: S

### R12-04 [Medium] [CONFIRMED] [Security / guardrail gap] The CLI's only automatic "hard refusal" is trivially bypassable
- Where: apps/architect-cli/src/refusal.ts:9-64
- Evidence: (a) `if (current === null) return null;` — a new path or a non-manifest existing file skips everything; (b) audit-disable only fires `if (!isPackBound(proposed)) return false` — the PROPOSED manifest decides, so dropping `meta.extends`/`compliancePacks` in the same edit disables the check; (c) both detectors `continue` when the entity or field is absent in the proposal (`if (now === undefined) continue;`, `if (af === undefined) continue;`) — rename/delete+re-add the field or entity unclassified and it passes; (d) reads `before.fields` / `now.fields` raw, never `resolvedFields`, so trait-carried phi is not seen (refusal.ts:53-54); (e) nothing examines `permissions`, `roles`, per-field grants, or pii/commercial_sensitive downgrades; (f) the refusal is returned to the model only — `tenantId: "cli"`, `attemptedAt: "1970-01-01…"` (refusal.ts:75-83), nothing is audited despite `auditSeverity: "P0"`.
- Impact: the guardrail gives a false sense of safety; the remaining defence is R12-02's uninformative y/N.
- Fix: evaluate on resolved fields, treat removal/rename of a protected field as weakening, key pack-bound on `current`, add permission-widening detection, and persist the refusal.
- Effort: M

### R12-05 [High] [CONFIRMED] [Cost control / claims-vs-reality] The per-request cost ceiling, the stream cost meter and the durable "inflation" estimator are wired to nothing in the deployed server — `--ai-max-request-dollars` is a no-op
- Where: apps/operate-server/src/node.ts:2667-2675 (designer built), 2716-2722 (flag routed only into the budget object); apps/operate-server/src/ai-design.ts:427,438-439,485-486,520
- Evidence: node.ts builds the designer as `buildDesignDesigner({ provider, model, providerLabel, ensureRoles: options.aiDesignRoles })` — no `maxRequestDollars`. `options.aiMaxRequestDollars` goes only to `buildAiDesignBudget({... maxUsdPerRequest })`, and `grep -rn "maxUsdPerRequest|inflationFor|observeInflation|onInflationObserved"` over non-test sources finds readers only inside ai-design.ts / ai-design-budget.ts themselves — nothing reads `budget.maxUsdPerRequest`, nothing calls `budget.inflationFor()` or passes `inflation` / `onInflationObserved` to `designManifest`. `buildDesignDesigner` (ai-design.ts:822-851) does not even accept `inflation`. Consequently in production `ceiling === null` (ai-design.ts:485), `meter === null`, `admitRequestCost`/`StreamCostMeter`/`reconcileRequestCost` never execute, and `meta.architect_estimate_inflation` (PostgresEstimateInflationStore, constructed at node.ts:2710) is never read or written.
- Impact: the operator-facing flag documented as "Per-REQUEST USD ceiling, refused before the call" (cli.ts:2466) silently does nothing; ~900 LOC of cost machinery (request-cost.ts, script-tokens.ts, inflation.ts, inflation-store.ts) and two ADRs' worth of claims (0311, 0330) are test-only. The only live ceiling is the monthly one (R12-06).
- Fix: thread `budget.maxUsdPerRequest`, `budget.inflationFor(tenant)` and `budget.observeInflation` into the per-call designer (needs tenant id in `ManifestDesigner` input); add an integration test that boots the wiring.
- Effort: S

### R12-06 [Medium] [CONFIRMED] [Cost control] Monthly AI budget is check-then-spend with no reservation, no concurrency cap and no per-tenant rate limit; the charge is best-effort
- Where: apps/operate-server/src/ai-design-routes.ts:180-195, 227-246; ai-design-budget.ts:133-172; design-runner.ts:184-190; ai-design-routes.ts:420 (`rateLimitPolicyId: null`)
- Evidence: `budget.check(tenant)` reads spend, then the LLM call runs (up to 3 attempts × 8192 output tokens), then `budget.record`. Nothing is reserved. `POST /v1/ai/design/jobs` returns 202 immediately and `startJob` is fire-and-forget, so a tenant admin can enqueue N jobs in a loop while spend is still $0 — all N pass. `record()` swallows store errors: "the unrecorded dollars are simply not charged" (ai-design-budget.ts:166-171). Every AI route has `rateLimitPolicyId: null`.
- Impact: a single `erp_admin` credential can overshoot the $25 default ceiling by an arbitrary multiple (bounded only by provider rate limits): e.g. 500 concurrent jobs × 3 attempts × ~$0.13 (Sonnet 8k out) ≈ $200 before the first `record`. Also an unauthenticated-cost DoS on a self-hosted GPU (cost is 0, so no ceiling at all — R12-07).
- Fix: reserve an estimate atomically (`UPDATE … WHERE spent + est <= limit`), cap in-flight jobs per tenant, attach a rate-limit policy.
- Effort: M

### R12-07 [Medium] [CONFIRMED] [Cost control] Any OpenAI-compatible paid proxy (OpenRouter, Azure, LiteLLM) and every local model is priced at $0, so the budget never trips
- Where: packages/ai-providers-openai/src/pricing.ts:69-71 (`if (pricing === undefined) return 0;`), provider.ts:135-140 (`UNKNOWN_MODEL_PRICING` all zeros); apps/operate-server/src/ai-design.ts:912-924; ai-design-routes.ts:193 (`result.usage.cost > 0`)

- Effort: S

### R12-08 [Medium] [CONFIRMED] [Reliability] No timeout and no cancellation on any LLM HTTP call; "aborting" a stream does not stop the upstream generation
- Where: packages/ai-providers-anthropic/src/provider.ts:100-104; ai-providers-openai/src/provider.ts:159-163; ai-providers-local/src/provider.ts:118-122; */streaming.ts `readSseStream` (anthropic :180-220)
- Evidence: every `fetchImpl(url, {method, headers, body})` omits `signal`, although `FetchLike` declares it; `CompletionRequest` has no abort field. `readSseStream` does `const reader = body.getReader(); while (true) { await reader.read() … }` with no `try/finally { reader.cancel() }`. When `designManifest` `break`s out of `for await` on `overCost`/`oversized` (ai-design.ts:616-622) the generator is returned but the body reader is never cancelled.
- Impact: a hung provider/Ollama pins a synchronous `POST /v1/ai/design` request (and its gateway slot) indefinitely; async jobs stay `running` forever. The "abandon the stream at the ceiling" behaviour stops reading but (LIKELY — depends on undici GC) does not close the socket, so the vendor keeps generating and billing up to `max_tokens`.
- Fix: per-request `AbortController` with a deadline; `finally { await reader.cancel() }`; plumb `signal` through `CompletionRequest`.
- Effort: S

### R12-10 [High] [CONFIRMED] [Security / review integrity] The reviewer-facing diff, schema view and risk score omit several permission-bearing parts of a manifest — an approved proposal can widen access unseen
- Where: apps/operate-server/src/manifest-diff.ts:341-363 (`grantMap`), 655-666 (roles), 310-335 (`classificationLayer`), 442-449 (`lifecycleIndex`), 725-740 (fail-open); apps/operate-server/src/design-review.ts:139-160, 231-235, 319-326; design-review-routes.ts:135-140 (role view shape); packages/auth/src/roles.ts:21, rbac.ts:74-98
- Evidence (each traced):
  1. **Role inheritance is invisible everywhere.** `RoleDefinitionSchema` has `inherits` (packages/auth/src/types.ts:12) and `rbacCheck` authorises on `resolveEffectiveRoles` (rbac.ts:74,98). The diff only computes `rolesAdded/rolesRemoved` by key (`missingFrom(nextRoles, activeRoles)`); the role view is `{name,label,description,grantCount}`; the risk report counts only direct grants and even says of an inheriting role "declared but granted nothing, so assigning [it] would give a user no access" (design-review.ts:319-326) — false when the role `inherits` an admin role. `ensureRolesInManifest` guarantees the operator roles (`erp_admin`, `platform_admin` by default, cli.ts:1951) exist with every CRUD grant, so `roles: { viewer: { name:"viewer", inherits:["erp_admin"] } }` is schema-valid, shows as a `low` "unreferenced_role", and yields full access.
  2. `grantMap` reads `grant.roles` only: adding/removing an `abac` obligation on a grant, and the per-field `create` arm (`permissions.fields[x].create`), are never diffed (only `.read`/`.update`, lines 358-361).
  3. Classification moves *between* sensitive classes produce no warning: `phi → pii` (which drops at-rest encryption and the auditable requirement) falls through both branches at 568-582 because `isSensitive` is true on both sides.
  4. Not compared at all: `traits` (custom trait field definitions, incl. their classification — `classificationLayer` iterates `entity.fields` only), entity `traits` membership (dropping `auditable`), `meta.extends` / `meta.compliancePacks`, `jobs`, `integrations`, `views`, `reports`, `dashboards`, `files`, `search`, `i18n`, `theme`, `customWidgets`, field `unique`/defaults, orchestration/scheduled workflows, and lifecycle transition `from`/`to`/guards (only state and transition *names* are compared, 496-499). 5 of 16 manifest sections are covered.
  5. Fail-open: `diffManifests` returns `emptyView()` (`comparable:false, impact:"none"`, zero warnings) when either manifest fails to parse or `compare` throws — "Activation review must never fail closed on a diff" (735-738). A reviewer sees "nothing to compare", not "diff failed".
  6. First activation (`active === null`, the common AI case) has no diff at all; the tenant-side `GET /v1/ai/manifests/{id}` returns no risk report (ai-design-routes.ts:305-310) — risk is only on the platform route.
- Impact: the human-approval control is weaker than it reads. A hallucinated or steered manifest can (a) hand a low-privilege role full access through `inherits`, (b) silently drop an ABAC condition, (c) downgrade phi→pii, (d) move sensitive fields into a custom trait — and the reviewer's three aids (diff, schema, risk) show none of it. Exploit requires either a model error or a description that asks for it; the description author is the tenant's own admin, so against the *platform reviewer* this is an integrity bypass, against the tenant it is an undetected mis-design.
- Fix: diff on the resolved manifest (traits resolved, role closure expanded into effective grants per entity/op), include `abac` and all three field arms, treat any classification change as a warning, add a generic "other sections changed" JSON-hash diff for the 11 uncovered sections, and return an explicit `diff_failed` state.
- Effort: M

## What the AI does for an ERP user — plainly
- EXISTS: (a) one-shot generation of a *schema-level* manifest (entities, fields, relations, roles, CRUD permissions) from ≤4000 chars of prose, validated by zod + kernel cross-validation, stored as a proposal, optionally reviewed, then activated as the tenant's live schema; (b) a developer CLI chat that can validate/hash/diff/summarise manifests and, behind flags, read files and write a manifest file.
- The server prompt never mentions workflows, lifecycles, views, jobs, reports, traits or `extends`, so the generated system is CRUD tables + role grants; it cannot extend the built-in ERP packs. Output is capped at `maxTokens = 8192` (ai-design.ts:162) — roughly a dozen entities before `truncated_json`, whose scripted retry is "Produce a smaller manifest — fewer entities and fewer fields per entity" (ai-design.ts:331).
- There is no iterative "change my existing system" path on the server: every design starts from the description only (no existing manifest in the prompt), and activating it replaces the active manifest.
- DOES NOT EXIST: any runtime AI over business data — no invoice/document extraction, no anomaly detection, no forecasting, no NL query, no copilot, no summarisation, no classification, no agent acting on records. No RAG, no embeddings call, no vector store (the `search` package and `files.embedding_status` are contracts with no writer). No fine-tuning/training pipeline: `packages/ml-training` (1,224 LOC) has zero importers. No model evals.

## Verified strengths (things that are genuinely done well, with file:line)
- Model output never reaches persistence unvalidated: `classifyDesignOutput` → `ManifestSchema.safeParse` → `tryValidateManifest` before `store.create` (ai-design.ts:719-801; ai-design-routes.ts:196-206); the serving path re-validates on load (tenant-gateway-cache.ts:235-250). The CLI write tool does the same (tools.ts:263-283).
- JSON extraction is careful and non-inventive: string-aware bracket balancing, fence/prose unwrapping, explicit refusal to repair truncated JSON, array-first detection so one element is not passed off as the design (packages/ai-architect-runtime/src/design-output.ts:77-216).
- The model has no tools on the server path, so tenant prose cannot cause side effects beyond the proposal row; activation is a separate authenticated call.
- Retry loop distinguishes "wrong question" from "broken output" and stops paying for the former (ai-design.ts:731-733); attempts are bounded at 3.
- Monthly budget check fails closed on an unreadable ledger (ai-design-budget.ts:138-150); the cost ledger write is an atomic upsert under tenant context (ai-architect-runtime-pg/src/cost-store.ts:54-65).
- Local-first provider resolution with a malformed local URL refusing rather than falling through to a cloud vendor (ai-design.ts:864-890).
- Provider API keys are read from env only and never logged; providers are dependency-free with injectable `fetch` (easy to test, small supply-chain surface).
- Cross-tenant review elevation is a transaction-local GUC, not a role assumption (design-review-store.ts:79, 140-148); tenant-facing stores bind `tenant_id` as a predicate as well as RLS (design-jobs.ts:183-192).
- `reviewedBy` is taken from the principal, not the body (design-review-routes.ts:388-391); a configured review gate denies `not_required` too (ai-design-routes.ts:326-337).

## Honest verdict
- Substance: a competently engineered **thin wrapper** — a single prompt + JSON validator + retry loop (≈930 LOC) on the server and a small tool-calling REPL (≈1,450 LOC) for developers, over three hand-rolled provider clients (≈2,300 LOC). The surrounding cost/guard/policy/ML packages are mostly contracts or unreachable.
- Size: AI-scoped non-test code ≈ 7,150 LOC in packages (+1,224 ml-training) + ≈4,050 in operate-server + ≈1,550 in the CLI ≈ **12.7k of ≈224k non-test TS (≈5.7%)**; code on a live LLM call path ≈ 4.7k (≈2%); prompt text totals ≈25 lines + one example manifest.
- Differentiation: the defensible asset is not the AI but the deterministic layer under it — a strict manifest schema/validator and a manifest→live-API compiler that make LLM output safe to accept. Any vendor with the same schema could reproduce the AI part in days. "AI-native ERP" overstates it: the AI authors an initial CRUD schema; it does nothing with business data at runtime.
- Lock-in: low (provider-neutral interface, OpenAI-compatible local path). Model/version management: weak (hard-coded lists, alias pinning, no evals to gate upgrades).
