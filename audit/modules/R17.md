# R17 — tenant-lifecycle, tenant-lifecycle-pg, billing, billing-runtime, billing-runtime-pg, billing-stripe

(Summary and tenant-lifecycle findings are appended below the billing findings; see the end of the file for the final Summary.)

## Findings

### R17-01 [High] [CONFIRMED] [Billing / lost usage] Periodic usage flush overwrites the day's usage row — only the last flush window of each UTC day survives
- Where: `packages/billing/src/usage.ts:52-59`, `packages/billing-runtime-pg/src/usage-store.ts:40-44`, `apps/operate-server/src/metering.ts:143-175,228-239`
- Evidence: the flush scheduler writes one record per `[lastFlush, now]` window (`metering.ts:232`), each keyed by `buildIdempotencyKey`, which truncates the period start to the **day**: `const day = input.periodStart.slice(0, 10); return \`tenant=${input.tenantId}:meter=${input.meter}:day=${day}\``. The store then does `ON CONFLICT (idempotency_key) DO UPDATE SET quantity = EXCLUDED.quantity, ...` (replace, not add), and `flushUsage` clears the in-memory bucket after each write (`metering.ts:172`). `meta.billing_usage_records.idempotency_key` is globally UNIQUE (`packages/kernel/src/bootstrap/meta-schema.ts:11088`). So with any `flushIntervalMs` shorter than 24h, flush N+1 on the same day replaces flush N's quantity with only its own window's count. The doc comment at `metering.ts:146-147` ("distinct period ⇒ distinct idempotency key") is false.
- Impact: systematic under-recording of metered usage (revenue leakage); the stored figure for a day is whatever the last window before midnight UTC happened to see. The only wired usage path in the deployed server is this one.
- Fix: key on the full period (start+end) or accumulate (`quantity = table.quantity + EXCLUDED.quantity`) with a per-flush dedup id; include `subscriptionId` in the key.
- Effort: S

### R17-02 [High] [CONFIRMED] [Billing / double-report] After an upsert the row's `id` column and the `record` JSON's `id` diverge, so `markSynced` matches nothing and the row is re-reported to Stripe forever
- Where: `packages/billing-runtime-pg/src/usage-store.ts:40-44,81-106`, `packages/billing-runtime-pg/src/stripe-sync.ts:66-85`
- Evidence: `record()` mints a fresh `id` per flush (`metering.ts:166`), but the `ON CONFLICT ... DO UPDATE` sets `record = EXCLUDED.record` and **not** `id`. `listUnsynced` returns `rowToRecord(row.record)` (the JSON, carrying the *new* id); `markSynced` runs `UPDATE ... WHERE id = $1 AND synced_to_stripe_at IS NULL` against the *column* (the first insert's id) → 0 rows, no error (result is not checked). The row therefore stays unsynced and is re-sent on every `syncOnce` (default hourly, `apps/operate-server/src/stripe-usage-sync.ts:21`). `createUsageRecord` defaults to `action: "increment"` (`packages/billing-stripe/src/client.ts:136`). Stripe's Idempotency-Key only protects for ~24h and rejects the same key with different parameters (quantity changes per R17-01), so the sync either errors every hour or, after the key expires, increments the customer's usage again.
- Impact: over-billing of tenants via Stripe (repeated `increment`s) and/or a permanently failing sync; combined with R17-01 the Stripe figure has no defined relationship to real usage.
- Fix: never regenerate ids on conflict (`RETURNING id`), mark synced by `idempotency_key`, check `rowCount`, use `action: "set"` for per-period totals.
- Effort: S

### R17-03 [High] [CONFIRMED] [Billing / durability] Metered usage lives only in process memory between flushes; lost on crash/restart, wrong with >1 replica, and the dedup set grows without bound
- Where: `packages/billing-runtime/src/meter.ts:24-48`, `apps/operate-server/src/metering.ts:110-123`, `apps/operate-server/src/node.ts:4344`
- Evidence: `UsageMeter` holds `buckets` (Map) and `seen = new Set<string>()`; `record()` adds every request id to `seen` and nothing but `reset()` (no non-test caller) ever removes one. Shutdown calls `metering?.flushScheduler?.stop()` only — no final `flushOnce()`. `flushIntervalMs` is optional ("omit to flush only on demand") and no on-demand caller exists in `apps/`.
- Impact: every deploy/crash loses up to one interval of billable usage; a long-running server leaks one string per metered request (unbounded heap); two replicas each write their own partial quantity to the same idempotency key (last writer wins, R17-01).
- Fix: persist usage events (append-only table with unique event key) and aggregate in SQL; flush on shutdown; bound/evict `seen`.
- Effort: M

### R17-04 [High] [CONFIRMED] [Billing / reachability] Invoicing, rating, tax, proration, dunning, credits, refunds are not reachable from any deployed entry point; the platform never produces an invoice
- Where: `packages/billing-runtime/src/engine.ts:86` (`closePeriod`), `packages/billing-runtime-pg/src/persisting-engine.ts:39`, `packages/billing-runtime-pg/src/invoice-store.ts:75`
- Evidence: `grep -rn "closePeriod|PostgresInvoiceStore|invoiceStore|computeTax|prorateUpgrade|nextDunningStage|applyCredit|rollupUsage|isInvoiceOverdue"` over `apps/` and non-billing `packages/` (non-test) returns only `apps/operate-web/lib/period-close.ts:87`, an unrelated ERP fiscal-period function. `node.ts` uses only `buildRequestMetering` (usage flush), `buildStripeUsageSync`, `StripeClient.createBillingPortalSession` and the webhook → `billing_subscriptions` snapshot.
- Impact: "billing" as deployed = Stripe-hosted subscription + a usage counter with the defects above. `meta.invoices` is never written; no dunning, no tax, no credit notes, no reconciliation between local records and Stripe (the `stripeInvoiceId` field is never populated anywhere). Consequently the statutory-retention carve-out for `meta.invoices`/`meta.tenant_credits` in the Article 17 erasure protects empty tables.
- Fix: decide whether Stripe is the invoicing system of record (then delete the local invoice model) or wire and harden it.
- Effort: L

### R17-05 [Medium] [CONFIRMED] [Billing / correctness] Fractional usage makes `closePeriod` throw: overage cents are not rounded but the line schema requires integers
- Where: `packages/billing/src/plans.ts:142-144`, `packages/billing-runtime/src/rating.ts:41-47`, `packages/billing/src/invoices.ts:41`
- Evidence: `overageCents = billableUnits * metered.perUnitCents` with `usedUnits` a float (`UsageRecordSchema.quantity: z.number().nonnegative()`, `storage_gb_month` is inherently fractional, `quantityPerRequest: z.number().positive()`); the result is passed to `InvoiceLineItemSchema.parse({ amountCents: rated.overage.overageCents })` where `amountCents: z.number().int()`. e.g. 10.5 GB × 3¢ = 31.5 → ZodError. The throw happens inside `hasBillableUsage` (`invoicing.ts:91`) before buckets are cleared, so the period can never be closed.
- Impact: latent (closePeriod unreachable, R17-04); if wired, any tenant with non-integer usage is un-invoiceable. Also no rounding rule is defined for money at all on this path.
- Fix: round explicitly (declared rule, e.g. half-up per line) in `computeOverage`.
- Effort: S

### R17-06 [Medium] [CONFIRMED] [Billing / invoice immutability] `PostgresInvoiceStore.upsert` rewrites totals, line items and status of an existing invoice with no status guard
- Where: `packages/billing-runtime-pg/src/invoice-store.ts:89-99`
- Evidence: `ON CONFLICT (tenant_id, number) DO UPDATE SET status = EXCLUDED.status, subtotal_cents = ..., total_cents = ..., line_items = EXCLUDED.line_items, paid_at = ..., voided_at = ...` — unconditional; an `open`/`paid` invoice re-drafted under the same number becomes `draft` with new amounts. No `INVOICE_TRANSITIONS` map exists in `packages/billing/src/invoices.ts` at all (statuses are a bare enum).
- Impact: issued tax invoices are mutable in place (no audit trail, no credit-note discipline); a period closed twice silently replaces the first invoice. Latent today (R17-04).
- Fix: `DO UPDATE ... WHERE invoices.status = 'draft'`, throw on refused write; add a transition map.
- Effort: S

### R17-07 [Medium] [CONFIRMED] [Billing / atomicity] Period close is not atomic and clears in-memory usage before anything is persisted
- Where: `packages/billing-runtime/src/engine.ts:121-123`, `packages/billing-runtime-pg/src/persisting-engine.ts:39-46`
- Evidence: `engine.closePeriod` does `this.meter.clearSubscription(...)` (default `clearAfter !== false`) and returns; only then `await this.usageStore.recordMany(...)` (one transaction **per record**, `usage-store.ts:62-64`) and `await this.invoiceStore.upsert(...)` in a third transaction. Any DB failure loses the period's usage irrecoverably; a failure between the two leaves usage rows with no invoice.
- Impact: lost revenue / inconsistent books on a transient DB error. Latent (R17-04).
- Fix: one transaction; clear buckets only after commit.
- Effort: S

### R17-08 [Medium] [CONFIRMED] [Tenant isolation] Every billing store read/write relies on RLS alone — no `tenant_id` predicate — so on an owner connection (RLS bypassed) they are cross-tenant
- Where: `packages/billing-runtime-pg/src/usage-store.ts:72-73,84-85,101-103,117-118`, `packages/billing-runtime-pg/src/invoice-store.ts:130,141`
- Evidence: `SELECT record FROM meta.billing_usage_records WHERE synced_to_stripe_at IS NULL ORDER BY recorded_at ASC LIMIT $1`; `SELECT * FROM meta.invoices WHERE number = $1 LIMIT 1`; `SELECT * FROM meta.invoices ORDER BY issued_at DESC LIMIT $1` (`listByTenant` — the tenant argument is used only for `set_config`). The repo's own convention (CLAUDE.md, ADR-0331/0333) states a table owner bypasses RLS and that the shipped compose connects as owner. `syncTenant(tenantA)` therefore lists every tenant's unsynced usage; `listByTenant(A)` would return every tenant's invoices.
- Impact: today limited (the sync resolver is keyed by subscription id, the invoice store is unwired), but it is a cross-tenant financial-data read the moment an invoice route is added. This package was missed by the repo's own "owner-dependent reads" sweep.
- Fix: add `tenant_id = $n` to every statement.
- Effort: S

### R17-09 [Medium] [CONFIRMED] [Stripe client] No API-version pin, no timeout, no retry, and idempotency keys on only one of four mutating calls
- Where: `packages/billing-stripe/src/client.ts:76-110,148-170`
- Evidence: `request()` sends only `authorization` (+ optional `idempotency-key`, `content-type`); there is no `Stripe-Version` header anywhere in the package (`grep -ri "stripe-version" packages/billing-stripe` → none). `fetchImpl(url, { method, headers, body })` passes no `signal`, so a hung connection blocks forever (and `syncTenant` is sequential). `createCustomer`, `createSubscription`, `cancelSubscription`, `createBillingPortalSession` pass no idempotency key; only `createUsageRecord` does. `StripeError.isRetryable()` exists but nothing retries.
- Impact: behaviour floats with the Stripe account's default API version — and the legacy `POST /v1/subscription_items/{id}/usage_records` endpoint this client depends on has been removed in recent Stripe API versions, so a newly created Stripe account cannot use the usage sync at all (LIKELY; not verifiable offline). A retried `createSubscription` after a network timeout creates a second subscription (double charge). `createCustomer`/`createSubscription`/`cancelSubscription`/`getSubscription` have no non-test caller (built but unreachable).
- Fix: pin `Stripe-Version`, add `AbortSignal.timeout`, idempotency keys on all POSTs, migrate to Billing Meters.
- Effort: M

### R17-10 [Medium] [CONFIRMED] [Billing / correctness] Usage idempotency key omits the subscription; quantity is rounded to an integer before reporting to Stripe
- Where: `packages/billing/src/usage.ts:52-59`, `packages/billing-runtime-pg/src/stripe-sync.ts:78`
- Evidence: key is `tenant|meter|day` while buckets are per `(tenant, subscription, meter)` (`packages/billing-runtime/src/ingest.ts:40`): two subscriptions of one tenant collide on the unique key and overwrite each other. `quantity: Math.round(record.quantity)` silently drops fractional usage (0.4 GB-month → 0) and `timestamp: Math.floor(Date.parse(record.period.end)/1000)`.
- Impact: lost/misattributed usage for multi-subscription tenants; systematic rounding loss for fractional meters.
- Fix: include subscription id; report in a smaller integer unit.
- Effort: S

### R17-14 [Critical] [CONFIRMED] [GDPR / data destruction] The asynchronous Article 17 flow labels the act `data_subject_erasure` and erases the entire tenant; the subject identifier has no code path to the eraser
- Where: `apps/operate-server/src/node.ts:3541-3556`, `packages/tenant-lifecycle-pg/src/deletion-runner.ts:83-90,158-165`, `packages/tenant-lifecycle-pg/src/shared-table-erasure.ts:770-777`
- Evidence: the runner's `run` callback input is `{tenantId, tombstoneId, executedBy, approvedBy, relatedDeletionRequestId, capabilities}` — there is no `subjectIdentifier` field, although `meta.gdpr_deletion_requests.subject_identifier` is `NOT NULL` and `SubmitDeletionRequestInput.subjectIdentifier` is required (`deletion-request-store.ts:163`). `node.ts:3551` hardcodes `kind: "data_subject_erasure"` and calls `deleteTenantAtomically`, whose only predicate is `DELETE FROM … WHERE t.tenant_id = $1::uuid` on every erasable table plus `DROP SCHEMA` of the tenant schema. `TombstoneRecordSchema` (`packages/tenant-lifecycle/src/tombstones.ts:416-432`) requires `subjectIdentifier` only for `user_deletion`, so the proof for a "data subject erasure" names no subject.
- Impact: a verified request to erase one person (one employee/patient/customer of a tenant) irreversibly destroys every record of every person in that tenant, and the stored proof mislabels a tenant wipe as a subject erasure. There is no per-subject erasure capability anywhere in scope.
- Fix: rename the request to tenant erasure until a subject-scoped eraser exists; refuse `data_subject_erasure` kind when the scope is the tenant.
- Effort: S (rename/refuse) / L (real per-subject erasure)

### R17-15 [High] [CONFIRMED] [Proof honesty] A tombstone's "cryptographic proof" is an unkeyed SHA-256 over its own row, and `verifyStoredEvidence` never consults the forensic chain — a DB writer can rewrite scope, digests and attestations consistently and pass every check
- Where: `packages/tenant-lifecycle/src/tombstone-proof.ts:125-127,425-427,445-464`, `packages/tenant-lifecycle-pg/src/deletion-pipeline.ts:637-640`, `packages/tenant-lifecycle-pg/src/deletion-reconciliation.ts:124-140`
- Evidence: `computeContentManifestSha256 = sha256(TAG + canonical(scope…))`, `computeProofSha256 = sha256(TAG + canonical({id, kind, tenantId, …, contentManifestSha256}))` — no key, no signature. The "witness" check is `isAnchoredByChain(stored)`: `stored.chainEntryHash !== null && stored.record.anchors.some(a => a.reference === stored.chainEntryHash)` — two columns of the **same row** compared with each other. `grep -rn "tombstoneChainPayload|deletion_event"` (non-test) finds no reader outside `tombstone-store.ts`: nothing ever loads the chain entry and compares its payload's `contentManifestSha256/proofSha256` with the tombstone row. `matchesAttestations` compares against the `attestations` JSONB of the same row. `auditCompleted` compares `request.completionSha256` — another mutable column.
- Impact: the advertised detectors (`scope_tampered`, `proof_mismatch`, `unwitnessed`, sev1 paging) catch only an edit that forgets to recompute a public hash. Anyone with UPDATE on `meta.tenant_tombstones` (the table owner — which the serving role must be, see R17-18) can make a tombstone claim any scope and every verifier returns `ok`. The chain entry does hold the original digests, but the comparison that would use it is not implemented.
- Fix: in `verifyStoredEvidence`, load the chain entry at `chain_sequence_number`, verify its signature, and compare its payload digests to the row; or sign the tombstone with the chain's Ed25519 key.
- Effort: M

### R17-16 [High] [CONFIRMED] [Proof honesty / GDPR] The proof is silent about, and the erasure leaves, large stores of tenant personal data: `meta.audit_log` before/after snapshots, `meta.users`, backups, and anything a caller declares `absent`
- Where: `packages/tenant-lifecycle-pg/src/shared-table-erasure.ts:93-137,323`, `packages/kernel/src/bootstrap/meta-schema.ts:162-180,449-457`, `apps/operate-server/src/node.ts:3555`, `packages/tenant-lifecycle/src/tombstone-assembly.ts:765-777`
- Evidence: (a) `PLATFORM_RECORD_TABLES` retains `audit_log`, whose columns include `before JSONB`, `after JSONB`, `diff JSONB`, `actor JSONB` (`meta-schema.ts:451-457`; `apps/operate-server/src/audit-log-store.ts:208` writes `after: input.after`), plus `access_review_*`, `gdpr_deletion_requests.subject_identifier` — classified as "not the tenant's data" and therefore *not named* in the tombstone (only `STATUTORY_RETENTION_TABLES` produce a retention claim). (b) `partitionSharedTables` skips any table without `tenant_id` (`:323`), so `meta.users` (`email`, `display_name`, `phone_e164`) is neither erased, retained-with-reason, nor mentioned, while memberships are erased. (c) the runner passes `attestations: []` (`node.ts:3555`) and `assembleTombstone` refuses `subsystem_unattested` for any non-absent subsystem, so the *only* configuration in which an unattended deletion completes is `object_storage/backups/search_indexes/caches: "absent"` — i.e. every completed proof carries a signed declaration that the deployment has no backups. (d) on the synchronous route the caller may instead POST `attestations` (`apps/operate-server/src/tenant-deletion-routes.ts:267,420`) — hand-typed `erased` figures for backups/object storage are signed and anchored unverified.
- Impact: a regulator-facing "proven erased" artefact that omits the audit trail's full record snapshots, the user directory, and all Postgres backups. For PHI/PII tenants this is a materially false erasure claim. `tenant_data_keys` crypto-shredding (outside scope) does not cover audit_log payloads (LIKELY — audit `after` is written by the app in clear; not traced end to end).
- Fix: add a `present_not_erased` disposition with horizon; name platform-record tables and `meta.users` in the proof; redact/erase audit payloads or declare them retained under `audit_logs_3y` with an expiry job.
- Effort: M

### R17-17 [High] [CONFIRMED] [Authorization] "Four-eyes" on tenant deletion is a typed string: one credential deletes a tenant by naming any other approver; the unattended runner uses two constants
- Where: `apps/operate-server/src/tenant-deletion-routes.ts:395-399,414-421`, `apps/operate-server/src/deletion-scheduler.ts:19-20`, `packages/tenant-lifecycle-pg/src/deletion-runner.ts:135-139`
- Evidence: the route takes `approvedBy` from the request body and checks only that it differs from the caller ("approvedBy must not be the caller"); no second authenticated principal, approval record or signature is consulted. `DEFAULT_DELETION_EXECUTED_BY = "system:deletion-runner"`, `DEFAULT_DELETION_APPROVED_BY = "system:retention-policy"` satisfy `executedBy !== approvedBy` at three "layers" (runner ctor, erasure, tombstone schema/CHECK) which all test the same inequality of two strings.
- Impact: the irreversible destruction of a tenant requires one compromised/malicious holder of the deletion role; the tombstone then records a fabricated approver as evidence. (The async flow does have a real second actor at *verify*; the sync route does not.)
- Fix: require an approval artefact created by a second authenticated principal (as the deletion-request verify step does) before the sync route executes.
- Effort: M

### R17-18 [High] [CONFIRMED] [Operational / least privilege] The deletion only runs on a session RLS does not confine — i.e. the serving process must own (or BYPASSRLS) every table — and does all work in one unbounded transaction
- Where: `packages/tenant-lifecycle-pg/src/shared-table-erasure.ts:680,1005-1012,1048-1095`, `packages/tenant-lifecycle-pg/src/deletion-pipeline.ts:421-606`, `apps/operate-server/src/node.ts:1740,3525`
- Evidence: the probe selects `row_security_active(c.oid) AS confined` and refuses `rls_would_confine_this_session` if true for any target; the routes and runner pass the server's ordinary `conn`. So a deployment that follows least privilege (non-owner serving role) can never complete an Article 17 deletion, and one that can delete has a serving role for which RLS is not a boundary at all. Inside one `conn.transaction`: a `DELETE … RETURNING pg_column_size(t)` and then a second `SELECT count(*)` for every erasable catalogued table (~97) plus every entity table (51+ for erp-core), then `DROP SCHEMA … CASCADE`, chain append, tombstone insert — no batching, no `statement_timeout`/`lock_timeout` (`grep` finds none), on the synchronous route inside an HTTP request. No lock or status gate stops the tenant writing concurrently (`--tenant-status-gate` is opt-in); a row inserted after the confirm pass survives the "proven" deletion.
- Impact: for a large tenant: long-held row locks and ACCESS EXCLUSIVE locks from `DROP SCHEMA`, WAL/replication-lag spikes, connection held for the duration, and a full rollback on any failure near the end. Strong atomicity is bought at the cost of operability.
- Fix: quiesce the tenant first (mandatory read-only), delete in resumable batches under a dedicated privileged role, commit the proof last.
- Effort: L

### R17-19 [Medium] [CONFIRMED] [GDPR deadline] A deletion that completes after its Article 12(3) deadline cannot be recorded, and poisons later reads; nothing detects an overdue request
- Where: `packages/tenant-lifecycle/src/gdpr-deletion.ts:181-189,253-259`, `packages/tenant-lifecycle-pg/src/deletion-request-store.ts:394-406,311-321`, `packages/tenant-lifecycle-pg/src/deletion-runner.ts:194-209`

The runner catches it as `completed_unrecorded`. Thereafter `read(id)` throws for that row and `completedWithTombstone()` (`result.rows.map(rowToDeletionRequest)`) throws for the whole page, breaking `auditCompleted`. `isOverdue` / `daysUntilDeadline` have no non-test caller outside the package (grep), and no store query filters on `deadline_at`.
- Impact: the one event that is a regulatory breach (late erasure) is unrepresentable, undetected, and degrades the evidence audit. `deferred` is a contract status no route or scheduler sets or resumes (`grep '"deferred"' apps/operate-server/src/deletion-*` → none); `GracePeriod` (deletion_grace 30d) has no consumer, so a verified request is executed on the next runner tick with no cooling-off.
- Fix: drop the completion-deadline refinement (record lateness as a field), add an overdue query + alert.
- Effort: S

### R17-21 [Medium] [CONFIRMED] [Retention] Statutory retention has no expiry and protects tables nothing writes; retained rows stay keyed to a "deleted" tenant indefinitely

### R17-22 [Low] [CONFIRMED] [Robustness] Runner/reconciler edge cases
- Where: `packages/tenant-lifecycle-pg/src/deletion-runner.ts:166-181`, `packages/tenant-lifecycle-pg/src/deletion-reconciliation.ts:362-367,409-410`, `apps/operate-server/src/tenant-deletion-routes.ts:425-446`
- Evidence: (a) `store.transition(…"rejected")` inside the `catch` is not itself guarded — a DB error there escapes `runOne` and aborts `runDue`'s loop. (b) `reconcileStranded` passes `now` as `olderThan`, so it assesses requests whose pipeline transaction is still running; after the 1h window an operator applying `never_committed` marks `rejected` a request whose long transaction then commits (`rejected → completed` is illegal → `completed_unrecorded`, tenant erased, request says rejected). (c) the sync route maps *any* thrown error to 409 "the tenant is unchanged", which is not established for a failure during COMMIT. (d) `onRun` retires the tenant row fire-and-forget (`void tenantStore.setStatus…`, `node.ts:3588`).
- Impact: rare inconsistent request/tenant state needing manual repair.
- Fix: guard, use an advisory lock per request to detect a live runner, distinguish commit-unknown.

## Summary (10 lines max)
1. Billing as deployed is a request counter flushed to Postgres and pushed to Stripe; invoicing/tax/dunning/proration/credits are contracts with no deployed caller (R17-04).
2. The wired usage path is wrong twice: flushes within a UTC day overwrite each other (R17-01), and after an upsert the row can never be marked synced, so it is re-reported to Stripe (R17-02); usage is also memory-only between flushes (R17-03).
3. Stripe client: sound webhook verification; but no API-version pin, no timeouts/retries, idempotency key on 1 of 4 mutating calls, secrets on argv (R17-09, R17-12).
4. Tenant deletion is genuinely atomic and injection-safe, with careful refusal ordering — the engineering is real.
5. But the async "data subject erasure" wipes the whole tenant (R17-14, Critical), and four-eyes is a typed string (R17-17).
6. The tombstone is an unkeyed hash of its own row and the verifier never reads the chain, so tamper-evidence is weaker than claimed (R17-15).
7. The proof omits retained audit_log snapshots, `meta.users` and backups; the only config under which the unattended runner completes signs "backups: absent" (R17-16).
8. Deletion needs an RLS-unconfined (owner) serving role and runs as one unbounded transaction with no tenant quiesce (R17-18).
9. No export/portability, no overdue detection, a late completion cannot be recorded (R17-19, R17-20); statutory retention has no expiry (R17-21).
10. Tests are numerous but SQL-shape-on-a-fake; they pin two of the billing bugs rather than catch them.
