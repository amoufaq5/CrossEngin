# R05 — packages/kernel (meta-schema, DDL vocabulary, manifest compiler, tenancy, workflow), packages/types, packages/config

## Summary (10 lines max)
- The kernel is a clean, pure, well-typed library: deterministic DDL emission, strict identifier quoting, a serious manifest cross-validator. No `any`, no TODOs, no swallowed errors.
- The single worst defect is a **raw-SQL sink in the manifest contract**: `default: {kind:"expression"}` is an unbounded string that flows verbatim into `CREATE TABLE … DEFAULT <expr>` for AI-/tenant-authored manifests (R05-01). Nothing whitelists it.
- **RLS is declared on all 115 tenant tables but is inert in the shipped deployment**: the compose stack connects API and migrator as `POSTGRES_USER` (a superuser), nothing emits `FORCE ROW LEVEL SECURITY`, `GRANT`, `REVOKE` or a role (R05-02). Every cross-tenant "grant" is a PUBLIC-settable GUC (R05-03).
- The manifest schema has **no size limits anywhere** (no `.max()` on any string/array/record), no identifier-length cap, no table/column-name collision check, and `validateManifest` accepts manifests the column store cannot serve (R05-04/05/06).
- `manifestHash` is not injective: `__proto__` keys inside `z.unknown()` regions are dropped and every array of named objects is order-normalised (R05-07).
- The 146-table catalog is ~50% unreferenced: by text scan 48 tables have no SQL reference at all outside kernel/tests and 23 more have no writer (71; the repo's own rule says 77). Several live concepts are modelled twice.
- No partitioning/retention for any unbounded append-only table; audit/chain immutability is not enforced at the DB (isolation policies are `FOR ALL`).
- Tests are numerous and real for validation/emit, but the catalog tests are mostly shape pins; nothing tests hostile manifest input.

## Findings

### R05-01 [High] [CONFIRMED sink / LIKELY end-to-end] [Security: SQL injection] Manifest `default.expression` is spliced verbatim into tenant DDL
- Where: `packages/types/src/meta-schema/field.ts:45-48` (`kind: z.literal("expression"), expression: z.string().min(1)`); `packages/kernel/src/ddl/column.ts:14-15` (`if (value.kind === "expression") return value.expression;`); sink `packages/operate-runtime-pg/src/column-plan.ts:140` (`defaultSql: … emitDefault(field.default)`) → `packages/operate-runtime-pg/src/entity-ddl.ts:263` (`` ` DEFAULT ${c.defaultSql}` ``) → `packages/operate-runtime-pg/src/tenant-schema-apply.ts:251` (`await tx.query(stmt)`, no parameters, so the simple-query protocol accepts multiple statements). Reached for activated per-tenant manifests at `apps/operate-server/src/node.ts:3969` (`tenantStoreRegistry.ensure(tenantId, tenantManifest)`).
- Evidence: grep for `"expression"` across `packages/*/src` and `apps/*/src` finds no validator, allow-list or parser for this string — only the schema, `emitDefault`, and three compliance packs using `now()`. `packages/kernel/src/ddl/column.test.ts:24` pins the behaviour: "returns an expression default verbatim". `validateManifest` (`manifest/validate.ts:38-71`) never inspects defaults. The same path applies to trait fields (`TraitSchema.fields` = `FieldSchema`).
- Impact: any manifest that reaches activation (the AI Architect's output, or a `source: 'manual'` proposal — `meta-schema.ts:11331`) can carry `expression: "''); DROP SCHEMA meta CASCADE; --"` or, without breaking out at all, a side-effecting function call evaluated on every insert: `set_config('app.platform_audit','on',false)` (session-scoped on a pooled connection → later requests on that connection read every tenant's audit log, tombstones and deletion requests, see R05-03), `set_config('app.current_tenant_id','<victim>',false)`, `current_setting('app.column_encryption_key')` (exfiltrates the per-tenant PHI key into a plaintext column), `pg_read_file(...)` when the role is superuser (R05-02). The human review gate is the only control, and the reviewer is shown a structural diff, not SQL. Prompt injection into the designer model is a realistic source. Not verified: exactly which roles may submit a `manual` manifest (outside my scope).
- Fix: replace the free string with a closed enum of server-side defaults (`now`, `current_date`, `uuid_v7`, …) mapped to SQL in the kernel; reject everything else in `FieldSchema`. Add a hostile-input test. Run tenant DDL as a role that is not the meta owner.
- Effort: S

### R05-02 [High] [CONFIRMED] [Security: tenant isolation] RLS is never forced and the shipped stack connects as a superuser, so all 197 policies are inert there
- Where: `packages/kernel/src/bootstrap/emit.ts:414-416` (`ENABLE ROW LEVEL SECURITY` is the only RLS statement; no `FORCE`); `emit.ts:482-491` (`emitBootstrapSql` emits schema, tables, indexes, policies — no `GRANT`/`REVOKE`/`CREATE ROLE`); `deploy/docker-compose.yml:11-16` (`x-pg-env: PGUSER: ${POSTGRES_USER}`) merged into migrate, api at lines 61/77/89.
- Evidence: repo-wide grep for `FORCE ROW LEVEL`, `GRANT `, `REVOKE `, `CREATE ROLE` in non-test source/deploy returns only comments (e.g. `kernel-pg/src/introspection.ts:92` "Nothing in the catalog sets that flag today") and one remediation string. `POSTGRES_USER` in the official image is the bootstrap superuser; superusers and table owners bypass RLS. `RlsPolicy.roles` exists (`bootstrap/types.ts:158`) and is used by 0 of 197 policies.
- Impact: in the reference deployment tenant isolation rests entirely on application-level `WHERE tenant_id = $1` predicates and `withTenantContext` discipline; the defence-in-depth layer the catalog, its tests and the docs present as "the tenant-isolation boundary" does not execute. Any query that forgets its predicate, and any SQL injection (R05-01), is cross-tenant. `packages/kernel/README.md:598-601` still lists per-tenant roles as "Deferred to Phase 2".
- Fix: emit `FORCE ROW LEVEL SECURITY` for every RLS table; ship a non-superuser, non-owner, `NOBYPASSRLS` serving role with explicit grants and make the compose file use it; fail boot when the serving session `rolsuper`/`rolbypassrls`/owns the tables (the probes already exist in kernel-pg).
- Effort: M

### R05-03 [High] [CONFIRMED] [Security: authorization model] Every cross-tenant and platform-write "grant" is a GUC any session can set
- Where: `packages/kernel/src/bootstrap/meta-schema.ts:496, 3777, 3897, 4167, 11626` (`using: "current_setting('app.platform_audit', true) = 'on'"` on `audit_log`, `tenant_lifecycle_events`, `gdpr_deletion_requests`, `tenant_tombstones`, `audit_integrity_verdicts`); `:518` (`app.platform_audit_write`); 18+3 policies on `app.platform_record_write`, 11+9 on `app.platform_config_write`, 2 on `app.platform_key_write`; `:11372` (`app.platform_review`).
- Evidence: policy census parsed from the file: 197 policies, 0 with `roles`, 0 restrictive. Custom `app.*` GUCs are settable by any role via `SET`/`set_config`. `:81-82` the tenant predicate itself is `current_setting('app.current_tenant_id', true)` — also caller-set.
- Impact: even with a correctly confined non-owner role, RLS only protects against *accidentally* unscoped queries. Any ability to execute SQL text in a serving session (R05-01, or any future injection) yields: read every tenant's audit trail and Article-17 records, write platform-scope audit rows/chain entries/keys, and impersonate any tenant. The elevations are declarations of intent, not authorization. The repo's own notes concede this; investors should read "RLS-enforced isolation" accordingly.
- Fix: bind elevations to database roles (`TO platform_auditor`) with `SET ROLE` per transaction, or sign the context (e.g. HMAC'd GUC verified by a `SECURITY DEFINER` function). At minimum combine with R05-02.
- Effort: L

### R05-04 [Medium] [CONFIRMED] [Security/Robustness: DoS, input validation] The manifest schema has no size or length bound anywhere
- Where: `packages/kernel/src/manifest/types.ts:57-76` (every section `z.array(...)`/`z.record(z.string(), …)` with no `.max`); `packages/types/src/meta-schema/entity.ts:5-9` (`ENTITY_NAME_REGEX = /^[A-Z][A-Za-z0-9]*$/`, no length); `field.ts:103-108` (field name, no length); `field-types.ts:5` (`maxLength: z.number().int().positive()`), `:25-26` (decimal `precision`/`scale` unbounded), `:47` (enum `values` unbounded strings); `field.ts:22-33` (`pattern: z.string().min(1)`, `expression: z.string().min(1)`); `workflow/types.ts:37-41` (`EffectSchema … .passthrough()`), `:88-93`, `:102` (`z.unknown()`).
- Evidence: `grep -n "\.max(" packages/types/src/meta-schema/*.ts packages/kernel/src/manifest/types.ts packages/kernel/src/workflow/types.ts` returns only the two min<=max refinements. Record keys (role names, workflow names, view ids, job ids) are unconstrained `z.string()`.
- Impact: (a) Postgres silently truncates identifiers at 63 bytes; `quoteIdent` (`ddl/identifiers.ts:3-8`) has no length check, so two long entity/field names sharing a prefix collide after truncation and `CREATE … IF NOT EXISTS` no-ops on the second. (b) `VARCHAR(10485761)`/`NUMERIC(5000,…)` pass validation and fail at DDL. (c) A multi-megabyte manifest is validated, hashed, diffed (`computeReachableStates` is O(states×transitions) with `Array.shift`), stored as JSONB and compiled into routes per tenant — an authenticated tenant can exhaust memory/CPU. (d) `ValidationRule.pattern` is an attacker-chosen regex; no consumer compiles it today (grep `validations` in operate-runtime/-pg/operate-server: no hits), so it is declared-and-ignored now and a ReDoS the day it is wired.
- Fix: cap name lengths (≤ 48 so derived index/policy names fit), array sizes, enum cardinality, precision ≤ 38, `maxLength` ≤ 10_485_760, total manifest bytes; constrain record keys with the same regexes as names.
- Effort: S

### R05-05 [Medium] [CONFIRMED] [Correctness] Distinct entity names map to the same table; validation does not detect it
- Where: `packages/kernel/src/ddl/identifiers.ts:10-15` (`toTableName`); `packages/kernel/src/manifest/validate.ts:173-181` (duplicate check is on the raw PascalCase name only); consumer `packages/operate-runtime-pg/src/column-plan.ts:196`.
- Evidence: executed the function body standalone: `ABTest`→`ab_test`, `AbTest`→`ab_test`; `HTTPLog`/`HttpLog`→`http_log`. No collision check in `column-plan.ts`/`entity-ddl.ts` (grep `collid|same table` → only a comment about unique indexes). `emitEntityTableDdl` uses `CREATE TABLE IF NOT EXISTS` + `ADD COLUMN IF NOT EXISTS` (`entity-ddl.ts:297`), so the second entity silently shares the first one's table.
- Impact: two entities' rows in one physical table keyed `(tenant_id, id)`: id collisions, cross-entity reads, constraints of one applied to the other. Reachable from an AI-authored manifest with near-duplicate names. Same class: a `reference` field `owner` and a scalar field `owner_id` both map to column `owner_id` (`ddl/column.ts:4-6`, `identifiers.ts:21-24`) — not checked.
- Fix: in `validateEntitiesTraitsRelations`, reject duplicate `toTableName(name)` and duplicate `columnNameForField` per entity.
- Effort: S

### R05-06 [Medium] [CONFIRMED] [Correctness] `validateManifest` never rejects reserved or trait-colliding field names; the check exists but is only called by the diff path
- Where: `packages/kernel/src/ddl/resolution.ts:114-128` (`checkEntityFieldNames` — rejects `id` and trait collisions); only caller `packages/kernel/src/ddl/diff.ts:52,54`. `validate.ts` calls `resolvedFields`, whose doc says (`resolution.ts:53-54`) "this tolerates a name supplied twice: the first wins. Rejecting a genuine collision belongs to `checkEntityFieldNames`".
- Evidence: `grep -n checkEntityFieldNames packages/kernel/src` → resolution.ts, diff.ts, tests. An entity field named `id` or `tenant_id` passes `EntitySchema` + `validateManifest`; `emitEntityTableDdl` then emits `"tenant_id" UUID NOT NULL, "id" TEXT NOT NULL, …plan.columns` (`entity-ddl.ts:284-286`) → `column "id" specified more than once`. A field that shadows a trait field (`created_at: text` on an `auditable` entity) silently wins over the trait's typed column.
- Impact: validated-and-approved manifests fail at provisioning (tenant falls back to JSONB store per the repo's own notes) or silently change the type of audit columns. `tenant_id` is not reserved anywhere.
- Fix: call `checkEntityFieldNames(entity, expandTraits(...))` from `validateManifest`; add `tenant_id` to the reserved set.
- Effort: S

### R05-07 [Medium] [CONFIRMED] [Integrity] `manifestHash` is not injective — content can change without the hash changing
- Where: `packages/kernel/src/manifest/hash.ts:4-25`.
- Evidence: (1) `sorted[key] = canonicalizeForHash(obj[key])` on a plain `{}`: for an own key `__proto__` (which `JSON.parse` creates) this sets the prototype instead of a property, so the subtree vanishes from the JSON. Reproduced standalone: `{"value":{"__proto__":{"evil":1},"x":1}}` and `{"value":{"x":1}}` canonicalise to the identical string. Zod strips `__proto__` in `z.object`/`z.record`, but not inside `z.unknown()` — `DefaultValue.literal.value` (`field.ts:43`), orchestration `steps`/`trigger`/`action` (`workflow/types.ts:90-102`), `compliancePackParameters` values — and `emitLiteral` (`ddl/column.ts:32-33`) serialises it with `JSON.stringify`, which *does* include the key. (2) `hash.ts:10-16`: any array whose items all have a string `name` is sorted by name, so reordering entity fields (physical column order), workflow states/transitions, view columns, or integration operations does not change the hash; arrays with duplicate names sort unstably relative to content.
- Impact: the hash is the manifest's identity — `meta.operate_tenant_manifests.manifest_hash`, the per-tenant schema registry's memo key, `manifestResolution.parents[].hash`, review/approval records. Two different documents can share one identity; a changed JSONB default is not re-applied because the registry memoises on the hash. Low exploitability, but an integrity primitive that is not collision-free by construction should not be used as an approval anchor.
- Fix: build with `Object.create(null)` or a `Map`/array-of-pairs; hash order-sensitively except where order is declared irrelevant; reject `__proto__`/`constructor`/`prototype` keys at parse.
- Effort: S

### R05-08 [Medium] [CONFIRMED] [Security: RLS policy shape] `operate_tenant_manifests` keeps the combined `ALL` policy the repo fixed everywhere else
- Where: `packages/kernel/src/bootstrap/meta-schema.ts:11371-11372`: ``using: `${TENANT_ISOLATION_USING} OR current_setting('app.platform_review', true) = 'on'` `` with no `command` and no `check`.
- Evidence: on a `FOR ALL` policy the `USING` expression is also the `WITH CHECK` (the file says so itself at `:11213-11216`). So a session holding the *review* elevation can INSERT/UPDATE/DELETE any tenant's manifest rows — including setting `review_status='approved'`, `status='active'`. There is also no CHECK tying `status='active'` to `review_status IN ('approved','not_required')` and no four-eyes constraint (`reviewed_by` is free TEXT, `:11341`), although the catalog enforces four-eyes with CHECKs elsewhere.
- Impact: this table decides what schema and permissions a tenant is served and is the input to R05-01's sink. The one table where a forged write becomes DDL is the one left on the permissive shape.
- Fix: split into isolation `ALL` + `SELECT`-scoped review read + narrowly scoped `UPDATE` on the review columns; add the status/review CHECK.
- Effort: S

### R05-09 [Medium] [CONFIRMED] [Integrity: audit] Append-only is not enforced by the database for audit_log / forensic chain
- Where: `meta-schema.ts:483-485` (`audit_log_tenant_isolation`, `FOR ALL`), `:11221-11223` and `:11286-11288` (chain entries/checkpoints isolation, `FOR ALL`). No trigger, rule or REVOKE exists (emitter cannot express one: `bootstrap/types.ts`).
- Evidence: comment at `:507-509` claims "The table stays append-only at the policy as well as in `PostgresAuditEmitter`" — true only for the *platform* arm; the tenant isolation arm permits UPDATE and DELETE of a tenant's own rows under that tenant's context. `audit_log` has no UNIQUE on `(tenant_id, chain_sequence_number)`. `forensic_chain_entries_tenant_seq_key` (`:11200-11204`) is `UNIQUE (tenant_id, sequence_number)` with nullable `tenant_id`, so for the platform chain (NULL) Postgres enforces nothing — duplicate sequence numbers are admissible; only `workflow_definitions` got the compensating partial unique index (`:7227-7230`).
- Impact: a tenant-context session (or the owner) can rewrite or truncate its own audit trail; detection depends on the hash chain being configured and on checkpoint cadence. For a product selling SOC 2/HIPAA evidence, "immutable audit trail" (`README.md:563`) is an application convention.
- Fix: `INSERT`+`SELECT`-only policies for these tables (no UPDATE/DELETE arm), plus a `BEFORE UPDATE OR DELETE` trigger; partial unique indexes `WHERE tenant_id IS NULL`.
- Effort: M

### R05-10 [Medium] [CONFIRMED] [Scalability] No partitioning or retention for any unbounded append-only table
- Where: `packages/kernel/src/bootstrap/types.ts:176-192` (`TableDefinition` has no partition/retention vocabulary); tables `audit_log` (`:430`), `events` (`:404`), `integration_calls` (`:560`), `ai_provider_calls` (`:628`), `job_runs` (`:691`), `workflow_events` (`:7792`), `rate_limit_decisions` (`:8853`), `gateway_pipeline_executions` (`:9428`), `feature_flag_evaluations` (`:9805`), `notification_deliveries` (`:6067`), `forensic_chain_entries` (`:11169`), `operate_entity_records` (`:10729`).
- Evidence: `README.md:598` "Deferred to Phase 2: Partitioning of meta.audit_log + meta.events". All PKs are a lone UUID `id`, which would have to change to include the partition key. `audit_log` carries three full JSONB snapshots per row (`before`, `after`, `diff`, `:455-457`) plus a GIN index on `actor` (`:476`).
- Impact: single-node Postgres growth is unbounded; index bloat and vacuum cost grow with every tenant; Article-17 `DELETE … WHERE tenant_id` on these tables is a full index range delete. Retrofits require table rewrites.
- Fix: declarative range partitioning on time for log tables (PK `(id, occurred_at)`), a retention job, and moving `before/after` to diff-only.
- Effort: L

### R05-11 [Medium] [CONFIRMED] [Schema design] The ERP's actual business data is one JSONB document table with one index
- Where: `meta-schema.ts:10729-10757` (`operate_entity_records`: `document JSONB`, UNIQUE `(tenant_id, entity, record_id)`, one index `(tenant_id, entity)`); `packages/kernel/src/ddl/field-type.ts:46-47` (`case "currency_amount": return "JSONB";`).
- Evidence: this is the default `--store pg` (per deploy compose). No FK, no CHECK, no typed columns, no expression index: every filter/sort on a ledger, invoice or stock table is a scan of that tenant's entity slice with `document ->> 'x'`. On the typed store, the dedicated money field type is still a JSONB blob, so amounts in that type cannot be summed, range-indexed or constrained in SQL; `decimal` → `NUMERIC(p,s)` is the only sound money path (`field-type.ts:18-19`), and `geo_point`/`geo_polygon` emit `geography(...)` (`:48-51`), which needs PostGIS that nothing installs.
- Impact: double-entry accounting on a schemaless document store with no database-level integrity; performance cliff per tenant-entity at modest volumes; `currency_amount` is a trap for pack authors.
- Fix: make the typed column store the default; map `currency_amount` to `(NUMERIC, CHAR(3))`; refuse `geo_*` unless PostGIS is present.
- Effort: L

### R05-14 [Low] [CONFIRMED] [Schema design] Business ids are globally unique on tenant-scoped tables; `users.email` is case-sensitive
