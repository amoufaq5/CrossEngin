# R19 — access-reviews(+runtime,+pg), certification-runtime(+pg), marketplace(+runtime,+pg), residency(+runtime,+pg), compliance

## Summary (10 lines max)
- None of the five domains is enabled in the shipped compose (`deploy/docker-compose.yml:147-175` passes only `--pack/--store/--port/--scheme/...`); all are opt-in flags, and `compliance` is not reachable from any binary at all.
- "Certification" is an automated **self-assessment over 4 controls**, sealed with an unkeyed SHA-256 stored beside the data, with no read route. 3 of the 4 controls can be reported `satisfied` vacuously or from operator-typed JSON; the 4th (encryption) checks a column *type*, in the wrong schema by default.
- Access reviews: no HTTP surface exists for a human reviewer; "auto-revocation" writes a decision row and revokes nothing in the auth system; the item is never marked resolved, so a campaign with ≥1 item never completes and re-mints duplicate revoke decisions every tick, while a campaign with **0 items** completes and seals "100% completion" evidence.
- Marketplace: Ed25519 signature is verified, but against a key supplied in the same payload (no trust root); the elevated-review exemption is derived from the author's self-declared `author.kind`; a published version row can be overwritten by any `pack_author`; an installed pack does nothing and the install route dead-ends in `installing`.
- Residency: a pre-auth request-rejection guard keyed on an optional, unauthenticated header; fail-open on missing header and on unknown tenant; no data-placement mechanism (one database); the Postgres directory has no writer.
- Compliance packs: `resolveCompliancePacks` has zero callers; 4 definitions exist, 5 of the 6 ids the ERP packs declare have none; parameters are validated then discarded.
- pg SQL is parameterised throughout (no injection found); tenant scoping is mostly explicit + RLS, with a few owner-bypass gaps.

## Findings

### R19-01 [High] [CONFIRMED] [Compliance claim] DR-readiness control is `satisfied` vacuously from an empty, operator-typed config
- Where: `packages/dr-runtime/src/readiness.ts:146` (`ready: counts.totalIssues === 0`), `apps/operate-server/src/dr-readiness.ts:26-34` (`runbooks/backups/replication ... .default([])`), `packages/certification-runtime/src/evidence.ts:136-139`, `apps/operate-server/src/certification.ts:125-136`.
- Evidence: runbooks, backups and replication lag come only from the `--dr-readiness-config` JSON file (all default `[]`); failovers/drills are read from tables that nothing in `apps/` writes (grep for `failoverStore.`/`drillStore.` finds only the two `listRecent` reads at `dr-readiness.ts:100-101`). With `{"input":{}}` every list is empty → `totalIssues === 0` → `ready: true` → `evidenceFromDrReadiness` emits `satisfied: true`, summary `"DR readiness: READY (0 issues)"`.
- Impact: control `resilience.dr_readiness` — described as "Backups are verified and unexpired, runbooks are current, and failover/drill RPO/RTO targets are met" (`controls.ts:100-101`), mapped to SOC 2 A1.2/A1.3 and HIPAA 164.308(a)(7) — passes for a deployment with zero backups, zero runbooks and zero drills. Where inputs are supplied they are self-declared (a backup's `verified` flag is typed into JSON). There is no automated backup in the repo.
- Fix: require non-empty evidence per dimension (no backups/drills/runbooks ⇒ `not_assessed`, mirroring `ENCRYPTION_SCOPE_ABSENT_FINDING`); source backups from a real backup job.
- Effort: S (fail-closed) / L (real signal)

### R19-02 [High] [CONFIRMED] [Compliance claim] Access-review control is `satisfied` by a campaign that reviewed nothing (0 items ⇒ "sealed at 100% completion")
- Where: `packages/access-reviews/src/evidence.ts:69-78` (`if (total === 0) return { completionRate: 1, ...}`), `packages/access-reviews-runtime/src/scheduling.ts:86-91` (`unresolvedItems(items).length === 0`), `apps/operate-server/src/access-reviews-lifecycle.ts:24-25` (`grants ... .default([])`, `principals ... .default([])`), `packages/certification-runtime/src/evidence.ts:177-207`.
- Evidence: a config with a campaign and no grants/principals (the defaults) starts, generates 0 items, is `isCampaignCompletable` on the next tick, is closed and sealed with `completionRate: 1`; `evidenceFromAccessReviewEvidence` only checks seal status and `completionRate >= 0.95`, and reports `"<framework> access review sealed at 100% completion"`. Nothing checks `totalItemsAcrossCampaigns > 0`, `strongAttestationRate`, or that any human attested (`strongAttestationRate` is read at `certification.ts:281` and never used by the assessor).
- Impact: `access.periodic_review` (SOC 2 CC6.1–6.3, HIPAA 164.308(a)(3)/(4), PCI 7.2.4) passes with no principal reviewed. Combined with R19-03 this is the *only* way the control can pass today.
- Fix: zero-item pack ⇒ `not_assessed`; require a minimum human-attested share.
- Effort: S

### R19-03 [High] [CONFIRMED] [Functional] Access reviews cannot be performed: no reviewer surface, items never resolve, auto-revoke re-fires every tick
- Where: `packages/access-reviews-runtime-pg/src/persisting-runtime.ts:300-314`, `apps/operate-server/src/access-reviews-lifecycle.ts:176-200`, `packages/access-reviews-runtime-pg/src/item-store.ts:31`.
- Evidence: `planAutoRevocations` only does `await this.decisionStore.record(decision)`; no code updates the item (`itemStore.upsert` is called solely from `generateItems`, `persisting-runtime.ts:86`). The scheduler comment "the auto-revocations just resolved items this list is stale about" (`access-reviews-lifecycle.ts:180`) is false. No route in `apps/operate-server/src` accepts a keep/revoke decision (grep `access-review|decisionStore.record` → none outside the scheduler). Consequences: (a) an in-progress campaign with ≥1 item stays `in_progress` forever; (b) each tick (default hourly) the same still-unattested items yield fresh `ard_` ids → unbounded duplicate rows in `meta.access_review_decisions`; (c) no evidence pack is ever produced for a non-empty campaign.
- Impact: the SOC 2/HIPAA access-recertification feature is non-functional for any real population. The test that should catch it stubs the runtime with `completable: true` and asserts only that `listByCampaign` was called twice (`apps/operate-server/src/access-reviews-lifecycle.test.ts:302-313`).
- Fix: transition item → `auto_revoked` in the same transaction as the decision; add reviewer routes.
- Effort: M

### R19-04 [High] [CONFIRMED] [Compliance claim] "Auto-revocation" revokes nothing
- Where: `packages/access-reviews-runtime/src/enforcement.ts:46-81` (`appliedAt: null`), `packages/access-reviews-runtime-pg/src/decision-store.ts:31-83`.
- Evidence: the decision is stored with `appliedAt/applicationFailedAt = null`; grep for writers of `applied_at` across `apps/` and `packages/` finds none outside the contract/store. No call into `meta.user_tenant_membership`, API-key config or JWT issuance. The boot log line prints `revoked=<n>` (`apps/operate-server/src/node.ts:2879`).
- Impact: an operator/auditor reading `revoked=3` or an `auto_revoke_rate` in a sealed pack would conclude access was removed; the principal keeps full access. For `--access-reviews-live-grants` the "grant" is an API key in the process environment, which the process cannot revoke at all.
- Fix: wire a revocation applier or rename to "revocation recommended" and never count it as resolved.
- Effort: M

### R19-05 [High] [CONFIRMED] [Compliance claim] Audit-log control verifies only hash *links*, not entry hashes or signatures
- Where: `packages/forensics/src/tamper-evident-logs.ts:96-112` (consumed at `apps/operate-server/src/certification.ts:308`), control text `packages/certification-runtime/src/controls.ts:84-86`.
- Evidence: `verifyChainIntegrity` checks `e.sequenceNumber !== i` and `e.priorEntryHash !== priorHash` then `priorHash = e.entryHash`. It never recomputes `entryHash` from the entry fields and never checks `signature`/`signingKeyFingerprint`. An attacker with table write can edit `payload_sha256`, `actor_reference`, `kind`, `recorded_at` of any entry (leaving `entry_hash` untouched) and the control still reports `"audit hash-chain integrity verified"`. It also does not compare `meta.audit_log` rows to the chain.
- Impact: control `audit.tamper_evident_log` claims "a hash-chained, signed log whose integrity verifies end-to-end from the genesis hash"; the evidence adapter does not test that.
- Additional (CONFIRMED): `PostgresForensicChainReader.loadChain` (`certification.ts:333-343`) has no scope predicate; for `tenantId: null` it issues a bare `conn.query`, so as table owner it reads every scope's entries interleaved → "sequence gap" → permanently `deficient` once two scopes exist (fail-closed, but wrong).
- Fix: use the signature-verifying verifier from `forensics-pg`; add `scopeFilter`.
- Effort: S

### R19-06 [Medium] [CONFIRMED] [Compliance claim] Encryption control checks a column comment + `bytea` type, in schema `meta` by default
- Where: `apps/operate-server/src/certification.ts:40` (`schema ... .default("meta")`), `:487`; `packages/kernel-pg/src/encryption.ts:47,69,414-418`.
- Evidence: coverage = columns whose comment contains `crossengin.encrypt=at_rest`, flagged plaintext iff `dataType !== "bytea"`. It does not sample content, so a `bytea` column holding plaintext bytes passes. The comments are emitted on **entity tables** (`packages/operate-runtime-pg/src/entity-ddl.ts:315-316`), which live in `public` (or per-tenant `t_<hex>` schemas), not `meta`; with the default config `total === 0` → `scope_absent` → deficient. An operator must set `schema: "public"`; per-tenant schemas are never covered.
- Impact: default config can never certify (false negative); a configured one proves "typed bytea", not "encrypted". The `scope_absent` guard itself is correct and well done (`evidence.ts:97-98`).
- Fix: derive schemas from the store; decrypt-probe one row per column.
- Effort: M

### R19-07 [Medium] [CONFIRMED] [Compliance claim] Certification report is a self-assessment with an unkeyed seal and no consumer
- Where: `packages/certification-runtime/src/report.ts:53-69,125`, `packages/certification-runtime-pg/src/report-store.ts:25-48`.
- Evidence: `sealedSha256 = sha256(canonical JSON)` — no key, no signature, not anchored in the forensic chain, stored in the same row as the data; anyone who can `UPDATE meta.certification_reports` recomputes it. `verifyCertificationReportSeal`, `formatCertificationReport`, `latestForFramework`, `listByFramework`, `listRecent` have no non-test caller in `apps/` (grep) — reports are written and never read by any route. The catalog is 4 controls (`controls.ts:44-111`); a SOC 2 report covers ~8 of the Trust Services criteria ids, HIPAA 7 citations. No change management, vulnerability management, vendor, HR, monitoring, incident response, MFA, or network controls.
- Wording: `"CERTIFIABLE"/"NOT CERTIFIABLE"` (`report.ts:125`), `certifiable: boolean`, package name "certification", `Certification: soc2_type2`. Nothing says "self-assessment". No auditor is involved; `accepted_by_auditor` evidence status has no writer.
- Impact: an acquirer must not treat `certifiable: true` as SOC 2/HIPAA readiness. Honest label: automated internal control monitoring over 4 technical signals.
- Fix: rename (`readiness`), sign + chain-anchor the report, expose a read route, state scope.
- Effort: S (wording) / M

### R19-08 [Medium] [CONFIRMED] [Logic] Campaign scope predicates do not implement their names
- Where: `packages/access-reviews/src/scope.ts:126-135`.
- Evidence: `case "all_users_with_role": return principal.principalType === "user";` (ignores `roleSlug`); `case "all_tenant_admins": return principalType === "user" && (!scope.includePlatformAdmins || principal.tenantId === null)` — matches every user, and with `includePlatformAdmins: true` matches *only* platform users (inverted); `case "custom_predicate": return true;` (predicate string never evaluated).

### R19-09 [Medium] [CONFIRMED] [Compliance claim] "Live grants" are the process's own API-key specs, not the user/membership tables; principal id is a hash of the secret
- Where: `apps/operate-server/src/live-grants.ts:118-139`, `apps/operate-server/src/principals.ts:80-87`.
- Evidence: `apiKeyPrincipalProvider` builds principals from `--api-key`/`OPERATE_API_KEY_SPECS`; real login users (`meta.users` / `meta.user_tenant_membership`) are never enumerated. `userId: subjectToUuid(spec.key)` = first 128 bits of unsalted `sha256(apiKey)` (122 bits kept), persisted to `access_review_items.principal_id`, `principal_label` and the sealed bundle; the spec's own named principal id is ignored. `grantedAt` is the Unix epoch, `mfaStatus: "none"`, `lastLoginAt: null` → every item scores high risk.
- Impact: access reviews do not cover the people who log in. A fast unsalted hash of a bearer credential is written to tenant-readable rows (offline verifier for low-entropy keys).
- Fix: source from membership table; use the spec's principal id, never the key.
- Effort: M

### R19-10 [Medium] [CONFIRMED] [Supply chain] Pack signature has no trust root; review exemption is self-declared
- Where: `packages/marketplace/src/signing.ts:97-107`, `packages/marketplace-runtime/src/submission.ts:71-82`, `packages/marketplace/src/packs.ts:203-214`, `apps/operate-server/src/marketplace-admin.ts:34-41,109-121`.
- Evidence: `verifyPackSignature` checks the signature against `publicKeyBase64` supplied by the submitter in the same body (`marketplace-authoring.ts` `SubmitBodySchema.publicKeyBase64`) or by the catalog file entry (`publisherPublicKeyBase64`). No registry of publisher keys, no binding of key→author. `requiresElevatedReview` returns false when `pack.author.kind` is `crossengin_official`/`certified_partner` — a field inside the submitter-authored manifest; `submit` then sets `securityReviewStatus: "exempt"`, which satisfies the stable-channel publish gate (`submission.ts:118-123`). The "community packs cannot request PHI access" rule (`packs.ts:165`) is bypassed the same way.
- Also: signature covers the manifest only; `bundleSha256`, `manifestSha256`, `packId`, `version` in the submit body are never checked against the signed manifest (`submission.ts:83-94`), and the manifest itself is not stored (`version-store.ts:75-80` columns).
- Impact: signing proves only self-consistency. Any `pack_author` can self-exempt from security review. Mitigated today because a reviewer-role principal must still call `publish`, the flag is off by default, and packs carry no payload (R19-12).
- Fix: platform-held publisher key registry; platform-assigned author kind; recompute hashes server-side.
- Effort: M

### R19-11 [Medium] [CONFIRMED] [AuthZ/Integrity] Published pack versions are mutable by any author; no ownership, no state guard, read-modify-write race
- Where: `packages/marketplace-runtime-pg/src/version-store.ts:72-122` (`ON CONFLICT (pack_id, version) DO UPDATE SET status = EXCLUDED.status, ... signature = EXCLUDED.signature ...` unconditional), `apps/operate-server/src/marketplace-authoring.ts:81-95,157-185`.
- Evidence: `buildSubmitHandler` → `engine.submit` builds a fresh `draft` record with no existence check → upsert overwrites an existing row, including a `published` one, replacing signature/bundle hash and resetting review state. `submitForReview`/`withdraw` are gated only on role `pack_author` — no check that the caller authored that pack (there is no author/owner column). Transitions load the row, mutate in memory, and upsert with no `WHERE status = <expected>`; two concurrent requests (e.g. reviewer records `failed` while a stale `publish` on a beta-channel version lands) are last-writer-wins. Reviewer and publisher may be the same principal; nothing prevents a principal holding both roles from reviewing their own pack.
- Impact: any author can withdraw or silently replace any other publisher's published version. Latent: `--marketplace-authoring` is off by default and the install catalog does not read this table.
- Fix: immutable published rows; owner column; status guard in the UPDATE predicate; four-eyes.
- Effort: M

### R19-12 [Medium] [CONFIRMED] [Claims vs reality] Marketplace install is a status row: no payload, dead-end lifecycle, catalog disconnected from the registry
- Where: `apps/operate-server/src/marketplace-admin.ts:98-130,143-163`, `apps/operate-server/src/node.ts:1321-1339`, `packages/marketplace/src/installations.ts:22-33`.
- Evidence: (a) `PackManifest` (`packs.ts:79-102`) has no entities/workflows/code field and no bundle is ever uploaded or stored — an installed pack can do nothing (declarative or otherwise); nothing reads `pack_installations`/`permissionGrants` outside the store (grep). (b) The install handler calls `engine.install` only; no route calls `grant` or `complete`, so an installation rests at `installing` or `permission_pending` forever; `uninstall` requires `installed` (`installing: ["installed","failed"]`) so it always returns 409; and the stuck row counts as active, so re-install is rejected `already_installed`. (c) The install catalog is a static file (`--pack-catalog`) carrying its own `securityReviewStatus` and public key; versions published through the authoring flow (`meta.pack_versions`) never reach it. (d) Compatibility is checked against constants for every tenant: `region: "us-east", planTier: "professional", compliancePacks: []` (`node.ts:1330-1336`). (e) `dependencies` are declared and never resolved at install. (f) No unique index on active `(tenant_id, pack_id)` (`kernel/src/bootstrap/meta-schema.ts:2477-2480` is a plain index) → concurrent installs both pass the in-memory `already_installed` check. (g) Admin role is hardcoded `erp_admin`, a tenant-level ERP role.
- Impact: "third-party marketplace" is contracts + two disconnected CRUD surfaces. Supply-chain execution risk is correspondingly nil today.
- Effort: L

### R19-13 [Medium] [CONFIRMED] [Residency] Region guard is fail-open, header-keyed, and is the only residency mechanism
- Where: `apps/operate-server/src/server.ts:142-158`.
- Evidence: `if (hint === undefined || hint === "") return null;` and `if (profile === null) return null;` — a request without `x-tenant-id` (API-key auth carries the tenant in the credential, so the header is unnecessary) or for a tenant with no profile is served. The code comment says "A tenant with no residency profile is unconstrained"; `RegionRouter.route` documents the opposite ("An unknown tenant denies (fail-closed)", `packages/residency-runtime/src/router.ts:39-46`) and has no caller. The decision is made before authentication on an attacker-controlled header and is never re-checked against the authenticated tenant.
- No data placement: there is one Postgres; nothing routes storage, backups, LLM calls or files by region. `allowedLlmProviders`, `dataClass`, `detectCrossRegionViolation`, `selectServingRegion`, `minimumProfileForPacks`, `buildMigrationPlan` have no caller outside the package (grep). Region migration is a 7-step plan shape with no executor.
- `PostgresTenantResidencyDirectory.upsert` has no caller, so `meta.tenant_residency_profiles` has no writer and `--residency-store` resolves `null` (⇒ serve) for every tenant unless rows are inserted by hand.
- Impact: residency is a cooperative request-misdirection hint (421/403), not an enforcement or data-locality control. A tenant with an `eu-only` profile is served from a `us-east` instance if the client omits one header.
- Fix: evaluate after auth on the resolved tenant; deny on unknown when a guard is configured.
- Effort: S (guard) / L (real residency)

## Verified strengths
- All SQL in the five pg packages is parameterised; schema identifiers are regex-validated before interpolation (`marketplace-runtime-pg/src/installation-store.ts:7,67-69`, `residency-runtime-pg/src/directory.ts:7,33-35`); tenant ids validated before `set_config` (`tenant-context.ts`).
- `evidenceFromEncryptionCoverage` refuses zero-scope as satisfaction (`certification-runtime/src/evidence.ts:97-105`); an empty forensic chain yields no evidence rather than a pass (`apps/operate-server/src/certification.ts:307`); `assessControl` is `not_assessed` on missing evidence and `certifiable` requires zero deficient/not-assessed (`assessment.ts:45-47,102`).
- Evidence store: rates quantised before hashing; `seal()` re-asserts status and every figure in the UPDATE predicate (`access-reviews-runtime-pg/src/evidence-store.ts:275-284`); `compile()` refuses to overwrite a sealed pack (`:199-200`); deterministic period-derived id.
- Certification/evidence reads are explicitly tenant-scoped beside RLS (`certification-runtime-pg/src/report-store.ts`, `certification.ts:255-266`).
- Domain-separated canonical signing bytes for packs, attestations, evidence and reports; fingerprint check before Ed25519 verify (`marketplace/src/signing.ts:102-106`).
- `decideRegionRouting` itself is fail-closed and small (`residency-runtime/src/router.ts:22-31`).
- Install routes take the tenant from the authenticated principal, never the body (`marketplace-admin.ts:87-93`).
