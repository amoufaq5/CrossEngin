# R06 — Request edge: api-gateway, api-gateway-runtime, api-gateway-pg, auth, rate-limiting

## Summary (10 lines max)
- Scope is ~9.6k LOC; roughly 40% (`rate-limiting` entirely, half of `api-gateway`) is zod contracts that nothing executes. The executed edge is `api-gateway-runtime/runtime.ts` + `auth.ts`, `packages/auth`, and three stores in `api-gateway-pg`.
- Crypto core of JWT verification is sound (EdDSA-only, kid required, strict Ed25519). Claim validation is not: `exp`/`iss`/`aud`/`sub` are all optional, and a token with no `tenant_id` takes its tenant from the client's `x-tenant-id` header; role = first entry of `scope` with no membership check. Safe only with the in-repo mint; unsafe by default with any external IdP (`--jwks-url`).
- Authorization library (`packages/auth`) is the strongest code here: default-deny, fail-closed ABAC. But read redaction covers only *classified* fields — a per-field read grant on an unclassified field is silently unenforced.
- The 17-stage pipeline has no try/catch around stages (non-handler throws → raw exception text in a 500), skips security headers and redaction on every non-2xx, rate-limits only after successful auth, and can 500 a request after its mutation committed because an observability record fails zod validation (>60 s handlers).
- Idempotency replays return an empty body and cache errors; key scope is (tenant, key). "Postgres" rate limiter counts in process memory and writes one row per request, including unauthenticated ones.
- SQL in api-gateway-pg is parameterised and tenant-scoped twice over; no injection or cross-tenant read found.
- 19 findings: 5 High, 8 Medium, 5 Low, 1 Info. No secrets found in scope.

## Findings

### R06-01 [High] [CONFIRMED] [AuthN / tenant isolation] A verified JWT with no `tenant_id` claim takes its tenant from the client-supplied `x-tenant-id` header
- Where: `packages/api-gateway-runtime/src/runtime.ts:369-371`, `packages/api-gateway-runtime/src/auth.ts:202-213`, `packages/api-gateway-runtime/src/adapters.ts:118-119`; consumer `apps/operate-server/src/principals.ts:91-108`
- Evidence: `if (typeof jwt.payload.tenant_id === "string") { ctx.tenantId = jwt.payload.tenant_id; }` — otherwise `ctx.tenantId` stays `null`. Then `resolvePrincipalForCredential`: `tenantId: authTenant ?? headerTenant` where `headerTenant = input.request.tenantHint` = raw `x-tenant-id` header (`adapters.ts:118`). The deployed resolver (`principalFromJwtClaims`) takes that value verbatim as the principal's tenant (its own doc comment: "the tenant comes from the request's `tenantHint` (the `x-tenant-id` header)"). The mismatch guard (`auth.ts:205`) only fires when BOTH are present.
- Impact: With `--jwks-url` pointing at any IdP whose access tokens do not carry a custom `tenant_id` claim (the default for Auth0/Keycloak/Entra/Cognito), every holder of any validly-signed token chooses which tenant they act in by setting one header: full cross-tenant read/write limited only by the role in `scope`. The in-repo login mint (`--credential-login`) sets `tenant_id`, so that path is not affected. There is no option to require the claim.
- Fix: For `bearer_jwt`, require a string UUID `tenant_id` claim (deny `credential_malformed` otherwise) unless the deployment explicitly opts into header-tenancy; never let `tenantHint` supply the tenant for a credential that has none.
- Effort: S

### R06-02 [High] [CONFIRMED] [AuthN] JWT `exp`, `iss`, `aud`, `sub` are all optional — a token that omits a claim skips that check
- Where: `packages/api-gateway-runtime/src/auth.ts:136-152`, `runtime.ts:360`
- Evidence: `if (typeof jwt.payload.exp === "number" && jwt.payload.exp + skew < now)`; `if (typeof jwt.payload.iss === "string" && jwt.payload.iss !== expectedIssuer)`; `if (aud !== undefined && !audOk)`; `ctx.authPrincipalRef = jwt.payload.sub ?? ""`. A signed token with no `exp` (or `exp` as a string, e.g. `"exp":"1700000000"`) never expires; with no `iss`/`aud` it passes issuer and audience binding; with no `sub` it authenticates as the principal `subjectToUuid("")` — one shared identity for every sub-less token. No `iat` check, no maximum lifetime, no `typ` check, no `jti`/revocation.
- Impact: With a shared third-party JWKS, any token minted by that IdP for a *different* audience/application that happens to lack `aud`, or a non-expiring service token, is accepted. Audience confusion is the classic multi-app IdP attack; "claim absent ⇒ check skipped" is fail-open inside the authentication stage of a repo whose stated invariant is fail-closed. Also undermines the documented session-TTL revocation story (a token without `exp` is permanent).
- Fix: Require `exp` (number), `iss`, `aud`, `sub` (non-empty string); reject otherwise. Add max-lifetime (`exp - iat`) bound.
- Effort: S

### R06-03 [High] [CONFIRMED] [AuthZ] Roles are the first entry of the token's `scope` claim; nothing binds them to a membership
- Where: `packages/api-gateway-runtime/src/runtime.ts:361-368`; `apps/operate-server/src/principals.ts:104,155`
- Evidence: `ctx.authScopes = typeof scope === "string" ? scope.split(" ")… : Array.isArray(scp) ? scp : []`; resolver: `grantedScopes: input.scopes`; `principalRoles: (p) => ({ primaryRole: p?.grantedScopes[0] ?? "anonymous" })`. No directory lookup, no `meta.user_tenant_membership` check on the JWT path (the gateway's `PrincipalResolver` for JWTs is "stateless: the token is the principal").
- Impact: (a) With an external IdP, `scope` is an OAuth scope string that the *client* requests; unless the IdP is locked down per-client, a user who can request `scope=erp_admin` (or `platform_admin`) becomes that role. Combined with R06-01 this is tenant-of-choice + role-of-choice. (b) Revoked memberships / suspended users keep their role until token expiry (and for ever under R06-02). (c) `scp` array elements are not type-checked (`scp as readonly string[]`). (d) Only the first scope is used — ordering of an OAuth scope string decides the role.
- Fix: Use a dedicated roles claim, validated against the manifest's role set, and resolve membership server-side (the table and `PostgresUserStore.membershipFor` exist).
- Effort: M

### R06-04 [High] [CONFIRMED] [AuthZ / data disclosure] Per-field `read` grants are enforced only for *classified* fields; a `fields.<x>.read` grant on an unclassified field is never applied to responses
- Where: `packages/api-gateway-runtime/src/manifest-redaction.ts:156-157`, `packages/operate-runtime/src/compile.ts:950`, `packages/operate-runtime/src/write-mask.ts:47-48`, `packages/auth/src/fields.ts:256-298`
- Evidence: `const classifiedFields = options.classifiedFieldsForEntity(entity.name); if (classifiedFields.length === 0) return null;` — the spec's field list is `classifiedFieldIndex.get(name) ?? []`, built from `resolvedClassifiedFields` (fields with a `classification` only; `packages/types/src/meta-schema/entity.ts:63-70`). `planClassifiedRead` iterates only that list. The classification-unaware `computeFieldRedaction` (which would iterate all field names) is callerless (its own comment, `fields.ts:86-90`). The *write* side explicitly does cover it (`write-mask.ts` comment: "an explicit per-field write grant on an unclassified field is still enforced, because maskWrite takes its candidate set from the grants *and* the classifications").
- Impact: A manifest (pack, Architect-designed, or per-tenant) that declares `permissions.Employee.fields.salary.read = {roles:["hr_manager"]}` on a field with no `classification` serves `salary` to every role holding entity `read`/`list`, while refusing them the write. I found no kernel rule requiring a field grant's field to be classified (`checkFieldGrantCoherence` does not mention classification) — LIKELY accepted by `validateManifest`; whether any shipped pack has such a field was not verified.
- Fix: Build the redaction candidate set from `classified ∪ fields-with-a-read-grant`, exactly as the write mask does; or refuse at validation a read grant on an unclassified field.
- Effort: S

### R06-05 [High] [CONFIRMED] [Error handling / info disclosure] Gateway stages are not wrapped: any throw outside the handler escapes `handleRequest` and the listener returns the raw exception message in a 500
- Where: `packages/api-gateway-runtime/src/runtime.ts:185-191` (bare `await stage()` loop; only `stageDispatchHandler` has a try/catch at 831-872); sink `apps/operate-server/src/node.ts:584-599` (`const detail = err instanceof Error ? err.message : "unknown error"` → body `detail`)
- Evidence: Throw sites inside the pipeline with no catch: `jwks.getPublicKeyForKid` (`auth.ts:127`), `opaqueTokenLookup.lookup` (396), `principalResolver.resolve` (`auth.ts:208`; in deployment this is wrapped by the Postgres ABAC attribute directory), `idempotencyStore.get` (609 — deliberately propagates per `idempotency-store.ts`), `rateLimitChecker.check` (696; Postgres-backed when `--rate-limit-policy` is set, and reached by **anonymous** requests), `persistIdempotency` (875), `applyResponseRedaction` (949), `recorder.build` (201, zod parse of the execution). The handler-throw path was hardened to a constant body (`HANDLER_THREW_CLIENT_DETAIL`, runtime.ts:100) — the stage-throw path was not.
- Impact: Postgres error text (relation/constraint names, connection strings in some driver errors, tenant UUIDs) reaches unauthenticated callers; no `PipelineExecution` is recorded for these requests (the recorder result is lost), so the audit/replay surface has a hole exactly when something is wrong. Also: no security headers on that 500.
- Fix: Wrap the stage loop; map any throw to `internalServerError` with the constant detail, record an `error` stage with the message, and still build the execution.
- Effort: S

### R06-06 [Medium] [CONFIRMED] [Security headers / redaction] Every non-2xx path short-circuits before `transform_response` and `apply_security_headers`
- Where: `packages/api-gateway-runtime/src/runtime.ts:185-191` (`if (denial !== null) { ctx.finalResponse = denial.response; break; }`), 881-902 (handler 4xx/5xx returned as a "denial"), 1042-1053
- Evidence: Security headers (HSTS, CSP, nosniff, XFO, referrer-policy) are merged only in stage 16; any 401/403/404/409/422/429/500 (gateway-generated *or* handler-returned) and the idempotent replay / OPTIONS short-circuits break out at an earlier stage. Same for redaction: `applyResponseRedaction` is never run on a handler response with status ≥ 400.
- Impact: (a) Error responses — the ones most likely to reflect attacker-controlled input (`no route for ${method} ${path}`, runtime.ts:518) — are served without `x-content-type-options`/CSP/HSTS. They are JSON, so exploitability is low, but the "default security headers applied" claim is true only for successes. (b) Handler error bodies are an unredacted channel by construction; today's operate-runtime 4xx bodies carry field *names*, a workflow state value (`'${t.name}' cannot fire from '${current}'`, handlers.ts:661) and `currentUpdatedAt`, not classified values — but any future handler that echoes a record in a 409/422 leaks classified fields with no stage to stop it. (c) `unique_violation` 409 is an existence oracle on a classified unique field (e.g. `mrn`) for a role that cannot read it.
- Fix: Run stages 15–17 unconditionally (finally-style) on whatever `finalResponse` is.
- Effort: S

### R06-07 [Medium] [CONFIRMED] [Brute force] Rate limiting runs after authentication and principal resolution; failed authentication is never rate-limited or counted
- Where: `packages/api-gateway-runtime/src/runtime.ts:165-183` (order: authenticate #5, resolve_principal #6, …, check_rate_limit #11), 340-356 / 397-409 (401 returned before stage 11)
- Evidence: A wrong `x-api-key` or bad JWT returns at stage 5; `stageCheckRateLimit` is never reached. Bucket keys are `tenant|principal|operationId` (`stores.ts:171`; PG checker uses the same dimensions) — there is no IP/credential-prefix scope in any executed checker, although `rate-limiting` models `ip_address` scopes.
- Impact: Unlimited online guessing of API keys (which are static, operator-chosen strings from `OPERATE_API_KEY_SPECS`, compared by `Map.get`) and unlimited JWKS/Ed25519 verification work per unauthenticated request. Anonymous requests that pass stage 5 all share one `anon|anon|<op>` bucket, so one anonymous client can exhaust the anonymous budget for a route for everyone (minor, since anonymous requests get 401 from handlers anyway).
- Fix: Add a pre-auth limiter keyed on client address (with a trusted-proxy rule for XFF) and count auth failures.
- Effort: M

### R06-08 [Medium] [CONFIRMED] [Idempotency] Replay returns the stored status with an EMPTY body; error outcomes are cached and replayed; no reserve step
- Where: `packages/api-gateway-runtime/src/runtime.ts:662-683`, 913-945; `packages/api-gateway/src/idempotency.ts` (evaluateIdempotency)
- Evidence: `const replayResponse = { status, headers: {"x-idempotent-replay":"true","content-length":"0"}, bodyBytes: null }` — only `responseSha256` is stored (`responseStorageUri: null`), never the body. `persistIdempotency` stores `completed_error` for 4xx/5xx handler results too and `evaluateIdempotency` replays any completed record with a matching hash.
- Impact: A client retrying a `POST` create after a lost response gets `201` with no body — it never learns the id of the record it created (and the UI/SDK will treat an empty 201 as malformed). A transient 5xx or a 409 returned by a handler is pinned for the TTL (24 h): retrying the same key after the cause is fixed replays the failure with an empty body. Two concurrent requests with the same key both execute (get → handler → put; documented as `IDEMPOTENCY_GUARANTEE` but it is the case the header exists for). Mitigating: handler *throws* are not persisted (catch returns before `persistIdempotency`).
- Fix: Store and replay the response body (or refuse replay with a 409 "already completed" that names the resource), do not cache 5xx, add an `in_progress` reservation row.
- Effort: M

### R06-09 [Medium] [CONFIRMED] [Idempotency scoping] Key namespace is (tenant, key) only — not principal, not route
- Where: `packages/api-gateway-runtime/src/runtime.ts:609` (`idempotencyStore.get({tenantId, key})`), 927 (`id: idem_${sha256(key + tenantId)}`); `packages/api-gateway-pg/src/idempotency-store.ts` (lookup by `tenant_id, idempotency_key`)
- Evidence: The request hash covers `method, path, principalId, bodySha256` (611-616), so a different principal or route reusing a key gets `replay_hit_mismatch` (409) rather than a replay — no cross-principal response leak. Cross-tenant replay is not possible (tenant comes from the credential).
- Impact: Any member of a tenant can (i) probe whether a given Idempotency-Key has been used in the tenant (409 vs normal processing) and (ii) pre-burn predictable keys (e.g. order numbers used as keys by another integration) so the legitimate caller's request is refused 409 for 24 h — a same-tenant denial of service. Also the check runs for GET (lookup issued for any method when a key header is present) and before the rate limit, so each request with a random key costs a DB read.
- Fix: Scope the key by `(tenant, principal, operationId, key)`.
- Effort: S

### R06-10 [Medium] [CONFIRMED] [Robustness] A principal whose role is not in the manifest crashes authorization with a 500 instead of a 403
- Where: `packages/auth/src/roles.ts:16-19` (`throw new UnknownRoleError(name)`), `packages/auth/src/rbac.ts:74`, `packages/auth/src/fields.ts:98,145,357,448`; caller `packages/operate-runtime/src/handlers.ts:246-263` (no catch; no reference to `UnknownRoleError` anywhere in operate-runtime)
- Evidence: `resolveEffectiveRoles` throws for an unknown *primary* role. `rbacCheck`/write masks do not map it. Only response redaction guards it (`redaction.ts:129` maps to `__unprivileged__`). The role comes from the JWT `scope` (R06-03), so any token whose first scope is e.g. `openid` produces `handler_threw: unknown role 'openid'` → 500 on every entity route.
- Impact: Fail-closed (no access), but a client-controllable 5xx: breaks IdP interop, pollutes error budgets/SLO burn (the SLO loop pages on 5xx), and is retried by clients. Also inconsistent with the redaction path's choice.
- Fix: Treat unknown roles as granting nothing in `resolveEffectiveRoles` callers on the request path (403).
- Effort: S

### R06-11 [Medium] [CONFIRMED] [Correctness] A successful request whose handler takes > 60 s (or > 300 s total, or spans a backwards clock step) returns 500 *after* the mutation committed
- Where: `packages/api-gateway/src/pipeline.ts:50` (`durationMs: z.number().int().min(0).max(60_000)`), `:103` (`totalDurationMs … .max(300_000)`), `:56-64` (`completedAt cannot precede startedAt`); thrown from `packages/api-gateway-runtime/src/pipeline-runner.ts:42` (`StageResultSchema.parse(result)`) and `:131` (`PipelineExecutionSchema.parse`), called at `runtime.ts:903-909` (after the handler returned and after `persistIdempotency`) and `runtime.ts:201`
- Evidence: `rec.record({stage:"dispatch_handler", outcome:"pass", startedAt, completedAt: this.now(), …})` zod-parses a duration computed from wall-clock `Date`s. Neither call is inside a try; the ZodError escapes `handleRequest` to the listener's 500 (R06-05), carrying the zod issue JSON as `detail`. Same failure if `principalId`/`tenantId` on the execution are not UUIDs (`pipeline.ts:99,111`) — `parseApiKeySpec` (apps/operate-server/src/principals.ts:49-66) validates neither, so an operator spec like `key:role:acme` makes **every** authenticated request 500 after its handler ran.
- Impact: Long-running synchronous routes exist by the repo's own account (the synchronous Article 17 tenant-deletion route "a large tenant can outlast", AI design, bulk lists). Such a request destroys/commits, then answers 500 with a schema dump; a client retries; without an idempotency key the retry re-executes, with one it gets an empty-bodied replay (R06-08). An observability record's validation is on the response's critical path.
- Fix: Never let execution-record validation fail the response: clamp/saturate durations, use a monotonic clock, `safeParse` and degrade the record.
- Effort: S

### R06-12 [Medium] [CONFIRMED] [Rate limiting / DoS] `PostgresRateLimitChecker` counts in process memory; Postgres is only a per-request decision log — which unauthenticated traffic can grow without bound
- Where: `packages/api-gateway-pg/src/rate-limit-checker.ts:124` (`private readonly buckets: Map<string, WindowState> = new Map()`), `:182-189` (counter read/write on the Map), `:208-219` + `:263-351` (one awaited `INSERT` in its own transaction per decision, allowed *and* denied), `packages/api-gateway-pg/src/pipeline-execution-store.ts:98-108` (`tenantId === null` → platform write elevation)
- Evidence: No statement reads a count back from `meta.rate_limit_decisions`; the window state lives only in `this.buckets`. The algorithm is a fixed window anchored at first hit (`nowMs - bucket.windowStartMs >= windowSeconds*1000`), not sliding. Buckets are never evicted (same in `InMemoryRateLimitChecker`, `stores.ts:136`). Anonymous requests reach stage 11 with `tenantId: null`, so each one — including every *denied* one after the anon bucket is exhausted — writes a platform-scope row.
- Impact: (a) Limits are per replica and reset on restart — N replicas give N× the declared limit; the deployed default without `--rate-limit-policy` is `InMemoryRateLimitChecker({limit: 10_000})` per (tenant, principal, operation) per minute (`packages/operate-runtime/src/compile.ts:999`), i.e. effectively none. (b) With `--rate-limit-policy` on, an unauthenticated flood to any existing route produces one DB transaction + one permanent row per request (no reaper for this table was found in scope) — the rate limiter converts a request flood into a storage/IO flood. (c) Unbounded Map keyed by principal id.
- Fix: Keep counters in a shared store (or accept per-replica and say so), do not persist denied/anonymous decisions synchronously, sample or batch the log, evict buckets.
- Effort: M

### R06-13 [Medium] [CONFIRMED] [AuthN availability / JWKS trust] Remote JWKS refresh runs on the request path with no timeout, no single-flight, and a 200 with no usable keys wipes the key set (adjacent file, one hop out of scope)
- Where: `apps/operate-server/src/jwks.ts:71-78` (`await this.refresh()` inside `getPublicKeyForKid`), `:95-104` (`this.keys = parsed` unconditionally on `res.ok`), `:66` (`globalThis.fetch(url)` with no `AbortSignal`)
- Evidence: When the cache is stale every concurrent request awaits its own `fetch`; a stalled IdP stalls every Bearer request indefinitely. `parseJwksDocument` returns an empty Map for any non-JWKS JSON, and `refresh` then replaces the last good set — contradicting the class comment "A failed refetch keeps the last good key set". Unknown-`kid` tokens can force a refetch every 10 s (`minRefetchMs`). Only `kty=OKP, crv=Ed25519` keys are kept; no `use`/`alg`/issuer binding — every key in the document is trusted for every issuer/audience (matters with R06-02).
- Impact: Authentication outage coupled to IdP latency; an unauthenticated attacker can drive periodic outbound fetches. An IdP that publishes RS256 keys only (the common default) yields zero usable keys → every JWT 401.
- Fix: Timeout + single-flight; keep last-good on empty parse; bind keys to issuer.
- Effort: S

### R06-14 [Low] [CONFIRMED] [AuthN] API keys: plain `Map.get` lookup of the raw secret; the constant-time matcher is dead code
- Where: `apps/operate-server/src/principals.ts:148-151` (`const spec = byKey.get(token)`), `packages/api-gateway-runtime/src/auth.ts:223-225` (`buildOpaqueCredentialMatcher` — zero non-test callers in the workspace)
- Evidence: Keys are held in memory in plaintext, keyed by the secret itself; `principalRef: spec.key` puts the raw API key into `ctx.authPrincipalRef` and into `PrincipalResolverInput.principalRef` (any resolver decorator or log line that prints the ref prints the key; the ABAC attribute decorator receives it). No key hashing, no prefix/ID split (the contract's `ce_(live|test)_…` prefix model in `auth-resolution.ts:63-66` is unused), no rotation, no per-key expiry. Keys are accepted from the `x-api-key` header only (good — no query-string route).
- Impact: Timing side channel is theoretical for a hash-map lookup; the real weaknesses are static, non-expiring, unrate-limited (R06-07) bearer secrets and the secret being used as an internal identifier.
- Fix: Store SHA-256 of keys, look up by non-secret key id, compare with `constantTimeEqualHex`.
- Effort: S

### R06-15 [Low] [CONFIRMED] [Idempotency / PG] Unvalidated key, lookup ignores the unique key's `operation_id`, upsert keeps a stale request hash
- Where: `packages/api-gateway-runtime/src/runtime.ts:594-595` (any header string is a key; `IdempotencyKeyShapeSchema` min 8/max 255/charset is never applied), `packages/api-gateway-pg/src/idempotency-store.ts:98-100` (`WHERE tenant_id = $1 AND idempotency_key = $2 LIMIT 1`, no `ORDER BY`) vs `:119` (`ON CONFLICT (tenant_id, operation_id, idempotency_key)`), `:120-127` (the `DO UPDATE SET` list omits `request_hash_sha256`, `principal_id`, `received_at`)
- Evidence: After a record expires (`replay_expired` → pass), reusing the key on the same operation with a different body updates status/expiry but leaves the *old* hash, so the genuine retry of the new request is then refused 409 `replay_hit_mismatch`. Reusing an expired key on a different operation inserts a second row; `get` may then return either row. `replay_in_progress` falls through to `pass` (`runtime.ts:684-691`) — moot today because nothing writes `in_progress`. A route with `idempotencyRequired` accepts a 1-character key.
- Impact: Edge-case false 409s and a guard weaker than its contract; no cross-tenant exposure (every statement is tenant-predicated *and* tenant-context scoped).
- Fix: Validate key shape at the gateway (400), include `operation_id` in the read, update the hash on re-use after expiry.
- Effort: S

### R06-16 [Low] [CONFIRMED] [Pipeline honesty] Six of the 17 stages are unconditional no-ops that record `pass`; the TLS stage can never fire; the request contract schema is never applied
- Where: `packages/api-gateway-runtime/src/runtime.ts:223-233` (receive), `:547-557` (negotiate_version), `:581-588` (negotiate_content for non-OPTIONS), `:737-747` (validate_request_signature → `no_request_signature_required`), `:749-759` (validate_request_schema → `body_present`), `:1064-1074` (emit_audit → reason `audit_emitted`, nothing emitted); `:263` TLS check vs `apps/operate-server/src/http.ts:68-79` (never passes `tlsVersion`) ; `packages/api-gateway/src/requests.ts:48-126` (`IncomingRequestSchema` — no caller parses it)
- Evidence: `stageEmitAudit` writes a stage result saying `audit_emitted` and calls nothing. `RouteDefinition.requestSchemaSha256` is never consulted; malformed JSON is recorded `body_unparseable_json` and passed on with `parsedBody: null` (`runtime.ts:247-249`). The contract rules "external requests must use https", header-name charset, `path` ≤ 2000 are unenforced because `buildIncomingRequest` constructs the object without parsing. Sunset/deprecation (`routes.ts:137-155`) is not implemented by `InMemoryRouteRegistry.lookup`; a wrong method yields 404 not 405.
- Impact: The persisted `PipelineExecution` (the artefact a replayer/auditor reads) asserts checks that did not happen. Not exploitable by itself; it is a material overstatement for diligence.
- Fix: Remove or implement; at minimum record `skipped`/`fallthrough` rather than `pass`, and stop recording `audit_emitted`.
- Effort: S

## Verified strengths (things that are genuinely done well, with file:line)
- Algorithm confusion is closed: only `alg === "EdDSA"` is accepted (`auth.ts:118`), `kid` is mandatory (`:124`), verification is `crypto.verify(null, …)` over an Ed25519 key built from 32 raw bytes with a strict 64-byte signature length check (`packages/crypto/src/signing.ts:114-135`) — `alg:none` and HS256-with-public-key both fail. Signature is verified before any claim is read.
- No client header can set role or principal: roles come only from the credential (`runtime.ts:361-368,414`), and when the credential carries a tenant a contradicting `x-tenant-id` is a hard 401 `tenant_mismatch` (`auth.ts:205-207`; test at `auth.test.ts:295`).
- Entity-level RBAC is default-deny with no wildcard grants: unknown entity, missing grant, or role not in grant → refused (`rbac.ts:76-107`); role inheritance cycles are detected, not looped (`roles.ts:12-15`).
- ABAC discharge is genuinely fail-closed and centralised: no evaluator, unresolved attributes, a throw, or an out-of-enum answer → `undischargeable` (`abac.ts:197-220`); batch answers must echo their index and length or the whole batch is refused (`abac.ts:233-259`); `deferred` maps to deny via a total map (`abac.ts:22-27`).
- Response redaction fails closed on unknown roles (`redaction.ts:126-129`), per-record pass can only relax the record-free set (`runtime.ts:1017-1025`), and specs are demanded per operation with a hard error when a classified entity has no operation (`manifest-redaction.ts:134-139,208`).
- Handler exceptions no longer leak: constant client detail, message goes to the recorded stage reason (`runtime.ts:100-101,855-871`).
- api-gateway-pg SQL is fully parameterised; table/schema names are module constants; every tenant-scoped statement carries both `set_config('app.current_tenant_id', $1, true)` in the same transaction and an explicit `tenant_id = $n` predicate (`idempotency-store.ts:88-101,112-146`, `pipeline-execution-store.ts:84-108`); tenant ids are shape-asserted before use (`assertScopeTenantId`).
- Rate-limit decision persistence failures are reported, never thrown (`rate-limit-checker.ts:263-351`); undeclared policy fails closed (`:160-178`).
- Idempotency cannot leak across principals or tenants: hash binds method+path+principal+body (`idempotency.ts:171-183`), store is tenant-keyed.

## Claims vs reality (docs/README/CLAUDE.md/comments that the code contradicts)
- CLAUDE.md "EdDSA JWT verification with iss/aud/exp/nbf" and `apps/operate-server/src/principals.ts:92-93` "the gateway has already checked signature + iss/aud/exp/nbf" — each claim is checked only **if present** (`auth.ts:136-152`). The pure contract `resolveAuth` (`auth-resolution.ts:181-193`) *does* require iss/aud equality; the runtime does not use it.
- `auth.ts:191-195` "the `x-tenant-id` request header (`tenantHint`) is only a hint" — it is the authoritative tenant for any JWT lacking `tenant_id` (R06-01).
- CLAUDE.md on `api-gateway-pg`: "sliding-window rate-limit checker" and "the sliding window was per-replica and per-restart [until ADR-0335]" — it is still a per-process fixed window; Postgres holds only the decision log (R06-12).
- CLAUDE.md "the 17-stage per-request pipeline … as real middleware … body parsing, … security headers" — six stages are no-ops recorded as `pass`, `emit_audit` records `audit_emitted` while emitting nothing, security headers and redaction are skipped on every non-2xx (R06-06, R06-16).
- `packages/operate-runtime/src/handlers.ts:228-229` "Field-level redaction happens at the gateway's `transform_response` stage, per-caller — handlers return every field" — true only for *classified* fields on 2xx responses; an explicit read grant on an unclassified field is not enforced (R06-04).
- `apps/operate-server/src/jwks.ts:45-48` "A failed refetch keeps the last good key set" — a 200 with an unusable document replaces it with an empty set (R06-13).
- CLAUDE.md "`api-gateway` — contracts for … idempotency records, content/encoding/language negotiation, … CORS" — accurate as *contracts*; none of negotiation/CORS/version strategies/sunset is executed.
- CLAUDE.md "8 auth schemes × 16 auth outcomes" — 2 schemes execute (bearer_jwt, api_key_header); `principal_disabled`, `principal_locked`, `mfa_required`, `scope_insufficient`, `weak_tls_rejected` outcomes are never produced by the runtime (`mfaProofAgeSeconds` is always `null`).
