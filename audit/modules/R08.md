# R08 — apps/operate-server composition root (bin, node.ts, cli.ts, server/http/edge, health, manifests, tenant gateway cache, schedulers, job routes, entity events, replay, residency)

## Summary (10 lines max)
- The deployed binary is one 4,716-line file whose `serve()` is a single **3,492-line function** (node.ts:883-4374) fed by a **2,533-line** if/else argv parser (cli.ts:528-3060) with **129 distinct serve flags**. One loopback test boots it (memory store, no flags). Everything else in `serve()` is untested wiring.
- The no-flag default is *safe but inert*: memory store, no credentials (every request 401). Nearly every security/ops subsystem is opt-in; the shipped `deploy/docker-compose.yml` passes 9 flags and so runs no audit chain, no rate-limit policy, no tenant-status gate, no scheduler/workers, no notification drain, no user-provisioning route.
- Highest-impact defects are in **per-tenant manifest routing**: a JWT caller that omits `x-tenant-id` is served the deployment's default manifest instead of its tenant's own (and the UI deliberately omits that header); per-tenant gateways silently drop the Postgres rate limiter and the durable idempotency store and reset their in-memory replacements every 30 s; an unauthenticated flood can evict the gateway cache.
- HTTP edge: the top-level 500 handler returns `err.message` to the client; no explicit timeouts/max-connections; no `unhandledRejection` handler; shutdown has no deadline, never closes the pg pool and loses in-flight audit/observer work.
- Residency guard is advisory only: keyed on an optional, unauthenticated header.
- Stripe secrets are argv-only (visible in `ps`). Event-triggered jobs can never match the emitter's names; emitted events copy the whole record (incl. classified fields) into `meta.job_runs`.
- Genuinely good: body-cap enforcement per chunk, /health–/readyz design, deterministic run ids making schedulers replica-safe, three-valued tenant gateway resolution, fail-closed role sets on cancel/admin routes.

## Findings

### R08-01 [High] [CONFIRMED] [AuthZ / tenant isolation of rules] JWT caller without `x-tenant-id` bypasses its tenant's own activated manifest
- Where: apps/operate-server/src/tenant-gateway-cache.ts:43-54, :398-400; packages/api-gateway-runtime/src/auth.ts:203-213; apps/operate-web/app/api/[...path]/route.ts:37-40
- Evidence: `resolveRequestTenant` returns a tenant for a Bearer credential only `if (hint === null || !UUID_RE.test(hint)) return null;` (hint = `x-tenant-id`). `buildPerTenantDispatch`: `if (tenantId === null) return opts.defaultDispatch(raw, body);`. The gateway itself accepts a JWT with no header (`tenantId: authTenant ?? headerTenant`), so the request authenticates and runs against the **boot manifest's** entities, roles, field grants, classification/redaction and ABAC obligations, over the same store object on `--store pg`. operate-web states "deliberately no `x-tenant-id`" — so every UI session (the JWT path `--credential-login` creates) always takes this branch.
- Impact: (a) the headline "tenant activates its AI-designed manifest" feature is not served to browser users at all; (b) any JWT principal chooses, per request, between its tenant's rules and the deployment's by adding/removing a header — stricter per-tenant permissions, write masks or redaction are bypassable. The module's own doc calls serving "their own data under somebody else's rules" the defect (tenant-gateway-cache.ts:186-190) and fixed it only for the `refused` arm. Gated on `--per-tenant-manifests`/`--ai-design` (implied by `--ai-design`, cli.ts:1952); not in the shipped compose.
- Fix: resolve the tenant from the verified credential (decode+verify the JWT before routing, or move per-tenant selection inside the pipeline after `authenticate`); never from the header.
- Effort: M

### R08-02 [High] [CONFIRMED] [Reliability / abuse control] Per-tenant gateways drop the Postgres rate limiter and durable idempotency store; in-memory replacements are discarded every 30 s
- Where: apps/operate-server/src/node.ts:3970-4011 (per-tenant build) vs :3306-3336 (default build); tenant-gateway-cache.ts:7 (`DEFAULT_TTL_MS = 30_000`), :306-307
- Evidence: default build passes `...(rateLimitChecker !== undefined ? { rateLimitChecker } : {})` and `...(idempotencyStore !== undefined ? { idempotencyStore } : {})` (node.ts:3334-3335); the per-tenant `buildOperateHttpServer({...})` call lists neither (grep: the two identifiers occur only at 3198-3335 and 4323). `server.ts:254-266` documents the fallback: `InMemoryRateLimitChecker` and `InMemoryIdempotencyStore`. Each cache expiry rebuilds the gateway, i.e. fresh empty maps. `billingPortal` is also not passed (node.ts:3321 only), so `POST /v1/meta/billing-portal` 404s for such a tenant (route registered only when wired: packages/operate-runtime/src/compile.ts:836).
- Impact: a tenant with an activated manifest has (1) no configured rate-limit policy, with counters reset every 30 s; (2) replay protection that forgets every key within 30 s and is per replica — including on the Article-17 deletion route, which is in `extraRoutes` and *requires* an idempotency key. Comment at node.ts:3958-3964 claims "activating a custom manifest never drops a tenant out of enforcement" — false.
- Fix: pass `rateLimitChecker`, `idempotencyStore`, `billingPortal` to the per-tenant build; add a test asserting option parity between the two call sites (or build both from one options object).
- Effort: S

### R08-03 [Medium] [CONFIRMED] [Information disclosure] Top-level 500 returns the raw exception message to the client
- Where: apps/operate-server/src/node.ts:585-593
- Evidence: `const detail = err instanceof Error ? err.message : "unknown error"; ... JSON.stringify({ type: ".../internal-error", ..., status: 500, detail, ...})`. This catch receives anything thrown by `server.dispatch` outside the gateway pipeline: pg driver errors (host, constraint/table names), tenant directory failures, interceptors (login, bounce webhook), `URL` parse errors, `TenantGatewayCache.build` paths etc. Reachable pre-auth (e.g. malformed request target → `new URL` throws in `splitTarget`, http.ts:41).
- Impact: internal schema/host/SQL detail disclosed to unauthenticated callers; contradicts the care taken elsewhere (tenant-gateway-cache.ts:339-342 "`err.message` must never reach it"). edge.ts:116 has no catch at all (throws to the runtime).
- Fix: fixed body + request id; log the detail server-side.
- Effort: S

### R08-04 [Medium] [CONFIRMED] [DoS] Unauthenticated requests can churn/evict the per-tenant gateway cache and force a DB transaction per request
- Where: apps/operate-server/src/tenant-gateway-cache.ts:49-53, :220-233, :294-302
- Evidence: any request carrying `Authorization: Bearer <anything>` and a syntactically valid UUID in `x-tenant-id` reaches `cache.serverFor(uuid)` **before authentication**; a miss runs `source.activeManifestFor` (a `withTenantContext` transaction, tenant-manifests.ts:328-339) and stores a `none` entry; at `maxEntries` (1000) "the oldest entry is evicted". The doc comment claims "an unauthenticated flood of random tenant headers never reaches the manifest source or the cache" (lines 40-41) — the Bearer-prefix check is not authentication.
- Impact: 1000 random UUIDs evict every real tenant's compiled gateway; each real request then recompiles a manifest (and, on pg-columns, re-enters `ensure`). No single-flight in `serverFor`, so N concurrent requests for a cold tenant do N compiles (also happens for every tenant every 30 s under load).
- Fix: route after authentication; add in-flight promise collapse; do not cache `none` for unauthenticated hints (or use a separate bounded negative cache).
- Effort: M

### R08-05 [Medium] [CONFIRMED] [Compliance] Residency guard is advisory: keyed on an optional unauthenticated header
- Where: apps/operate-server/src/server.ts:137-153
- Evidence: `const hint = ...raw.headers["x-tenant-id"]; if (hint === undefined || hint === "") return null;` — no header, no check; the check is never repeated against the authenticated tenant. API-key and (per R08-01) UI JWT requests normally carry no such header. `profile === null` (unknown tenant) is also unconstrained. Region is a free string cast `options.region as Region` (node.ts:2775).
- Impact: an EU-only tenant's data is served from any region to any client that simply omits the header; the 421/403 only fires for cooperative clients. Not a control an auditor can rely on.
- Fix: enforce post-auth against the credential's tenant (gateway stage or handler decorator like the tenant-status gate); validate `--region` against the `Region` enum.
- Effort: M

### R08-07 [Medium] [CONFIRMED] [Operability] HTTP listener has no explicit timeouts, connection cap, backpressure or error hooks; no process-level rejection handlers
- Where: apps/operate-server/src/node.ts:4303-4306; bin/operate-server.ts:198-214
- Evidence: `const server = createServer((req, res) => { void listener(...) }); await new Promise<void>((resolve) => server.listen(options.port, resolve));` — no `headersTimeout`/`requestTimeout`/`keepAliveTimeout`/`maxConnections`/`maxHeadersCount`, no `server.on("error")` (a bind failure is an unhandled `error` event and the listen promise never settles), no `clientError` handler. Protection is whatever the Node runtime defaults are (Dockerfile pins `node:20-bookworm-slim`: 60 s headers, 300 s request). Each connection may buffer up to 10 MiB (request-body-limit.ts:21) for 5 minutes with no concurrency bound, before auth. `grep unhandledRejection|uncaughtException` over src/ and bin/: none. Dozens of `void this.tick()` timers (scheduler.ts:112-113, prune-scheduler.ts:47-48, manifest-activation-poller.ts:106-108): a throw from an `onError`/`onTick` callback is an unhandled rejection → process exit.
- Impact: slow-body/many-connection memory exhaustion (mitigated only by Caddy in the reference stack); crash-on-stray-rejection with no log context.
- Fix: set timeouts and `maxConnections`; bound concurrent body buffering; add `unhandledRejection`/`uncaughtException` handlers that log and exit non-zero deliberately.
- Effort: S

### R08-08 [Medium] [CONFIRMED] [Operability] Graceful shutdown is incomplete
- Where: apps/operate-server/src/node.ts:4312-4372; bin/operate-server.ts:198-200
- Evidence: `close()` stops timers, then `void Promise.all([auditChain?.observer.drain(), workersDrained, executionCapture?.drain()]).finally(() => server.close(...))`; bin: `void running.close().then(() => process.exit(0));`. (1) The listener keeps accepting new requests during the drain; observers are drained *before* in-flight requests finish, so executions completing afterwards (audit-chain entries, metering, capture) are dropped by `process.exit(0)`. (2) No deadline: a stuck drain or long request holds shutdown until the orchestrator SIGKILLs. (3) The pg pool (`conn`) is never closed; in-flight scheduler ticks (delivery drain, deletion runner, integrity proof) are not awaited — `stop()` only clears the interval. (4) A second SIGTERM re-enters `close()`; `server.close` then errors, the promise rejects with no `.catch` → unhandled rejection, exit code 1. (5) `metering?.flushScheduler?.stop()` with no final flush visible here (SUSPECTED — flush behaviour lives in metering.ts).
- Impact: lost audit/metering records and half-finished background work on every deploy; non-zero exits on routine restarts.
- Fix: stop accepting → await in-flight → drain observers → await scheduler ticks → close pool, all under a deadline; make shutdown idempotent.
- Effort: M

### R08-09 [Medium] [CONFIRMED] [Maintainability / test risk] `serve()` is a 3,492-line function; `parseServeArgs` 2,533 lines; composition is essentially untested
- Where: apps/operate-server/src/node.ts:883-4374; cli.ts:528-3060; node.test.ts:166-178
- Evidence: script-measured lengths (see Code quality). `serve` has ~45 top-level `if (…options.X…)` feature blocks (plus nested ones) sharing 41 top-level mutable `let` locals (node.ts:1404-1417, 2269, 3110, 3198, 3226…) with order-dependent closures (`const registry = () => tenantStoreRegistry`, node.ts:1660, assigned 2,200 lines later at :3895). `buildPrincipalWiring(apiKeys).principalRoles` is rebuilt 17 times. The only test that executes `serve` is "boots a listening server and answers a request" (memory store, no flags). R08-02 is exactly the class of defect this produces: two 40-line option literals that must stay in step and did not.
- Impact: every feature increment edits one function; regression risk is high and invisible; onboarding cost for an acquirer's team is severe. Many features silently `skip` with a `console.warn` when a prerequisite is missing (e.g. node.ts:1719-1731, 3509-3516) rather than refusing the boot, so a mis-typed deployment runs without the control it asked for.
- Fix: split into per-subsystem `mountX(ctx): {routes, schedulers, close}` modules with a typed boot context; table-driven CLI; integration tests per flag group against a real Postgres.
- Effort: L

### R08-13 [Low] [CONFIRMED] [Multi-replica correctness] Cross-replica invalidation is opt-in and incomplete
- Where: apps/operate-server/src/node.ts:2735, :4035-4051, :1676, :1791; manifest-activation-poller.ts:46-50
- Evidence: activation invalidates only the local cache (`onActivated: (tenantId) => gatewayCache?.invalidate(tenantId)`); other replicas converge after the 30 s TTL unless `--manifest-refresh-ms` is set. ### R08-14 [Low] [LIKELY] [Scheduling semantics] Cron producer enqueues only the latest tick and fires the *previous* occurrence for a new tenant; ticks can overlap
- Where: apps/operate-server/src/scheduler.ts:110-145; packages/jobs/src/cron.ts:448 (`cronPrevOnOrBefore`)
- Evidence: each tick asks for the most recent occurrence ≤ now per job per tenant. Occurrences between two scheduler ticks (interval > cron period, downtime, slow sequential per-tenant loop) are never enqueued; on first sight of a tenant the last occurrence — possibly months old — is enqueued immediately. `setInterval(() => void this.tick())` has no in-flight guard; the tenant loop is sequential with one INSERT per job per tenant per tick (N tenants × M jobs round trips).
- Impact: missed runs under load/outage; surprising catch-up run of e.g. a period-close job on tenant creation. Latent today (no handlers, R08-10).
- Fix: persist a per-(tenant, job) high-water mark; guard re-entrancy; batch inserts.
- Effort: M

In-process state that does not scale horizontally: default rate limiter and (without the flag) idempotency maps; tenant gateway cache; tenant-status, ABAC-attribute and column-key caches (TTL-bounded); SLO rolling windows and incident-episode memory; request-id counter; `PAGE`/escalator edge-triggered state. Schedulers are replica-safe only where the write is idempotent (cron enqueue: deterministic run id, scheduler.ts:99-101); no advisory lock or leader election exists for the delivery drain, deletion runner, integrity proof, checkpoint, SLO or Stripe-usage schedulers started at node.ts:4281-4297 — their duplicate-safety rests on each store (not verified here).

## Verified strengths (things that are genuinely done well, with file:line)
- Body cap enforced per chunk before buffering, no "unlimited", shared by Node and Fetch paths: request-body-limit.ts:125-145, node.ts:557, edge.ts:57.
- Health probes: liveness touches nothing, readiness is `SELECT 1` with in-flight collapse and a timeout race; response is a closed vocabulary (check name + enum), no versions/timings/errors: health.ts (buildReadinessProbe, readinessResponseBody).
- Tenant gateway resolution is three-valued and refuses (503, no message leak) rather than falling back when a valid manifest cannot be built: tenant-gateway-cache.ts:251-266, 347-377. Stored manifests are re-validated (zod + kernel cross-validation) before compile: :235-250.
- Job cancel: tenant from credential, principal recorded, run id validated, store error not leaked, empty role set refuses: job-cancel-routes.ts:123-168.
- Manifest activation serialised per tenant with an advisory xact lock; every query binds `tenant_id` and runs in tenant context: tenant-manifests.ts:306-326.
- Cron enqueue is idempotent across replicas by deterministic run id + `ON CONFLICT DO NOTHING` (packages/workflow-runtime-pg/src/job-enqueue.ts:171-190).
- New secrets are env-only with weak-secret refusal and password-on-argv refused by name: node.ts:669, 993, 1102; cli.ts:2966-2972.
- Boot is loud: PHI storage, cursor disclosure, DB TLS assurance, unique enforcement are printed either way and several unsafe combos refuse to boot (node.ts:676, 1003, 1065).

- tenant-gateway-cache.ts:37-39 the header "is honored only for … a JWT, whose tenant the gateway's cross-check will verify" — true when present; the absent-header case silently selects the wrong gateway (R08-01).
- CLAUDE.md "`operate-server` … framework-neutral `dispatch` core with a Fetch/Workers edge adapter — both now enforce…" — adapter has no deployed caller (R08-16).
- CLAUDE.md describes residency as "enforced, pre-auth on every request" — only on requests that volunteer the header (R08-05).
- compose comment lines 94-97 (credentials never on argv) vs `--stripe-api-key`/`--stripe-webhook-secret` having no other route (R08-06).
- scheduler.ts:99-101 "running this on every replica … safe" — true for duplication; silent about missed occurrences (R08-14).
- CLAUDE.md's own P1 item ("event names can never match") is confirmed in code (R08-10).
