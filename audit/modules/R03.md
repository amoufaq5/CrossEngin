# R03 — packages/operate-runtime-pg (all src) + kernel-pg/src/{connection,node-pg}.ts

## Summary (10 lines max)
- Value binding is disciplined: every runtime value (tenant id, ids, filters, cursor components, LIKE terms, the pgcrypto key) is a bound parameter; identifiers go through `quoteIdent`'s allow-list regex. I found no injection through query strings, cursors, sort/filter names or schema names.
- One real injection sink remains: a manifest field `default: {kind:"expression"}` is an unvalidated `z.string().min(1)` that is concatenated raw into `CREATE TABLE` / `ALTER TABLE … ADD COLUMN … DEFAULT <expr>` and sent over the simple-query protocol (multi-statement capable). Reachable from per-tenant activated (AI-authored) manifests.
- RLS is decorative on the column store. Policies are created without `FORCE ROW LEVEL SECURITY`, the serving role must own the tables (it runs `ALTER TABLE`/`DROP POLICY` on every boot) and in the shipped compose it is the cluster superuser. Isolation therefore rests solely on the explicit `tenant_id = $1` predicates — which are present on every statement I traced.
- Tenant context is set correctly: `set_config(..., true)` inside an explicit transaction on one pooled client; no session-level leak.
- Concurrency is weak: READ COMMITTED, `get` never locks, so the handler's optimistic-concurrency check and write guards are check-then-act. The sequence allocator runs in its own transaction before validation, so numbers are burned (not gapless).
- Boot DDL is non-transactional, unlocked, non-CONCURRENT, and re-validates every FK on every boot.
- A re-activated tenant manifest that is "refused" silently flips the tenant from their typed tables to the JSONB store (data appears to vanish; new writes fork).
- Pool has no error handler, no timeouts, no size config.
- Tests are 100% fake-connection SQL-shape tests; nothing in this package executes SQL.

## Findings

### R03-01 [High] [CONFIRMED sink / LIKELY end-to-end] [Injection] Manifest `default.expression` is raw SQL concatenated into DDL (multi-statement capable)
- Where: `packages/kernel/src/ddl/column.ts:15` (`if (value.kind === "expression") return value.expression;`); `packages/types/src/meta-schema/field.ts:45-48` (`expression: z.string().min(1)` — no other constraint); consumed at `packages/operate-runtime-pg/src/column-plan.ts:140` (`defaultSql: … emitDefault(field.default)`), emitted at `entity-ddl.ts:263` (`` ` DEFAULT ${c.defaultSql}` ``) into `CREATE TABLE` (`entity-ddl.ts:286,297`) and `ALTER TABLE … ADD COLUMN IF NOT EXISTS` (`entity-ddl.ts:196`); executed at `tenant-schema-apply.ts:249` (`await tx.query(stmt)`) and `column-store.ts:291`.
- Evidence: grep for `expression` in `packages/kernel/src/manifest/*.ts` (validation) returns nothing; no reader other than `emitDefault`. `node-pg.ts:50,100` passes `params === undefined ? undefined` → node-postgres simple protocol, which accepts several statements per string (`rowsResult` at `node-pg.ts:35-44` explicitly handles the multi-result array). Per-tenant path: `apps/operate-server/src/node.ts:3969` `tenantStoreRegistry.ensure(tenantId, tenantManifest)` → `applyTenantManifestSchema`. The tenant manifest comes from the AI design flow (`ai-design.ts:759` `ManifestSchema.safeParse` + `validateManifest`), neither of which inspects the expression. `apps/operate-server/src/manifest-diff.ts` contains no occurrence of `default`, so the reviewer's diff view does not surface it (one hop not traced in full — hence LIKELY for the whole chain).
- Impact: a tenant who can steer the Architect (prompt) into emitting e.g. `default:{kind:"expression",expression:"0); COMMIT; <any SQL>; BEGIN; CREATE TABLE IF NOT EXISTS x(a int"}` gets arbitrary SQL as the serving role once the proposal is approved and activated. `COMMIT` inside the batch defeats the surrounding transaction's rollback. In the shipped compose the serving role is `POSTGRES_USER` (`deploy/docker-compose.yml:14,23`) i.e. the initdb superuser → cross-tenant read/write of every table and `COPY … TO PROGRAM` on the DB host. Even a single-expression payload is harmful: `DEFAULT current_setting('app.column_encryption_key', true)` on a plaintext column exfiltrates the tenant's column key through the API; a volatile `DEFAULT pg_sleep(…)` on `ADD COLUMN` rewrites/locks the table.
- Fix: replace free-form expression with a closed enum (`now()`, `gen_random_uuid()`, `CURRENT_DATE` …) in `DefaultValueSchema`; reject anything else in `validateManifest`; additionally refuse `;`, `--`, `/*`, `$$` defensively in `emitDefault`.
- Effort: S

### R03-02 [High] [CONFIRMED] [Tenant isolation] RLS on entity tables is not effective for the serving role; no FORCE ROW LEVEL SECURITY
- Where: `entity-ddl.ts:307-309` (`ENABLE ROW LEVEL SECURITY` + `CREATE POLICY … USING (…)`, no `FORCE`), same for join tables `entity-ddl.ts:417-419`. `column-store.ts:284-311` `ensureSchema` runs `CREATE SCHEMA`, `CREATE EXTENSION`, `ALTER TABLE`, `DROP POLICY`, `CREATE INDEX` as the serving connection on every boot (`apps/operate-server/src/node.ts:808`).
- Evidence: `grep -rn "FORCE ROW LEVEL"` over non-test sources hits only `kernel-pg` introspection/rekey code, never an emitter. A role that can `ALTER TABLE`/`DROP POLICY` is the owner; owners (and superusers) bypass non-forced RLS. Compose connects as the superuser (`deploy/docker-compose.yml:14`).
- Impact: the "second belt" does not exist on the column store (nor, in the compose, on the JSONB store). Isolation depends on every statement carrying `tenant_id = $1` — true today for every statement in this package (see strengths), but a single future omission is a cross-tenant leak with no backstop. Comments claiming RLS confines (`entity-store.ts:90-91` "the RLS policy (not just the WHERE…) confines the query", `sequence-store.ts:13-14`, `settings-store.ts:13`, `subscription-store.ts:29`) are false for the deployed role.
- Fix: split roles (migrator/owner vs. `NOBYPASSRLS` runtime role with DML grants only), add `FORCE ROW LEVEL SECURITY`, move DDL out of the serving process; add a live non-owner test in CI.
- Effort: M

### R03-03 [High] [CONFIRMED mechanism / LIKELY business impact] [Concurrency] No row lock on read-for-check; default READ COMMITTED; optimistic concurrency and write guards are check-then-act
- Where: `node-pg.ts:106` (`BEGIN` — default isolation); `column-store.ts:446-458` `getOn` (plain `SELECT … LIMIT 1`); `entity-ops.ts:126-138` `getOp` (no `FOR UPDATE`); `EntityStore` has no locking read. Consumer: `packages/operate-runtime/src/handlers.ts:505,522-524` (`before = await store.get(…)`; `if (current !== expectedUpdatedAt) return 409`).
- Evidence: column-store `updateOn` (`column-store.ts:529-532`) is a blind `UPDATE … WHERE tenant_id=$1 AND id=$2` with no `updated_at = $expected` predicate. Two concurrent PATCHes with the same `expectedUpdatedAt` both read the same row, both pass, both write: last writer wins silently. Only the JSONB `updateOp` locks (`entity-ops.ts:165` `FOR UPDATE`), and only for its own internal read, after the handler's check.
- Impact: lost updates despite the advertised optimistic-concurrency contract; any guard/effect that reads state then writes (period lock, posted-entry immutability, payment application, running balances) races. For an accounting product this is double-application / lost-posting risk.
- Fix: put the version predicate in the `UPDATE` (`AND updated_at = $n`, 0 rows → 409) or add `getForUpdate` and use it in `writeTxn`; consider SERIALIZABLE/REPEATABLE READ with retry for effect units.
- Effort: M

### R03-04 [High] [CONFIRMED] [Data integrity] A refused re-application silently flips a tenant between typed tables and the JSONB store
- Where: `tenant-store-registry.ts:163-193` (on `applied:false` the entry is replaced with `store: null`), `:202-206` `storeFor` → null, `:315-324` router falls back to `PostgresEntityStore`. Refusal triggers: `tenant-schema-diff.ts:190-216` (any changed column type or classification on an existing column is `blocking`).
- Evidence: `apply()` unconditionally `this.entries.set(tenantId, {…store…})`; the previous applied store for the old manifest hash is discarded. `apps/operate-server/src/node.ts:3901-…` `onApplication` only logs; the gateway is still built with the router (`node.ts:3948-3955`).
- Impact: a tenant who re-activates a manifest that changes one field's type (plausible from an AI redesign: `text`→`integer`, `pii`→`phi`) immediately sees all existing records disappear (reads go to `meta.operate_entity_records`), keeps writing into the JSONB store, and — once an operator runs the reported SQL (retry after 60 s) — flips back, at which point everything written in between disappears instead. No error reaches the tenant. Only entities with an encrypted column are refused (`PlaintextFallbackRefused`).
- Fix: on a refused re-application keep serving the previous applied store read-only or return 503 for that tenant; never route a tenant that has an existing schema to the fallback.
- Effort: M

### R03-05 [Medium] [CONFIRMED] [Ops/availability] Boot DDL: unlocked, non-transactional, non-CONCURRENT, FK re-validation on every boot
- Where: `column-store.ts:284-311` (each statement via pool `conn.query`, no advisory lock, no transaction); `entity-ddl.ts:372-375` (`DROP CONSTRAINT IF EXISTS` then `ADD CONSTRAINT … FOREIGN KEY` — full validation scan + lock on both tables every boot); `:308-309` (`DROP POLICY` / `CREATE POLICY` every boot, ACCESS EXCLUSIVE); `:306,328,173` (`CREATE INDEX` / `CREATE UNIQUE INDEX` without `CONCURRENTLY`); `:252` (`ALTER … SET DEFAULT` every boot).
- Impact: restart time and write-blocking grow with data size; two replicas booting together race the DROP/CREATE pairs (`policy … already exists` → boot failure); during a rolling deploy there is a window with the FK absent (orphans can be written by the old replica, after which `ADD CONSTRAINT` fails and the new replica cannot boot); a table with RLS on and no policy between the two statements denies non-owners. The per-tenant path does this correctly (one transaction + advisory xact lock, `tenant-schema-apply.ts:229-230`), so the two paths disagree.
- Fix: take the same advisory lock; skip unchanged constraints/policies (introspect first); `NOT VALID` + `VALIDATE`; `CREATE INDEX CONCURRENTLY`; move to a migrate step.
- Effort: M

### R03-06 [Medium] [CONFIRMED] [Correctness] Sequence allocator is not gapless and runs outside the write transaction
- Where: `sequence-store.ts:27-52` (own `withTenantContext` transaction on the pool); caller `packages/operate-runtime/src/handlers.ts:435` (`applyEntitySequences` runs before `validateEntity` at `:440` and before `writeTxn` at `:443`).
- Evidence: allocation commits independently; a subsequent 422, guard refusal, unique violation or rollback burns the number. The header comment hedges with "gap-free-per-allocation", which is not a property anyone needs.
- Impact: gaps in invoice/credit-note numbering — a statutory problem in jurisdictions requiring gapless fiscal numbering (the product ships tax/WHT features). Uniqueness under concurrency is fine (single atomic upsert). Also each create needs a second pooled connection for the allocation (minor).
- Fix: allocate inside the write transaction (pass `tx`), after validation.
- Effort: S–M

### R03-07 [Medium] [CONFIRMED] [Schema] Identifier collisions are neither validated nor detected; `IF NOT EXISTS` hides them
- Where: `kernel/src/ddl/identifiers.ts:10-15` `toTableName` (`HTTPServer` and `HttpServer` → `http_server`; `ENTITY_NAME_REGEX = /^[A-Z][A-Za-z0-9]*$/` admits both); join table `` `${leftTable}_${rightTable}` `` (`column-plan.ts:310`) can equal an entity table (`OrderItem` vs m2m `Order`↔`Item`); `entity-ddl.ts:44-52` index names truncated to 63 chars and built as `<table>_<column>_uniq|_trgm` (`order_line`+`item` == `order`+`line_item`); FK name `` `fk_${plan.table}_${col.column}` `` (`entity-ddl.ts:391`) is not truncated in code but Postgres truncates it.
- Evidence: the module admits the first case: `boot-schema-targets.ts:297-299` "Two entities can snake-case to one table name, and an entity can collide with a join table's `<left>_<right>`; the store serves such a manifest as a single merged table". `validate.ts` checks only duplicate entity *names* (`:177`).
- Impact: (a) two entities silently share one table → entity A's list returns B's rows, bypassing per-entity RBAC inside the tenant; (b) two unique declarations mapping to one index name → second `CREATE UNIQUE INDEX IF NOT EXISTS` is a no-op, uniqueness silently unenforced while `uniqueIndexFields` (`entity-ddl.ts:62-68`) attributes violations to the wrong field and the boot survey reports it enforced; (c) two FKs sharing a 63-char prefix: the second `DROP CONSTRAINT IF EXISTS` drops the first's constraint. None occur in shipped packs (not measured exhaustively) but per-tenant manifests are machine-authored.
- Fix: validate uniqueness of derived table/join/index/constraint names (post-truncation) in `validateManifest`; hash-suffix long names.
- Effort: S

### R03-08 [Medium] [CONFIRMED] [Performance] Indexes do not match the queries issued
- Where: search/contains predicate `list-sql.ts:291,478` (`unaccent(<col>::text) ILIKE '%'||unaccent($n)||'%'`) vs index `entity-ddl.ts:328` (`USING gin ("col" gin_trgm_ops)` on the bare column). Comment at `list-sql.ts:290` claims "A plain-column pg_trgm GIN index still accelerates this" — it cannot: the indexed expression is `col`, the predicate's is `unaccent(col::text)`.
- Also: `idx_<table>_tenant` (`entity-ddl.ts:306`) duplicates the PK prefix `(tenant_id, id)`; no index on any reference column (FK `RESTRICT`/`CASCADE` checks and `?customer_id=` filters seq-scan the child table); no index on sort keys (`created_at` etc.) so every keyset page is a full per-tenant sort; JSONB store has only `(tenant_id, entity)` + the unique key, so any sort/filter on a document field scans and sorts the whole entity; `guardedTimestamptzCast` is admitted unindexable (`temporal-sql.ts:57-61`).
- Impact: one GIN index per text column on every write for zero read benefit; list latency linear in rows per tenant/entity; delete latency linear in child table size.
- Fix: immutable `f_unaccent` wrapper + expression trigram index (or drop unaccent from the predicate); index FK columns; composite `(tenant_id, <default sort>, id)` indexes.
- Effort: M

### R03-09 [Medium] [CONFIRMED] [Availability] Pool has no error listener, no timeouts, no sizing; rollback failures return a broken client
- Where: `kernel-pg/src/node-pg.ts:87-95` (`new Pool({host,port,user,password,database,application_name,ssl})` — no `max`, `connectionTimeoutMillis`, `idleTimeoutMillis`, `statement_timeout`, `idle_in_transaction_session_timeout`); no `pool.on("error", …)` anywhere in the file; `:110-119` swallows a failed `ROLLBACK` then `client.release()` without the error argument.
- Impact: node-postgres emits `error` on the pool when an idle client's backend dies (DB restart/failover); with no listener that is an uncaught exception → process crash. Default `max=10` with no acquire timeout: a create holds one client in `writeTxn` while other paths (settings read, sequence allocation, key provisioning) need another → under ≥10 concurrent writers requests can hang indefinitely. A client whose ROLLBACK failed is returned to the pool possibly mid-transaction (next borrower inherits an aborted transaction or, worse, prior `set_config` state). No statement timeout means one unindexed `ILIKE` scan or a boot `CREATE INDEX` holds a connection without bound.
- Fix: add listener, sizes and timeouts; `client.release(err)` on rollback failure.
- Effort: S

### R03-10 [Medium] [CONFIRMED] [Billing] Stripe ingest has no ordering or replay guard; entitlement picks "latest updated row"
- Where: `stripe-webhook.ts:119-133` (verify → map → `store.insert`), `subscription-store.ts:45-72` (blind upsert on `(tenant_id, stripe_subscription_id)`), `entitlement-store.ts:54-66` (`ORDER BY updated_at DESC LIMIT 1`).
- Evidence: no `event.id` dedupe table, no comparison of `event.created` with the stored row. Signature and tolerance are checked by `verifyStripeWebhook` on the raw bytes (`node.ts:1267`), which is correct.
- Impact: Stripe does not guarantee order: a delayed `customer.subscription.updated(active)` processed after `…deleted` re-activates a cancelled tenant (free service); a replay inside the tolerance window re-applies an old snapshot. A tenant with two subscriptions is gated by whichever row was touched last (an old cancelled one can lock out a paying tenant, or vice versa). Tenant attribution comes from `metadata.tenant_id` (`stripe-webhook.ts:57-59`), trusted because the event is signed — acceptable only if tenants cannot set subscription metadata (e.g. via Checkout `subscription_data.metadata`); not verifiable from this package.
- Fix: store `last_event_created`/event id and ignore older events; resolve entitlement by status priority, not recency.
- Effort: S

### R03-11 [Medium] [CONFIRMED] [Compat] Emitted DDL requires PostgreSQL ≥ 15 while the declared floor is 14
- Where: `entity-ddl.ts:347` (`ON DELETE SET NULL ("col")` — column-list form, PG15+; the function's own comment says so) vs `kernel-pg/src/preconditions.ts:4` `MIN_POSTGRES_MAJOR = 14`. `pack-erp-core/src/relations.ts:78,128` declare `onDelete: "set_null"`.
- Impact: `--store pg-columns` with the default pack cannot boot on a server the precondition check accepts (syntax error mid-`ensureSchema`, after tables were created — see R03-05 for the half-applied state).
- Fix: raise the floor to 15 for the column store or emulate with a trigger.
- Effort: S

### R03-12 [Low] [CONFIRMED] [Error handling] Typed-column filter/cursor values that cannot be cast raise in Postgres (client-triggerable 500)
- Where: `column-store.ts:991-1000` `columnComparableValue` returns `true` for every type other than instant/date/time/numeric; the comment at `:986-989` asserts "a `TEXT`, `BOOLEAN`, `UUID` or `JSONB` column compares the string it is given". `castSuffix` (`:389-392`) appends `::BOOLEAN` / `::UUID` / `::JSONB` / `::TEXT[]`.
- Evidence: `'maybe'::boolean`, `'x'::uuid`, `'x'::jsonb`, `'x'::text[]` all raise `invalid input syntax`. So `?is_active=maybe`, or a forged cursor `{"k":["x"],"id":"…"}` on a boolean/uuid sort key, reaches the cast. Not injection (value is bound); the handler layer turns it into a 500.
- Fix: add guards for BOOLEAN/UUID/JSONB/arrays (or compare `col::text = $n`).
- Effort: S

### R03-13 [Low] [CONFIRMED] [Secrets] Bound parameters are still logged by Postgres; the "never appears in logs" claim is too strong
- Where: `tenant-context.ts:14-28` ("a value interpolated into SQL text lands in `log_statement = 'all'` output… Bound… the key itself never appears").
- Evidence: with `log_statement='all'` or `log_min_duration_statement`, Postgres logs extended-protocol statements with a `DETAIL: parameters: $1 = 'app.column_encryption_key', $2 = '<key>'` line (`log_parameter_max_length` defaults to -1 = full). The same applies to plaintext PHI bound into `pgp_sym_encrypt($n::text, …)` (`column-store.ts:803-804`). Binding does keep it out of `pg_stat_statements` and query text.
- Impact: on a deployment with statement logging (common on managed Postgres) the per-tenant column key and PHI plaintext are in server logs.
- Fix: document `log_parameter_max_length=0` as a requirement, or `SET LOCAL log_statement='none'` is not available to non-superusers — prefer app-side encryption for PHI.
- Effort: S (doc) / L (app-side crypto)

### R03-14 [Low] [CONFIRMED] [Design] The serving process needs DDL/extension privileges at runtime
- Where: `column-store.ts:74-81` (`CREATE EXTENSION IF NOT EXISTS unaccent/pg_trgm/pgcrypto` at every boot and every tenant activation — `tenant-schema-apply.ts:227`), `tenant-schema-apply.ts:233` (`CREATE SCHEMA`), `tenant-schema-erase.ts:204,341` (`DROP SCHEMA … CASCADE`).
- Impact: least privilege is structurally impossible for the request-serving role (root cause behind R03-02 and the blast radius of R03-01). The erase guards themselves are sound (see strengths).
- Effort: M

### R03-15 [Low] [CONFIRMED] [Correctness] Record ids are process-local time+counter
- Where: `records.ts:28-38` (`rec_${Date.now().toString(36)}${counter…}`), used by both stores (`entity-ops.ts:147`, `column-store.ts:472`); client-supplied `id` accepted if it matches `/^[A-Za-z0-9_-]{1,200}$/` (`records.ts:41-44`).
- Impact: two replicas (or a restart within the same ms) can mint the same id for the same tenant+entity → PK violation → 500 on create (not attributed by `rethrowUniqueViolation`, `column-store.ts:328-339`). Ids are guessable/enumerable (not a boundary, but worth knowing). Use UUIDv7.
- Effort: S

### R03-16 [Low] [CONFIRMED] [Scalability] Unbounded reads
- Where: `entity-ops.ts:32-43` `listOp` (no LIMIT); `column-store.ts:352-355,581` (`limit: 1_000_000`); `entity-store.ts:279-316` `pruneDanglingLinks` loads every link and every record id of both entities into memory and issues one `DELETE` per dangling link; `tenant-schema-erase.ts:124-138` exact `count(*)` per table (deliberate, once per tenant).

### R03-18 [Info] [SUSPECTED] [Erasure] Erased tenant schema can be re-created by a later `ensure`
- Where: `tenant-schema-apply.ts:233` (`CREATE SCHEMA IF NOT EXISTS`) and `tenant-store-registry.ts:192` (applied entries never expire; `forget` exists but I did not trace a caller on the erase path).
- Impact: if the tenant's manifest row is still active after erasure, a boot/poller `ensure` on any replica re-creates an empty `t_<hex>` schema after a tombstone asserted its absence; replicas holding a cached store keep issuing SQL against dropped tables. ## Verified strengths (things that are genuinely done well, with file:line)
- Tenant context is transaction-local and bound: `tenant-context.ts:12` (`set_config('app.current_tenant_id', $1, true)`), executed on the same dedicated client inside `BEGIN…COMMIT` (`node-pg.ts:103-119`). No session-level `SET`. Extra settings (the pgcrypto key) use the same form (`tenant-context.ts:28`).
- Every data statement in this package carries an explicit bound `tenant_id` predicate, independent of RLS: JSONB ops `entity-ops.ts:39,106,134,150,165,172,186`; links `entity-store.ts:158-160,175-177,196,225-227,247,287-293,308-310,322`; column store `column-store.ts:408,452,489,531,558,634-636,653-655,673-676,697,732`; sequences/settings/subscriptions/entitlements all `WHERE tenant_id = $1::uuid`. I found no query path that runs entity SQL outside `withTenantContext`/`scoped`. Transaction-bound stores reject a different tenant (`entity-store.ts:50-54`, `column-store.ts:575-577`).
- Identifier handling: `quoteIdent` is an allow-list (`/^[a-zA-Z_][a-zA-Z0-9_]*$/`, throws otherwise — `kernel/src/ddl/identifiers.ts:1-8`); schema names validated by regex in every constructor (`entity-store.ts:29,106`, `column-plan.ts:59,161`, `sequence-store.ts:22`, …); tenant schema names derive from a strict UUID (`tenant-schema.ts:54-74`) and refuse truncation; JSON paths are regex-guarded before interpolation (`entity-ops.ts:23,70`); filter operators come from a closed regex one layer up (`operate-runtime/src/list-query.ts:356`). SQL types are generated from zod-validated integers (`kernel/src/ddl/field-type.ts`).
- Cursor contents are never trusted: components are bound, type-guarded before a cast (`list-sql.ts:306-333`), and uncomparable ones degrade to the NULL tail instead of raising (for the guarded types).
- Dropped filter/search predicates are refused rather than silently widening (`list-sql.ts:74-87`, `column-store.ts:414-415`, `entity-ops.ts:111-112`).
- Composite tenant-scoped FKs `(tenant_id, ref) → (tenant_id, id)` (`entity-ddl.ts:364-377`) genuinely prevent cross-tenant references; `SET NULL (col)` avoids nulling `tenant_id`.
- Unique indexes are tenant-prefixed (`entity-ddl.ts:171`), and the per-tenant applier uses savepoints correctly (`tenant-schema-apply.ts:255-272`).
- Schema erase is careful: name must be a derived tenant schema and decode to this tenant (`tenant-schema-erase.ts:306-318`), four-eyes, trial cascade in a savepoint to detect collateral (`:194-220`), absence confirmed before commit (`:429-437`), under the same advisory lock as apply.
- pgcrypto key never enters SQL text; empty key refused (`column-store.ts:244-250`); encrypted entity cannot be served from the plaintext fallback, including inside `withTransaction` (`tenant-store-registry.ts:332-337,385-391`).
- Stripe: signature verified over the raw request bytes before any parsing is trusted (`stripe-webhook.ts:120-124`, `node.ts:1267`).
- JSONB `updateOp` locks the row (`entity-ops.ts:165`).

## Claims vs reality (docs/README/CLAUDE.md/comments that the code contradicts)
- `entity-store.ts:88-95`, `sequence-store.ts:13-14`, `settings-store.ts:12-14`, `subscription-store.ts:28-30`, `entitlement-store.ts:35-37`: "confined by RLS". Not for an owner/superuser role, which is what the compose uses (R03-02). CLAUDE.md itself concedes owners bypass RLS; these comments were not updated.
- `list-sql.ts:290`: "A plain-column pg_trgm GIN index still accelerates this" — false (R03-08). CLAUDE.md's register (P1 item 1) already records this; the comment remains.
- `sequence-store.ts:10`: "Durable, gap-free-per-allocation" — numbers are burned on any failed create (R03-06).
- `column-store.ts:986-989`: BOOLEAN/UUID/JSONB "compares the string it is given" — they raise (R03-12).
- `tenant-context.ts:17-21`: bound key "never appears" in `log_statement='all'` output — parameters are logged (R03-13).
- CLAUDE.md "Strict TypeScript / fail closed": `settings-store.ts:36` fails open to defaults.
- CLAUDE.md states `MIN_POSTGRES_MAJOR` 14 as the floor; the column store's own DDL needs 15 (R03-11).
- CLAUDE.md claims the manifest path is validated ("zod schemas are the source of truth"); the one free-SQL field has no validation at all (R03-01).
