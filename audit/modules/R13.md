# R13 — apps/operate-web, web-ui, deploy/, scripts, root files, docs/vision.md

## Summary (10 lines max)
- CRITICAL: `deploy/.env.example` (commit 7bc8db9, on origin/main) contains what look like a live Anthropic API key, a real DB password, the production domain and a personal email.
- The shipped compose runs the API as Postgres superuser/owner (RLS inert), with no backups, limits, log rotation, headers, CI/CD or rollback; most platform subsystems are flag-off.
- The AI compose overlay and the Vercel/Supabase guide (plus operate-web README, run-dev.ps1, .env.example bootstrap) were not updated for the new login: following them yields a UI nobody can sign in to.
- operate-web auth design is sound in outline (httpOnly/secure/strict cookie, header allowlist, API-verified JWT) but has an open redirect (`?next=/%09/evil.com`), no Origin/CSRF check, login-CSRF, unbounded proxy buffering, no logout revocation.
- XSS sink: server-rendered tenant-authored notification HTML via `dangerouslySetInnerHTML`, no CSP anywhere. CSV export has formula injection.
- Finance display defects: 2-dp hard-coded, tenant currency appended to every amount, float re-summation and 200-row truncation on period close.
- Frontend: 0 tests, no i18n/RTL (despite MENA-first vision), weak a11y, desktop-only, browser N+1s.
- Root README/CONTRIBUTING are grossly stale (51 pkgs/119 tables/59 ADRs vs 87/146/358); LICENSE is a placeholder.
- vision.md: roughly 4 of 16 major promises delivered, 6 partial, 6 contracts-only/absent (files, reporting, integrations, Fireworks/embeddings, mobile/on-prem, kanban/calendar/map).

### R13-02 [High] [CONFIRMED] [Deploy/Tenancy] Shipped compose runs the API as the Postgres superuser/table owner, so RLS is not in force for the serving role
- Where: deploy/docker-compose.yml:11-16 (`x-pg-env`: `PGUSER: ${POSTGRES_USER}`), :23 (`POSTGRES_USER` = the initdb superuser), :77 (migrate) and :89 (api) both merge `*pg-env`.
- Evidence: the same role that initdb creates as SUPERUSER applies the schema (owner of every `meta.*` table) and serves requests. Postgres superusers and table owners bypass RLS unless `FORCE ROW LEVEL SECURITY` is set; no second role, `GRANT`, or `ALTER ROLE … NOBYPASSRLS` exists anywhere under `deploy/`.
- Impact: in the only turnkey deployment, the "tenant isolation by RLS" control is inert; isolation rests solely on every query carrying an explicit `tenant_id` predicate. Any store that forgets one (the repo's own notes list several historic cases) is a cross-tenant read/write with no backstop. - Effort: M

### R13-05 [Medium] [CONFIRMED] [Security/Web] Open redirect on `?next=` via tab/newline (`/%09/evil.com`) in both the middleware and the login form
- Where: apps/operate-web/lib/session.ts:75-82; consumers middleware.ts:31 and app/login/page.tsx:57 (also lib/unauthorized.ts:30).
- Evidence: `safeNextPath` checks only `raw.charAt(1)` for `/` or `\`. WHATWG URL parsing strips ASCII tab/CR/LF, verified: `node -e 'new URL("/\t/evil.com","https://a.test/x").href'` → `https://evil.com/` (same for `\n`). So `https://erp.example.com/login?next=/%09/evil.com` → after a successful login `window.location.href = "/\t/evil.com"` navigates to evil.com; for an already-signed-in user the middleware 307s there immediately (`NextResponse.redirect(new URL(safeNextPath(...), req.url))`).
- Impact: credential-phishing springboard off the real login page (user types a real password on the genuine domain, lands on a look-alike "session expired, sign in again" page). The function's own comment claims this class is closed.
- Fix: resolve `new URL(raw, origin)` and require `url.origin === origin`, returning `url.pathname+url.search`; reject control chars.
- Effort: S

### R13-06 [Medium] [CONFIRMED] [Security/Web] Catch-all proxy: no CSRF/Origin check, login-CSRF possible, unbounded body buffering, no timeout, internal URL leak, client IP dropped
- Where: apps/operate-web/app/api/[...path]/route.ts:17-70; app/api/auth/login/route.ts:62-70; middleware.ts:21.
- Evidence / sub-items:
  - CSRF defence is `SameSite=strict` only (lib/session.ts:35). No `Origin`/`Sec-Fetch-Site` check and no token. SameSite is *site*-scoped, and the shipped stack hosts a second origin on the same site (`api.{$DOMAIN}`, Caddyfile:15) — any future sibling subdomain (docs, marketing, a tenant-hosted page) can drive state-changing POST/PATCH/DELETE through `/api/*` with the victim's cookie. All five verbs incl. DELETE are proxied (route.ts:76-80).
  - Login CSRF: `/api/auth/login` calls `req.json()` regardless of `Content-Type` (login/route.ts:65), so a cross-site `<form enctype="text/plain">` can post a JSON body and sign the victim's browser into an attacker-controlled account (Set-Cookie on a top-level navigation response is honoured for SameSite cookies). LIKELY (not run in a browser).
  - `await req.text()` (route.ts:49) and `await upstream.text()` (:65) buffer whole bodies with no size cap and no `AbortSignal` timeout; the gate before it is "cookie is non-empty" (:18-19, middleware.ts:21), so any anonymous client with `Cookie: operate_session=x` can make the Node process buffer arbitrarily large bodies / hold sockets. Caddyfile has no `request_body max_size`.
  - 502 body returns `detail: String(err)` and `hint: Is operate-server running at ${UPSTREAM_BASE_URL}` (route.ts:55-60) → internal hostname/port to the same anonymous caller (the login handler deliberately avoids this, login/route.ts:81-84).
  - Header allowlist forwards only `authorization`, `accept`, `content-type` (route.ts:41-46): `Idempotency-Key`, `If-Match`, `Accept-Language`, `X-Request-Id`, `X-Forwarded-For` are all dropped, and upstream response headers (`Retry-After`, RateLimit-*, `ETag`, `Sunset`) are discarded (:66-69). Consequences: the API sees every UI user as the `web` container's IP (no per-IP limiting/lockout, audit rows without client IP), UI mutations can never be idempotent-retried, and binary/streamed responses are corrupted by `.text()`.
  - Path: `path.join("/")` of decoded segments (route.ts:31) lets `%2F`, `%3F`, `%23` inject path/query/fragment upstream; host is fixed so no SSRF, and every upstream path is reachable by design, so impact is limited to bypassing any future path-based filtering. LIKELY.
- Impact: Medium overall; the DoS and same-site CSRF are the material ones.
- Fix: verify `Origin` equals own origin on non-GET; require `content-type: application/json` on login; cap body (e.g. 10 MiB) and add `AbortSignal.timeout`; forward `x-forwarded-for`/`idempotency-key`; generic 502.
- Effort: S-M

### R13-07 [Medium] [CONFIRMED] [Security/Web] No logout invalidation and no revocation; session = bearer JWT in a cookie for its full TTL
- Where: apps/operate-web/app/api/auth/logout/route.ts:5-17 ("Nothing upstream is called: the API's tokens are stateless").
- Evidence: logout only overwrites the cookie. A copied token (browser extension, proxy log, shared machine, XSS-less theft via backup) stays valid until `exp`; deploy/README.md:262-268 confirms role/membership changes and user suspension also do not bite until expiry, and the only kill switch is rotating the signing key for everyone. Logout is also an unauthenticated, CSRF-able POST (forced sign-out; low).
- Impact: for an ERP holding finance/PHI, "sign out" and "suspend user" not terminating access for up to the token TTL (default 1h) is an audit finding (SOC 2 CC6.x).
- Fix: jti denylist or short TTL + refresh with server-side session row; call a revoke endpoint on logout.
- Effort: M

### R13-08 [Medium] [SUSPECTED] [XSS] Server-rendered notification HTML is injected with `dangerouslySetInnerHTML`, with no CSP anywhere
- Where: apps/operate-web/app/setup/page.tsx:845-848 (`dangerouslySetInnerHTML={{ __html: digest.body }}`); apps/operate-web/next.config.mjs:1-6 (no `headers()`), deploy/Caddyfile:8-18 (no `header` directives).
- Evidence: `digest.body` is rendered server-side by `renderDigest` (apps/operate-server/src/digest-template.ts:171-203), which first tries a tenant-authored *override* template (:186) whose `htmlBody` is author-supplied markup; the server's defence is a refuse-list at authoring time (apps/operate-server/src/notification-template-routes.ts:42-49: "the body itself is author-supplied HTML"). Substituted values are escaped; the template body is not sanitised at render or in the browser. A second `dangerouslySetInnerHTML` at app/admin/settings/page.tsx:441 only takes static literals (`"Regional &amp; operational defaults"`) — safe but gratuitous.
- Impact: any bypass of the server-side blocklist (blocklists for HTML are historically bypassable), or any template row written by another path (direct DB, future route), becomes stored XSS in every recipient's `/setup` page. HttpOnly protects the token, but the script can drive `/api/*` as the victim (same origin). No CSP, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` or HSTS is set by Next or Caddy to contain it.
- Fix: sanitise with DOMPurify (allow-list) client-side or render as text; add CSP + standard headers in Caddy.
- Effort: S

### R13-09 [Medium] [CONFIRMED] [Security/Data] CSV export does not neutralise formula cells

### R13-10 [Medium] [CONFIRMED] [Money/UI] Money display is wrong for multi-currency and non-2-decimal currencies; client-side float re-summation of ledger lines
- Where: apps/operate-web/lib/format.ts:15-19, 53-66; app/e/[slug]/page.tsx:27-34 (`cellKind`); lib/period-close.ts:46-64, 96-131; lib/aging.ts:9-21, lib/wht.ts:7-9.
- Evidence: (a) `groupNumber` hard-codes `minimumFractionDigits: 2, maximumFractionDigits: 2` → KWD/BHD/JOD (3 dp) are rounded on screen, JPY shown with `.00`. (b) `formatCell(...,"money")` appends the *tenant default* currency (`fmt.currency`) to every money cell (format.ts:62,65) even when the record carries its own `currency` field — a USD invoice in an AED tenant renders "1,000.00 AED". (c) "money" is guessed from the field *name* regex `/(total|amount|price|cost|subtotal|tax|budget|salary)/` so `debit`, `credit`, `balance`, `rate`, `withheld` are not money while `tax_id`-like numeric names would be. (d) `summarizeLines` sums JS doubles, rounds to 2 dp and declares "balanced" with `< 0.005`; lines come from `listRecords(LINE_SLUG, "?limit=200…")` with no pagination (period-close.ts:107), so a revaluation entry with >200 lines is shown truncated and "unbalanced". (e) Aging/WHT response types are `number` — the server ships money as JS numbers for those reports (not this app's fault, but the UI cannot repair precision).
- Impact: display-level only (server remains authoritative), but an accountant reading the wrong currency label or a false "unbalanced" flag on period close is a trust-destroying defect in a finance product.
- Fix: per-record currency + `Intl.NumberFormat(locale,{style:"currency",currency})` with ISO-4217 minor units; server-declared money kind; server-computed totals.
- Effort: M
