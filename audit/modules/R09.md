# R09 — operate-server authN / sessions / platform admin / tenant boundary / key handling

## Summary (10 lines max)
1. Secrets hygiene failure outside the code: `deploy/.env.example` carries a real-looking Postgres password and Anthropic key next to the production domain (R09-01, Critical).
2. Password login is carefully built for uniform responses and a strong KDF, but its only brute-force control (per-user lockout) is bypassable by parallel requests, is an unauthenticated CPU-exhaustion vector, and lets anyone lock any user out permanently (R09-02/03, High).
3. Sessions are stateless 1–24 h JWTs with no revocation, logout, MFA, password policy or reset flow; suspending a user/tenant or revoking a membership does not end access (R09-04/07/08).
4. Platform authority is a role *string* with no tenant binding; the user-registry role can grant any role (incl. `platform_admin`) in any tenant (R09-05, High).
5. JWT verification skips absent `exp`/`iss`/`aud`, and a token without `tenant_id` takes its tenant from a request header — a cross-tenant break for any third-party-IdP deployment (R09-06, High).
6. API keys have no entropy floor, are static/unrevocable, and one code path hashes them into a persisted id (R09-10/13).
7. Key management is env-var master secrets with no rotation and no KMS; tenant "per-tenant keys" all derive from one secret; `pii` and the entire default JSONB store are plaintext at rest (R09-12).
8. SQL in scope is parameterised and tenant-scoped correctly; no injection or cross-tenant SQL defect found. ABAC evaluator is fail-closed and prototype-safe.
9. Many protections are "reported at boot, served anyway" (tenant gate, cursor sealing, unique, view permissions) and are off on the shipped compose.
10. Tests are plentiful for pure logic but fake-DB only, and none covers the defects above.

## Findings

### R09-01 [Critical] [CONFIRMED] [Secrets] Real-looking production secrets committed in `deploy/.env.example`
- Where: `deploy/.env.example:5`, `:12-13`, `:117` (introduced by commit `7bc8db9` "Modify .env.example with new Postgres and domain settings")
- Evidence: `POSTGRES_PASSWORD=Ams808727778…` (20 chars, human-chosen, replaces `change-me-to-a-long-random-string`); `DOMAIN=crossengin.com`, `ACME_EMAIL=a.mowfak@…`; line 117 a commented `ANTHROPIC_API_KEY=sk-ant-usr-1…` (~108-char token, replaces the placeholder `sk-ant-...`). Type: database password + Anthropic API key. Not verifiable offline whether live, but the diff replaced placeholders with specific values beside the real production domain.
- Impact: anyone with repo read access (and every clone/fork/CI log) holds a candidate DB superuser password for the public domain and a billable LLM key. In a diligence context this is also direct evidence that secrets hygiene is by convention only (no secret scanning, no pre-commit hook).
- Fix: rotate both immediately; purge from history (`git filter-repo`) or accept as burned; restore placeholders; add gitleaks/secret-scanning to CI.
- Effort: S

### R09-02 [High] [CONFIRMED] [AuthN] Login lockout is bypassable by concurrency, and the KDF is an unauthenticated CPU-exhaustion vector
- Where: `apps/operate-server/src/auth-token-route.ts:220-263` (read → `isLocked` → `verifyPassword`), `:419-421` (`onFailure` after the verdict); `credential-store.ts:149-164`; wiring `node.ts:4183-4240`.
- Evidence: the lock decision is taken from the row read at `findByEmail` (`if (isLocked(record, input.now))`), the password is then verified, and only afterwards is `recordFailure` issued. Nothing re-checks the lock after verification and the success path (`:434-449`) never consults it. `recordFailure`'s atomic `credential_failed_attempts + 1` protects the *count*, not the *admission*. So N requests sent in parallel all read `locked_until = NULL` (a ~1 ms query) and all get a real `verifyPassword`, queued on the libuv pool (~130 ms each, pool of 4). The module's own header says "In front of the gateway there is no rate limiting" (`:30`) and there is no per-IP or global limiter anywhere in the interceptor.
- Impact: (a) the "10 attempts / 15 min" bound is really "as many guesses as can be queued before the 10th failure commits" — thousands per burst, repeatable at every lock expiry because the lock check on expiry again reads unlocked; a correct guess inside the burst mints a token even though the account is locked by then. (b) Each unauthenticated request for ANY email (known or not — `spendPasswordWork` on every path) costs 130 ms of a 4-thread pool shared with fs/dns: ~31 req/s pins the pool indefinitely, stalling every legitimate login and any `dns.lookup`/fs work in the process. Password body may be 1 KiB and the request queue is unbounded.
- Fix: reserve the attempt atomically *before* verifying (`UPDATE … SET attempts = attempts+1 WHERE id=$1 AND (locked_until IS NULL OR locked_until < now()) RETURNING …`, refuse if 0 rows), re-check lock before minting; add a global concurrency cap/semaphore on derivations (shed with 429/503), per-source and per-account rate limiting (trust `X-Forwarded-For` from Caddy explicitly), and raise `UV_THREADPOOL_SIZE` or move scrypt to a worker pool.
- Effort: M

### R09-03 [High] [CONFIRMED] [AuthN/DoS] Any unauthenticated party can keep any user locked out indefinitely, platform-wide, with ~1 request per 15 minutes
- Where: `credential-store.ts:155-159`; `auth-token-route.ts:94-106`, `:243-257`.
- Evidence: `credential_locked_until = CASE WHEN credential_failed_attempts + 1 >= $2 THEN now() + make_interval(secs => $3)` — the counter is only ever zeroed by `recordSuccess` or `setCredential`; lock expiry does not reset it. After the first 10 failures every later single wrong guess re-locks for the full window. While locked, a *correct* password is refused (`account_locked`, `:243`). `meta.users.email` is globally unique with no tenant scope, so the victim need not share a tenant with the attacker; the `tenant` field only has to be any valid slug.
- Impact: targeted, cheap, persistent denial of service against any known email (including the platform operators' UI accounts). There is no unlock path short of `operate-server set-credential` from a shell, which *replaces the password* — no "clear lock" command, no admin route, no self-service. `deploy/README` admits the lockout DoS; it does not mention that it is permanent at 1 req/window.
- Fix: reset the counter when a lock expires (or use a sliding window table keyed (user, source)); prefer progressive delay + per-source limiting over hard account lock; add an operator unlock route that does not rotate the credential.
- Effort: M

### R09-04 [High] [CONFIRMED] [Session] Session tokens are irrevocable bearer JWTs; suspension, membership revocation, role change and password change do not end a session
- Where: `token-mint.ts:116-125` (claims: no `jti`, no session id, no credential/membership version), `MAX_SESSION_TOKEN_SECONDS = 86_400` (`:82`); `principals.ts:97-107` (`principalFromJwtClaims` — "stateless 'the token is the principal' model"); `platform-users.ts:909-950` (suspend/retire only flips `meta.users.status`), `:1032-1075` (membership revoke); `credential-store.ts:206-214` (password change).
- Evidence: after login nothing on the request path reads `meta.users.status`, the membership row or `credential_updated_at`: `principalFromJwtClaims` builds the principal from `sub`/`scope`/`tenant_id` alone. There is no logout endpoint, no refresh/rotation, no denylist; the only revocation is rotating `OPERATE_TOKEN_SIGNING_KEY`, which logs out every user of every tenant (single fixed kid `login-v1`, `credential-auth-env.ts:34`, so there is no overlap window either).
- Impact: a fired employee, a compromised account whose password was just reset, or a user whose role was downgraded keeps full access (including a `platform_admin`-roled session) for up to the TTL (default 1 h, configurable to 24 h). A stolen token cannot be killed individually. Tenant suspension only bites if the opt-in `--tenant-status-gate` is on (R09-08).
- Fix: short access token + server-side session/refresh record; or stamp a per-user `token_version`/`credential_updated_at` claim checked against a cached directory (the tenant-status and ABAC caches already show the pattern); add logout; support two kids for rotation.
- Effort: M

### R09-05 [High] [CONFIRMED] [AuthZ] Platform authority is a bare role *name* with no tenant binding; the user-registry grant can mint any role in any tenant (privilege escalation to platform_admin, four-eyes roles, etc.)
- Where: `platform-admin.ts:372-384` and `platform-users.ts:728-742` (`guard`: `rolesOf(ctx, principal).some((r) => ctx.adminRoles.has(r))`); `principals.ts:159` (`primaryRole: p?.grantedScopes[0]`); `platform-users.ts:175-190` (`primaryRole: z.string().min(1)` — any string, any `tenantId`); `node.ts:4189-4192` (login role = `membership.primaryRole`); `cli.ts:1949` (default admin role `platform_admin`); `deploy/.env.example:22` ("Use the platform_admin role + any placeholder tenant uuid to unlock /v1/platform").
- Evidence: every platform surface checks only whether the credential's role string is in a configured set. The role string comes from an api-key spec, the JWT `scope` claim, or — for password logins — `user_tenant_membership.primary_role`, which `POST /v1/platform/tenants/{tenantId}/members` writes verbatim with no validation against the manifest's roles, no reserved-name list and no check that the granter may confer that role. `cli.ts:276` documents `--platform-user-role` as a *separate, lesser* grant than `--platform-admin-role`.
- Impact: (1) a holder of only the user-registry role can grant themselves (or an accomplice) a membership in any tenant with `primaryRole: "platform_admin"` (or the deletion/erasure/audit-read/four-eyes-approver role), log in naming that tenant, and hold that authority — the separation of duties between the two flags, and four-eyes on deletion (grant two accounts), is defeatable by one actor. (2) Any deployment that sets `--platform-admin-role` to a name a tenant manifest also uses (e.g. `erp_admin`) makes every tenant's admin a cross-tenant platform admin. (3) With an external IdP (`--jwks-url`), whatever lands first in `scope`/`scp` is the role; many IdPs let the client request scopes. Grants are audited (good) but not prevented.
- Fix: model platform authority explicitly — a dedicated platform tenant id (or a `platform: true` credential attribute) checked in `guard`; refuse reserved platform role names in `GrantMembershipInputSchema`; validate `primaryRole` against the target tenant's manifest roles; require four-eyes (or forbid self-grant) on membership grants.
- Effort: M

### R09-06 [High] [CONFIRMED — gateway code outside scope, consumed by `principals.ts`] [AuthN] JWT verification treats `exp`, `iss`, `aud` and `tenant_id` as optional; a token without `tenant_id` takes its tenant from the caller's `x-tenant-id` header
- Where: `packages/api-gateway-runtime/src/auth.ts:136-151` (`if (typeof jwt.payload.exp === "number" && …)`, `if (typeof jwt.payload.iss === "string" && …)`, `if (aud !== undefined && !audOk)`); `auth.ts:202-209` (`tenantId: authTenant ?? headerTenant`); `runtime.ts:369-371`; `apps/operate-server/src/principals.ts:97-101` ("the tenant comes from the request's `tenantHint` (the `x-tenant-id` header)").
- Evidence: each claim is enforced only when present. A correctly signed token with no `exp` never expires; with no `aud`/`iss` it is accepted for any audience/issuer; with no `tenant_id` claim `principalFromJwtClaims` resolves the tenant from the spoofable header.
- Impact: tokens minted by this server always carry all claims, so the password-login path is safe. But the supported `--jwks-key/--jwks-file/--jwks-url` paths accept third-party-IdP tokens: any token that IdP signs for a *different* audience (if it omits `aud`), or any token lacking a `tenant_id` claim (the norm for a stock OIDC provider) lets its bearer address **every tenant** by changing a header, with whatever role is in `scope`. That is a full cross-tenant break conditional on IdP configuration, and nothing at boot warns about it.
- Fix: require `exp`, `iss`, `aud` and (for bearer_jwt) a tenant claim; reject, not skip, when absent; never fall back to the header for a JWT.
- Effort: S

### R09-07 [Medium] [CONFIRMED] [AuthN] No password policy, no MFA, no reset/change flow, no self-service
- Where: `auth-token-route.ts:51-55` ("deliberately no min() above 1"); `set-credential.ts:82-89` (any non-empty env value is accepted); `principals.ts:104,137` (`mfaProofAgeSeconds: null` on every principal).
- Evidence: a 1-character password is accepted at set time and at login; no breached-password or complexity check; MFA is modelled in the gateway contract and never produced; the only way to set or change a password is an operator with shell access running `set-credential` with the plaintext in `OPERATE_NEW_PASSWORD` (so operators know/choose every user's password, and it sits in `/proc/<pid>/environ` and shell history of `docker compose exec -e`). No forgot-password, no user-initiated change, no forced rotation.
- Impact: not sellable to any buyer with SOC 2/ISO/HIPAA access-control requirements as-is; operator-known passwords defeat non-repudiation of every user action in the audit trail.
- Fix: min length ≥ 12 + breached-list check in `set-credential` and a future change route; TOTP/WebAuthn; one-time set-password links; read the password from stdin/TTY.
- Effort: L

### R09-08 [Medium] [CONFIRMED] [Tenancy] Tenant lifecycle enforcement is opt-in and off in the shipped deployment; `platform.*` is exempt
- Where: `cli.ts:586` (`let tenantStatusGate = false`), `server.ts:387-388`; `tenant-status-gate.ts:184` (`DEFAULT_EXEMPT_OPERATION_PREFIXES = ["platform."]`), `:288-289` (no-tenant principal passes); `deploy/docker-compose.yml:147-209` (flag absent).
- Evidence: without `--tenant-status-gate`, nothing on the request path reads `meta.tenants.status`. Suspending/archiving a tenant from the console (`platform-admin.ts:494-535`) changes a column and a 200; the tenant's API keys and existing sessions read and write as before. Only *new password logins* to a `deleted` tenant are refused (`node.ts:4201-4204`, `blocksReads`), and a `suspended` tenant can still log in.
- Impact: "suspend tenant" (non-payment, abuse, breach containment) and the Article 17 `pending_deletion` read-only window are no-ops on the reference deployment; writes continue into data queued for erasure. With the gate on there is still a ≤30 s TTL (≤5 min on DB errors, `DEFAULT_MAX_STALE_MS`) during which a suspended tenant writes.
- Fix: default the gate on (provision api-key tenants at boot or fail), keep the survey; invalidate the cache from the transition handlers in-process.
- Effort: S

### R09-09 [Medium] [CONFIRMED] [AuthZ/Audit] Tenant console writes are unaudited and the transition is an unguarded read-then-write
- Where: `platform-admin.ts:413-429` (create: no audit event at all), `:509-517` (`getById` → `canTransitionTenant` → `setStatus(id, target)` with no source-state predicate, although the guarded `transitionStatus` exists at `:246`); `node.ts:1390-1401` (no auditor passed; lifecycle trail optional and "Never fails the request").
- Evidence: `PlatformAdminContext` has no `audit` member (contrast `PlatformUserRoutesContext.audit`, required). Tenant creation writes nothing to `meta.audit_log`; suspend/archive/reactivate write a lifecycle event best-effort after the fact (`lifecycleRecorded: false` on a 200). `setStatus` is `UPDATE … SET status = $2 WHERE id = $1`.
- Impact: the highest-privilege acts on the platform (create a tenant, cut one off) leave no tamper-evident record; a `reactivate` racing the deletion flow can overwrite `pending_deletion`/`deleted` with `active` (the code comment at `:448-451` concedes the window). Also `schemaName: z.string().min(1).optional()` (`platform-tenants.ts:97`) is stored unvalidated — harmless only while nothing interpolates `meta.tenants.schema_name` (grep found no reader today).
- Fix: require an auditor (record-before-write, as the user routes do); use `transitionStatus(id, target, [current.status])`; validate `schemaName` with `SCHEMA_IDENTIFIER_RE` or drop the field.
- Effort: S

### R09-10 [Medium] [CONFIRMED] [Credentials] API keys: no entropy/format floor, plaintext comparison via `Map`, the key itself is used as the principal reference, and a malformed spec echoes the secret
- Where: `principals.ts:48-65` (`parseApiKeySpec` — only non-empty), `:51,55` (`throw new Error(\`invalid --api-key …: ${JSON.stringify(raw)}\`)`), `:121-123,151-152` (`byKey.get(token)`; `principalRef: spec.key`); `api-key-source.ts:60-65`.
- Evidence: a spec `a:platform_admin:<uuid>` boots; nothing rejects a 1-char or dictionary token (the pre-ADR-0358 default was literally `devkey`). Keys are held in process memory in plaintext and matched with a hash-map lookup (not constant-time; practical risk low). The lookup returns the raw key as `principalRef`, which flows into `ctx.authPrincipalRef` (`api-gateway-runtime/src/runtime.ts:413`) — any consumer that logs or persists that field persists the credential (not traced to a sink; SUSPECTED for persistence). A spec with a typo is thrown with the whole spec — token included — into the boot error/log. Keys cannot be rotated, expired or revoked without a restart, and a bare spec shares one placeholder principal (`DEFAULT_PRINCIPAL_ID`, `:42`) so audit rows cannot attribute actions to a key.
- Impact: the shipped bootstrap credential is a static, never-expiring `platform_admin` key with tenant-wide and cross-tenant blast radius (provision/suspend tenants, and with other flags: users, deletion). Weak keys are accepted silently.
- Fix: enforce ≥32 bytes of entropy at parse (reuse `refuseWeakSecret`), store SHA-256 and compare constant-time (`buildOpaqueCredentialMatcher` already exists unused), use a key id not the key as `principalRef`, redact the token in parse errors, add expiry + a key-id for audit.
- Effort: S

### R09-11 [Medium] [CONFIRMED] [Disclosure] Classified field values leak through list cursors on the shipped deployment (cursor sealing is opt-in and unset)
- Where: `cursor-encryption.ts:174-183` (`mode: input.allowDisclosure ? "plaintext_accepted" : "absent"`, `sealer: null`), `:321-326` (`CURSOR_DISCLOSURE_MAY_SERVE` — every verdict `true`, incl. `plaintext_disclosing`); `deploy/docker-compose.yml:128` (`CURSOR_ENCRYPTION_SECRET: ${CURSOR_ENCRYPTION_SECRET:-}`); `deploy/.env.example:110` (commented out).
- Evidence: the module's own text: "a caller who names one is served a body with that field redacted per their own grants and a `nextCursor` of base64url(JSON.stringify({k: [...sort values], id})) carrying its plaintext". The boot decision only logs. The compose default (`erp-core`) has `Employee.work_email` (pii) sortable.
- Impact: any authenticated tenant user with a list grant reads PII/PHI they are field-level-denied, by `?sort=<field>&limit=1` and paging. Within-tenant, but it defeats the field-classification control the product sells.
- Fix: refuse a classified field in `?sort` for callers who cannot read it (correct fix), and make sealing mandatory (generate/require the secret) rather than reported.
- Effort: S–M

### R09-12 [Medium] [CONFIRMED] [Key management] One static master secret per purpose, no rotation, keys visible to the database; what each attacker gets
- Where: `column-encryption.ts:271-292` (`deriveTenantColumnKey(secret, tenantId)`; `generation` parameter never supplied by any caller); `cursor-encryption.ts:130-151` (same); `data-key-envelope.ts:212-214,241-248` (KEK and seed both derived from `COLUMN_ENCRYPTION_SECRET`); `credential-auth-env.ts:34` (single fixed kid); `node.ts:669,993,4645` (env only — good).
- Evidence/analysis:
  - **DB-only attacker (dump/backup/SQLi-read):** gets scrypt+pepper password hashes (pepper not in DB — good), `phi`/`regulated` columns as pgcrypto ciphertext, wrapped DEKs (envelope mode). Gets **in plaintext**: every `pii`/`commercial_sensitive`/`internal` field (only `requiresEncryptionAtRest` classes are encrypted, `column-encryption.ts:88`), and *everything* on the shipped `--store pg` JSONB store, where no column is encrypted at all.
  - **DB admin / anyone who can read server logs or `pg_stat_statements`-level traces:** decryption is server-side `pgp_sym_decrypt` with the key delivered via `set_config('app.column_encryption_key', $2, true)`; the key is in Postgres memory per transaction and will appear in logs if `log_parameter_max_length`/`log_min_duration_statement` with parameters or `auto_explain` is enabled. The envelope therefore protects against stolen backups, not a live DBA.
  - **App-env attacker (one env var):** `COLUMN_ENCRYPTION_SECRET` ⇒ every tenant's column key in `derived` mode and every KEK (hence every DEK) in `envelope` mode; `OPERATE_TOKEN_SIGNING_KEY` ⇒ forge a session for any user/tenant/role incl. `platform_admin`; `CREDENTIAL_PEPPER` + DB ⇒ offline cracking; `OPERATE_API_KEY_SPECS` ⇒ platform admin directly. All four sit in one container environment.
  - No rotation path exists for the master secret, the pepper, the cursor secret or the signing key (rotating the signing key = global logout; rotating the column secret = all ciphertext unreadable; the `generation` argument is wired to nothing).
- Impact: single-secret blast radius is the whole platform; "per-tenant keys" give cryptographic separation only against a DB-only attacker, not key isolation between tenants. No KMS/HSM integration.
- Fix: KMS-held KEK per tenant (seam `ColumnEncryptionKeySource` exists), key generations recorded on rows, dual-kid JWKS, documented rotation runbooks; encrypt `pii` as well or state plainly that it is plaintext at rest.
- Effort: L

### R09-13 [Medium] [CONFIRMED] [Credentials] Access-review live grants derive a principal id from a hash of the API key — the exact thing `principals.ts` says must never be done
- Where: `live-grants.ts:125` (`userId: subjectToUuid(spec.key) as Principal["userId"]`), wired at `node.ts:2875` (`new AuthLiveGrantSource(apiKeyPrincipalProvider(apiKeys))`); contradicts `principals.ts:34-37` ("the key itself — must not be hashed into an id, because a principal id is not a secret … turns an audit reader into an offline attacker").
- Evidence: `subjectToUuid` = first 122 bits of unsalted SHA-256 of the input. With `--access-reviews-live-grants` that value becomes `principalId`/`grantId`/`displayLabel` on generated review items and decisions, which are persisted and served to reviewers.
- Impact: anyone who can read access-review items can brute-force low-entropy API keys offline (there is no entropy floor, R09-10). It also means the id under review is not the key's real principal id (`spec.principalId`), so a review decision/revocation is attributed to an identity that exists nowhere, and `principalKind` is forced to `"user"` for what the gateway calls a `service_account`.
- Fix: use `spec.principalId` (or a random per-key id), never a function of the key.
- Effort: S

### R09-14 [Medium] [CONFIRMED] [AuthN] Remote JWKS: no scheme check, no fetch timeout, no in-flight collapse, empty set replaces good keys; `--jwks-file` keys unvalidated
- Where: `jwks.ts:69-76` (stale ⇒ every request `await this.refresh()`), `:92-102` (`this.keys = parsed` unconditionally on any 200), `:63` (`globalThis.fetch(url)` — no AbortSignal/timeout); `cli.ts:725-727` (`--jwks-url` taken verbatim; `http://` accepted); `node.ts:620-627` (`--jwks-file` entries skip `isEd25519PublicKeyBase64`, unlike `--jwks-key`).
- Evidence: read end to end. When the TTL lapses, each concurrent request starts its own fetch and waits on it; if the IdP hangs, every authenticated request hangs (`fetchedAt` only advances on success). A 200 with `{}` or a non-Ed25519 key set empties the cache (global 401 until the next successful fetch). An `http://` JWKS URL lets a network attacker supply their own signing key ⇒ forge any principal.
- Impact: availability coupling to the IdP on the hot auth path; total auth bypass if deployed with a plaintext JWKS URL.
- Fix: require `https:`; 2–3 s timeout; single-flight refresh; keep last good set when the new one is empty; validate file keys.
- Effort: S

### R09-18 [Low] [CONFIRMED] [Timing] Residual user-enumeration timing and lock-clock skew in login
- Where: `auth-token-route.ts:419-431` (the `recordFailure` UPDATE — a WAL-committing write — is awaited before the 401 only for an existing, unlocked user with a hash; unknown/suspended/no-credential users issue no write); `:303-310` (`isLocked` compares the DB-clock `locked_until` with the process clock `input.now`).
- Impact: a commit-latency delta (≈ms) on top of ~130 ms scrypt distinguishes "real account, wrong password" from "no such account" with enough samples (samples are capped by the lockout, so weak). Clock skew between app and DB shortens/lengthens locks despite the comment claiming the DB clock is authoritative.

## Verified strengths (things that are genuinely done well, with file:line)
- Password KDF path is sound: scrypt with per-hash params + HMAC pepper held outside the DB, async derivation, re-hash on parameter upgrade (`auth-token-route.ts:259-300`), pepper strength validated at boot and by the CLI (`credential-auth-env.ts:88-107`, `set-credential.ts:75-79`).
- Uniform refusal: one 401 body for ten refusal reasons, work spent on every pre-verification path, password verified before the membership read so no tenant-membership oracle (`auth-token-route.ts:196-284`, `:317-322`); `.strict()` request schema refuses a caller-supplied `role`/`scope`/`tenant_id` (`:47-57`) — the role comes only from the membership row (`node.ts:4189-4192`).
- Login cannot mint a token for a tenant the user is not an **active** member of, or for a non-active user, or a read-blocked/unknown-status tenant (`node.ts:4190-4204`, fail-closed on unknown status).
- Signing key: one env seed, public half derived (cannot be mis-paired), refused at boot if malformed or if `--jwks-url` would discard it (`credential-auth-env.ts:109-136`, `cli.ts:1819-1846`); verifier pins `alg === "EdDSA"` and requires `kid` (gateway `auth.ts:120-128`), so no alg-confusion/`none`.
- All SQL in scope is parameterised; the only interpolated identifiers are schema names behind `^[a-z_][a-z0-9_]*$` (`credential-store.ts:52,75`, `platform-users.ts:195,356`, `platform-admin.ts:20,125`, `rekey.ts:94,129`, `envelope-tenant-readiness.ts:69,167`) or `quoteIdent`-escaped catalog names (`tenant-ciphertext-probe.ts:223-229`). No injection found.
- Membership statements run inside `withTenantContext` **and** carry an explicit `tenant_id` predicate (`platform-users.ts:592-603`, `:654-663`), so they are correct as table owner too; guarded status transitions re-assert the source state in the `UPDATE` (`:504-518`).
- User-registry writes are audited before the write and refused (503) when unrecordable; failed writes get a paired refusal row (`platform-users.ts:751-792`); `buildPlatformUserRoutes` throws without an auditor (`:1118-1123`).
- Every platform route calls `guard` first; empty admin-role set ⇒ nobody (`platform-users.ts:733-742`, `platform-admin.ts:378-384`). No route lets a caller pick their own role.
- ABAC evaluator is fail-closed and prototype-safe: `hasOwnProperty` on both attribute and record sources, absent/structured values deny for every operator incl. `ne`, unknown key ⇒ `undischargeable`, `null` attributes ⇒ `undischargeable` (`abac-policy.ts:332-341`, `:381-462`); attributes only attached for an **active** membership and only for `user` principals (`abac-attributes.ts:86-89`, `:297-320`).
- Secrets come from the environment, never argv, for pepper / signing key / column & cursor secrets / new password (`credential-auth-env.ts`, `set-credential.ts:82`, `node.ts:669,993,4645`); boot lines print only the public key (`credential-auth-env.ts:150-160`).
- Tenant-status cache separates first-lookup failure (propagates → 503) from refresh failure (bounded stale), with single-flight (`tenant-status-gate.ts:113-146`).
- `rekey` requires the tenant id twice, refuses a write-permitting tenant without an explicit hatch, and states the stale-key window honestly (`rekey.ts:155-172`, `:374-398`).

## Claims vs reality (docs/README/CLAUDE.md/comments that the code contradicts)
- `principals.ts:34-37` says an API key "must not be hashed into an id"; `live-grants.ts:125` does exactly that (R09-13).
- `credential-store.ts:146-147` / `auth-token-route.ts:306-308`: "The lock is set from the database clock … a drifted worker must not unlock an account early" — the *check* uses the process clock (`isLocked(record, input.now)`), so a drifted worker does unlock early (R09-18).
- `auth-token-route.ts:30-34`: "Hence the per-user lockout, counted in SQL" is presented as the answer to having no rate limit; the lockout does not bound concurrent attempts or CPU cost (R09-02) and is itself a DoS primitive (R09-03).
- CLAUDE.md describes `--platform-user-role` as a grant "separate from `--platform-admin-role`"; because membership roles are free strings and platform authority is a role name, the former trivially confers the latter (R09-05).
- CLAUDE.md: gateway does "EdDSA JWT verification with iss/aud/exp/nbf and a JWT-vs-header tenant cross-check" — each check is skipped when the claim is absent, and with no `tenant_id` claim the header *is* the tenant (R09-06).
- CLAUDE.md "Fail closed … deny rather than allow": tenant lifecycle enforcement, cursor sealing, unique enforcement and view permissions are all report-and-serve by default (R09-08, -11, -19).
- `deploy/.env.example` header implies placeholders; it contains real-looking secrets (R09-01).
- `platform-admin.ts:448-451` concedes the unguarded `setStatus` race while a guarded `transitionStatus` sits 200 lines above in the same class.
