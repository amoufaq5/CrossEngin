# R21 — packages/testing (vitest preset + workspace strategy rules) and repo-wide test-quality assessment

## Summary (10 lines max)
- 753 test files / ~18.6k `it(` / 34.6k `expect(`: overwhelmingly real behavioural unit tests of pure logic; almost no trivial tautologies. That part is genuinely good.
- There is **no test that talks to a real Postgres, anywhere** (0 files; the 4 grep hits for PGHOST are env-parsing tests). Every `*-pg` package (147 test files) and every SQL path in the server is tested against 63+ hand-copied fake connections; 63 of those fakes silently answer `{rows: [], rowCount: 0}` to SQL they do not recognise.
- Tenant isolation / RLS, sequence atomicity, `FOR UPDATE SKIP LOCKED` worker claims and upsert semantics are asserted by **JS re-implementations inside the fake** or by `toContain("…")` on the SQL string. RLS is never executed.
- No CI, no git hooks, no coverage dependency, no thresholds: nothing runs the 18,929 tests or the 10 "workspace rules" except a human typing a command. `packages/testing/src/strategy/{ci,coverage,flake,budgets,test-kinds,fixtures}.ts` (791 LOC) model a CI pipeline / coverage gate / flake quarantine and have **zero importers**.
- The workspace rules themselves are careful regex/hand-lexer scanners with vacuity floors and negative controls — better engineered than usual — but are a compensating control for the missing DB integration tests, are name/text heuristics, and under `pnpm test` (turbo) would be served from cache when *other* packages change.
- Absent categories: real-DB integration, HTTP e2e (exactly 1 loopback smoke test, memory store), concurrency/race, property/fuzz (0), load (0), AI evals against a model (0), frontend (0 tests for operate-web), upgrade-migration against real data (0).
- Money tests use only round amounts; no rounding/minor-unit/3-decimal-currency/idempotent-repost/concurrent-posting cases.
- `node.ts` (4,716-line composition root) at 17.3% line coverage means the wiring that decides which of this is actually live is the least-tested file.

## Findings

### R21-01 [High] [CONFIRMED] [Testing] Zero tests execute against a real Postgres; all SQL, RLS and transaction behaviour is verified only against fakes
- Where: repo-wide. `git ls-files '*.test.ts' | xargs grep -lE "new Pool\(|createNodePgConnection\(|testcontainers|pg-mem|pglite"` → only `packages/kernel-pg/src/connection.test.ts` (env parsing, `:68 it("throws when PGHOST is missing"`), `apps/architect-cli/src/apply.test.ts:67`, `apps/operate-server/src/set-credential.test.ts:63` (both assert the *absence* of PGHOST). `pnpm-lock.yaml` has no `testcontainers`, `pg-mem`, `pglite`.
- Evidence: 121 test files reference `PgConnection`; fake factories: `mockConnection` ×31, `fakePg` ×19, `fakeConn` ×5, `fakeChainPg` ×4, + singletons (63 files define one). 63 test files contain a silent `return { rows: [], rowCount: 0 }` fallback arm; only 6 throw on unexpected SQL.
- Impact: classes of defect that cannot be caught by construction — non-existent/misspelt columns in WHERE/RETURNING/ORDER BY, type-inference and cast errors (`uuid <> text`), NOT NULL/CHECK/FK/unique violations, RLS policy refusals (42501) and RLS-confined zero-row reads, owner-vs-non-owner behaviour, `ON CONFLICT` target mismatch with actual constraints, transaction-local `set_config` scoping, advisory-lock semantics, isolation-level races, driver type mapping (`Date`, NUMERIC-as-string, JSONB), DDL emit validity, keyset pagination ordering, index usage/performance. The repo's own docs list ~15 production-grade defects of exactly these classes found "only live, by hand". A buyer gets no regression protection for any of them: the "verify live against a throwaway Postgres" step is a manual convention with no artefact.
- Fix: one Postgres service (docker/testcontainers or pglite for the subset it supports), bootstrap `emitBootstrapSql`, run every `*-pg` store and the operate-server request path against it **as a non-owner role**; keep fakes only for error-injection.
- Effort: L

### R21-02 [High] [CONFIRMED] [Testing/Security] Tenant-isolation tests assert a JavaScript imitation of RLS, not RLS
- Where: `packages/operate-runtime-pg/src/entity-store.test.ts:24-73` and `:158-165`
- Evidence: the fake keeps `let tenantCtx`, sets it when `sql.includes("set_config")`, then `const visible = backing.filter((r) => tenantCtx !== null && r.tenant_id === tenantCtx);` and dispatches on `sql.includes("SELECT document")`. The test `it("a record created in one tenant is invisible to another")` therefore passes for *any* SELECT text — a store that dropped `tenant_id = $1` from its WHERE, or a policy that was never created, is indistinguishable. Unknown SQL returns `{ rows: [], rowCount: 0 }` (`:72`). Same idiom in `subscription-store.test.ts:18-27`, `sequence-store.test.ts:13-30` (`// RLS: only the tenant in context may write/read its rows.` followed by a JS `expect`). 54 test files use a second tenant; none against a database.
- Impact: the product's primary security boundary (multi-tenant isolation) has no automated test that would fail if a policy were missing, permissive, or bypassed by table ownership.
- Fix: real-DB two-tenant matrix per table/store, connecting as a non-owner role without BYPASSRLS.
- Effort: M (after R21-01)

### R21-03 [High] [CONFIRMED] [Testing/Finance] Concurrency-critical guarantees are "tested" by string match or by the fake doing the work
- Where: `packages/operate-runtime-pg/src/sequence-store.test.ts:41` `it("increments atomically per (tenant, name, period)"` — the increment is performed by the fake at `:18-25` (`const next = current === undefined ? start : current + 1; counters.set(key, next);`), so the store's actual `ON CONFLICT … DO UPDATE` arithmetic is never evaluated. `packages/workflow-runtime-pg/src/timer-claim.test.ts:43`, `activity-claim.test.ts:47`, `timer-worker.test.ts:65`: `expect(sql).toContain("FOR UPDATE SKIP LOCKED")`. `packages/dr-runtime-pg/src/failover-store.test.ts:75-78`: `toContain("ON CONFLICT (execution_id) DO UPDATE")`.
- Evidence: the only `Promise.all` races in the whole suite (8 sites, e.g. `apps/operate-server/src/data-key-envelope.test.ts:609`, `health.test.ts:462`) exercise in-process promise-collapse caches. No test issues two concurrent statements to a database.
- Impact: gap-free/duplicate-free invoice numbering, double-claim of jobs/timers by two workers, idempotency replay, double GL posting under concurrent transitions are all unverified. For an ERP these are audit-relevant.
- Fix: real-DB concurrency tests (N parallel allocators; two workers claiming one batch; concurrent `mark_paid`).
- Effort: M

### R21-07 [Medium] [LIKELY] [Tooling] Under `pnpm test` (turbo) the workspace rules would be cache-hits when the code they inspect changes
- Where: `turbo.json:12-14` (`"test": { "dependsOn": ["^build"] }` — cached, no `inputs`), `packages/testing/package.json` deps = `vitest`, `zod`, devDep `@crossengin/config` only; `packages/testing/src/strategy/workspace-sql-scan.ts:32` `REPO_ROOT = join(…, "..", "..", "..", "..")` reads every other package's `src/` from disk.
- Evidence: turbo hashes a task by the package's own files + its dependency graph. `@crossengin/testing#test` has no dependency on kernel or any store package, yet its tests read `packages/kernel/src/bootstrap/meta-schema.ts` and ~900 other files. A change to a store's SQL does not change that hash. (Not executed — builds/tests are forbidden in this review; hence LIKELY.) The documented command `pnpm -r test` bypasses turbo and is unaffected; the root `test` script is the turbo one.

- Effort: S

### R21-08 [Medium] [CONFIRMED] [Testing robustness] The ten strategy rules are regex/hand-lexer scanners over source text; soundness rests on coding-style invariants and hand-written declarations
- Where / evidence:
  - `pg-column-coverage.ts:1325` `code.matchAll(/INSERT\s+INTO\s+([^\s(]+)\s*\(/g)` and `:1398` `/\bUPDATE\s+([^\s(]+)\s+(?:[A-Za-z_][\w]*\s+)?SET\s/g` are **case-sensitive** (the reference collector at `:1241` has `/gi`; these do not). Lower-case SQL would be invisible, unreported. Not live today (grep finds no lower-case DML in `src/`), so latent.
  - `:1325` requires a parenthesised column list: `INSERT INTO t SELECT …` / `INSERT … DEFAULT VALUES` is never seen. SELECTs with alias/join/expression/`*` are "silently skipped" by design (comment block above the SELECT loop, ~`:1366-1376`). WHERE/RETURNING/ORDER BY columns are never checked (stated in-file).
  - `parseCatalogSource` (`:651-762`) recognises only `export const META_X: TableDefinition = {` and column entries that are object literals (`if (!entry.startsWith("{")) continue;` `:716`) — a column supplied by spread/shared constant, or a table built by a helper, is dropped without a finding. Holds for today's catalog (146 literal declarations, no spreads — checked), enforced only by a `>= 145` floor.
  - `stripComments` (`:350-412`) treats a template literal as flat text to the next backtick — nested templates inside `${…}` mis-pair; `opensRegexLiteral` (`:326`) is a one-character look-behind heuristic. The file itself records this lexer being wrong "for four increments".
  - `pg-unreachable-stores.ts:1191-1209` `findConstructions`: "reachable" = *some non-test file contains `new Name(`*, matched by bare name. It does not establish the constructing code is reachable from an entry point (ten stores sit behind factories, acknowledged), and same-named classes collide.
  - `pg-record-retention.ts:136-139`: cascade detection requires `"tenant_id"` and `references: TENANT_FK` on **one line**; an inline `references: { table: "tenants", onDelete: "CASCADE" }` or a wrapped line evades it. Finding kind `protected_table_not_in_catalog` (`:47`) is declared and tested for membership (`pg-record-retention.test.ts:15`) but **no code path emits it** — `auditRecordRetention` (`:148-187`) never consults the catalog's table list.
  - `entity-field-aperture.ts:748-900` binds a `.fields` read to `Entity` by regex over type annotations in the enclosing function; anything typed structurally, destructured, or passed through a helper is rejected as `foreign_type`/`unresolved_binding` (not a finding).
  - The dynamic per-entity tables (`ColumnMappedEntityStore`, the store that holds the ERP's actual business data) are outside every SQL rule by construction: declared gaps at `pg-column-coverage.ts:1588-1597` ("the JSONB document table is passed in…", column-store / entity-ops).
  - ~75 + 15 + 287 + 28 + 28 + 23 + 12 hand-written declarations carry prose `reason`/`note` fields whose truth no machine checks; the tests check shape (`reason.length > 20`).
- Impact: these rules lower the false-negative rate of a fake-only test strategy; they do not replace executing SQL. A reader should treat "0 findings" as "0 findings among statements written in the house style".
- Positive: every rule has vacuity floors (`pg-column-coverage.test.ts:658,734-737`), an explicit unresolved bucket compared both ways (`auditScanGaps`, `:1622`), and a negative control on the real tree (`:763 "would catch the defect it was written for"`). This is above-average craft for the genre.
- Fix: use the TypeScript compiler API or, far cheaper, run the statements against a real catalog (R21-01), which subsumes rules 2, 6, 7, 8, 9.
- Effort: L (replace) / S (case-insensitive flags, emit the dead finding kind)

## Honest paragraph — what "18,929 tests, all green, 94% line coverage" buys a buyer
It buys strong evidence that the *pure* layer — zod contracts, state machines, planners, RBAC/ABAC decisions, the redaction and write-mask logic, tombstone/proof construction, JWT verification, the accounting effects' debit/credit topology — does what its authors intended on the inputs they thought of, and that refactors there will be caught quickly (97 s, no skips, no flake patterns). It does **not** buy evidence that the product works against a database: not one test executes SQL, so 94% line coverage of a `*-pg` store means its string-building lines ran and a fake said "ok". Tenant isolation, RLS, sequence atomicity, worker claim safety, migrations, pagination and every constraint are covered at 0% in the sense that matters. It does not cover the 4,700-line composition root (17%), the browser UI (0 tests), real HTTP beyond one smoke test, concurrency, performance, or AI output quality; ~1,600 tests cover packages nothing deploys. And nothing runs any of it automatically. Treat the number as "unit-tested business logic of good quality", and budget for building the integration/e2e layer from zero before trusting a production change.
